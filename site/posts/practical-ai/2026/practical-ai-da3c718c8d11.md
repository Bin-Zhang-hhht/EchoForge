## 速读

嘉宾 Hamza Tahir 是 ZenML 联合创始人，做了五年 MLOps 之后转向 Agent 基础设施。这期节目的核心论点听起来有点扫兴：Agent 工程在很大程度上是 MLOps 的再发明，真正的新问题是「耐久性」——当 Agent 不再跑在你的笔记本上，而是以十万计在企业云环境里执行任意代码时，任务队列、检查点、幂等、在飞更新、失败重放这些老派工程会重新变得生死攸关。适合正在把 Agent 从演示推向生产的工程师与平台团队。

嘉宾谈及自家新项目（ZenML 之上的 Agent 运行时，逐字稿拼写不一，下文记作 Kitaru）的部分带有立场；对模型能力的具体比较（如 GLM 与 Opus 的差距）是他的即席判断，节目未给出评测依据。

## 主题正文

### 一切皆图：Agent 工程是 MLOps 的再发明

Tahir 回顾了 ZenML 五年的轨迹：开源 MLOps 框架，把「加载数据、预处理、训练、评估」这类确定性流水线抽象成图。Agent 时代到来时他发现行业在重演历史——「MLOps 是 DevOps 的自我再造，Agent 又是 MLOps 的自我再造」，本质上都是如何让不确定性的代码安全、可靠、可重试地跑起来；他在大会上听到的许多演讲，和当年 MLOps 会议上的如出一辙（`00:02:55–00:04:43`）。

他的技术概括是：所有软件都是图，经典流水线是有向无环图（DAG），而 Agent「到处都是环」——它只是一张展开的图：LLM 调用、工具调用、再 LLM 调用，trace 本身就是图。早在 2024 年就有用户「黑」他们的流水线引擎来跑动态步骤与条件分支，于是 ZenML 引入了动态模式：支持运行时定义、而非开局静态编译的图。此后真正的新命题集中在耐久性、状态管理、重试与重放（`00:06:01–00:08:14`）。

### 从本地到企业：没有上限的规模与 harness 之争

耐久性之所以现在才成为问题，是因为此前的 Agent 革命发生在本地：Claude Code、OpenClaw 这类进程跑在自己的电脑上，本地恢复失败相对简单。一旦 Agent 迁出笔记本、进入企业云里的沙盒执行任意代码、调用 MCP、加载技能，问题性质就变了。Tahir 判断这场迁移今年已真实发生，而且一旦解除「笔记本的缰绳」，规模没有技术上限制——「只要付得起，为什么不每小时跑十万次 Agent 执行」；采用曲线是缓慢积累后突然爆发（`00:09:00–00:12:12`）。

在基础设施之上，他把当下的行业之争概括为 harness 与模型的耦合。他的定义：LLM 本身只是 token 生成器，结构化输出与工具调用是对 token 的策略约束，把 token 映射成动作的那个 while 循环是 Agent，而让「大脑」长出「双手」的软件程序——负责上下文压缩、工具参数校验、记忆索引——就是 harness。关键观察是：模型性能渐近后，改进程序就能赢，于是一年半的强化学习把 harness 与模型深度耦合——Opus 4.8 在 Claude Code 里「知道」自己身处何处，工具调用参数精准；把 GPT-5.5 塞进同一个 harness 表现就差。与之对抗的是开放 harness 阵营（LangGraph、Pydantic AI 等）：标准不应绑死模型，否则政策一变业务就被动。他坦承胜负未定——「Claude Code 就是好用，我为什么要换」（`00:13:00–00:18:29`）。

### 自建 Agent 平台的架构阶梯

对不同工作负载他的建议分两层：简单场景直接用托管服务（如 Anthropic 托管 Agent，harness 内置了例行任务）；一旦业务流程变复杂——取订单、LLM 处理、后处理——且要上规模，就值得自建内部 Agent 平台。他把这与 Uber 的 MLOps 平台类比：平台未必是赢得市场的原因，但建设过程本身会让你吃透自己的业务场景（`00:23:01–00:25:15`）。

自建的阶梯被他一步步铺开：选 harness，部署到计算目标（ECS 或 Kubernetes），用 FastAPI 之类的 API 触发 Agent——马上发现这不是毫秒级返回的 REST 请求，而是长时间有状态进程，于是引入 worker 与任务队列；worker 会因网络故障、节点被占而挂掉，于是在中间放消息总线做持久化；接着出现幂等、可观测性、多步骤依赖，复杂度从「加个队列」膨胀成「需要 DAG 编排」。更麻烦的是在飞更新：一个跑了三十天的任务，代码已经更新，第三十一天该用新代码还是旧版本？运行中途模型被禁用了怎么办？他的立场是：别让开发者把精力耗在防御性代码上，要让他们去进攻性地写用例（`00:25:34–00:29:28`）。

### 编码工厂的脆弱点与「重放」这门学问

他以当下最热的「编码工厂」为例串起这些坑：Agent 执行代码需要沙盒（E2B、Daytona、Modal 因此火爆）；在两万次工具调用、功能即将完成时代码执行环境挂掉，文件系统挂载方式决定你能否回到现场；就算跑完，结果不符合预期时，你还需要回到过去做实验——用 GLM 换掉 GPT 会不会更快更便宜？工具是不是给多了导致混乱？（`00:31:23–00:32:44`）

这里他给出一个科学上的诚实提醒：在多轮对话中途换模型做重放，本质是「坏实验」——你永远不知道换了模型的 Agent 是否本可以走到那一步；harness 的差异也让中途接管困难。Kitaru 的工作正是把这件事做得尽量可行：以 harness 为入口做适配器（Anthropic、OpenAI 的 Agents SDK 等），在执行中把关键状态快照到外部存储，配合可模拟工具调用、替换模型的重放；基于足够多的生产 trace 样本，就能看出「本该用更小的开源模型」这类改进信号。他强调这些仍在与客户打磨、并不完美（`00:34:53–00:38:10`）。

### 修补是打地鼠，终局是「训练师 Agent」

对「优化这个、那个又坏」的工程现实，他的第一原则朴素而有力：把一切都做检查点，先保证能回看；实验多到人力做不完，所以终局必须由 Agent 来做实验。他给用户的起步建议很具体：先跑一周，筛出「最贵且成功」的 trace,对照检查点找瓶颈与共性失败模式。Kitaru 第一天就发布了 MCP CLI,因为愿景是给每个生产 Agent 配一个「训练师」伴生 Agent——持续观察、重放、实验、修改。他直言这还是梦想，需要更多工具与基础设施（`00:38:10–00:41:25`）。

收尾的一悲一喜：悲观的是行业正处在 2021 年 MLOps 时刻的翻版——工具爆炸、资本涌入、同一批问题有几十种解法，而 harness、基础设施与部署范式的「正典划分」远未形成，模型厂商把能力压进自家 harness、排斥互操作的做法也有负面的经济影响；乐观的是 MiniMax、Kimi、GLM、Mistral 等开源模型让「换掉大厂模型」在经济上成立——他说两周前的 GLM 已约等于 Opus 4.8 的九成五——企业一旦认真自建平台，开放 harness（包括法律、科学等垂直专用）就会起量。当 token 的价格回归「电费」,真正的竞争力差异就在企业内部的基础设施上（`00:42:00–00:45:20`）。
