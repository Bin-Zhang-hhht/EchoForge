# Harness 工程：给编码 Agent 套上"导航与传感器"，而不是五十个 Markdown 文件

## 速读

Thoughtworks 杰出工程师 Birgitta Boeckeler 全职研究"LLM 如何改变软件交付"两年半，本期把她的 harness 工程词汇表带给听众：harness 是套在模型外面负责编排的那层骨架(Claude Code、Cursor 都是),而开发者真正要工程化的是自己扩展出来的外层——前馈的 guides(约定、知识库、codemod)与反馈的 sensors(静态分析、测试、LLM judge)。

最值得带走的三点：静态分析可以在 Agent 时代复活——给 lint 消息写自定义文案,把"该不该豁免"的判断权和 review 线索一并交给 Agent;测试有功能正确性与回归传感器两个角色,让 AI 写全部测试则前者无解,"人评审测试"又太繁琐,验收测试的输入输出可评审性是当前最值得投入的方向;信任不是感觉,是概率×影响×可检测性的风险评估,而问责要与环境激励一致,否则逼出来的只有走捷径。

## 主题正文

### 定义:harness、agent 与那层"洋葱"

Boeckeler 先承认这个领域的词都在漂移,然后给出她当前的用法:harness 指套在语言模型之上、负责编排一切的那层东西——带系统提示、会请求工具调用,也就是我们此前叫作 agent 的骨架;Claude Code、Cursor 或更轻量的 pi 都算编码 harness。它与模型一起运行的那个实例才是 agent。而 harness engineering 有两个层面:让 harness 本身更好(更多工具还是更少工具,各有流派),以及她在文章里聚焦的那层——使用者(应用开发者)为自己代码库对 harness 的扩展:先选基础 harness,再往里加技能、工具与信息,像一层层洋葱。术语尚未定型,她也希望外层那个"被工程化的洋葱"能有个独立的名字。（`00:02:17–00:04:29`）

对"要不要先学一堆技能再开始"的入门焦虑,她的建议出人意料:什么都别加,先用原厂设置跑一阵,体会它开箱即用的边界;模型变强很快,早前攒下的技能与指令也许已经多余,值得定期重估。（`00:04:37–00:06:12`）

### Guides 与 sensors:一套用来思考的词汇

她造的这对词是整期的骨架。guides 是前馈:预先写下要它做什么、不要做什么,载体通常是一堆 markdown(CLAUDE.md/AGENTS.md 最为人熟知),内容可以是规范性的(仓库约定),也可以是信息性的(应用背景、架构描述)。sensors 是反馈:第一次不完美时,让它自我纠正的信号源——可以是另一个 LLM(比如带评审指令的 skill),也可以是跑在 CPU 上的计算性检查(静态分析、测试套件、覆盖率)。guides 侧同样可以有计算性的:codemod 工具(如 OpenRewrite)承担版本升级迁移中八到九成的机械改动,语义部分留给 LLM 补。一言以蔽之:guides 提高第一次就做对的概率,sensors 提供自我纠正的回路。她还借控制论作比:被调节的对象就是我们生成中的代码库,可调节的维度包括可维护性、架构适应度(各类"ility"与 fitness function)、耦合与功能正确性。（`00:06:12–00:12:39`）

三个"X 工程"的关系也随之厘清:prompt engineering 在大模型时代已经没那么关键(回到小模型时也许会回归);context engineering 是调优喂给模型的信息;harness engineering 则是它的一个具体形态——guides 调优指令,sensors 提供反馈信息。（`00:12:39–00:13:42`）

### 静态分析的复活:自定义消息 + 判断权下放

sensors 侧她实验最多的是静态分析——一个被人类荒废已久的工具:顾问生涯里她见过太多组织角落里躺着无人看顾的 Sonar 服务器。荒废原因有二:资深开发者知道 lint 保不了质量;更重要的是信噪比太差,消息多到没人愿意逐条调优。Agent 时代出现了新机会:你可以重写每条 lint 消息的文案。她的 ESLint 实验是 max-lines-per-function:消息不再是"函数 120 行超限",而是"这可能是个坏味道,请考虑是否拆分、是否职责过多,请做出判断;若确属合理(比如测试数据函数),允许为该函数创建规则上调阈值"。Agent 于是既自纠、又在显式处留下豁免痕迹,人只需 review 那些上调点。曾经因为太繁琐而无人维护的"基线常清",现在可行了。（`00:13:42–00:16:42`）

主持人补充的圈复杂度场景正是典型失败模式:AI 生成的代码圈复杂度动辄上百,还有难以卒读的布尔表达式。sensors 触发后会发生什么?它启动一个小回路:分析工具报圈复杂度超标,附带的提示告诉它如何处理(可以判断后上调),Agent 自纠、再问传感器,循环到达标。她对"代码可读性不再重要,反正 AI 以后会改"的说法做了正面反驳:诡异布尔表达式对人类难读,对 AI 改动同样更危险——AI 做安全变更需要的东西和我们一样。（`00:16:43–00:18:57`）

### 测试的双重角色,与"评审别人的测试"这个未解难题

测试作为传感器有两个角色:检验功能正确性,以及充当回归传感器——"它多擅长告诉我们东西坏了"。后者是可维护性议题,前者则藏着一个尖锐问题:如果测试和代码都是 AI 写的,全绿也不保证测的是该测的东西——TDD 的本意从来不是"有测试",而是"先写测试",因为测试是终极规格,逼人想清楚要什么。这在她看来仍是基本未解的问题:让人的角色变成"只评审测试"?可评审自己没写过的测试极其乏味,而人真正该想的是组合空间的全景。她提到与同事 Matteo Vaccari 的探讨:找到合适的验收测试层,把输入输出(尤其 HTTP 的请求/响应组合)写成"容易评审的数据";单元测试留给 AI 行不行?这是一个按情境而定的风险决策——API、UI、写库、发事件,不同应用需要的反馈回路完全不同,没有一刀切的答案。（`00:19:29–00:23:00`）

### 实战 harness:传感器摆哪、怎么知道它有用

"最小可行 harness 长什么样"她说难以一概而论,更有价值的是元问题:怎么知道 guides/sensors 有效?guides 侧已可做 skill evals——同一场景带技能与不带技能各跑一遍,看技能是否真的加分(模型也在变,LLM 生成的技能有时只是重复模型已知的事)。sensors 侧还没有现成工具,她做了个推测性实验:用一个 sidecar 记录会话中每次传感器状态的历史,于是能看到覆盖率与违规数在会话中如何起伏;这与流水线的困境同构——永远绿的流水线反而可疑,它得偶尔红一下才证明安全网真的在。agent traces 是正在冒头的新兴方向(节目提到一家由 GitHub 前 CEO 创办的公司发布了追踪编码会话的 CLI,名称本文未引用以免失实),终局是回答"有 guides/sensors 时是否更快到达目标、到被迫干预前跑了多久"。（`00:23:00–00:27:17`）

放置位置是成本决策:运行时长、能耗、token 都不同,所以要决定传感器跑在会话中、提交前、PR 评审还是 CI/CD。她引 OpenAI 团队的 harness engineering 文章把定时重跑称为"垃圾回收"——他们让 Agent 触碰全部代码五六个月,技术债依然在复利,所以要有按计划表跑的传感器。她自己的应用里就有三个每周手动跑的 skill:模块化评审、基于 Thoughtworks 内部安全准则的安全评审、依赖新鲜度与替换建议;先从"每周出一份人看的报告"起步即可,以后可升级为建单甚至开 PR。这套东西把一个真实小用户量应用的维护压到每周半小时。摆位哲学是左移:便宜又快的卫生型传感器,就该在本地 diff 上、提交前跑——"提交后能做的,提交前也能做,别把质量往后推"。（`00:30:47–00:37:17`）

文件级之外还有跨文件层。主持人讲了一个失控瞬间:让 Agent 修一个单元测试的某段逻辑,它把整个文件都重写了——guide 里明明写了别动其他部分,却因一句"只改这里"没说而全盘覆盖。Boeckeler 说这正是耦合层的问题:她给 POC 加一个查询参数改了 15 个文件,这就是抽象不足的味道;基于 import 关系的计算性分析能找到热点但帮助有限,反倒是 LLM judge 效果好得多——她用了 Vladik Khononov(平衡耦合一书作者)写的 skill,专家写透权衡与语义的提示,质量可观。（`00:27:47–00:30:47`）

### 判断权、传感器打架、信任公式与人类问责

"分析工具说该修,但在这个项目里修了反而坏"的老问题,答案是前述的判断权下放:在自纠指南里明说"可以判断后豁免,但要留下理由"。信任程度则按域分级——函数行数可以放手,安全类只许"上报不许自裁"。更有前瞻性的问题是:传感器互相矛盾怎么办?她观察到的唯一小例子已经出现:Agent 为了满足"函数/文件最大行数"把 React 组件越拆越小, props 一层层传七八个下去;若再开一个"组件健康度"传感器,它会不会在两种判断之间乒乓球?权衡遍布软件交付,这是 harness 工程尚未回答的问题。（`00:37:17–00:40:15`）

对"如何在 Agent 大量生成与修改代码时建立信任",她给出的不是感觉而是公式:概率×影响×可检测性。概率来自你对该 Agent、该模型、该代码库混乱程度的经验(烂摊子上出错概率自然高);影响看用例(POC 还是关键业务流);可检测性看反馈回路的厚薄——三者合起来决定让它无人监督跑多远、评审细到每一行还是只看传感器。多 Agent 协作也是 harness 的一部分:最常见的传感器就是一个被派生的 sub-agent,带着全新无历史的上下文(有时甚至换一个模型)以"无偏视角"评审代码。（`00:40:15–00:43:39`）

问责则是她"心情矛盾"的社会性观察:Agent 是机器,没有组织归属与问责;但一些组织一边用吞吐指标施压("你有了 AI,必须快 X%"),一边在事故后把人推出顶罪——DORA 的数据里 AI 辅助交付伴随稳定性下降,近几个月的几个知名事故通报里已能看到这种苗头。人必须担责,但担责要成立,组织就得给人相应的空间、环境与激励,否则逼出来的只会是走捷径。角色变化上,"90% 代码由 AI 写"其实说的是"由 AI 打字";给 Agent 下任务本身就是技术工作,经验越丰富提示越好。抽象层确实在上移,但不同于汇编到编译器的那次——编译器确定可复现,LLM 是语义的、解释性的、概率的。她判断未来最重要的技能是质量工程师式的事前风险评估(那位从招聘转行、比谁都懂整个系统的 QA 是她心中的范本),而"为我们自己的处境描述什么叫好"本就是行业的短板;描述不出来,传感器与指标都无从谈起。（`00:43:39–00:50:25`）

未来她并不看好"五十个 markdown 文件就是终局"——"如果我们就这么干工程,还配叫工程师吗?"同样不看好"一百个工具加五十个传感器"的堆料:有了某个传感器,对应的 guide 是否还需要?平衡没有精确度量,大概又得靠手感。模型在变、基础 harness 在变、你自己的 harness 也在变,终极度量只有两个:软件交付绩效(稳定性与吞吐)和用户价值——"我们是在更快地造更多垃圾,还是在真正为用户创造价值?"（`00:50:25–00:52:55`）
