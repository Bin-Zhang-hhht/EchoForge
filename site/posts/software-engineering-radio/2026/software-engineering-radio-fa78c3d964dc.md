## 速读

这期的特殊性在于说话的人：嘉宾 Owen McGirr 是爱尔兰多尼戈尔的开发者、2022 年 MIT Technology Review"35 岁以下创新者"，也是脑瘫人士和 AAC（辅助沟通）用户——他为本节目准备的回答就是用文字转语音生成的。主持人 Gavin Henry 与他从两个视角谈无障碍：作为构建 SayIt!、Switchify 等辅助技术的开发者，以及每天依赖这些技术生存的用户。

最值得带走的三点：无障碍晚做的代价是"和自己的设计打架"，趁早的唯一检验是能否用 tab 和 enter 走完主流程；他给 Codex 搭的测试 harness 只允许模型发送"下一条/上一条/选择"等五个开关动作——提示词决定 AI 说什么，环境决定 AI 能做什么；而 AI 工具自身的交互（超时弹窗、快速闪过的状态）对 AAC 用户可能让协作直接不可用。

## 主题正文

### 无障碍的定义：不是附加层，而是"产品是否可用"的度量

Owen 给无障碍的定义落点很实际：让用户能以"对他有效的方式"使用软件，而不只是开发者想象的那种方式——触摸、键盘、开关、语音、读屏、眼动、头控都算访问方式，还要考虑疲劳、速度、错误恢复、认知负担，以及能否独立完成真实任务。软件最常见的隐性假设是：用户看得清屏幕、点得准小目标、有两只手和足够的精细动作、能在系统认为合理的时间内做出反应。他最讨厌的反例是还没读完就超时消失的警告对话框——这类设计默认了用户未必拥有的速度与动作能力。（`00:02:53–00:04:26`）

至于能否事后补无障碍，他的答案是"能，但更贵也更差"：补上去的标签可能存在，流程却别扭、焦点乱跳、只在最简单场景可用。企业和法务常常在投诉、诉讼或合规截止日之后才认真对待，那时改造的已是定型的设计决策。他的结论是：无障碍必须进入设计和工程过程本身，它衡量的是产品对需要它的人是否真的可用。（`00:04:53–00:05:56`）

### 开发者速赢：把鼠标收起来，用 tab 走完主流程

访问方式的清单很长——触摸、鼠标、键盘、语音控制、读屏器、开关、眼动、头控、面部表情、气控设备，或它们的组合——但核心只有一句：不存在唯一的默认用户。他心目中的好无障碍是一笔带过也成立的细节：结账或注册流程全程不碰鼠标，tab 顺序合理，每个输入框有真标签而非占位符，出错时焦点移到错误处并说明改什么，按钮是按钮、链接是链接，超时有预警且可延长。（`00:06:03–00:07:19`）

给开发者的速赢清单围绕"正确使用平台"展开：优先用原生控件，因为原生按钮生来就知道自己是按钮；自绘控件就得自己补齐名称、角色、状态、焦点与键盘行为；标签齐全、焦点顺序合理、触控目标够大、支持动态字号、不用颜色单独传义；错误的处理要让焦点落在有用的地方。他的检验方法可以照抄：只用 tab、shift-tab、enter、escape 走一遍主流程，再用读屏器走一遍，有条件再用开关导航走一遍——并且"不要只测单个组件是否可达，要测整个任务是否可达"。最后他给了一个自己的实验：写 harness 让 Codex 看截图、推理屏幕内容、只通过 ADB 发送 Switchify 开关动作——AI 看不懂 UX 的地方，真实用户可能同样困惑。（`00:07:45–00:09:41`）

### SayIt! 与 AAC 设计：把"参与"而不是 WPM 当指标

节目里他不是用 SayIt! 说话，而是用 Podium Speak——他为科学家 Dr Claire Malone 做的网页演讲工具：对话要的是速度和灵活，演讲要的是可靠和按段推进，两者是不同的问题；这次录制的语音经 OBS 路由成麦克风输入。SayIt! 本身从 iOS 原生 AAC 应用（Swift）转向了 Next.js 的 PWA：用户打字、应用用 TTS 读出，难点从来不只是调语音 API，而是压缩"说出有用的话"所需的动作数——常用短语、快速访问、合理的分类、图标支持、可预期的布局。（`00:09:45–00:11:46`）

他反复强调两个容易被工程忽略的维度。一是疲劳与对话节奏："如果我得按二十下才能开口，对话已经走远了"；延迟会直接改变对话的韵律。二是度量方式：字每分钟只是故事的一半，更好的指标是参与度——能不能打招呼、接住问题、礼貌插话、开个玩笑、从错误中恢复并保留继续的精力。Web 化带来跨设备与易更新，但浏览器 TTS 的可用性、时序、音量、中断行为各不相同，而通信工具的可靠性底线极高："它不是效率工具，它可能就是用户的嗓子。"（`00:11:46–00:14:51`）

### Switchify：从个人需要长出的 Android 开关访问系统

Switchify 是一个 Android 无障碍服务，面向无法舒适使用触屏的人：用物理开关或摄像头面部手势操控手机。架构上，这个常驻服务监听无障碍事件、读取无障碍节点树、把屏幕过滤成可操作节点，并在其上建扫描模型——应用暴露了良好的无障碍信息就走条目扫描，否则退到点扫描或雷达扫描（直接选屏幕坐标），这个兜底很重要，因为不是每个应用都为无障碍而写。选中之后，它能派发点击、滑动、长按、滚动、返回/主页等系统动作和更复杂的手势模式；输入侧统一映射为"下一项/上一项/变向/暂停"等内部动作。（`00:14:51–00:16:46`）

做这个的动机是他自己：iOS 用了十年，桌面靠 Grid 3，但想要一个适配自己使用方式、可配置动作的 Android 开关系统。技术栈是 Kotlin 加 Jetpack Compose（设置界面），核心却是那个无障碍服务——扫描层、开关事件、访问技术、菜单、手势执行、摄像头开关、PC 控制各层独立；平台只给原语（事件、节点、全局动作、手势派发、悬浮层），扫描顺序、分组、如何从坏状态里逃出来，全都要自己造。配套的 Switchify PC 是 C#/.NET 写的 Windows 托盘程序，经蓝牙配对、校验认证协议消息，把手机上同一套开关动作变成 Windows 的鼠标、键盘、窗口控制——包管理、代码签名和 UIAccess 权限这类"无聊"的细节他也特意点名：安装太难，功能就等于不存在。（`00:16:46–00:22:36`）

### 用 Codex 当"陌生用户"：约束环境才是测试的关键

近期 Switchify 的实现工作约九成五由 AI 完成——但他刻意划清边界：产品构想、设计方向和"什么真正可用"的判断来自他这个开关用户与 AAC 用户，AI 负责写码、重构、生成测试、探索边界情况。真正精彩的是他的 AI 测试 harness：父进程持有模拟器、ADB 连接、截图和全部配置，先备份现有设置、装上 debug 版 Switchify、启用已知测试档案，且只在模拟器上跑、结束后恢复设置——甚至有独立进程盯着，主测试崩溃也能还原。（`00:22:36–00:25:02`）

设计上有三处讲究。第一，模型只看 ADB 截图，不给无障碍树、不许 UI Automator——既因为开关用户看不见这些信息，也因为自动化 API 会干扰被测的无障碍服务；辅以动作历史和一份解释层级扫描、主次高亮、逃生状态的操作指南。第二，每一步都是全新的 AI 进程，上下文只来自 harness 提供的记录。第三，也是最关键的约束：模型只能返回严格结构化的 JSON，动作只有五个——next、previous、select、capture、stop；不能发明 ADB 命令、不能点坐标、不能滑动、不能用系统返回键逃生，越界的返回在到达设备前就被父进程拒掉。动作经调试桥走的是 Switchify 自己的扫描管理与无障碍服务逻辑——AI 不是在假装按触屏，而是真的在走开关路径。（`00:25:02–00:28:07`）

他对结果的态度同样克制：AI 不代表残障用户，它没有疲劳、不自主运动和沟通成本；但模型反复看不懂"高亮是否可操作""选择是否进入了下一层"的地方，恰恰暴露了把系统知识留在设计者脑子里的模糊交互。AI 是一个"故意陌生的用户"，它的误解决不需要自动成立为 UX 问题，而是给出该与真实用户一起核查的精确坐标。方法论的概括是"环境就是一切"：提示词只影响 Agent 说它在做什么，环境决定它真正能做什么——就像让开发者"把鼠标收起来一天"，只不过 harness 能强制执行。要在 AI 上做无障碍测试，就得让约束由工具架构强制，而不是写在提示词末尾的一段话。（`00:28:42–00:31:39`，`00:38:50–00:41:25`）

### AI 工具自身的无障碍：能暂停、肯等待，才是给 AAC 用户的入场券

这期最独特的部分，是他对 AI 工具本身可用性的批评。最大的障碍说出来很简单："我希望我能和 Agent 说话。"AI 产品默认两种用户——键盘敲得快的人，或对着麦克风自然说话的人，AAC 恰好卡在两者之间：他的沟通基于文字，但绝不等同于普通键盘输入，每一轮可能要花长得多的时间。于是超时成了致命设计：临时对话框对鼠标用户是小刺激，对开关或 AAC 用户可能让交互彻底不可用——等他组织好回复，对话框已经消失。（`00:31:45–00:33:31`）

他给出的交互要求非常具体：需要用户决策时，Agent 应该暂停并无限期等待，"沉默不代表我不在场"；要能暂停（冻结在已知状态、不丢上下文、不留下改一半的文件）、能排队补充指令、能用无障碍开关动作打断、能以适配扫描的方式呈现状态；暂停、停止、取消要界限分明，因为取消会丢工作，必须是慎重动作。他偏好给 Agent 一大块工作、把上下文留在一条长线程里（把关键决策写进仓库等持久处），最好的 Agent 体验不是盯着它每一步，而是"我确立意图，Agent 保持意图，回来时拿出它实际做了什么的证据"。技术加速了计算机那一侧的对话，却没有让人这一侧同样可达——保留行动权（agency）才是底线：任何时候都能用一个可靠的无障碍动作拿回控制。（`00:33:31–00:38:48`）

### 平台对比与给开发者、厂商的话

跨平台经验谈同样具体：触屏是"点或路径上的有界动作"，鼠标却涉及空旷空间里移动、悬停、跨窗口拖拽——两种范式改变了访问系统的设计。iOS 内建无障碍一致性强但第三方施展空间小；Android 靠无障碍服务开放得多，代价是厂商行为差异和应用节点树质量参差；Windows 桌面控制能力强，但应用与技术栈太杂，一致性最难。互相学习的方向：Android 学 iOS 的一致性，iOS 学 Android 的开放，Windows 学移动端的简单可预期，移动端学 Windows 的自动化 API 与键盘可达。他给平台厂商的原则是一句硬话：无障碍 API 是核心基础设施——一次破坏焦点或手势行为的更新，对辅助技术用户不是小回归；Android 直到第七个大版本才让无障碍服务能执行手势（手势模拟），平台不暴露的 API，开发者只能绕，用户买单。（`00:42:16–00:44:48`，`00:46:09–00:46:44`）

给开发者的话回到工程本位：把无障碍当正常工程需求而非收尾抛光，用语义组件、保持焦点顺序、尊重用户的字号与对比度设置；tab 和 enter 是最好的朋友——走不完主流程就说明结构有问题；自动化检查只能抓明显问题，"工作流是否累人、错误能否恢复"只有真实用户能告诉你。他留给工程师的一句话是：无障碍不是可选项，也不是"有时间再做"的部分，它决定软件是否成立——按自己想象中的用户去构建，会无意中排除他人；从无障碍出发去构建，往往得到更清晰、更健壮、对所有人都更好用的软件。残障人士也不应只做流程终点的用户，而应参与设计、工程、测试与决策。（`00:45:09–00:46:01`，`00:47:44–00:48:15`，`00:50:06–00:50:12`）
