Kapfhammer 对谈 Red Hat 首席软件工程师、Linux 内核维护者、Rust for Linux 核心团队成员 Danilo Krummrich。这期节目讲在 Linux 内核中引入 Rust：内核三十多年来几乎完全用 C 编写，而嘉宾给出的理由是大约三分之二的严重内核 CVE 源于内存安全缺陷；Rust 不靠垃圾回收，靠所有权、生命周期和编译期检查提供内存安全。节目以他用 Rust 编写 NVIDIA GPU 驱动的 Nova 项目为例展开。（`00:00:19–00:01:18`，`00:10:02–00:10:53`）

对内核与系统工程师最有价值的三层内容：一是 Nova 与 C 版驱动 Nouveau 的关系、只支持 Turing 之后带 GSP 固件的 GPU 这一明确边界，以及 Linux 6.15 以 stub 驱动形式上游化的现状；二是 Rust 原生不支持自引用结构，内核用 pin-init 把初始化顺序变成编译器检查的数据依赖，这是内核 Rust 与用户空间 Rust 的关键差别之一；三是零成本抽象的真实样例——数千行 Io 寄存器抽象最终编译成一次 load 或 store，以及用生命周期替代引用计数省下的内存分配与原子操作。（`00:21:57–00:23:53`，`00:30:33–00:33:33`，`00:42:27–00:44:14`）

## 主题正文

### 为什么内核要第二种语言：内存安全

主持人先把背景立起来：Linux 内核三十多年来几乎完全用 C 实现，因此选择 Rust 是一个重大决定，他请嘉宾解释社区为何支持引入第二种语言——这是主持人的提问框架。（`00:10:02–00:10:23`）Krummrich 的回答带有限定词："我认为"大约三分之二的严重内核 CVE 源于内存安全缺陷，而三十年的 C 纪律没有让这个数字朝好的方向移动；Rust 是系统级语言，没有垃圾回收器、运行时极小、可直接控制内存，并且与 C API 兼容。（`00:10:23–00:10:53`）

他给内存安全的定义是：编译器强制保证代码只触碰自己实际拥有、且仍然有效的内存，并且只以被允许的方式触碰。（`00:11:03–00:11:14`）支撑这一保证的是 Rust 强大的类型系统——可以把 API 语义的很大一部分编码进类型——加上内置借用检查器提供的所有权与生命周期追踪；C 与 C++ 操作的是裸指针，编译器无从检查，而 Rust 的引用带有来源、所有权和生命周期信息，很多此类缺陷因此在编译期就被发现。（`00:11:43–00:12:27`）

### 从 Nouveau 到 Nova：动机、边界与现状

先看 Nova 所在的位置。DRM（direct rendering manager）是内核里处理 GPU 的子系统，从分层看是 GPU 驱动的最底层；嘉宾把它比作"GPU 的操作系统"——驱动要处理任务与命令提交、调度、依赖管理、内存与地址空间管理，DRM 为每个驱动提供这些"操作系统"的公共组件以及通往其他子系统的胶水代码。（`00:01:33–00:02:14`）Nova 就是用 Rust 编程语言编写的 GPU 驱动，技术上属于 DRM 子系统。（`00:02:14–00:02:41`）

在 Nova 之前、且至今仍在的上游驱动是 C 写的 Nouveau：约二十年的开发历史，支持大量旧 GPU；随着需求和新 GPU 架构不断变化，它越来越难维护——这是 Nova 的动机之一。主持人把两者概括为"Nouveau 是 C 实现的 NVIDIA GPU 驱动、Nova 是 Rust 实现"，嘉宾确认这个理解正确。（`00:02:52–00:03:41`）

嘉宾在 C 里撞墙的经历（主持人特意请他讲"为什么不得不用 Rust 重新开始"）：他加入 Red Hat 后第一次接触 DRM 子系统，最初负责 GPU VM——GPU 的虚拟地址空间管理器，并以 Nouveau 作为该组件设计的试点，还为 Nouveau 写了面向 Vulkan 兼容用户态驱动的新 UAPI。但在现有基础设施上正确实现 Vulkan 兼容 UAPI 做不到不出问题，症结在于 Nouveau 积累的历史分层，问题大多集中在锁等基础设施上；这在架构层面撞了墙，让他作为贡献者逐渐承担起驱动责任后，决定另寻他路。（`00:05:20–00:07:08`）另一重痛点是 GSP 固件长期不稳定：NVIDIA 的分发方式是固件、树外内核驱动、用户空间一起改、一起打包发布，这对必须与固件二进制保持兼容的树内驱动行不通；在 Nouveau 已有硬件抽象层之上再叠一层不断变化的固件抽象层，带来的是更多复杂度和更多"手工摊开的 vtable 混乱"，不可持续，于是走向新驱动。（`00:07:10–00:08:05`）

主持人请他补齐了两个术语。"Vulkan 兼容"指暴露给用户空间的 UAPI 能让用户态库在其上构建与 Vulkan 标准（而非某个厂商私有 API）对接的接口——Vulkan 对 GPU 虚拟地址空间的控制更细粒度，需要由用户空间决定地址布局与对象映射，内核把这部分控制权交出去；"in-tree 驱动"指驱动位于 Linux 源码树内、在 Linus Torvalds 的内核 Git 树中得到支持。（`00:08:08–00:09:17`）主持人一度把 Nova 表述为用户空间驱动，嘉宾纠正：Nova 是内核态驱动；用户态驱动例如 Mesa 的 NVK——Mesa 是包含多个用户态驱动的大库，坐在内核驱动之上。（`00:09:18–00:09:40`）

边界与结构。Nova 明确划线：只支持 Turing 架构及之后、内置 GSP（GPU System Processor）的 GPU；GSP 是 GPU 上的主微控制器，运行名为 NVIDIA Resource Manager 的固件，代内核驱动管理 GPU 引擎与资源。嘉宾提醒，现代 GPU 中"操作系统"的很多职能其实发生在固件里。（`00:03:54–00:04:45`）结构上，Nova 主要由两块组成：Nova Core 是核心驱动，负责硬件与固件抽象，向坐在它上面的组件提供 API；Nova DRM 是真正的 DRM GPU 驱动，把 Nova Core 当后端来操作硬件、与固件交互；第三个组件 vgpu 是 NVIDIA VFIO 驱动，同样架在 Nova Core 上，向虚拟机暴露 VFIO 功能。（`00:22:31–00:23:08`）

现状与上游化时间线。主持人问 Nova Core 是否在 Linux 6.15 引入，嘉宾澄清：6.15 引入的是 Nova 本体，但当时只是个 stub 驱动——对上只实现绝对核心的驱动基础设施、核心 PCI 基础设施，通过核心 Io 基础设施读几个寄存器，本质上是给这些先行基础设施做的概念验证。（`00:21:57–00:22:21`）目前的重心在 Nova Core 这个地基上：固件加载的"大块头"已经实现、与固件通信的基础接口已就绪（"非常不平凡"的部分），正在做核心内存管理原语——页表管理，以及 channels（向 GPU 提交工作的概念）；vgpu 驱动并行推进，Nova DRM 也随着地基大体完成开始投入更多精力。（`00:23:08–00:23:53`）

那 Nova 现在能用的吗？嘉宾的口径是"取决于 functional 是什么意思"：它能加载固件、能与 GSP 通信、能正常卸载，基础都在；但上面没有任何东西向用户空间提供功能——"可以用，但还没给用户提供任何东西"。（`00:24:09–00:24:35`）

### 编译期的安全网：Result、Drop 与驱动生命周期规则

主持人请嘉宾举一个"C 里可能出、Rust 里编译器直接拦下"的具体 bug。Krummrich 的例子是 Result 类型：编译器保证调用方必须处理返回值可能包含的错误，需要时自动沿调用栈向上传播；错误检查不能被忽略，也不能像 C 那样忘记检查返回值后继续当作没有错误运行。（`00:13:56–00:14:24`）

生命周期是这个安全网的另一半。他的解释是：编译器确保一个引用只在程序内某个作用域中有效；这个作用域既可以是常规的控制流作用域，也可以是通过泛型关联类型等机制表达的语义作用域。内核在 driver core 里大量使用这一概念——驱动模型规定某些资源只能在特定作用域内被访问、使用和持有，这个作用域就是驱动与它所操作的设备绑定的期间。（`00:12:49–00:13:40`）

边界也要说清楚。Rust 的 Drop trait 可以给类型实现析构，对象离开作用域时析构函数被调用、资源被正确清理；但这不是语言保证——在安全代码里"忘记"一个值是合法的，内存泄漏并不在内存安全保证的覆盖范围内。（`00:14:49–00:15:14`）

主持人在节目中读了 Greg Kroah-Hartman 在内核邮件列表的引语："我们拥有的大多数 bug——按数量计，而非按严重程度——源于 C 中那些愚蠢的小角落 case，它们在 Rust 里完全消失了。"嘉宾认为这在很大程度上符合他的经验，例外是刚才说的内存泄漏这类仍会存在的情况；而且不止于此：driver core 大量依赖生命周期语义来强制驱动生命周期规则，这些规则一旦出错是内核 bug 的主要来源之一，Rust 把它们变成编译期强制，这是超出"小角落 case"的更大收益。（`00:15:22–00:16:28`）

### 自引用结构与 pin-init：把初始化顺序变成数据依赖

自引用结构是 C 内核代码里的常见形态：一个对象的某个字段指向同一对象的另一个字段；最广为人知的例子是 C 的链表实现，几乎所有核心原语都以某种形式内嵌这种自引用结构（主要是链表），Rust 侧必须解决这个问题。（`00:30:33–00:31:24`）

难点在于 Rust 原生不支持自引用结构，因为所有权模型假设值是可以被移动的。语言里有 pin 类型，但它解决不了"初始化时就需要 pin 住"的问题；标准库里 MaybeUninit 式的绕法——先初始化字段再断言全部初始化——本质上又是 unsafe，而这正是他们想避免的。（`00:31:36–00:32:12`）

内核本身就有"东西不能动"的原语：典型场景是用 kmalloc 分配一块缓冲区、初始化全部字段、再把它传给别处。Rust 侧的解法是 pin-init 组件：它提供的 initializers 是"在给定内存块上初始化一个结构的配方"，实现者既不可能忘记初始化某个字段，也不可能用错初始化顺序。主持人把它概括为"用编译器强制取代约定强制"，嘉宾确认完全正确。（`00:32:27–00:33:33`）

这套机制在驱动状态管理上落地。驱动存放运行数据的核心容器是所谓 bus device private data；C 代码的大问题之一是初始化顺序——一旦某些字段初始化完并做了注册（比如中断注册），中断处理函数可能会回头碰这些数据，只能碰已初始化的字段，C 靠部分初始化的结构体蒙混过关，而这在 Rust 里根本不合法。他们的做法是让 private data 携带一个生命周期：设备资源绑在这个生命周期上，驱动无法在其生命周期之外持有资源；注册本身作为对象存在 private data 里，只有 pin-init 允许它们取得自引用的字段才能访问——于是全部依赖关系和初始化序列变成由编译器检查的数据依赖。嘉宾强调这是超出"小角落 case"的收益。（`00:36:28–00:38:41`）

背景铺垫是驱动生命周期本身：设备插入后 driver core 通过匹配过程找到正确驱动，probe 函数被调用；从 probe 到 remove（退出函数）之间驱动全权操作设备；probe 里通常做初始化——分配设备资源、完成注册，而注册才是让驱动真正"有事可做"的入口（异步调用从这里进入驱动），例如 IRQ 注册。（`00:34:48–00:35:59`）

一个有意思的推论是引用计数的变化：嘉宾说，据他所知 Nova 目前没有一个引用计数——因为很多驱动在既有的生命周期模型下根本不需要引用计数；当然也有引用计数合理的场景，比如页表管理将来会需要 PTE 的引用计数。依托驱动生命周期模型及其层级性质，大量场景可以只靠自引用结构撑过去。（`00:33:54–00:34:37`）

### 内核里的 Rust 与用户空间 Rust 不一样

Rust 程序员熟悉的 crate 在内核里是"逻辑代码单元"，自然对应一个内核模块。目前的 kernel crate 承载了所有有 Rust 代码的子系统的核心基础设施，以及可视为 Rust 子系统的核心原语（写抽象的地基）；依赖层级是 kernel crate 为根、所有驱动为叶子。但他们正想摆脱这个结构：因为所有子系统挤在 kernel crate 里，Rust 代码必须集中放在内核的 rust 目录，而不是各自子系统目录里；按子系统拆成独立 crate 才能做更细粒度的依赖，也才能支持驱动模块之间的依赖——Nova DRM 将暴露与 Nova Core 的 API，这目前不被内核构建系统原生支持，他们有临时方案，但希望构建系统改造后原生支持。（`00:27:15–00:28:42`）

内核的构建层级是：调度器、内存管理等绝对核心原语在下，DRM 这类为驱动提供组件的子系统居中，驱动在树顶。对 Rust 驱动有一条规则：不直接调用 C 原语——那会经由 FFI 层引入大量 unsafe 交互——而是调用那些理想情况下只提供安全 API 的抽象。（`00:28:58–00:30:13`）

工具链也和用户空间不同。内核不用 cargo，用自己的 kbuild（主要基于 makefile）构建，Rust 工具链只是这个构建系统支持的"又一个编译器"。外部 crate 通常不进内核树，例外是 vendored 的 crate——pin-init 是最好例子：它因内核需求而动，但是独立项目、也在内核之外被其他项目使用，内核以"树内一份拷贝、并入构建系统"的方式 vendor 它。（`00:39:24–00:40:25`）rustfmt、Clippy、rustdoc 仍然可用，只是经由构建系统的额外 make 目标：比如格式化源码树的 rustfmt target，Clippy 则通过调用 make 时设置标志或环境变量启用。（`00:40:35–00:41:16`）

测试同样如此：可以用 Rust 写 KUnit 测试，写法与用户空间测试相近，区别在于它们不在宿主机上跑，而是在内核里作为启动序列的一部分执行，结果看内核日志。（`00:41:41–00:42:03`）

### 性能：零成本抽象与"生命周期换引用计数"

零成本抽象在内核里最现成的例子是 Io 基础设施：围绕内存映射寄存器和共享内存中的结构构建抽象。两者实现不同但概念相同（正在统一）：projections 提供对一个结构越来越窄的视图，直到只剩一个可读写的原语；寄存器一侧技术上也是对"代表寄存器的原语"的位段投影。这套东西有几千行代码、对接 DMA 内存、共享系统内存、内存映射 I/O 等不同后端，做了大量构建期检查和类型安全，但驱动里真正用起来时，最终编译成的就是一次 load 或 store——"数千行代码编译成两条汇编指令"。（`00:42:27–00:44:14`）

Rust 不只是不慢，嘉宾还给出了变快的例子：C 代码里为追踪对象存活经常做引用计数，但在概念上未必必要——C 只有两条路，要么按约定共享裸指针、祈祷释放后没人解引用，要么上引用计数、转而依赖每个人都在正确时机放下引用；Rust 用原生生命周期让编译器接管追踪，根本不必引入引用计数，从而省下内存分配和原子操作。（`00:44:24–00:45:34`）

至于基准测试，嘉宾明确说目前做的不多：性能关注点主要在核心抽象上，而且与其说是测量，不如说是检查编译产物——看汇编长什么样、有没有引入额外开销、是否达到了设计意图。现在也很难比较，因为固件加载序列和核心内存管理 API 还在实现中，没有可对照或可运行的东西；性能考量"是将来的事"。（`00:46:06–00:46:46`）

### 挑战与展望：语言复杂度与上游化策略

主持人请嘉宾从"C 内核工程师开始 Rust 驱动项目"的经历里挑一个挑战。嘉宾的回答是：没有某个单一概念特别难，难的是语言整体复杂度——带来强大类型系统和借用检查器的那些东西，相比 C 是一门复杂得多的语言，语法也不同；写了多年 C、语言已感觉自然、注意力都在写代码本身之后，重新把注意力放回语言学习上，是一种转变。（`00:47:31–00:48:16`）

对未来的期待（嘉宾口径）：第一个目标是让每个人都能轻松地用 Rust 写驱动，因为这是能立即获得收益、又无需妥协的地方；驱动是 CVE 问题的主要来源之一，而 Linux 是单内核，驱动稳定性提升会让整个系统受益。他希望基础设施足够完善，让想写驱动的人可以直接动手写、直接上游化，而不必先自建核心基础设施。主持人复述为"现在的 Rust for Linux 是在建地基，好让将来写 LCD 面板或新 GPU 驱动的人直接复用"，嘉宾确认。（`00:48:38–00:49:25`）

这期节目最后的一段经验是上游化策略。内核有条基本规则：没有使用者的代码不能上游。他们的解法是先上游一个 stub 驱动，从而在内核里把驱动逐步搭起来；由此形成一种嘉宾认为不寻常的动态——Nova 需要一块新基础设施，就把这块基础设施做出来，在 Nova 里作为第一个用户使用，基础设施建设与真实使用之间来回迭代。通常驱动是在下游开发完、作为一大块代码一次性上游的；而在内核内以小块上游的做法让维护者、贡献者和评审者更容易参与，并且显著提升了代码质量——一大块代码丢进来时，所用核心基础设施的核心维护者很可能根本没看。嘉宾觉得这值得思考，也许会改变将来其他驱动在内核里的构建方式。（`00:50:06–00:52:17`）
