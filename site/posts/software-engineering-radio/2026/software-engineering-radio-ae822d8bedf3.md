## 速读

AWS 高级首席工程师 Clare Liguori 是 Strands Agents SDK 的亲历者:从 Amazon Q Developer 时代给 Claude 2 手写"请在 JSON 前不要说话"的解析重试循环,到顿悟"扔掉全部脚手架"的模型驱动路线。本期把这条演化史和 Strands 的核心机制讲透:steering 钩子用确定性 Python 拿到 600 次评测 100% 准确、轨迹存进向量库变成"过程记忆"、以及 AI Functions 这种运行时生成代码的新形态。

最值得带走的三点:workflows 看似确定实则脆弱,会被模型进步反噬——steering 用"事后即时校验+拉回"的思路反而更准;模型每三到六个月一次大跃迁,你三个月前生成的提示、SOP 与轨迹都可能正在拖累 Agent;以及那条反直觉建议——很多场景不该建 agent,把数据做成 MCP server 让别人的 agent 来用就好。

## 主题正文

### 起源:从解析 JSON 的重试循环到"扔掉脚手架"

Liguori 对 agent 的定义朴素到只剩三件事:模型、工具、提示。Origin story 始于三年前的 Amazon Q Developer,那是 Claude 2 的年代——模型还没有结构化的工具调用区,工具只能用 markdown 写进系统提示,再指望模型用严格 JSON 回复想调哪个工具;而模型"沉迷自然语言",总要在 JSON 前加一句"以下是我选择的工具",把解析器搞挂。团队的解法是重试循环:把 JSON 解析错误原样喂回模型,它下一次就能自己修对——"模型对反馈的适应性极好"是第一课。到 Sonnet 3.5 时代,推理请求里有了结构化的工具区,他们却已经堆起了巨型提示管线、主动式 RAG 拼装——然后发现这些脚手架反而在限制新模型:一个回答 AWS 文档问题的 agent,主动注入的 RAG 内容会让它怀疑自己训练数据里的正确直觉,把注意力钉在不相干的检索结果上;把 RAG 从"预注入上下文"改成"agent 自己决定查不查的工具"之后,准确率反而大涨。这就是 model-driven approach 的顿悟:简单提示+工具+模型,让它自己选工具、选上下文。内部成果是 Q CLI 三周上线;去年 5 月这套内部框架以 Strands Agents 之名开源,至今下载量超过 2500 万。（`00:00:54–00:11:08`）

### Workflows 的幻觉与 steering:校验"已经做了什么"

她把常见的过度设计归为两类:围绕模型堆自定义编排(模型升级即作废——model-driven 的好处是升级只需改一行 model ID),以及用 workflows 换取确定性。航线机组排班、贷款审批这类场景确实需要确定性,但工程师的直觉是回头写 for 循环和 if 语句——实践证明这极其脆弱:你为"贷款审批"写死步骤,用户改问"这笔贷款风险如何"时,整个 agent 就废了。Strands 给出的答案是 steering:不规定步骤,而是给 agent 立规矩("要调用贷款审批工具,必须先验证收入且达标"),在它即将越界时校验"已经发生了什么"并拉回——把软件执行从"构建时预定全部步骤"翻转为"对既成事实的即时校验"。她发布的实验里,这种做法的准确率反而超过 workflows。（`00:11:48–00:16:54`）

steering 与各家 harness 都有的 hooks 之别在一字之间:hook 只能看到"即将发生什么"(挡掉 rm -rf 足矣),steering 拿到的是完整轨迹——而自动化业务流程恰恰需要后者("它要调贷款审批了?先查账,收入验证做了吗、返回值是多少")。她给出的杀手级用例是跨工具的输入幻觉:上一个工具取出的 user ID,被下一个工具幻觉成别的值——steering 可以在调用前核对"这个 user ID 真的来自上游输出吗"。（`00:17:26–00:20:16`）

支撑这一切的是 Ledger——agent 全部动作的账本,hooks 本可以自己攒,Strands 开箱即用,还附带现成的 steering provider(比如 LLM-as-a-judge:一句话评估"它做了什么、即将做什么、可以吗")。与记忆系统的关系她划成三层:短期记忆是可回溯的原始对话史,中期是滚动摘要(丢细节),语义记忆是提炼出的" Nuggets"——她见过 agent 给用户存的记忆里赫然写着"此人爱用英式俚语"。更有意思的是把轨迹本身当记忆:某个 AWS API 要求先按序调用 18 个前置工具才能执行,他们把成功轨迹以提示为键存入语义/向量库;模型极擅长知识迁移,相似提示检索出旧轨迹后即可改写复用——这是一种"过程记忆",给高频用例带来确定性与效率。但她立刻补上反噬警告:模型每三到六个月一次大跃迁,旧模型生成的轨迹、SOP、提示都可能让系统劣于"最新模型的裸奔"——过期与重估是必须设计进去的。（`00:20:31–00:25:40`）

### 600 次评测跑出 100%:确定性 Python 钩子的胜利

steering 钩子的杀手锏是它可以完全确定性:纯 Python、可单元测试"测到死",甚至用 Rego/Cedar 做可验证的策略。她发布的对照实验里,自己写的 Python steering 钩子在 600 次评测运行中拿到 100% 准确,workflows 约 80%,纯提示远远落后。100% 从何而来?因为"哪些工具输出是关键、哪些数据必须跨工具一致"只有 agent 开发者知道——把这份领域知识写成确定性检查,剩下的自然语言(比如发给用户的邮件措辞)才交给 LLM-as-a-judge 看语气。评测集覆盖四类规则:工具顺序(先验证后审批)、输入幻觉(该输入必须来自某工具输出)、自然语言约束(不许因用户怂恿而失礼)与工作流依从性——她发现有些模型会稳定地跳过"完成后给用户发确认"这一步(觉得动作做完就是做完了),steering 一句"你还没发确认"就拉回来了。最惊人的是成本:小模型(如 gpt-oss-120b)加 steering 比更可靠的 frontier 模型便宜得多。对照方案是 SOP——用 Strands 的工具为 agent 生成一步步的系统指令,在她测的场景里也达到 99% 准确,但输入 token 是三倍;她称之为"提示跑步机":从一小段提示开始,为每个边缘案例打补丁,always/never/must 越堆越多,最终长成庞然大物。长任务场景 steering 也有结构优势:Ledger 里的完整历史不必喂给模型,Python 函数可以照常在全量历史上校验规则;而 workflows 的节点之间会持续丢失上下文。（`00:26:03–00:34:59`）

### 工具、MCP 通用语与 AI Functions

工具接入上 Strands 走"函数即工具"路线:Python 写个 Pydantic 风格函数即成工具,TypeScript SDK 用 Zod;而 MCP 正在成为工具生态的通用语——她看到公司纷纷用 MCP 网关把内部 API 的 OpenAPI schema 变成 MCP server,任何 agent 开发者即刻可用。她给的取舍口诀是"方法与库":一次性、单 agent 用的就写原生函数;要跨 agent、跨框架复用,或本来就有一个 API,就升级成 MCP server。更实验性的产物在新的 Strands Labs 组织里:AI Functions——你写一个普通签名的 Python 函数,但函数体是一个提示,运行时生成并执行代码,再配上前置/后置条件(收据 OCR 是她的例子:前置"必须有图片",后置"必须有结构化的总额/商家/明细",不满足就带着反馈再 prompt,直到满足)。背后的理论是:同一提示在生产上跑一千次会得到一个"代码解的高斯云",你拿到的是真实运行时反馈(延迟、自纠次数、真实输入)——这些在预生产环境用测试数据拿不到;假以时日可以逼近最优解、再左移回代码库,甚至她怀疑永远不必左移:Sonnet 4 时代签入的代码,用 Opus 4.7 重新生成也许就是更好的。奖励函数的设计还没想透——今天的后置条件是二元的(行/不行),以"用了几轮才对"为梯度的奖励函数还是空白。（`00:35:26–00:46:16`）

### 部署模式:单 agent 优先、子 agent 作工具、"别急着建 agent"

生产经验浓缩成一句话:从最简单的开始。绝大多数用例只需要单 agent 加上 hooks/steering;工程师们造的复杂编排,大多数场景根本不需要——"先做最简单的,评测,你会被今天的模型吓一跳"。她喜欢的唯一复杂模式是 sub-agents as tools:主 agent 把"抓网页提取事件"派给专职子 agent,子 agent 扔掉整页 HTML 只返回事件——百万 token 的窗口也不该拿来装垃圾上下文;主持人惊呼这是"重新学了一遍封装"。多 agent 模式她认为多数出于组织而非技术原因——微服务的翻版:每个团队拥有自己的 agent、以 API 相连、长时运行,交互模式与普通工具不同;退款处理是典型,各团队 agent 之间要传递商品、客户风险画像、既往沟通等上下文,需要多少取决于用例。历史管理上她观察到近四个月最重要的新模式是"保存进度":agent 把工作状态以自然语言存盘,醒来时从"前世"的笔记恢复——像她每天下班把大脑倒进 Obsidian。（`00:46:16–00:55:31`）

生产化是 Strands 的卖点之一:OpenTelemetry 开箱即用(追踪里能看到工具调用、输入输出与思考过程——"结果不对时回放它怎么走到这一步"离线评测也靠它)、会话持久化开箱即用(S3 或文件);内部从零到生产普遍三到六周。新的托管服务 AgentCore Harness 在 Strands 之上补齐记忆、身份、CloudWatch、MCP 网关连接与运行时部署,让你只回答"模型、提示、工具"三件事。她特别强调评测:给 agent 选第一个用例,就选"能确定性评测轨迹"的——工具调用对不对、顺序对不对、输入对不对;聊天机器人最难评(多轮对话只能靠 LLM judge 和用户体感),自动化用例反而是低垂果实(有既有流程可对照)。AWS 内部因此开始认真投入 A/B 测试——过去靠确定性测试就够,agent 不给你同样的答案两次,只能灰度 10% 用户跑几周;她形容这像"开着车换车的每个零件"。反模式清单同样具体:两年前"人人建 agent"的浪潮留下一百万个重叠难分的 agent,如今的方向反过来——先问"这是不是该做成 MCP server,把数据与上下文提供给少数中心 agent";AWS 自家的 AWS MCP Server(预览版)正是这个思路的产物:与其做一个 AWS agent,不如给工具和技能,让用户的 agent 自己来。（`00:55:31–01:05:49`）

Strands 的下一步是服务"在 harness 之上建 agent"的人:事件驱动的 agent、可中断的超长时运行 agent。最后的寄语简短:"玩得开心。从模型、工具、提示开始。"（`01:06:40–01:07:48`）
