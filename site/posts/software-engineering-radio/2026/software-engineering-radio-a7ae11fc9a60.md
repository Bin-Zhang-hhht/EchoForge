## 主题正文

### 迁移之痛：五年积累、作者离职、没人知道覆盖了什么

Rabinovich 说 Groundcover 的大多数客户都来自某个传统厂商，而迁移最大的障碍不是新技术，是存量：整个研发组织往往有几百个仪表盘、成百上千个监视器（告警）、几十个集成和数据管道配置——那是 5–10 年间由许多人（有些已经离职）共同留下的资产，连「我们到底有什么」的知识本身都丢了。（`00:01:47–00:03:18`）最极端的客户有 10,000 个监视器；常见量级是几百个监视器加几十个仪表盘，通常靠基础设施即代码生成，手工建不出来。（`00:04:57–00:05:29`）

为什么明知难还要搬？他自己创过业前就是受害者：旧模式有两个死结——一方面要靠 APM/OpenTelemetry SDK 埋点生成数据，而「你不知道你不知道的」，没埋点的故障就是盲区；另一方面按数据量计费太贵，授权费之外还有流量出口费，形成恶性循环：埋更多点→账单爆炸→削减埋点→挫败，以至很多组织设有专职角色只管「把可观测性成本压住」。（`00:05:44–00:07:10`）

### 商业模型决定产品行为：BYOC 与激励对齐

Groundcover 的答案是 bring-your-own-cloud：数据面整个跑在客户的 AWS/GCP/Azure 账号里，厂商只管控制面，因此不按数据量计费；配合自研 eBPF 传感器生成更多数据——客户不多花钱，两个机制互相放大。（`00:07:10–00:08:08`）他更点破了行业激励问题：按数据量赚钱的厂商，看到客户发送垃圾数据时没有动力阻止——「garbage in, garbage out，但垃圾数据养着它的营收」；而 Groundcover 因为不靠量赚钱，直接把过滤条件下推到节点传感器，垃圾日志在源头就丢掉，不必序列化、走网络、再在对端丢弃。（`00:08:48–00:10:45`）

### 迁移方法论：先发现，再排序，用小胜建信任

第一道工序他们叫「为可观测性做可观测性」：客户往往有五六十个活跃集成却不自知——配置散落各处、出自几十人之手。Groundcover 先检查数据本身，从数据里反推出「你其实有 50 个活跃集成」，再自动把每个厂商的集成配置翻译成自家的等价物，客户看报告、点下一步。（`00:10:55–00:12:40`）

正式迁移从发现开始：抓取全部资产（仪表盘、监视器、日志管道、权限策略），先可视化呈现「我们要搬什么」；然后按元数据排优先级——最近一周还在编辑的仪表盘大概率比一年没动的重要，正在报警或上周报过警的监视器是关键，一年没响过的大概次要。（`00:13:00–00:14:36`）另一个视角是「缺口排序」：5000 个指标映射上了 4900 个，缺的 100 个里先补「被 80 个仪表盘依赖」的那一个。（`00:14:36–00:15:25`）他把迁移比作搬家/搬银行：一样令人紧张，但关键是给客户信心与反馈回路——每补上一个集成，数据自动可视化、清单自动打勾，「这些小胜利撑着人走完全程」，最后把成果摆给所有利益相关者收尾。（`00:15:25–00:16:31`）

翻车案例也很有教育意义：一个客户的新旧多个版本同一服务并行运行（日志方案在渐进迁移），平台按数据把监视器映射到了新日志结构，却漏了老版本的不同结构——部分仪表盘加载不出来、数据在但形状不对。客户团队非常投入，指着屏幕说「这面板只有一半数据」，双方下钻原始数据才发现背后有层层转换；这次教训直接换来了如今更强的数据检查能力。（`00:16:42–00:19:02`）顺带揭穿一个行业暗面：有些客户的仪表盘在老厂商那边本来就是坏的，客户并不知道，迁移时反而期待它工作——厂商有责任证明这一点。（`00:20:03–00:20:36`）

### OpenTelemetry 解决了一半：数据中立，仪表盘依旧私有

作为 CNCF 主力项目，OpenTelemetry 统一了可观测性信号的语义（什么是 trace、log、metric）并提供 SDK 与 Collector 实现——这是「让客户能在厂商间自由迁移」的第一步：数据结构与生成方式中立了，集成和管道也内置其中。（`00:22:00–00:23:54`）但他坦率指出边界：各家仪表盘的 schema 与特性、监视器定义、管道与集成配置仍是厂商私有；可视化层的标准化虽有倡议，离成为标准还很远。（`00:24:53–00:25:36`）

### 验证与成功标准：85% 但按价值排序

最难验证的是「从未触发过的监视器」——没有任何数据样本可以比对，只能假设几个月没响的不太重要，「我们可能到不了 100%，但能覆盖 99% 真正要紧的」。（`00:25:47–00:26:37`）常规验证则是双跑：迁移期间客户把数据同时发给新旧两家，平台对新旧查询做同屏预览（时间序列组件应看起来一致），客户批准后标记完成、批量入账；关键资产 100% 确认前不切旧厂商。（`00:26:42–00:29:17`）他的成功定义值得记住：**按价值与紧急度排序后迁移掉 85% 的总资产**就是成功迁移——搬家恰好是重新审视的机会，那些坏仪表盘也许根本不值得搬过去。（`00:31:09–00:31:54`）

迁移健康的度量：集成数量（原始数据丢了才是真损失，仪表盘丢了只是重建工时）、未迁移资产数、活跃监视器数，以及摄取量对比——BYOC 客户往往发得多得多（老厂商 1 TB/天，Groundcover 可能 5–10 TB/天），对比时要按环境与日志级别切片：dev/CI/staging 在老厂商那边本来就被跳过，生产环境逐环境、逐级别确认「不少于原有数据」。（`00:32:00–00:35:49`）

展望里他给出两个方向的区分：AI for observability（agent 辅助根因分析、与人对拍假设）与 observability for AI——当全行业都在把 agent 和 LLM 调用塞进后端，「怎么观测 agent、怎么确认它在做该做的事」成了新问题：agent 不确定性破掉了「trace 里期待特定状态码」的旧测试范式，evals 与 LLM 可观测性正在成为新产品类目。（`00:36:00–00:38:18`）
