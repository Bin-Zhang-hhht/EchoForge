## 主题正文

### 人怎么感知延迟：P99 心理与一个 400 毫秒的故事

Garg 的定义从用户出发：延迟是「从用户发起动作到体验到响应」的耗时。（`00:01:35–00:02:29`）人的敏感度分层很细：邮件客户端 Superhuman 把每次按键交互的目标定在 100 毫秒内（50–100 毫秒感觉良好，超过 100 立刻变差）；语音场景 500–600 毫秒尚可忍受；普通 UI 按钮超过 30–40 毫秒就发黏；人甚至能感知 5–10 毫秒的击键延迟。（`00:03:19–00:04:24`）更重要的是**感知的不对称性**：用户实际按 95–99 分位的最差体验打分——Wispr 内部抱怨「慢」的时候，看分布往往是一两个离群案例在定调。（`00:04:36–00:05:11`）

追长尾是最难的部分，因为 P99 背后可能有一百种原因。他们的解法是对延迟的每一段做观测，把每个网络跳的时间拆出来。（`00:05:23–00:06:02`）他讲了一个典型案例：语音听写管线（语音模型 + LLM 后处理）某天响应整体上涨 300–400 毫秒，数据到得快、处理得也快，问题出在两个模型**之间**——部署配置阴差阳错让第一个 GPU 落在加州、LLM 的 GPU 落在中西部，音频跨区跑了一圈。外表一切如常，打开引擎盖才发现网络往返，最后收回同区域解决。（`00:06:34–00:07:53`）

关于规模：每次扩容都会暴露新的延迟源——路由、数据库负载——而且它们在不同规模点位「突然爆雷」。（`00:08:09–00:08:41`）他们不做专门的延迟回归测试，理由很现实：这套系统复杂到无法在预发环境真实模拟，GPU 负载高度随机不可预测；替代方案是全量延迟分析 + 灰度发布 + 每小时监控，出了问题快速发现快速修。（`00:08:41–00:10:08`）

### AI 应用的延迟为什么是另一回事

与老式 Web 应用（认证、查库、渲染的离散步骤）相比，AI 工作负载有两点质变：一是**自回归生成**——ChatGPT 一个词一个词往外蹦，每个词都要喂回模型再生成下一个，是一整条解码循环；二是计算落在 **GPU** 上而非 CPU。（`00:16:44–00:19:01`）这让 AI 应用更像流式应用，但又不同：音视频流的难在大数据量，AI 流的难点在服务端「超随机、可能很久」的计算，你要把它藏起来。（`00:19:30–00:20:11`）

为什么用户能忍受 LLM 的等待、却对搜索引擎加 100 毫秒就翻脸？他给两个原因：一是**即时价值差**——Google 100 毫秒给你的是一堆还要点进去验证的链接，ChatGPT 给的是最终答案；二是**预期管理**——ChatGPT 语音模式把 3–4 秒的「AI 停顿」压到 500 毫秒之后，「再让我用回长停顿的版本，我很快就会弃用」。（`00:14:27–00:15:48`）流式输出的粒度本身也是 UX 决策：一个词一个词刷屏根本没法读，所以按块推；Gemini 曾做逐行淡入，那是显示策略不是服务端行为。（`00:20:21–00:21:16`）

### 延迟预算：产品约束，不是工程口号

Wispr 对响应长度有硬性要求：听写的输出必须与输入大小相近——用户不希望系统替他扩写、替他决定说什么；至于问答类产品长度为何各异（ChatGPT 偏长、Claude 偏短），他把原因归于产品目标不同，并观察到点一次「展开」后同服务的后续回答会越变越长——个性化的适应。（`00:22:09–00:23:52`）工程上最大的取舍是**延迟对吞吐**：请求来了立刻处理，还是攒一批一起送 GPU？攒批能在同等算力上服务两倍请求——在 GPU 短缺的时代，这就是商业问题。（`00:25:53–00:27:19`）模型大小是另一根轴：大模型好而慢、小模型快而差，按请求路由（医疗数据用最新 GPT-5.1，判断语气用小模型）成了标配，甚至可以让一个中等模型先判断「这是易题还是难题」再分发。（`00:27:35–00:28:51`，`00:31:29–00:31:51`）

他们把这套东西落成「延迟预算」：由产品侧定义用户可接受的最大时长——分别为平均值与 P99 设目标（他们的 LLM 预算是 50–100 词 250 毫秒）——然后工程端在这个约束下试遍各家族模型，选「在预算内最准的那个」。实测两端都会翻车：过小或过度量化精度崩，过大直接爆预算。（`00:30:32–00:31:27`，`00:32:02–00:33:13`）预算的用法是先定总目标、再看现状各段耗时、然后「挪时间」：网络操作省下 100 毫秒，就多出 100 毫秒给更大的 LLM。（`00:33:34–00:34:10`）

### 投机解码与省出来的预算

最见效的一招是**投机解码**（speculative decoding）：先猜输出再验证——编码工具里没改动的行大概率原样输出，听写里句子前半段在填充词出现前大概率不变；猜对的部分按批验证，猜错才重算。上线后他们的 LLM 延迟在很多场景直接砍半甚至更多，省出的预算立刻用来加第三、第四个模型把结果做得更好。（`00:34:25–00:36:21`）其他两件套：**量化**——FP32 到 FP16 再到 INT8 整数运算（无需处理指数，快得多），配合量化感知训练保精度，如今多数大模型推理已跑在量化算术上（他引用马斯克/xAI 想连训练都用整数的说法，作为观点呈现）；**蒸馏**——让大模型在一百万条样例上作答，再用答案教小模型模仿，小模型在单一任务上能做到不输大模型，是法律/医疗等垂直 AI、端侧推理（语法检查、车载视觉）与隐私场景（数据不出设备）的共同解法。（`00:39:23–00:41:00`，`00:41:52–00:46:38`）

规模与随机性是最后两块。GPU 批处理要求请求同质，一个 200 词问题配 10 词回答、旁边再来个反向的，并行优化就变形；但规模也带来「把相似请求路由到同机」的新优化机会——规模既帮忙也拆台，真正痛的是资源耗尽。（`00:48:31–00:50:09`）关于 GPU 行为的可预知性，他的答案是五五开：曾有一个 CUDA kernel 的 flag 在特定负载模式下带来 25% 的性能提升——「这不可能事先猜到，只能靠观测与 profiling 抓出来」。（`00:50:25–00:51:23`）至于随机性与幻觉：先设护栏（知道答案该多长就能截断），再在生成中途用启发式或另一个 LLM 抓跑偏——让系统在正常问题上不脱轨是开发者的责任。（`00:46:47–00:48:31`）

收尾是他的黄金法则：**一切非关键操作都滚出关键路径**——「3 毫秒这里、5 毫秒那里，好的条件下转眼就是 100 毫秒」；最容易避免的开销恰恰来自那些看起来人畜无害的代码。剩下的就是硬功夫： dive 进日志、读懂 kernel。主持人把这归结为早年「响应式应用」的老原则：不需要内联响应的，统统异步加事件。（`00:51:32–00:53:14`）
