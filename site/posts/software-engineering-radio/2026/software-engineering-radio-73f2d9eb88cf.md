## 主题正文

### C 的慢，是特性先落地、标准再追认

Gustedt 开场就自嘲「C 真的很慢」：标准化的原则是只收录已经实现的东西，一个特性从出现到进标准有很长的周期。（`00:01:47–00:02:11`）他对比 C++ 的「做了又撤、前后不一致」，强调 C 追求慢而稳的节奏。（`00:02:11–00:02:38`）这个模式的最好例证是新增的位操作工具：popcount 这类函数各家编译器早有内置实现，标准只是统一命名，glibc 的头文件提供宏接口、翻译到编译器的 builtin，最终甚至不产生函数调用而直接生成指令；编译器团队要做的功课只是对齐标准规定的名字与参数。（`00:10:53–00:12:45`）反过来，运行时性能在不同编译器之间确有差异，基准测试是唯一裁决方式。（`00:13:39–00:14:11`）

标准之外这五年最大的产出是指针来源（provenance）技术规范：由剑桥大学的 Peter Sewell 主导、磨了约十年，定义「指针指向哪个对象」的精确模型——每次分配或变量声明都产生不同的来源，编译器由此可证明两个指针不指向同一对象，从而安全地做别名分析与优化。它不消灭野指针，消灭的是「这两个参数会不会指向同一个东西」的不确定性；编译器厂商还需逐项核对实现是否符合该模型。（`00:02:38–00:05:04`，`00:05:11–00:07:20`）他同时观察到编译器诊断能力在这五年有真正的飞跃。（`00:07:28–00:08:00`）

### C23 与 C2y：十二年等来的特性版本

C23 是 C11 以来第一个真正的特性版本（中间的 C17 只修 bug），变化包括：符号表示限定为二进制补码（人人都在用，现在终于写进标准）；auto 与 typeof 类型推断；系统化的属性（attributes）语法；标识符全面遵循 Unicode 规则；标准库新增编码转换、位工具（stdbit.h）与检查溢出的运算接口。（`00:08:15–00:10:46`）

下一版没有 C26，直接叫 C2y（年份未定，估计 2028–2029），且将是又一个特性版本：if/switch 语句内定义变量（借鉴 C++）、预处理器新增 `__STDC_COUNTER__` 式的计数器特性（为宏生成的变量提供唯一命名）、移除「无人实现过」的虚数类型、新增此前竟不存在的复数字面量。（`00:15:45–00:16:23`，`00:17:00–00:19:26`）委员会只有约 30 人定期开会，走全体会议加邮件列表的流程，所有论文与修订版本都在委员会网站上公开。（`00:20:53–00:21:27`）

细节上值得一提的还有：`_BitInt(N)` 精确位宽整数其实源自 Intel，但动机出乎意料——FPGA 设计里需要按比特定制整数类型来精确布局计算网络；而 128 位整数则是把 `uintmax_t` 卡在 64 位的人为上限打开，服务于密码学等真正需要宽运算的场景。（`00:25:41–00:28:19`）机器学习走的是反方向——想要 8 位浮点，但各家规范至少十种、尾数安排互不相同，暂时无法标准化。（`00:28:19–00:29:54`）空指针常量 `nullptr` 从 C++ 借来，从宏升级为语言内建，绕开了大写 `NULL` 宏底层表示含混的老问题（传给 printf 之类可能出错）。（`00:30:24–00:31:54`）属性语法则确立了「属性作用于其左侧构造」的统一规则，标准属性如 `deprecated`，同时给厂商留出扩展空间。（`00:31:55–00:34:27`）

泛型方向上，auto 保持代码一致（x 类型变了 y 自动跟着变）、typeof 服务宏开发、空花括号初始化让数组（含运行时定长的 VLA）整体默认初始化——这些都已在编译器里存在多年，标准只是盖章，老编译器也能回植。（`00:34:37–00:38:45`）他投入很多精力的 lambda 与复合表达式则没能进 C23：回调场景里闭包写在一处显然更好，但「lambda 能看到周围哪些变量、如何捕获」这类设计问题让委员会分歧极大，「有时你会觉得大家要为这个打起来」。（`00:38:45–00:41:07`）

### 程序失败的四种形态，与「听编译器的话」

《Modern C》第三版完全为 C23 重写（电子版里检索 C23 有约 200 处），并随书附一个「平滑过渡头文件」：把 C23 的新名字映射到老编译器的内置实现（如 `unreachable`），只为困在两三年前编译器上的项目兜底。（`00:41:12–00:42:39`，`00:43:08–00:45:06`）

本书最被主持人称道的是他对程序失败的分类学，共四层：一是「过错」（wrongdoings）——解引用无效指针这类用户错误，应当由编译器诊断或让程序尽快失败；二是「程序状态退化」——malloc 返回 NULL、文件系统写满，这类可检查，系统调用的返回值必须逐一确认；三是「不幸事件」——线程竞态这类「各自局部都正确、合起来不工作」的问题，只能靠设计避免；四是「一系列不幸事件」——每个局部决策都合理，合起来却原地转圈（他比作在每个路口都左转、永远绕着街区走），需要算法层面证明「总有进展」。（`00:45:29–00:50:42`）对策与之对应：纪律与编程风格、检查每个系统调用返回、以及为并发专门学习原子与互斥（书中有专章）；后两类没有通用规则，需要真正的证明。（`00:50:58–00:53:19`）他正在推进的 C 契约（contracts）提案已发表论文，尚未进入委员会讨论——这是让语言层面自动保证更多性质的方向。（`00:55:02–00:55:42`）

给工程师的一句话建议：坚持一种一致的编程风格，并且听编译器的话——把警告清零，就能解决一半的失败。（`00:56:19–00:56:45`）C 的生态位依然独特：它是语言之间的通用语，所有语言都在某一层面对接 C——Rust 库暴露 C 接口给所有语言用，Python 想要快就把热点写成 C 库。要不要学 C？他反问式地肯定：它常年是全球使用量前三的语言。（`00:56:49–00:57:47`，`00:57:50–00:58:00`）
