## 主题正文

### 应用与模型怎么分家：确定性归代码，模型只拿「受控的自由」

Dandigam 给出的分工标准很干脆：凡是从明确事实与规则就能可靠决定的，都归应用——认证、授权、策略检查、数据获取这些确定性逻辑；模型的价值在于理解灵活的自然语言、比较与排序选项、理解人类输入，然后给出建议与下一步。（`00:02:59–00:03:54`）他反复用「模型不应拥有系统」来提醒：模型只负责系统中的一部分，在它介入之前，运行时应当已经完成了用户校验、权限、策略与限流这些检查，确认「这是一个模型可以替用户行动的位置」。（`00:03:54–00:06:43`）

结构化契约是另一条硬规则。自由文本是给人看的，应用之间传递的是结构化数据——模型输出的决策对象至少要包含 outcome（比如「需要澄清」「建议就绪」「已提议购物车」「需要确认」「无法完成」）、reason code、状态和下一步能理解的字段。（`00:11:28–00:13:30`）但 schema 验证（Python 用 Pydantic、TypeScript 用 Zod，JSON Schema 则语言中立）只能证明输出形状对了：价格是数字、必填字段在、类型正确；它证明不了这个价格是当前实价、匹配用户要求——语义检查仍然要靠应用代码去做。（`00:13:30–00:14:33`）

### Workflow 还是 Agent：先问「谁决定下一步」

全篇最实用的分界：workflow 里代码决定下一步，agent 里模型决定下一步。（`00:06:45–00:08:42`）「按上次订单复购」路径完全确定，写 workflow 就够；而「四个人七点一刻前的晚餐、预算 70 美元、一份素食、有过敏限制、不要披萨」这种带硬约束与软偏好的开放请求，才需要 agent 逐轮决定调用哪个工具。（`00:08:42–00:11:08`）因此「最大自主权」在生产里通常是错误的默认——先问这个任务是否真的需要模型来决定路径。（`00:06:45–00:06:57`）

模式上他列得很清楚：prompt chaining（一步喂给下一步）、routing（请求属于明确类别时分流，比如支持请求单独交给 support agent）、编排模式、独立读取的并行执行，以及需要边界化审查修复的 evaluator loop；agent 侧再分单 agent、多 agent 与 coordinator/supervisor。（`00:21:36–00:23:21`）多 agent 的正确形态未必都很「自主」：协调者 owns 整个晚餐请求，餐厅、饮食、配送三个专家可以只是服务、固定子流、结构化模型调用或有界 agent；应用仍然控制支付与下单，必要时插入人工确认。（`00:23:24–00:24:55`）并行也有代价：降低墙钟延迟的同时抬高模型与工具的峰值用量，各分支重复共享上下文、可能各自失败，而最慢的必需分支仍决定最终响应——只有任务真正独立且延迟收益可观时才值得。（`00:24:49–00:25:54`）

他自己最有分量的证据是一个生产案例：工作流里有一个模型控制的路由步，为关键路径挑选专家，但追踪显示应用上下文几乎在每种情况下都已经决定了需要哪个专家——这个路由只带来额外一次模型调用、更多延迟和一条新失败路径。他们删掉了路由决策，改为确定性调用专家，专家内部仍保留有价值的模型推理。他的结论值得贴在工位上：不是每个委派决策都需要 agentic，确定性仍然有用。（`00:28:03–00:28:42`）

### 四类失败与工具边界：失败方式决定重试策略

他把 agent 系统的失败分成四类，且强调分类本身就影响可靠性：验证失败（输出不符结构或业务不变量）、策略拒绝（系统正确拒绝——未授权支付或超预算，这是预期结果而非技术故障）、工具失败（能力选对了但 API 超时或报错）、交付失败（决策正确但下游通知或动作没送达）。四者需要不同的重试、告警、指标与责任人；排障时先分类，才能定位「到底哪里失败了」。（`00:14:42–00:17:12`）

工具侧的边界设计：只读工具风险窄，可以在流程较早阶段运行；写操作要过审批门，配合验证、超时、幂等与显式确认。（`00:17:22–00:19:05`）一个具体细节是幂等键：读操作超时可以放心重试，但下单请求超时后不能盲目重试——订单可能已经存在，必须先查结果再决定。（`00:18:34–00:18:49`）

### 运行时：持久状态、同步/异步阈值与流式的边界

agent 一旦跑在一次请求之外，就需要持久执行状态、检查点、run ID、幂等、取消、超时处理、恢复机制，以及在原始连接断开后继续上报进度的办法。无状态端点可以失败后让调用方重试，而长跑的 agent 可能已经调用了多个工具、创建了外部状态——恢复逻辑必须分清什么已完成、什么重复是安全的。（`00:28:50–00:30:10`）他还区分了三种容易混淆的状态：active state（完成当前 run 所需的请求、约束、工具结果、重试计数）、长期记忆（跨交互有意保留的用户偏好）与共享上下文（多步共享的可信信息，如用户档案、支付方式）；三者存储与隐私约束不同，PII 与未经用户确认的信息不应进入长期记忆。（`00:29:59–00:32:16`）

同步还是异步，他给了一组可直接抄的阈值：P95 能稳在约 8–10 秒内、路径可预测、不需要持久等待或人工批准的，保持同步；可能超过 10–15 秒、依赖多个可变外部服务、需要断线存活或等待审批的，返回 run ID 改用进度模型。以他的食品助手为例，合理的起点是：500 毫秒内确认收到请求、一两秒内给出首个进展、三到五秒内给出首个可用结果、P95 完成约 10–12 秒——最终仍由产品体验决定。（`00:33:57–00:35:26`）流式进度要走产品批准的生命周期事件（「正在搜索营业中的餐厅」「核对素食与过敏信息」），token 流式可以让解释显得响应快，但绝不能暴露原始推理、内部专家消息或敏感工具载荷。（`00:35:38–00:37:22`）中途失败则回退到上一个安全检查点，给用户可读的错误与替代选项。（`00:37:22–00:37:52`）

### 让它可验证：测试、调试、成本与所有权

测试策略的二分同样干净：确定性部分（权限检查、策略、schema、预算计算、工具适配器）用普通软件测试——快、不依赖真实模型、走常规 CI；涉及模型判断的部分（是否主动要求澄清、是否选对工具、是否遵守饮食与过敏约束）用行为评估，且要在 trace 级与总体结果级两层都做。（`00:38:08–00:40:30`）行为评估有两条路：mock 全部工具、保留真实模型，验证给定输入下的输出与工具选择；或者用 LLM 作为裁判，让另一个模型判断输出是否符合用户要求。（`00:40:38–00:42:54`）

观测的最小字段集合值得照抄：贯穿全链路的 run/session ID（跨服务可用）、所用 agent 与 workflow、prompt 版本、模型版本、schema 版本、检索上下文引用、路由与状态转换、工具调用与结果、验证与重试/回退决策、延迟与 token 与估算成本、是否请求人工、最终结果；同时日志必须 PII 安全——剥离、遮蔽或用 ID 代替。（`00:44:52–00:47:23`）他讲了一个典型 bug：多步生产流里 parsing 步骤失败后没有停止，而是产出空结果让后续步骤继续；另一次重试从略不同的检查点恢复、走了不完整状态的默认路径——最终输出看起来像模型质量问题，根因却是解析器 fail-open。修复是让 parser fail closed、把状态转换显式化、改进 trace 并加入回归场景。（`00:47:35–00:48:38`）

成本方面，他的建议是在服务级度量而非单次调用级：每次模型调用都可能重发部分对话与系统指令，并行分支成倍放大，评估循环与重试继续加码——成本是通过许多「单独看都合理」的选择悄悄涨起来的。只有按「一次成功响应的平均花费与延迟」度量，才能把资源消耗和用户拿到的结果对上账。（`00:50:27–00:52:41`）顺带的判断是：复购、退款这类确定性路径用代码就好，开放式的、需要边处理边决策的任务才值得上模型与 agent。（`00:52:41–00:53:54`）

所有权上他认为 prompt 直接决定用户响应，所以 prompt 与模型版本由产品拥有（与工程协作维护安全版本与发布），应用逻辑归工程，模型支持、成本与预算归基础设施或平台团队。（`00:53:54–00:56:01`）给第一个生产 agent 团队的建议浓缩成一句：从边界开始，而不是从自主权开始——先定义 agent 能看什么、哪些决策保持确定性、可调用哪些工具、哪些动作需要人工确认；像设计成功路径一样设计失败路径，限定重试与成本，并提供安全回退，让每个能力在出错时都容易被禁用。（`00:56:01–00:56:41`）
