## 速读

Software Engineering Radio 745 期，主持人 Jason Davey 对谈 ArduPilot 系统负责人、Samba 与 rsync 共同开发者 Andrew Tridgell，讲开源飞行控制软件：ArduPilot 为遥控飞机等载具提供固件，跑在从掌心大小到半吨级的各类载具上；节目从硬件底座讲到固件分层、级联 PID 与多副本 EKF 状态估计，再到 SITL 锁步仿真与 Renode 微控制器仿真撑起的测试体系。节目明确把载人载具与武器化载具排除在项目边界之外。（`00:00:21–00:01:02`，`00:04:36–00:04:51`）

对做嵌入式与机器人软件的工程师最有价值的三层内容：一是硬件与软件的配合——微控制器、IMU/GNSS 传感器、从 I2C 到 DroneCAN 的总线生态，以及从舵机到液压驱动的执行器谱系；二是飞行控制的基本功——一打左右的线程与"一线程一总线"架构、级联 PID、约 21 状态的多副本 EKF 与车道切换；三是测试体系——SITL 锁步仿真、红绿自动化回归测试和刚并入主库的 Renode 微控制器仿真，后者已经侦破多起常规手段久攻不下的悬案。（`00:06:54–00:11:39`，`00:17:58–00:23:34`，`00:43:31–00:50:57`）

## 主题正文

### 从 Samba、rsync 到 ArduPilot 系统负责人

Andrew Tridgell 目前的公开身份是澳大利亚国立大学（ANU）副教授，开源履历上最著名的两件作品是 rsync 与 Samba——后者让 Linux 与 Windows 系统之间实现文件共享。2011 年他加入 ArduPilot 开发——一个为无线电遥控飞机等载具提供固件的关键开源项目——如今是该项目的系统负责人（Systems Lead），偶尔也通过自己的公司 Aerial Robotics Australia 向客户提供咨询服务。（`00:00:21–00:01:02`）

### 载具版图与明确边界

主持人先请嘉宾把"我们在谈哪些载具"说清楚。ArduPilot 跑的载具范围从能放在掌心到重达数吨：船、潜艇，甚至有一颗卫星——那是个趣味项目，大家搭接收站去收它发出的 ping；还有一个刚起步的步行机器人项目。但绝大多数用户是多旋翼或固定翼，且多为 VTOL（垂直起降）固定翼——有机翼、电机布置五花八门、能垂直起降的飞机；多旋翼则多为高端型号，"不是你手里那种 DJI 小飞机"：ArduPilot 跑在世界上最大的多旋翼上，能吊起半吨以上的重量，个头堪比卡车。（`00:01:39–00:02:46`）

地面与小众场景也在覆盖之列：绕着本地公园给场地画线的小型地面 rover，在澳大利亚北部海域巡逻、一次出海约六个月的大型巡逻艇。开发者之间甚至有个"运动"——去展会上认出哪些展品其实是 ArduPilot 底层，这类载具占比相当高；有的厂商乐意承认"我们就是用 ArduPilot"，有的市场部门则嘴硬说"都是我们自己开发的"。（`00:03:19–00:03:45`，`00:03:50–00:04:32`）

边界同样清晰：项目明确避开"掌控人类生命的载具"，也避开携带武器的武器化载具——除此之外，"任何会动的东西"以及不少不动的东西都在做。这是嘉宾主动声明的项目政策，本期节目的全部讨论都局限于这一边界之内。（`00:04:36–00:04:51`）

术语也有历史包袱：UAV 历史上指 unmanned aerial vehicle（无人飞行器），也有 unpiloted aerial vehicle 等变体；潜艇这类载具不叫 UAV，而叫 ROV（遥控载具）；ArduPilot 自己把 VTOL 固定翼叫 quadplane——即便它未必是四旋翼、甚至看起来完全不像飞机，只因项目当初从 quadplane 起家，名字就留下来了。嘉宾坦言，这类项目的术语常常一团糟，偶尔也试着清理。（`00:05:27–00:06:26`）

### 硬件底座：微控制器、传感器、总线与执行器

最常见的微控制器是 STM32 变体，目前最主流的是 STM32H7 系列（如 H743、H757），有的板上装两颗。传感器侧，TDK 的 ICM 系列 IMU（三轴陀螺加三轴加速度计）常见，气压计几乎标配，罗盘常见但并非必需；GNSS 接收机极其普遍——除潜艇外几乎每台车都有，常见如 u-blox F9P 双频接收机，习惯上大家仍叫它 GPS。GPS 与 GNSS 的区别：GPS 专指美国的卫星星座，因最早而得名；GNSS 是涵盖北斗等各国星座的统称，还有专做增强改正的卫星，如今甚至有人用 Starlink 信号做定位。（`00:06:54–00:08:49`）

再往外是空速传感器、激光雷达与相机等测距设备、避障雷达和水下或空中的声呐。ArduPilot 里有数百个传感器驱动，支持的飞控板与外设约 300 种，总线横跨 CAN、I2C、SPI、UART 与以太网。（`00:08:54–00:09:25`）

总线话题里有个插曲：I2C 在这个领域"用得多，更准确说被滥用得多"——它本是为板上芯片间一厘米级连接设计的，而无人机世界直接拿它横穿两米长的机翼，电气上相当糟糕，但图个方便。认真的载具如今多用 DroneCAN——这个从 ArduPilot 项目里诞生的协议架在 1 Mbit 的 bxCAN 上，越来越多人在用头部 1 Mbit、数据段可变速率的 CAN FD；玩法还包括把串口隧道进 DroneCAN、DroneCAN 隧道进串口，甚至 DroneCAN 套串口再套 DroneCAN。（`00:09:43–00:10:51`）

载具的价值跨度同样巨大：瑞典公司 Everdrone 送除颤器的无人机是要认真保命的工程；公园里飞控用橡皮筋胶带固定、整套电子件 100 美元的泡沫飞机也是用户——既有价值百万美元的载具，也有一两百美元的。（`00:10:58–00:11:39`）

执行器一端同样从下到上：电机从拇指大小的有刷/无刷电机到喷气涡轮，桨从两三厘米到几米长；水下推进器因流体动力学不同而另有设计；舵机从普通遥控舵机到高端的 DroneCAN 舵机——后者回报位置与受力，能高频回传"我实际做了什么"，对可靠性至关重要；低端则是开环："命令副翼抬起来——抬了吗？但愿吧，继续飞。"汽油发动机（EFI、化油器）与各种转速反馈方案也常见。嘉宾特别推荐爱丁堡的 Flowcopter：用矿用液压马达驱动巨型旋翼的飞行器，"蒸汽朋克"式的样子——用户拿 ArduPilot 折腾出的东西，正是这个项目的乐趣所在。（`00:12:10–00:13:39`，`00:13:51–00:14:35`）

嘉宾的观察是：让飞行器起飞确实难，但只要电机与控制面可控、能把机体稳住，"很多东西都飞得起来"。他经常被人找来验证疯狂的新构型——先放进仿真器看控制回路能不能让它动起来，"做这类事从不无聊"。（`00:14:41–00:15:13`）

### 飞控固件与线程架构

飞行控制器运行 ArduPilot 主固件：全部控制算法与通信协议，后者最重要的两件是 MAVLink（封装全部遥测数据）与 DroneCAN。固件约 75 万行代码，核心以 C++ 为主，按 HAL（硬件抽象层）切分。（`00:15:35–00:15:56`）最常用的 HAL 是 ChibiOS RTOS、多跑在 STM32 上，另有 Linux HAL——树莓派、Nvidia 板子上也能跑，澳大利亚那些远程海岸巡逻艇就是树莓派加各种扩展板控制网络与执行器；还有跑在高通 DSP 上的 QuRT RTOS。Zephyr 移植正在进行——昆士兰的开发者 David Buzz 负责，录制节目前一天嘉宾刚第一次在名为 Cube Orange 的飞控板上启动了 Zephyr；Linux、ESP32 等移植各有专人维护。（`00:16:05–00:17:17`）

线程架构上，固件大约跑一打线程，哲学是"一线程一总线"——两三条 I2C、三条 SPI、两条 CAN、五条 UART，每条总线一个线程，理由是总线会阻塞；另有一个充当监督者的 main 线程做高层协调。状态估计的 EKF（扩展卡尔曼滤波）与速率控制、姿态控制、速度与位置控制、导航等算法都跑在 main 线程上。（`00:17:58–00:18:35`）

架构基调是级联 PID，但也支持其他架构——有载具用 LQR 这类系统，甚至有跑神经网络的，但都相当罕见，几乎人人用级联 PID。VTOL 控制负责人 Leonard Hall 照看整套级联架构，从底层速率控制一直到高层导航。（`00:18:51–00:19:30`）

### 级联 PID：让任意构型飞起来的骨架

PID 是控制系统里的通用件：比例、积分、微分三个增益，应用极广；ArduPilot 各层都在用 PID，但不是教科书上的经典款——实现更复杂，专门处理 PID 的那些"尖锐边角"。最底层是 rate PID：输入是滤波后的陀螺数据——数据先按电机 RPM 反馈施加陷波滤波，可能同时跑 6 到 12 个，滤掉电机振动对应的频率——得到三轴角速度；每轴一路 PID、各有增益，目标速率来自飞行需求：想保持水平就是零，推杆则对应期望的转动速率。最简单的飞行模式（acro）里飞行员直接给速率——FPV 无人机做花式动作时就是这种单层、非级联的 PID。（`00:25:58–00:28:10`）

往上是姿态层：attitude PID 追踪目标姿态（以四元数表示），其输出成为 rate PID 的目标——级联由此而来；再上是速度 PID（水平 x/y 与垂直各一路）驱动姿态 PID；再上是位置 PID 输出速度目标以保持位置；最顶是导航层，可用 PID 也可用完全不同的算法。调参即逐层调级联各级的增益。（`00:28:10–00:29:19`）

用"向前飞"把整条链串一遍：期望的前向速度意味着低头——一个期望姿态；低头意味着一个期望转动速率——平滑过渡到该姿态；最底层，电机指令经由 mixer（混控器）——纯算法地把名义 roll/pitch/yaw/climb 速率按几何与电机数量映射为电机输出；中间还有推力线性化，补偿电池电压与油门-推力的非线性，让 PID 面对线性化后的系统。细节不少：低头前飞要补推力（向上的分量变小了），前飞还能从桨盘获得平动升力，气压计甚至会被推力角度变化影响读数——"传感器会被你的飞行方式改变"，这些都是让飞机正确飞行路上的小插曲。（`00:29:24–00:31:45`）

控制频率上，多旋翼默认主回路（PID）跑 400Hz——同级 MCU 上每圈做的工作比默认数千赫兹的 betaflight 多；PWM 输出同样 400Hz，简单固定翼默认 50Hz。嘉宾最近用 chirp 信号实测真实电机/电调/桨的控制带宽：即便 5–7 寸小四轴，3dB 滚降通常也只有约 10–12Hz，比他预期的低；但仍值得把环路跑得更快——Andy Piper 主导的"fast rate"支持让 rate 环跑 2 到 4 kHz、姿态环 400–600Hz、更高层更低。大载具反而用低频率：一吨级的车跑多 kHz 是浪费周期——"车越大越贵，越能用更便宜更慢的 CPU"，嘉宾称之为一个反讽。（`00:32:08–00:34:18`）

### 状态估计：多副本 EKF 与"车道"切换

状态估计由 Paul Riseborough 负责，是全项目投入巨大的领域：它融合所有传感器输入，回答"我在世界哪里、哪面朝上、机头朝哪"。ArduPilot 支持高端传感器——有人给载具装过十万美元级的 IMU，但极少；绝大多数用户用的是"便宜而欢快"的 IMU，于是"所有传感器都在对你说谎，EKF 的活就是把谎言整理成真相"——每个传感器都有误差。（`00:19:50–00:20:13`）

误差类型随飞行阶段变化：振动、漂移、温漂、大气影响；EKF 要把这些错误输入整合成尽可能准确的状态估计。这大约是一个 21 状态的 EKF，状态包括四元数姿态、位置、速度，以及陀螺、加速度计、磁力计偏置和风估计等大量偏置状态；而且不止跑一个 EKF——飞行中会基于内部误差估计与传感器一致性在多个 EKF 之间实时切换。（`00:20:26–00:21:19`）

最常见的配置是三个 IMU，默认每个 IMU 一条"车道"（lane）各跑一个 EKF；还有"传感器亲和"选项——可以为每条车道绑定完全独立的传感器组（不同的空速计、罗盘、GPS），条件允许时这样能进一步提升鲁棒性。（`00:21:45–00:22:28`）

切换不是投票制：一个监督者观察误差状态并执行车道切换，倾向留在当前车道——不希望来回抖动。判据是"innovation"（新息）：EKF 的核心是预测-校正，先预测传感器读数再与实际比较，差值即 innovation，可以是水平位置上的米数或空速上的米每秒；系统把各 innovation 合成为车道整体误差估计，超过阈值且备选车道估计更低时才"不情愿地"切换——切太快会引起飞行控制的扰动。（`00:22:35–00:23:34`）

嘉宾讲了一个治理位置跳变的案例：常见视频里小四轴悬停稳在厘米/毫米级，主人凑近自拍——他"看得脊背发凉"，因为一旦状态估计跳变，飞行器可能突然认定正确位置在"那边 50 厘米"——正是头所在之处。补救机制是：车道切换按飞行模式通知高层控制算法"我已重定位"；在位置保持（而非飞往指定经纬度）模式下，监督者会相应修正保持的目标位置，使外观上无跳变——Kalman 滤波到高层监督代码之间专门有这条通信链路，并配套大量测试，主要贡献者包括日本的合作机负责人 Randy McKay、阿德莱德的 VTOL 负责人 Leonard Hall 与墨尔本的 Paul。（`00:23:55–00:25:43`）

### 代码库组织、闪存约束与构建发布

代码全部用 Git 托管在 GitHub，大量 submodule 承载 MAVLink、DroneCAN 等通信协议及各自的协议编译器——从协议规格语言生成 Python 或 C++ 等所需语言。核心代码按库组织：罗盘库 AP_Compass 采用"前端-后端"拆分——前端协调所有罗盘，后端按具体器件动态启用；惯性传感库 AP_InertialSensor、GNSS 库 AP_GPS、气压计库 AP_Baro 同构；每个库有自己的测试与仿真器；再有 PID 库 AC_PID 与高层控制、导航等库。（`00:34:35–00:35:50`）

子系统由专人维护：例如固定翼高度/速度控制的总能量控制系统 TECS（最初由 Paul Riseborough 编写）近年由新的维护者接手管理，处理雷达、扫描激光雷达的接近传感器库也有专人负责。（`00:35:56–00:36:25`）

固件按载具分目录分别构建：copter、plane、rover、antenna tracker、submarine、blimp 等；另有 AP_Periph 外设固件——跑在独立 MCU 上、通常经 DroneCAN 连接的数传或空速计等设备各有自己的固件目录。（`00:36:30–00:36:54`）

闪存是硬约束：H743 的 2MB 闪存分两个 1MB bank，先划出 128KB 给 bootloader；参数与航点若板上有 FRAM（Ramtron）外存则放外存，否则再划两个扇区做日志式存储——最终默认构建可用闪存约 1.5–1.9MB。因为"跑得太近"，项目最近把编译优化从 -O2 换成 -Os，典型板子默认构建也就剩二三百 KB 闪存。项目早期从 8 位 AVR（128KB 闪存、8KB 内存）起步，空间耗尽后多年前转 32 位平台；流行的 STM32F405 板只有 1MB 闪存、更少内存，功能随之裁剪。（`00:41:06–00:42:47`）

发布走 master 加 stable 双线：录制时 4.7.2 beta 1 正在评审。构建服务器一次性构建数百个固件，即便用嘉宾多年前写的 ccache 提速，仍然很慢；固件发布后地面站会提示用户升级、重烧、再飞行。（`00:38:27–00:39:19`）功能装不进默认固件时走 custom.ardupilot.org：菜单式勾选数百项功能、选飞控板、点构建，服务器给出定制固件——多数人跑默认固件，冷门功能走自定义。维护这套自定义构建服务器的"非常有才华的开发者"来自 Google Summer of Code；ArduPilot 不少核心开发者都从 GSOC 学生起步，最终全职投入项目。（`00:39:37–00:40:44`）

### 测试体系：SITL 锁步仿真与自动化回归

真机测试费时、昂贵且危险，ArduPilot 大量依赖 SITL（software in the loop，软件在环）与硬件在环测试：多套物理引擎支撑自动化测试，CI 上大规模跑。（`00:37:20–00:37:34`）

SITL 的架构：一套物理模型仿真传感器与环境，挂钩到编译给桌面 CPU 的 ArduPilot——代码足够可移植，x86-64、Apple Silicon、Windows 都能跑。默认采用锁步调度：仿真时间与物理时间分离，节奏算法默认把仿真对齐到真实时间，也可设 100 倍加速或 0.1 倍减速；物理推一步、固件调度走一步，来回交接，保证结果不依赖宿主 CPU 快慢——繁忙的桌面、老树莓派、最新 CPU 跑出的结果一致。物理后端可选：内置引擎比较简陋，但可连 X-Plane、RealFlight 等更精细的引擎，按任务需要的保真度来选。（`00:43:31–00:45:36`）

调试工作流，嘉宾以 VTOL 回转过渡——从固定翼飞行转垂直降落——中的过冲/振荡为例：这是很难的控制区间，成因可能是风、空速计误差、振动，或倾转电机没按预期速率倾转。做法是先看用户日志——ArduPilot 有非常细的日志系统可分析真实飞行——再在 SITL 里设参数复现症状，然后挂调试器单步（锁步调度让单步成为可能）；定位后把复现该问题的用例加进 autotest 子系统（即 CI 跑的那套）：先有红灯测试，补丁打上转绿，测试与修复一起入库，保证该问题不再回归。（`00:45:52–00:47:38`）

反向的问题也存在：传感器"太准"。有用户的 GPS 在载具静止数小时时给出毫米级精度，EKF 反而被"饿着"了——EKF 需要变化才能观测载具状态，无变化时可能发散；于是有加速测试让仿真跑 12 小时静止在跑道上、无振动无事件，确认 EKF 不因输入匮乏而发散。（`00:47:45–00:48:12`）

### Renode：把整块飞控板搬进仿真器

Renode 是一个开源微控制器仿真项目，ArduPilot 刚把 Renode 支持并入主库（AM32 电调固件也一并支持）：数百种飞控板与外设都能在仿真的微控制器里启动，I2C/UART/SPI 传感器有仿真件；时钟树、RCC 寄存器、UART、SPI 外设都仿真到可以运行"未经修改的固件"的程度。再把 SITL 引擎接上，就能通过一个小启动界面选飞控板、用配置工具把 GPS 挂到 UART、气压计挂到 I2C，点下开始，用地面站连接这块仿真出来的飞控板并"飞行"，还可以挂调试器，甚至接 Sigrok（开源逻辑分析系统，配 PulseView）在仿真微控制器内部抓 SPI/UART/I2C 总线信号——嘉宾形容"相当烧脑"，并已借它找到不少 bug、解决了一些常规手段久攻不下的悬案。（`00:49:07–00:50:57`）

第一个案例正是这条路的起因：ArduPilot 的 crash dump 系统会在运行时捕获 STM32 里的总线错误、锁死等灾难性错误，把寄存器与内存状态写到闪存或 SD 卡，供事后挂调试器取全线程回溯；曾有用户改了几个 DShot 相关参数就触发崩溃转储，转储看起来像 ChibiOS HAL 里 DShot 核心代码的问题，但在 Renode 里复现后发现，真正出错的是 ArduPilot 内部某一层的锁问题（该层名 ASR 无法可靠转写）——能复现，修复就变得轻而易举，很快提交了修复 PR。更关键的收获是影响评估：复现后确认该问题不会影响飞行中的载具——只在地面边输出 DShot 边改参数重配通道时才会触发，不必紧急发版，修复延后到后续版本。（`00:51:10–00:52:54`）

进行中的案子是"软重启导致舵机打到极限"的老问题——副翼顶死在极限位置可能损坏舵机，这类外设重初始化行为在常规调试环境里极难抓，在 Renode 里容易得多；问题已复现，项目最多产的开发者、同在堪培拉的 Peter Barker 正用它追查。下一个目标是启用 Renode 的逆向调试——捕捉到错误后把时间往回"倒带"，看状态如何一步步走到这里，目前还差一点，但接近可用。（`00:53:13–00:54:26`）

### 开发流程与开源社区

改动生命周期：开发者提出并自行实现功能，先在 SITL 和真机上自测，在 GitHub 开 PR；每周两次开发电话会（堪培拉时区周二早上、周三晚上各一场）集体评审最新 PR；AI 评审系统（Claude 与 Codex）评审所有 PR 并运行测试，人工评审随后把关。简单的功能很快能进，复杂的可能要六个月以上。（`00:37:34–00:38:27`）

嘉宾在收尾时把感谢给了整个社区：写文档的 Henry，把"从未测试过的最新固件"装上复杂载具、飞行后回传日志与视频反馈的用户群，开发者社群内部的情谊——"如果你还没参与过这样的开源项目，我强烈建议你加入一个，它会丰富你的人生，是很棒的工程经历"，也感谢为项目出资的合作伙伴。（`00:54:42–00:55:32`）

参与入口：ardupilot.org 主站，其下的 discuss.ardupilot.org 论坛（Discourse），以及非常活跃的 Discord（ardupilot.org/discord）；年度聚会下月在加拿大渥太华举行（十月下半月，上一届在英国北部的 Richmond），嘉宾提到年会前一两个月核心开发者都在冲刺准备演讲素材，项目正处于开发量的高峰期。（`00:55:53–00:56:56`）
