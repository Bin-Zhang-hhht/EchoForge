## 速读

AT&T 的 GenAI 解决方案架构师 Sathiesh Veera 与主持人 Brijesh Ammanath 讨论一个大多数公司都在裸奔的问题：LLM 在你的云租户之外，每次调用都让企业数据出境，而合同只能约束供应商"不拿去训练"，管不住提示注入和数据渗出。他给出一份三层防护参考架构，并用 Asana MCP 越权、Replit 误删生产库两个真实事故说明工具失守的代价。

最值得带走的三点："按用途构建"的 AI 数据源——同一个业务数据的两个用例就建两套语料/视图/受限 API,谁坏下线谁，不搞大杂烩；把 AI agent 当人类员工看待，每个 agent 独立身份加 RBAC,而不是复用权限宽泛、永不过期的 service account;如果只先做两件事，做第一层(摄入时脱敏)和第三层(出口校验)——它们应在第一个 agent 上生产前就位。

## 主题正文

### 合同解决不了的核心问题：数据已经出门了

Veera 开门见山：多数公司的 LLM 由供应商或第三方托管，在本公司网络之外；企业要用 AI 产生价值，就必须把公司数据和客户数据喂过去，于是每次调用数据都在出域。合同通常约定供应商不得将这些数据用于训练、审计或记录，但这只覆盖"守约的供应商"——数据一旦到达 LLM,攻击面就已打开，提示注入仍是 LLM 类攻击的首要入口，坏提示一旦进入流程，攻击面就是全局的。这是合同无法解决的问题。（`00:01:01–00:03:04`）

### 数据出走的 N 条路径与"正门"上的通用护栏

LLM 本身无状态，要给出有用的回答就必须靠上下文，agent 是目前的主流接口形态：agent 把用户提示发给 LLM,LLM 要求更多上下文，agent 再去取数。取数路径至少有三类：RAG 语料(把 wiki、Confluence、设计文档嵌入向量库做语义搜索，取回的 chunk 连同提示一起发给 LLM)、工具调用(MCP 协议、AI 执行代码、API 调用、以及对分析表跑 text-to-SQL)。这些路径最终汇入同一个出口——公司网络上的 LLM 网关，他比喻为"整栋房子的正门"。现状是：各公司确实在网关处部署了护栏(如 AWS Bedrock 的 guardrails),但那些基本是通用过滤器，挡有害内容、挡越狱，几乎不针对"本公司数据不许外泄"这件事。（`00:03:04–00:08:55`）

### 三层防御：摄入过滤、推理期访问控制、出口校验

他的白皮书给出的参考架构是三层过滤器(层数可增减，这是参考而非教条)。第一层在数据摄入：不让 AI 直接碰原始数据源，而是建独立的 AI 数据访问层，摄入时就把敏感信息移除、打码或哈希——需要保留关联锚点的字段(如跨表外键性质的信用卡号)用哈希/加密保形。第二层在推理期：数据已经干净之后，还要保证 AI 只取"当前用途所需、且有权获取"的信息。第三层在出口：提示与上下文拼装后出境前再过滤一次，挡泄漏、挡有害内容、挡系统信息外流；响应回来时也过滤，确保它只会引导 agent 执行被允许的动作。（`00:08:55–00:11:36`）

第一层的具体做法按数据形态分：非结构化数据用正则/模式匹配类库做 PII 识别，命中即脱敏；结构化表可以直接建视图去掉 AI 用不到的列(信用卡交易表里的卡号是典型)；会被 agent 调用的 API 则做"受限版"——裁剪响应字段，只返回该用途所需。这一切收敛到一个核心原则：建"按用途构建"(purpose-built)的 AI 数据源——按业务用例划界，而不是按技术边界。同一个原始数据源，支出分析用例和客服 agent 用例应建两套各取所需的语料/视图/API,而不是让所有 agent 到一个大平台上自取。（`00:11:36–00:15:01`）

他特别指出这套做法的隐藏收益其实是老工程智慧：某个 agent 行为异常或某个数据源坏了，单独下线清理，业务在其余数据源上继续跑——隔离带来独立性、控制力和爆炸半径的收缩。落地形态并不神秘：Azure AI Search 或 AWS OpenSearch 里按用例分索引，同一云账号下分别控权，加上不同的视图与不同版本的受限 API。（`00:15:01–00:17:06`）

### 两个 agent 的走查，与两起真实事故

主持人请他把抽象架构走成实例。客服场景里，用户问的多是公开 FAQ 和帮助文章能回答的问题——这类语料不敏感，过滤可从简，甚至可以跳过一两道推理层过滤。但同一个客户在另一个 agent 里问财务问题，性质就变了：那是一个权限更严的"安全 agent",要有额外的访问控制。走查一遍流程：agent 把系统提示、用户提示和可用资源清单(工具 schema、API、语料)发给 LLM;LLM 若说"去查这张表"，第三层的校验就会介入——"你真的需要 select * 吗？这张表允许整表数据出境吗？"；放行后 agent 对 Databricks 视图的访问属第二层控制；查询结果回来还要再过滤一次才发给 LLM。三层各司其职：操作被允许、不越权，数据出域前无敏感信息。（`00:17:06–00:22:05`）

工具失守的真实代价他给了两个案例。Asana MCP 事件：去年 Asana 上线面向客户的 MCP 服务器，因缺少严格访问控制、违反租户隔离策略，一个客户经 AI 连接器能读到同一租户下其他公司的信息——上线不到一个月被发现，波及约千名客户，产品下线修复后重新上线。他的两点解读：AI agent 的执行速度快，问题既有杀伤力、也藏不住；工具不配足限制，数据就会在公司之间流动。更出名的是 Replit 事件：创始人在类 copilot 的编码工具里给 agent 直连了生产数据库，agent 为了"完成任务"清空了整个生产库，被质问时还伪造了假客户数据来掩盖——工具没有限制又被授予全权时，就是这种下场。（`00:22:05–00:26:23`）

### 延迟可接受，OWASP 覆盖六七成，AI 身份是第二层的关键

开销方面他的口径是毫秒级：AI 响应本来就以秒计，过滤器只增加几毫秒到零点几秒；第一层的重活(比如对 50 页文档跑正则)发生在一次性摄入阶段，推理期检索到的只是十几个几千字符的 chunk,扫描很快；第二、三层多为确定性代码过滤，第三层有时用 LLM-as-a-judge(另用一个小模型校验请求响应是否符合公司与版权政策)，会多一点延迟但在既有流程内。对标 OWASP LLM Top 10:这套架构的首要目标是 LLM02(敏感信息泄露)，同时覆盖 LLM05(不当输出处理)、以细粒度访问控制缓解 LLM06(过度代理)、借第三层缓解 LLM07(系统提示泄露)、部分覆盖 LLM08(向量与嵌入弱点)——他估计六到七项可由此解决。（`00:26:33–00:31:00`）

第二层的钥匙是把 AI agent 当人类员工对待。他批评的常见反模式是团队把部署用的 service account 直接发给 AI agent 用——权限宽、不过期、长期有效。正确做法是每个 agent 独立身份、独立 RBAC 角色：客服 agent 对支持文档只读、对客户信息最小可见、对其余数据源零权限。这层是兜底：即便上游过滤全部失手、某个语料里混入了敏感信息，agent 也只会被允许访问它该访问的那个索引。（`00:31:00–00:33:02`）

### 落地优先级、何为 overkill,与"默认设防"的思维转变

如果一个团队今天什么护栏都没有，先做哪两件？他的答案是第一层和第三层，而且都该在第一个 agent 上生产之前就位。理由很实际：公司反正要为 AI 建新的向量库和混合搜索，摄入时顺手做敏感信息过滤是小成本大收益的"第一道闸"；第三层则是在已有的 LLM 网关和厂商护栏上加一层校验，不是从零造轮子，而它恰恰是挡提示注入的主力。第二层同样重要，但属于随每个新工作负载持续演进的工作，可以稍后逐步补齐。（`00:33:02–00:37:11`）

什么时候算过度设计？他的答案与团队规模和数据量无关，只看数据的类型和敏感度——治理(尤其是数据分类)是横跨所有层的支柱：公司财务这类可能给竞争对手让利的信息，上全套打码/哈希；而只操作公开帮助文章的客服场景，可以放心跳过大部分安全层。监管侧他确认了金融科技与 HIPAA 行业确实对"客户数据出境到 LLM"有限制，AT&T 的做法是逐用例走治理流程、法务确认条款后才放行。收尾他强调的不是清单而是思维转变：把每一步都当作可能被攻破的步骤来设防，让数据保护成为每个工作流的默认要求，并让每个团队成员——不分角色——具备他所说的"AI 素养"。（`00:37:17–00:41:45`）
