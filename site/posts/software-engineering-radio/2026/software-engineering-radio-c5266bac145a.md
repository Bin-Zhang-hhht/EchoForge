## 速读

DRM(GPU/图形)子系统维护者、Red Hat 杰出工程师 Dave Airlie 有近二十年内核维护经验。这期节目以 DRM 为样本,把"世界上最大的软件工程项目"如何运转讲得明明白白:80-150 名分层维护者、DRM 每个内核周期 300+ 贡献者与 200 万行代码、九到十周的发布节奏、merge window 与 linux-next 的纪律,以及"先 revert 再问问题"的回归哲学。

最值得带走的三点:维护者的工作到高层就变成"促成与创造环境"——trust the hierarchy,评审在邮件列表公开留痕;供应商共享 Windows/Linux 驱动代码的诱惑几乎总会产出二等驱动,因为厂商与内核提取共性的向量不同;AI 补丁评审已在内核落地——Meta 的回归发现框架误报率约 50% 仍被认可,因为"漏进世界的回归是真金白银的代价"。

## 主题正文

### 规模:300 人、200 万行,和一个"促进者"的角色

DRM 是 Direct Rendering Manager 的遗留名,如今就是内核的 GPU/图形子系统。Airlie 给出内模块的规模图景:Linux 内核自称"世界上最大的软件工程项目",维护者平均 80 到 150 人、层级浮动,年度 Maintainer Summit 由 Linus 邀约约 30 名顶层维护者;子系统没有严格定义,"一个维护者维护的东西就是一个子系统",大的包括图形、网络、x86/arm64、存储、文件系统与内存管理。DRM 的数字连他自己都吃惊——前一晚刚统计:每个内核周期有超过 300 人贡献。他的角色更像公司高管:与共同维护者 Simona Vetter 之下有六七位次级维护者,再往下层层递进;他每周的主要工作是向 Linus 提交汇总 PR,个人亲自评审的占比很小——"层级已经足够大,我必须信任下级维护者做了恰当评审",而所有评审都在邮件列表公开留痕可查。（`00:00:56–00:05:54`）

他坦承 DRM 最大的挑战就是规模本身:在 10 人、40 人层面的维护者并不理解 300 人时问题如何变质。为此 DRM 采用了内核里非典型的"团队共治"——共用一棵人人可提交的树,30-40 人的提交者组(x86 子系统当年只用 3 个人就做到了)。而他个人的功课是"往后退一步":放弃自己的小众工作流,采用让整个社区更容易的方法,哪怕让自己更累。（`00:08:28–00:11:41`）

代码体量:子系统的手写代码至少 100 万行,自动生成的头文件再添 50 万到 100 万行("既惹人烦又非常有用");每个内核周期(约三个月)经他手 2000-3000 个变更集、50-60 个来自次级维护者的 PR;修复期每周约 5-6 个 PR、每个含 10-15 个补丁。（`00:10:29–00:11:41`）

### 与 Linus 共事,和九到十周的发布纪律

Linus 高度放权:"你打理你的花园",信任你,直到你给他理由不再信任。Airlie 与他共事 20 年,有过几次网上可查的公开争执;日常交互其实很少——每周发修复 PR,系统自动回执即平安,收到 Linus 本人的回复"通常只有你做错了什么的时候",因为"他不擅长给正面反馈"。每九到十周一次的大 PR 才是容易触怒他的那个:变更越多回归越多,"只能祈祷他没抓到严重的回归"。他的自我定位是"伞":替下级挡住 Linus 的怒气——这些年 Linus 已温和许多。（`00:06:04–00:08:19`）

发布节奏是九到十周(由 Linus 视心情决定):头两周是 merge window,Linus 合入所有维护者的 PR 并稳定;此后每周日(太平洋时间)发 RC2、RC3 直到 RC7,下一周发正式版(偶有 RC8,历史上出过一次 RC9)。merge window 有个常见误解:它是 Linus 合并的窗口,不是你开发的窗口——所有工作都应提前就位在 linux-next 里,由专人每天合并全网的树、提前暴露冲突;未经 linux-next 的东西 Linus 会收,但经常很不高兴。DRM 的做法是:AMD、Intel、Qualcomm 各有厂商树,加一棵杂项树;自己的 next tree 常年开放,到上游 RC6 就关闭——没赶上的等下一个周期(RC6 后塞东西的自由是他的酌情权,历史上"放任自流没有带来质量")。回归的定义也出自 Linus:RC1 之后任何对用户变糟的东西——性能或功能都算;"如果没人注意到,就还不算回归",处理哲学是"先 revert,再问问题",尽管工程师的本能总是想先修好它。（`00:11:41–00:18:15`）

回归长什么样?最容易理解的是"笔记本屏幕不亮了""闪烁了""挂起恢复坏了";数据中心则是"标准负载变慢了";Steam Deck 升级新内核后散热或帧率不如从前,也算。报告来源很多:用户直接发邮件、嵌入式工程师(如 Steam Deck 的回归经 Valve 到 AMD 再上报)、发行版打包 RC 内核后的反馈,以及 Linus 本人——他恰好是某张十年老显卡的唯一用户。（`00:18:15–00:20:29`）

### 词汇表:补丁、backport、revert 与稳定内核

补丁是内核里"最小且自包含的工作单元":commit message 极其重要("如果 commit message 里出现了'和''但是',那也许该拆成两个补丁");一个补丁是评审的最小粒度;补丁系列加 cover letter 描述整体意图。工具核心是 Git,发送用 b4(替代 SMTP 把系列发进邮件列表),public-inbox 充当所有历史补丁的归档数据库(配 lei 反向查询),老派选项还有 quilt、stgit。backport 是"为旧内核改造补丁"——能直接 apply 的不算真 backport,把安全修复改写到代码早已大变的八代之前的老内核才是;Red Hat 更是整子系统级 backport(把整个 DRM 搬到八个版本前的 RHEL 内核),Ubuntu、Android 同理——"只要你基于 Linux 内核发布产品,就需要会 backport 的工程师"。revert 则因 Git 历史不可变:打反向补丁,并且 revert 自己也要当补丁对待——带上所回退补丁的标签,让稳定内核与 backport 自动跟上。稳定内核是 Greg Kroah-Hartman 约十年前推行的设计:为想留在旧版本上的用户(尤其 Android 设备)提供安全与回归修复,周期性选出 LTS;原则是"不强制维护者为稳定内核增加工作量",适合进稳定的补丁通常小于 100 行且自包含。（`00:25:30–00:33:11`）

### 供应商共享代码之弊,与碎片化的安全、CI 现实

Airlie 博客里那句"盼着操作系统间共享厂商代码的人,一般不会让 Linux 变得更好"是本期最有洞察力的段落:厂商接到"给我们 Linux 支持"的需求时,第一直觉是"把 Windows 驱动和 Linux 驱动的代码共享起来省成本"——于是上硬件抽象层、移植而非重写,结果要么是二等驱动、要么无法上游、要么在厂商与上游之间再垫一层阻抗。根源是共性的提取向量不同:内核想在所有 Linux 驱动间提取共性,厂商想在 Windows 与 Linux 代码间提取;无线子系统的历史是前车之鉴——内核提供了统一的 802.11 层,厂商驱动却照着旧思路写了好几年。（`00:20:44–00:23:47`）

为什么内核不吃 GitHub 模式?一是规模:单一中央树的 PR 模型撑不住;二是社区对开发流程中使用专有工具的强烈抵触(DRM 自己用 GitLab 托管树);而老一套也有新麻烦——Gmail 不想收你的邮件,你的邮件服务器就形同虚设。安全是特例:内核有专职安全团队(Greg 领衔、Linus 参与), embargo 只有 7 天——"Linus 认为安全修复就是修复,安全圈戏太多";CVE 体系正在重建,且上游的 CVE 未必适用于你的下游用例,而 CV 扫描器还做不到这种细腻。AI 生成的安全报告正在饱和带宽:"好坏都有,但坏的也浪费你处理别的事的时间。"CI 则高度碎片化:内核工作流没有中央收集点,集中式 CI 也会被规模压垮,各子系统自建反而是对的;图形子系统的 pre-merge CI 在 Qualcomm 推动下建设,Intel 的邮件列表 CI 加 patchwork "用麻绳和铁丝拼起来但能用",AMD 有内部 CI;著名的零日机器人响应时间不可预测。fuzzing 则经历了流行周期: syzbot 是"智能垃圾制造机"——懂系统调用结构、会传非法句柄穿透表层,专挖最深处的怪异竞态,但报告的很多问题深到没有用户会踩到,反而可能被过度优先。（`00:24:19–00:41:55`）

### 人是最难的部分:新人、跨子系统与"把专家放进同一个房间"

新人怎么加入?他的排序很诚实:第一,"找一份让你参与内核的工作";第二,解决自己的 itch——用 ChatGPT、Gemini 之类帮你读代码也行。关键建议:不要从 LKML 开始,那是"丢补丁、经常被无视"的地方;要找到子系统自己的社区(GitLab、IRC、Discord),潜伏一阵,读补丁、试着评审,小改动可以做"顺路补丁"。要项目列表?难办——经验丰富的开发者遇到清单上的问题十分钟就修完了;新项目(如 Nvidia 的 Nova 驱动)在达到可并行的基线之前,想带人也带不了。（`00:42:26–00:45:53`）

跨子系统变更是另一层难:bug 报告进来先查是不是自己的问题,不是就得引导报告人"去烦对的人";缓解之道是尽量走标准内核 API(如跨设备共享内存的 DMA-buf 层),并让相关两侧的人共同维护它。大型跨子系统变更会提前半年到一年规划;真正难的是造跨子系统的核心功能——"双方都觉得自己对,但不解决问题",而弥合阻抗失配、处理性格冲突正是他喜欢维护工作的原因。他反复强调信任的社会性:某显卡驱动几年前在公司内部私自开发一两年后再上游,立刻暴露结构性问题——"他们说五年前试过某方案失败,可你是在内部试的,公开试过我们就有证据,后来者就不会浪费时间"。内核的竞争力在于把全行业那五到十个懂某个问题的人放进同一个地方,让他们彼此说话、彼此信任。（`00:45:54–00:53:20`）

### RC 健康直觉、AI 评审与 Rust 的社区动机

怎么判断一个 RC 健不健康?Linus 是高手——每周 RC 邮件里都有"趋势预警":补丁比预期多吗?抽样看看是大量小修复还是少而复杂的大改动,后者会让他"加发一个 RC8";Spectre、Meltdown 这类安全事件就曾导致周期延长。Airlie 自己的仪表盘朴素有效:每周固定几路 PR(杂项树、AMD、Intel 两路)周五前没到就是出事了;RC4-5 之后 PR 还动辄五六百行,他就下去深挖。黑屏是 stopper——"黑屏意味着装不了 Linux";好在如今 RC1 极少再是"彻底的垃圾场",放在二十年前,装 RC1 是要准备丢文件系统的。（`00:53:20–00:56:39`）

AI 是过去一年社区"既感兴趣又有争议"的话题。转机来自 Maintainer Summit:Linus 说他看到 Google 和 Meta 的一些 AI 评审效果不错——而"评审带宽不足"正是峰会年年不变的抱怨。Meta 的 Chris Mason 写了专攻回归发现的 AI 框架,验证方法很聪明:跑在历史补丁上,看它能否提前指出后来才被修复的问题;误报率约 50%,但 Airlie 认为依然值得——回归溜进内核流出去"是真实世界里的真金白银"。他自己用 Claude 写了一个 Claude 评审器(以 Claude Opus 逐补丁评审),在 freedesktop 上搭了 public-inbox 基础设施让评审像补丁一样线程化,每天手动跑、当参考资料用——"如果将来又出了问题,而参考里它当时就指出来了,那就是推动它上正轨的时机"。Google 上周也发布了补丁评审系统(名称 ASR 无法确认,故不引用),他打算接洽让 DRM 补丁也接受评审。对 AI 生成补丁,他见过 Claude 协助写的,"不算糟糕",预计未来一年这个方向会大发展。（`00:57:21–01:01:11`）

支持 Rust 进内核,他的动机出乎意料地是社区性的:维护者峰会年年抱怨"我们都老了,灰胡子越来越多";而图形子系统恰好以年轻社区著称,Rust 阵营又是一群二三十岁的年轻人——"让年轻人借 Rust 进入内核,带来不同的视角,是好事"。他的工作方式依旧是"表态开放、提供空间、亲自动手的让别人来":回到 Red Hat 找了位写 Nouveau 的优秀 C 工程师劝他试 Rust,对方从"不喜欢"走到了 Rust 核心维护者。安全价值他也认可:图形子系统的用户态 API 极宽、常被利用;"最好的 C 程序员也有状态不好的那天",而 Rust 的编译器与类型系统(尤其生命周期——"我们二十年里把生命周期相关的错犯了个遍",从 SMP 到线程化中断到热插拔,每次新变化都翻出新错法)能从根上拦住。二十年的变迁总结:本质没变(写补丁、走树、发邮件列表),但门槛与质量大幅提高,流程从"即兴发挥"固化为真正的流程——"少了点乐趣,但少了点乐趣是重要的:你不能再突然做一个让全世界一半电脑不稳的内存管理改动了"。而不变的部分依然迷人:昨天他还在给 Nvidia GPU 驱动写代码,刚到的 Spark 盒子正被开源驱动点亮——"二十年了我还是喜欢这个"。（`01:01:22–01:08:00`）
