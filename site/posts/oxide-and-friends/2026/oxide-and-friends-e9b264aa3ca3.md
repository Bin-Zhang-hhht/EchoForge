## 速读

Oxide 工程师 Rain Paharia 围绕博客文章《The Hardest Kind of Unsafe Rust》复盘自家开源 crate IDDQD（键可从值借用的 Rust 映射）的排险过程：为什么这类泛型 unsafe 必须容忍「任意病态的用户代码」，以及对应的完整验证阶梯——朴素对照实现的属性测试、panic 倒计时测试、LLM 对抗审查、Miri 双别名模型，直到形式化方法的工具缺口。适合写 Rust 库、关注 unsafe 边界与高保障验证的工程师。

## 主题正文

### IDDQD 是什么，为什么必须 unsafe

Omicron 从 CockroachDB 读出大量「胖记录」（如 sled 清单），需要按 UUID 或若干字段组成的自然键建立索引；Rust 标准库的 map 要求 key 与 value 分开存，UUID 就得存两份，既浪费又可能失同步（`00:06:37`–`00:09:54`）。同事 John Gallagher 的第一版「存记录、从记录提取键」要求键实现 Clone——UUID 无所谓，自然键就难受了；Rain 接下的挑战是让键直接借用自值，而这件事无法在安全 Rust 里高性能地完成，于是有了 IDDQD（`00:09:54`–`00:12:09`）。unsafe 的正当性来自可计算性：按 Rice 定理，不存在能精确区分「有/无未定义行为」程序的编译器，安全 Rust 因此宁可错杀，unsafe 就是给「人能证明、编译器不能证明」的场景留的逃生舱（`00:15:01`–`00:18:42`）。谱系上，Haskell 的 unsafePerformIO 是先驱，而 Rust 是第一个把 unsafe 与 safe 放进同一门系统语言的——对比当年 V8 想做个本地扩展就要跳进 C++ 修改运行时，这是质的区别（`00:19:01`–`00:22:29`）。

### 规则、最难的类别与社会契约

unsafe Rust 的确切规则尚未完全形式化（Ralf Jung 等人在 POPL/PLDI 的系列工作仍在推进），但共识部分很清楚：不允许数据竞争、不允许读未初始化或已释放内存、不允许同一块内存同时存在两个可变引用——哪怕没人用它。原因藏在优化里：Rust 给每个 `&mut` 打上等价于 C `restrict` 的标记，而这条 LLVM 路径此前几乎无人使用，启用过程甚至挖出了 LLVM 的 bug（`00:27:21`–`00:31:25`）。连 `split_at_mut` 这么小的函数都要清点一整套不变量：参数必须是 `&mut`、mid 必须在界内……（`00:48:30`–`00:51:15`）。而「最难的类别」是泛型 unsafe——你的正确性依赖用户提供的 trait 实现，用户却可以在 `Ord` 里随机翻转比较符、在 `Hash` 里掷硬币。Rain 的心态切换是把软件工程思维换成信息安全思维：假设有人要攻破你的假设（`00:38:13`–`00:41:15`）。触发他写博客的导火索之一是 Bun 被收购后九天用 Rust 重写一百万行代码的事件——大量未经审视的 unsafe 破坏了「写 unsafe 的人替写 safe 的人负重」的社会契约（`00:32:03`–`00:37:38`）。

### 修复：正确的代价可以是不性能

实际找到的 bug 很有代表性：一个「几乎总是正确、只在恰当时刻说谎」的病态 `Ord` 实现可以骗过 IDDQD 存入重复索引，进而产生同一内存的两个可引用别名。修复分两手：一是加 tiebreaker 保证绝不会错误匹配到别的条目（宁可漏匹配）；二是更漂亮的取舍——一旦检测到用户代码行为不端，就退化为完全不调用用户代码的线性扫描，用性能换正确性，「欢迎写出病态代码的人自己去查为什么变慢了」（`00:55:34`–`00:58:01`）。

### 验证阶梯：从朴素实现到形式化

Rain 给出的验证阶梯值得任何写数据结构的人抄走。第一层是桌上筹码级的：写第二个「显然正确但很慢」的实现，生成随机操作序列做属性测试，两边结果必须一致（`01:03:57`–`01:06:05`）。第二层是针对用户代码的两面：既有正确实现的测试，也有错误实现的回归测试集（pathological.rs）。第三层是 panic 安全：用户代码可能随时 panic，panic 倒计时属性测试（每个可 panic 点插桩、按经验分布生成倒计时）摇出了三四个隐患；一位读博客的社区成员提交修复后，现在可以承诺「用户代码 panic 绝不会改动 map」（`01:07:06`–`01:10:45`）。第四层颇为新颖：把自己写的病态测试作为种子交给 LLM 做对抗审查——Claude Opus 4.7 与 GPT-5.5 各自独立找到了一到两种新的不变量破坏方式，GPT-5.5 「嚼了二十分钟」交出答案；Bryan 强调这是 LLM-for-rigor 的典范用法，因为发现物极易验证（`01:11:38`–`01:13:36`）。第五层是 Miri：它实现 stacked borrows 与 tree borrows 两种别名模型，IDDQD 两者都过（进了 CI），还为迁就较严格的 stacked borrows 做了专门适配；更聪明的用法是「解析桥接」——先论证「某不变量被破坏即 unsound」，之后用快速属性测试守护不变量即可，不必事事跑慢速解释器（`01:13:36`–`01:18:38`）。最后是形式化方法：他试过，结论是缺口在工具而非理论——若能证明「无论用户代码多么病态，不变量都不会被破坏」，将是这篇博客最好的续篇（`01:19:03`–`01:20:09`）。
