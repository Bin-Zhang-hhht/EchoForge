## 速读

这期 Oxide and Friends 请来产品保障（product assurance）团队的 Steve Karam，讲他们如何在一台 Helios 主机上仿真出一整个 Oxide 机架：项目叫 VOXEL（Virtual OXide Emulation Lab），从 shell 脚本堆出来的内部工具演化为 Rust 实现，能在其上运行未经修改的 stock Omicron 与 stock Hubris 固件，还成了 multi-rack 开发的开发载体。适合关心大规模系统测试环境、软硬件协同和 LLM 辅助工程的工程师。最值得关注的点：一是他们给仿真划的「谎言边界」——仿真能跑通正式发布软件就算数；二是 LLM 的真实用法——擅长枚举寄存器和理解文档，但也会一本正经地胡说，纠偏靠人。

## 主题正文

### 为什么需要一个「软件机架」

Oxide 的产品是一个完整机架：机架本体、交换机组、计算 sled、电源以及机架各处的小控制器。测试这种产品最直接的困难是，真正的测试环境永远稀缺。他们造过 racklet——两台交换机、四个 sled 的迷你机架——但 Adam Leventhal 直说这在经济上完全不成立：为 32 个 sled 准备的交换机只带 4 个 sled，钱花得不值，它只是测试工具，不是产品（`00:09:25`–`00:10:31`）。而 multi-rack（多个机架协同）的研发需要的不止一个机架，硬件更是捉襟见肘（`00:29:13`–`00:30:06`）。

在 VOXEL 之前，团队有一个叫 four-by-two 的内部方案：用大量 shell 脚本在启动时把虚拟部件拼成机架。它可用，但把所有事情堆到 launch time 意味着启动要四十分钟、坏了很难自愈，而且问题总在最后两分钟才爆出来（`00:11:56`–`00:13:13`）。

### VOXEL：把机架装进软件

VOXEL 这个名字出自 Ry Goodfellow，意为 Virtual OXide Emulation Lab（`00:12:37`–`00:13:05`）。与前身相比的两个关键变化：其一是 build 与 deploy 分离——给定一个 Omicron 提交，先克隆、编译出一个「完美的 sled 镜像」并做快照，再让每个虚拟 sled 复用这个镜像扮演自己的角色；其二是全面从 shell 脚本转进 Rust，加上一个常驻在 sled 里的 Rust agent，告诉每个镜像「你是交换机」「你是 sled 三」（`00:13:19`–`00:14:50`）。整个机架拓扑用一个 TOML 文件描述，可以灵活搭出三节点、六节点，或者留两个 sled 待加入来测试即插即用（`00:32:45`–`00:33:40`）。

Andrew Stone 补充了一个工程角度：VOXEL 刻意让命令行界面模仿内部制造工具，用过 Pilot 登录 racklet 的人「手指已经会打 VOXEL 了」，加上它本身就是 Rust 写的生产级代码，工程师愿意真的用它（`01:19:13`–`01:20:24`）。

### 仿真与模拟的「谎言边界」

Bryan Cantrill 把仿真和模拟的区别概括为「都是谎言，问题只在谎言到哪里为止」。Steve 给出的例子是 SP SIM：一组轻量 stub，按服务处理器的协议返回「预期中的正确响应」——这是模拟，天生偏 happy path（`00:17:45`–`00:19:09`）。而 VOXEL 的 SP 仿真走得更远：它真的运行 stock Hubris 固件镜像，支持固件刷新、DICE 身份与远程证明等真实机制（`00:25:39`–`00:26:41`）。

团队给自己立的规矩是：不要修改被测软件。Steve 最初为了方便在 VOXEL 里给 Omicron「变」出不存在的端口，被同事指出这是把本末倒置写进仿真（`00:16:39`–`00:17:09`）。落到判据上：VOXEL 加 SP 仿真如今可以跑起多节点、多机架的 lab，用的是未经修改的 stock Omicron 与 stock Hubris 镜像——仿真与真实产品的这条「谎言边界」就在这里（`00:28:11`–`00:28:34`）。Bryan 补充了边界另一侧的坦白：Propolis 不模拟 AMD 平台里 SMN/SMU 一类的底层初始化通道，最早的平台引导被直接「快进」，反正那个层级的 bug 也不是 VOXEL 要解决的（`01:06:32`–`01:07:56`）。

### 用 LLM 起步：一个周末写出的 SP 仿真器

SP 仿真的起点颇具戏剧性：Steve 让 Claude 在周末试着写一个 STM32H753 微控制器仿真器。他的预期是不可能有结果，实际运行后「只花了两三个小时微调」，就能把最小化的 Hubris 固件镜像刷进去并跑起来（`00:19:30`–`00:22:07`）。此后一步一步补齐：rack 初始化用到的最小指令集、传感器模型、乃至根可信侧的行为，都是围绕「stock 软件跑不通哪里就补哪里」推进的（`00:23:44`–`00:25:39`）。

Steve 总结 LLM 在这个项目里的真实画像：它非常擅长枚举寄存器、整理「构成一个系统的全部小部件」，也擅长文档理解——把 RFD 和设计文档作为上下文喂进去，结果会「清晰得多」（`00:57:45`–`01:00:35`）。Bryan 的观察是这奖励了文档密集的工程文化：工程文化越严谨，LLM 越有用（`01:00:35`–`01:00:53`）。但反面同样具体：项目早期它产出过大量「flagrant bullshit」，要靠拿真实 racklet 的日志反复纠正（`01:14:00`–`01:14:41`）；ICE40 FPGA 的 A0/A1 状态寄存器没人想到要建模，虚拟电源时序器因此空转，补上才恢复（`01:09:17`–`01:10:26`）；还有一次是它信誓旦旦称根可信与 SP 可以共享一个线程，拆开之后性能提升 500 倍（`01:02:54`–`01:03:41`）。

### 从仿真到 multi-rack：真实软件链穿过虚拟硬件

multi-rack 的试验同样建立在 VOXEL 上。Oxide 有两个路由协议：机架内部走 DDM（Andrew 也坦承记不全称），跨机架他们先在 VOXEL 里用 QSFP 前端口直连两台虚拟交换机，让 DDM 交换前缀（`00:38:08`–`00:40:53`）。关键在于：让前端口跑 DDM 的那一长串改动全部是生产软件——从 Wicket 的 commissioning API 到机架网络配置、rack join 服务、bootstrap agent、scrimlet 上的 reconciler，最后由 Dendrite 调 softNPU 配置虚拟交换芯片；VOXEL 只在顶上提供编排、在底下替换硬件（`00:42:30`–`00:47:07`）。

这个过程中还沉淀出一个副产品：commissioning API。Wicket 原先只有不稳定的内部 API，随交付规模变大、自动化变多而难以为继，团队用全栈同款的 Dropshot + Progenitor 组合做了带版本的正门式 API，约两周的压缩工期内交付，同时满足了机架交付自动化与 multi-rack 研发两个需求（`00:52:24`–`00:55:36`）。

### 成熟度与门槛

这个项目从立项到演示大约十二周（`00:47:40`–`00:48:20`）。它现在可以直接吃 Omicron 官方 CI 产物：每次提交产出的镜像不做修改就能拿来搭 VOXEL lab；Steve 还用系统自更新（system-update）给仿真出来的 SP 和根可信刷固件、替换主机 OS 与全部 zone，唯一失败在没有模拟 boot disk（`01:14:41`–`01:16:00`）。硬件门槛也在叙述中被拉低：一台 32 线程、96GB 内存的 Minisforum 迷你主机就能跑六到八节点的机架乃至 multi-rack（`01:21:27`–`01:22:22`）。Bryan 的总结是：正因为被测软件已经足够成熟，出了问题可以先怀疑 VOXEL，这种仿真在软件早期阶段反而做不了（`01:04:39`–`01:05:13`）。
