## 速读

AWS Agentic AI 组织下 Agentic DevOps 负责人 Neha Goswami 接受 SED 访谈（主持人为 Matt Merrill），讲清 AWS 如何把 Agent 引入 DevOps 与应用安全。核心产品是 DevOps Agent 与 Security Agent：告警发生时 Agent 先做调查、把根因与缓解步骤写进工单，被叫醒的工程师主要工作变成"审计"Agent 的结论。

这期最有价值的是把"Agent 化运维"落到具体数字与边界：内部使用成功率 85%–95%、预览中根因准确率约 94%（6% 失败由工程师兜底）、按任务小时计费且空闲不收费、以及"确定性不会消失、工程师仍在环且对系统负责"的明确立场。适合正在评估 Agent 化运维工具、或担心被取代的 DevOps/SRE 从业者。

## 主题正文

### Agentic DevOps 的定义与 AWS 的定位

Neha 在 AWS 的 Agentic AI 组织领导 Agentic DevOps 团队，负责把 Agent 引入 DevOps 与应用安全，在 Amazon 近 22 年。她的定义是"模型在流程中做推理，并由模型决定该调用哪些工具来实现被给定的目标"（她自述是"粗略而言"的定义）。核心判断是：代码正以空前速度被 AI 工具产出（她说"data is showing us"，未给来源），挑战在于如何让变更安全上生产以匹配产出速度。她给出的框架句是：Agentic 对 DevOps 既是"变革的催化剂，也是变革的解药"——催化是代码量激增的交付压力，解药是 Agent 擅长推理"构建为何失败、管线为何卡住、如何修复"。（`00:04:43–00:07:01`）

面对主持人"AWS 是否什么服务都自己建"的提问，Neha 澄清 AWS 的心智模型是"从客户需求出发、反向推导（work backwards）"，并提到她此前公开说过 AWS 不建自己的 CI/CD 平台或代码仓库——因为客户环境五花八门（她列举 GitLab、Datadog、Splunk、ServiceNow 等集成），问题空间在工具之上：如何连接分散工具间的数据与流程。但她也留下条件："如果为实现减少客户运维痛苦这个更高层目标需要建代码仓库、建管线，我们当然会做。"（`00:07:01–00:10:16`）

### Amazon 内部模式与产品起源

Amazon 的端到端所有权文化是背景：开发者自建、自测、自部署、自运维，"大多数组织"没有独立的 ops/DevOps/QA 团队；管线、策略、构建/部署与工单系统由中央团队拥有，具体配置由各团队负责。近两年的变化是"campaign"（影响大量团队的大规模变更，如 API 升级、框架迁移）在中央运行并不断"向左移动"到开发周期更早阶段。她引述约两年前公布过的统计：中央化的 Java 版本升级节省了"数百万、数百万美元"与"许多个 SDE 年"的工作量，该技术现已产品化为 AWS Transform——中央团队批量改包、产 PR 供团队审，甚至代为构建验证与部分测试。（`00:10:31–00:15:18`）

DevOps Agent 与 Security Agent 的起源来自内部流程的三大支柱：page 之苦（SDE 被叫醒的频率）、部署速度、部署安全；应用安全评审"理所当然耗时，但确实拖延发布"是另一个痛点。英雄用例是事件响应——"凌晨 3 点工程师被叫醒"，产品由此起步，上线前大量内部团队已在用。内部使用的成功率是 85%–95%，"取决于团队在做什么以及如何配置"。dogfooding 的意义是反馈飞轮：内部测试发现缺陷、每轮发布后系统性修复并固化进产品。（`00:16:13–00:19:37`）

### 从告警到根因的用户体验

Agent 化事件响应的旅程在人类被 page 之前就开始了：配置 resolver group（团队-系统所有权映射）后，Agent 预先构建子系统拓扑作为内置智能。告警超过阈值时触发 autocut 流程：自动生成工单、同时 page 工程师、Agent 启动调查，输出告警时间、涉及系统、根因、检查过哪里、假设与缓解步骤——"大量工作已经替工程师做了"。工程师醒来后的工作是审计 Agent 的结论然后执行。集成 ServiceNow 等外部系统时把详情回传由其渲染，多数用户留在工单系统内。拓扑在应用层建模整个应用，事件越多 Agent 学得越好。（`00:25:42–00:29:39`）

两个关键产品决策：定价按 active agent tasks（任务小时）计费，空闲不收费，只在 Agent 干活时计费；triage agent 做事件去重——"同一事件开了 5 张工单，告诉你只有一个根因"，她坦言构建原因之一正是计费考虑（"你不想为重复付钱"）。（`00:30:02–00:30:46`）

### 工程师在环与责任边界

Neha 明确"今天工程师必须在环"：仍由工程师被 page 并对系统运行负责，工程师当前角色是审计者。未来方向是让审计更轻松——展示 Agent 如何得出结论、建议的变更有多安全、帮助测试变更；"这条线会移动"，Agent 做更多动作、工程师做更多审计。主持人引述预览中 94% 的根因准确率；她补充剩余 6% 的失败样貌：Agent 错误关联数据、得出错误结论。关于责任，她说得很直接："责任仍在工程师身上，这一点没有改变。"她也把同一能力延伸到低严重度事件与 bug，"为什么不行呢"。（`00:31:13–00:34:12`）

对确定性的立场同样鲜明："确定性完全不会消失"，真正的问题是"在何处、以什么形式、如何正确地注入确定性"。当前两种注入方式：默认只读权限边界（"不能随意扩大权限，扩大是刻意为之"）；对变更做真实测试（起测试环境跑测试）。她还提到自动化推理（automated reasoning）——用数学建模系统、对比变更前后、检测非预期漂移，对策略尤其有用，与 LLM 是不同技术；DevOps Agent 已部分内置，会做更多。（`00:34:43–00:37:03`）

### 评估、架构与学习闭环

评估分三层：内部 benchmark、平行 benchmark（反映内部加外部当前工作流、纳入客户反馈）、有公开 benchmark 时也采用。早期以人工验证为主，部分用 LLM 自动化，"但我不认为我们见过能完全委托给 LLM 的案例"；在线数据（生产环境真实反馈）有人工查看加自动化扫描，"我们的准确率不是 100%"。反馈会分类：普适性改进回灌产品，误配置则改进产品使其不易被误配。架构上强调给 Agent 哪些工具、如何组织，以及区分"有用数据 vs 噪声"；Agent 的建模方式模仿内部 on-call 工程师的调查流程，大上下文窗口承担相当部分、再靠拓扑压缩适配。（`00:19:53–00:22:14`，`00:38:36–00:40:24`）

透明性与学习闭环：展示更多 Agent 工作、帮审计者定位 Agent"在哪一步走错了"；工程师可在产品内给负反馈记入 Agent 历史，工单最终解决时会记录真正根因（"至少内部如此"），Agent 据此持续改进。客户最有意思的 MCP 集成是写操作类——基于 Agent 结果去更新工单、更新事件追踪系统的"下一步"；她强调这不是系统写入，"仍只是记录工作"。（`00:37:20–00:41:19`）

### SRE 的未来、角色变化与建议

对"SRE 是否会消失"，她的判断是不——"事件会变少但仍会来"，但培训方式会变：过去 SRE 靠反复见同一问题形成模式匹配，现在部分模式匹配由 Agent 完成，SRE 要在更少样本下做好模式匹配，处理更复杂、Agent 失败或只做一半的场景；"琐碎案例没有 SRE 喜欢做，真正的硬骨头正是他们训练和学习的方式"。招聘上她明确回避给具体数字（"甚至不能给是/否"），但强调建设这些产品仍大量需要开发者和有 SRE 经验的人。角色本身没变，但期望变了：PM 能自己用 coding agent 做原型、更多经理在写代码、工程师更贴近产品。（`00:42:06–00:45:37`）

给从业者的建议是：自己先动手用 agentic 工具，"你必须知道这些工具有多强大"；持续使用会发现仍需要人做复杂问题解决，"持续玩这些工具的人对进入下一层复杂度更有创造力"——向栈的上方移动、去解决更复杂的问题。收尾她最兴奋的是 Agent 正在做大量信息综合，未来会采取更多行动，期待"完全无聊的事"和"不用凌晨 2 点醒来"的事被代理。（`00:46:02–00:48:55`）
