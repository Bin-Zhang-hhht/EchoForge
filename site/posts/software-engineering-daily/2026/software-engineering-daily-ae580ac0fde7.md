## 速读

SolarWinds CTO Krishna Sai 与 Sean Falconer 聊 AI 时代的可观测性与运维 Agent。SolarWinds 二十五年积累的产品组合横跨可观测、事件响应与服务管理三域，客户是背着 SLA 的 IT/运维团队——一位大型系统集成商 CIO 的原话是："我对 SLA 负责，但我说不清一个 SLA 到底由哪些东西构成。"这正是复杂度的写照，也是公司把重心押向 agentic AI 的原因。

最值得带走的三点：他们的平台哲学是"模型提议，平台处置"（the model can propose, but the platform must dispose）——模型只负责推理与提议，一切变更经由强制最小权限的控制接口执行；自治不是开关而是分级能力，每个动作类型都可以从"仅建议"逐级开放到"受约束的自主执行"；以及工程师的职责正从"写逻辑"转向"工程化上下文"，责任点前移且变得概率化。

## 主题正文

### 为什么运维是 Agent 的好战场：SLO 就是意图

Sai 先用 AI 辅助编程打了底：SolarWinds 全体工程师都开了 copilot 与 Agent，提交/PR 速度提升约 25%–30%，部署频率上升、lead time 改善，生成代码的接受率随模型与 Agent 成熟显著提高——但瓶颈也随之移到了代码评审，代码质量、flaky 测试与安全合规仍是显忧（`0:06:20`）。他看重的不是数字本身，而是编程给出的心智模型：让 Agent"给函数加 OAuth"时，它会读仓库、查依赖、改多处、跑测试——"设定意图，由系统决定采取哪些动作来达成目标"，这正是企业软件里 Agent 的思考起点（`0:06:20`）。

主持人接了一句行业观察：编程之所以是尖刀连，因为它是个"硬真值环境"——输出虽不确定，正确性却能确定性地验证（编译、单测），天然形成强化学习回路，而大多数领域没有这个条件（`0:09:39`）。Sai 的回应是把运维世界的对应物摆出来：SLO/SLA 就是那个可以被测量的"意图"。他给了一个 Agent 排障的完整链路：系统观察到错误率上升，判断只影响某个服务，关联到十分钟前的一次部署，再比对上一次事故的 trace 模式，最后得出"这是一次错误的配置变更"——每一步都是可从历史知识中学到的动作（`0:10:27`）。

### 从监控到 Agent：被复杂度逼出来的演进

他把行业演进串成一条线：监控（轮询、手工阈值）→ 可观测（多信号表达与关联）→ AIOps（信号关联与决策，仍很早期）→ copilot（辅助人类决策）→ 如今 agentic AI 的"早期绿芽"——能在边界内偶尔自主行动的 Agent。推力除了技术自身的演替，还有一个近乎生存性的现实：复杂度、工具蔓延与数据量爆炸，"人力在维护这些环境的健康上不再可扩展"（`0:13:08`）。

更具体的病根是竖井：ITOM 与 ITSM 的竖井既存在于组织里，也存在于数据里——数据摄取早已做得很好，结果却是"巨大的数据竖井"。想让 Agent 工作，竖井让一切变得复杂昂贵，还要再搭一层独立的 AI 系统去重新摄取、处理数据，于是战情室的桌面上摆满了各种控制台（`0:15:56`）。

SolarWinds 内部设计讨论常用的类比是大脑：五感全天候摄取信号，潜意识过滤出值得注意的（嘈杂商场里有人叫你的名字，你立刻竖起耳朵），再交给意识处理。映射到平台：一侧是优化"平均检测时间"的可观测系统，另一侧是优化"修复"的行动、runbook 与工作流，两者合成统一系统；潜意识对应后台处理，意识对应人类介入——而"有意识的动作"正逐渐分化出不同程度的自治（`0:15:56–0:20:12`）。

### 配置 Agent：不崩溃的故障最危险

copilot 阶段的本质是"坐在系统旁边的接口层"：帮你总结、解释错误模式、写跨指标的查询——有用，但根本上仍是响应式的（`0:20:46`）。他举了配置 Agent 说明差别。配置是现代系统里"杠杆最高、风险也最高"的面：DNS 配错、证书过期、权限过宽的安全规则——这些故障大多数不崩溃、不抛异常，只是行为的悄然劣化，"系统只是忠实地按你的配置在执行"，你根本意识不到事故已经发生（`0:20:46`）。

copilot 世界里，这类故障在事后被发现、工程师被呼、copilot 来总结。而他们正在把它变成持续行为：配置 Agent 持续观察服务是否劣化，一旦发现就把劣化关联到某次配置变更，然后做有效决策——回滚、还是把人拉进来（`0:20:46`）。这就是从"事后总结"到"环境式 Agent"（ambient agent）的迁移：主持人说得直白——在运维场景，我不想问"有没有问题"，我要系统自己知道有问题、先干活、到需要人类决策时再叫我（`0:27:16`）。

### AI by design：模型提议，平台处置

Sai 反复强调的内部概念是 AI by design——既不是 AI first 也不是 AI everywhere，而是"从第一天起就假设 AI 组件会存在、会演化、最终会自主运行"地设计平台。多数团队的错误是把 Agent 当事后加装的功能，结果是"花几十亿美元造出的强大模型，蹲在脆弱的护栏后面"，然后抱怨最好的模型不给力——因为你没有为它设计能行动的系统（`0:20:46`）。他们的口号："模型可以提议，但平台必须处置。"模型是推理组件，平台才是安全边界（`0:20:46`）。

由此落下来的是几条具体的架构决策。其一是 LLM 网关：早期团队把日志直接接到 LLM 上，demo 里惊艳高管，一进生产就撞墙——成本不可预测地飙升、敏感数据出问题、各家硬编码不同模型，最后既换不了供应商也执行不了策略。网关把模型选择抽象、PII 脱敏、限流、审计这些横切关注点收拢成平台服务（`0:20:46`）。其二是别把 MELT 数据（指标、事件、日志、trace）直接灌给模型：日志极其嘈杂，必须先压缩、去重、摘要，把"半个 million 行日志"变成"变了什么、什么异常、什么是新的"的紧凑表示，再喂给推理层（`0:20:46`）。

### 三平面与分级自治

平台整体分成三个平面：数据平面负责 MELT 与拓扑的摄取和归一化，控制平面负责策略与动作，推理平面是智能与 Agent 所在之处。这个切分既是刻意为之，也呼应了 Kubernetes、service mesh 的既有设计——分布式状态、部分失败、"组件不应有隐式权限"，这些运维世界的老问题原样适用。推理平面是"显式按权限设计"的一等公民（`0:36:07`）。

关键的直觉是："让推理平面里的模型做它们擅长的事——有表达力但不危险。"模型负责探索假设、提议动作；任何涉及变更与动作的执行，永远经过强制最小权限的控制接口（`0:36:07`）。自治则被当作分级能力而非开关：每类动作都有自治级别，从"仅建议、零变更"到"批准后执行"，再到"低风险场景下受约束的自主执行"，并可按动作类型、环境、服务、团队细调（`0:36:07`）。配套的两件基建是全量事务级可追溯（出了问题要能回看发生了什么、谁授权的）与"对自治本身的一等可观测"——OpenTelemetry 社区正在为后者推进标准。可追溯的紧迫性立竿见影："你一开放网关和 agentic 框架，一夜之间就会有 20、50、100 个 Agent 冒出来"（`0:36:07`）。

### 一个见效的用例：ITSM 工单 Agent

主持人问模型选型：边界清晰的 B2B 运维问题需要万亿参数模型吗？Sai 的答案是把选择权放在网关层，按用例定模型；他们大量使用 Claude 系模型，也用 Haiku 做特定场景（`0:29:14`）。最生动的例子在 ITSM 产品里：一张工单平均要被转手约 15 次才到对的人，接手的人面对整段历史认知负担巨大。他们的 Agent 读历史工单数据，生成上下文摘要——这是什么问题、客户是谁、敏感度如何、谁看过、他们当时怎么想——再附一份建议回复，人只需快速编辑后发出（`0:29:14`）。

效果数字很直白：这个用例的采用率"即时见效"，MTTR 一夜之间改善 30%–50%（原话为 "MTTR goes up by 30% to 50%"，按上下文指修复效率的提升）。他把这点归因于方法论："如果你以系统化的方式设计、工程化、搭平台原语、以用户体验优先，而不是把 flaky 的 Agent 拴在不稳定的环境上，你就能在这些 agentic 用例上看到即时的 ROI，同时保住边界与选择权"（`0:33:20`）。

### 从写逻辑到工程化上下文

对工程师角色的变化，他的概括是"这不只是工具切换，而是责任切换"：从逻辑的作者，变成上下文的工程师。传统世界里责任是超确定的——你写的代码坏了你负责；agentic 系统里责任点前移且变得概率化，而工程师天性追求确定，这个适应是全行业的细微功课（`0:41:53`）。他特别提了一个少被谈到的话题——情绪韧性：这些系统先是"我有了超能力"的惊喜，随后开始幻觉、做出出乎意料的选择，让人恼火。能成功的是把结果当反馈而非失败的人："有意思，缺了什么上下文？我忘了在提示或系统里编码什么约束？"——张口就说"垃圾，我自己写脚本"的团队留不下来（`0:44:45`）。工程师的分级标准也随之变化：不再是语法与风格指南，而是架构系统的能力、驾驭系统造出好产品的能力（`0:46:47`）。

关于初级工程师，他给的是两面答案：初级确实更快学会驾驭这些系统；资深则更懂"agentic 系统不替代基本工程纪律——它暴露并放大本来就存在的混乱"。有清晰所有权、良好数据与运维根基的团队把 Agent 用作力量倍增器，没有这些根基的团队只会觉得 Agent 不可预测。SolarWinds 的内部做法是建活跃的 AI 社区，让资深与初级日常互享"什么有效、什么无效、该补哪些架构根基"（`0:48:28`）。ROI 的建议同样务实：先做客户服务这类强指标域（工单偏转率、首次响应时间、解决时间都可测），工程生产力本身定义不良——commit 速度之类只是早期信号，真正要补的是把 lead time、变更失败率这类指标与业务结果挂钩（`0:50:25`）。
