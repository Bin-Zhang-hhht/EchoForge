## 速读

Airbnb 首席工程师 Adam Miskiewicz 向 Gregor Vand 讲述 Viaduct——Airbnb 已开源的"数据导向服务网格"与 GraphQL 平台：如今 Airbnb 约 80% 的流量、全部 API 流量经过它，服务约每秒一百万多次 GraphQL 操作，schema 有约 2.5 万个类型、几十万个字段，租户模块代码达数百万行。

最值得带走的三点：Viaduct 与 Apollo Federation 式"子图即服务"的根本分歧——它的子图是托管在同一平台里的 tenant module，业务逻辑直接写进平台，因为"微服务疲劳"才是它诞生的语境；现代版 Viaduct 的核心是一条内核空间/用户空间式的严格边界（引擎 vs 租户 API）加一条极简心智模型——"一切皆 Resolver"，配合同请求内同参数不重复执行 resolver 的异步记忆化；以及他对 AI 时代的判断：Agent 只想写代码，不想搭基础设施，"用强类型数据图描述全部核心业务数据、让人和机器都能灵活查询"的 GraphQL 理念可能因此复兴。

## 主题正文

### 起源：入职第二天的 GraphQL 工作组

Miskiewicz 的路径是"小公司到大公司"的反向样本：巴尔的摩的交互agency、做 React Native 工具链的 Expo，然后进入 Airbnb——入职时是前端工程师，八年里看着工程组织从 500 人涨到 3000 人，而他已经有七年半没写前端了（`0:02:15`）。入职第二天，他被拉进一个约 20 人的 GraphQL 工作组：当时 Airbnb 正在从数百万行代码的 Ruby on Rails 单体里切出微服务，iOS、Android 与 Web 工程师都想要强类型 API，此前只有 Ruby 圈子一个名为 Grafast 的意见化框架实验（它其实不是 GraphQL）（`0:04:47`）。

当时的微服务结构是三层：底层数据服务包装数据库、暴露 Thrift API；顶层展示服务从 MVC 系统移植 controller 逻辑、暴露 REST/JSON；中间是杂七杂八的派生数据服务。GraphQL 的第一版方案离 Viaduct 很远：把 Thrift schema 自动转成 GraphQL，再把各展示服务的 schema 缝合成一个巨型 schema、单一端点。他称之为"面向服务的 GraphQL"——顶层字段就是服务名，根本不是实体图（`0:04:47`）。这是 Apollo Federation 出现之前、GraphQL 开源仅几年的年代，schema stitching 是当时的主流玩法。这个过渡版的价值是让三端客户端用上 GraphQL 和代码生成；由于端点形状与 REST 一致，客户端迁移很容易（`0:08:45`）。一个有趣的细节：Thrift 到 GraphQL 的转换是全自动的，所以后端工程师"基本不需要知道"——当年他们在刻意"保护后端同学"，让其专注微服务迁移，而客户端工程师则抢着要新工具（`0:11:16`）。

### 数据架构工作组与 Viaduct 的诞生

2019 年夏，新 CTO 到任就问"我们的数据到底在怎么回事"：数据存储碎片化、离线数据一团糟、数据管道出问题，而公司正在准备 IPO——财务 reporting 要求核心数据说得清。由此成立了八人组成的数据架构工作组，外请顾问 Raymie Stata，整栈端到端地推倒重议。产出有三：离线体系的大幅改善、核心在线数据系统 UDS（统一数据存储）的重构，以及 API 侧"统一数据访问层"的构想——这就是 Viaduct（`0:12:24`）。第一版上线很快，几个月就发布了，第一个用它的功能是行程页右上角"查看当前行程"，还有愿望清单。名字的来历很朴素：viaduct 是桥（高架桥），Airbnb 起名素来只会加 air 前缀，这次想要"连接很多服务"的意象（`0:12:24–0:16:26`）。

### 三原则：中央 schema、托管业务逻辑、可重入 API

Viaduct 的哲学转变有三条指导原则（`0:16:58`）。第二条"业务逻辑托管"从一开始就是铁律：彼时 Airbnb 正患"微服务疲劳"——早期工具贫乏，迭代慢、依赖难懂，微服务写业务逻辑的意见化框架让人难以快速试错。于是 Viaduct 反其道而行："先做不能扩展的事，之后再想办法扩展"，长期愿景是 Airbnb 自己的 serverless 平台（`0:17:40`）。与 Apollo Federation 的对比因此清晰：大家都是统一图、对客户端只发布一个 schema，但 Viaduct 的"子图"不是独立服务，而是 tenant module——有 schema、有代码、有写法约定、可打包，"在代码库里看着像一个个小服务，只是被托管在一个大平台里"（`0:19:27`）。

第三条"可重入 API"是他认为最独特的部分：在图内声明字段的数据依赖，而不是出门找服务。经典例子是全名字段——声明"我需要 user 实体的 first name 和 last name"，Viaduct 负责取数、计算、把数据交给 resolver。这个想法从第一天就有，而且随图增长越用越顺：如今图里约 2.5 万个类型、几十万个字段，Airbnb 大部分在线数据都在图里——在较高层做展示型功能时，常常整个功能写完都不需要一次直接的服务调用，全程通过重入回调图本身（`0:21:08`）。

### 架构：引擎空间与租户空间

Viaduct 本体是一个意见化的 GraphQL 服务器，底层从头到尾是 GraphQL Java。现代版把它切成三层：引擎层只管执行模型的核心——高性能地执行 selection set、并发模型、并行取数与批处理、避免 N+1、请求内缓存；其上是租户 API 与运行时，提供强类型接口（Airbnb 的 JVM 大栈里，所有在 Viaduct 写代码的人都用 Kotlin）；最上面才是托管的业务代码（`0:24:03`）。

类型数据的边界划在哪是关键决策：引擎并不关心强类型，"只是搬运数据"，因此类型信息不能穿透整个系统——否则无法单独部署某个租户。他们常用的类比是内核空间与用户空间：引擎空间 vs 租户空间，边界不完美但足以提醒所有人"这两层必须严格分离"（`0:24:03`）。

### 经典到现代：成功者的自我革命

录制时点，Airbnb 大部分流量仍跑在经典版 Viaduct 上；现代版正在灰度，2026 年内全面推进。一个体现边界价值的细节：内部已经在跑现代引擎，上面用 shim 层托着经典 API（`0:27:18`）。为什么要重写？经典版"是自己成功的受害者"——工作组长出有机采用、随后按客户需求一个功能叠一个功能，运行时性能、构建时间、开发者循环都出现痼疾；更根本的是旧架构里引擎与租户 API 刻意重叠（codegen 出领域模型再挂实现，"重写这个方法即完成功能"的人体工学很好），但边界模糊到"说不清引擎从哪开始、租户 API 到哪结束"，想要更多租户隔离与自治却保留中央平台杠杆，在旧架构里被判定为不可逾越。连平台团队自己都难以在旧代码上工作，速度被拖垮（`0:28:13`）。

撑着这一切的是体量：Airbnb 约 80% 的流量、全部 API 流量经过 Viaduct，"它已经大到不能倒"。可靠性因此压倒开发者体验多年——他特意向内部开发者致意——"即便它不是完美方案，它也是你手上唯一的方案"，而团队的任务就是把它变成真正好的方案（`0:31:19`）。

现代版的回报是一条极简心智模型："一切皆 Resolver。"经典版的接入决策是一张大流程图，现代版把重入能力直接内建进 resolver 概念（`0:35:33`）。性能上则有一个大多数 GraphQL 服务器都没做的核心机制——异步记忆化：GraphQL 的执行是深度优先的并行遍历，叠加重入后容易做重复功；现代版规定同一请求内、同字段同参数的 resolver 不重复执行，收益可观（`0:35:33`）。规模压力的画风也很极端：单条查询取 10 万到 30 万个字段、返回数 MB——"你可以说别这么干，但说易做难"，平台团队必须接住这些真实用例，这背后是实打实的图算法问题。强类型改用值类（value class）承载，生成物大幅减少，构建时间随之缓解（`0:35:33`）。

### 开源：问责机制与不能偷懒的抽象

开源现代版的决定很早，CTO Ari 是推手。他的说法不是常见的"技术品牌"叙事，而是把开源当作问责机制：把工作摊开给世界看，接受检验，公开讨论"我们为什么这么做、如何在我们这个规模上运维"。为此团队在 monorepo 里隔离出现代版、剔除内部依赖；把 Viaduct 拆出 Airbnb 的泡泡并不轻松，但这个过程反过来强化了抽象——"开源了就不能偷懒"，必须同时服务外部用户与 Airbnb 自身（`0:41:00`）。迁移策略是"新用例用现代版"，但绝不强迫重写：未来几年消灭经典版的方式将是 AI 辅助迁移（`0:43:09`）。对想上手的人他有一句诚实的提醒：开源出来的是 Viaduct 的真核心，但让它在 Airbnb 规模运转的基础设施粘合剂尚未开源——"你不会免费得到 Airbnb 的规模"（`0:44:38`）。

### AI 时代：统一数据图的可能复兴

节目过半才第一次提到 AI，Miskiewicz 的判断分几层。工程会剧变但不会消失："我们可能不再手写很多代码，但仍然对代码负责。"在 500 到 1000 人以上协作的规模，"大规模编程"（programming in the large）的强模式会变得极重要——谁都能力 vibe code 一个后端，他也支持初创公司"留在单体里"，但规模一大，让很多人和很多事协同的架构就是刚需（`0:46:00`）。他预期服务不会消失，但数量会显著坍缩，单服务上可扩展的不只是人还有 Agent。他引用 Ona（前 Gitpod）团队的观点：Agent 产出代码之后，部署、观测、事故处理依然要在，"管理整个软件开发生命周期在很长时间里不会是单个 Agent 能做到的"——所以大公司需要稳定的托管平台，小公司用 Vercel、Fly.io 这类平台，因为"没有它你真的玩不转"；而 Agent 只想写代码，不想搭基础设施（`0:49:00`）。

这直接通向他的 GraphQL 判断。批评者说"GraphQL 太复杂，只有最大的公司需要"，他承认部分成立；但 GraphQL 的理念——用强类型的数据导向 schema 表达全部核心业务数据，再用一种人机都能灵活查询的语言暴露出去——在 AI 时代反而更有价值：你是要教会 AI 公司里每个服务每个 API 的细微差别，还是教它一张关系已经编码好的统一数据图？"灵活"正是关键：用 RPC 或 REST 也能暴露数据，但 GraphQL 让你按需组合出恰好表达所需内容的查询。他坦承自己立场有偏，但认为 GraphQL 可能迎来一波复兴（`0:50:48`）——主持人补了一句近在眼前的先例：被看衰十年又全面翻红的 Postgres（`0:52:40`）。
