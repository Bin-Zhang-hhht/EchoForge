## 速读

软件工程师习以为常的一切——弹性 CI/CD、可观测性、秒级反馈——在硬件工程里大多不存在。Nominal 联创 Jason Hoch（Palantir 分布式数据系统、Vercel 云基础设施出身）在这期访谈里给出了硬件世界的数据真相：一架试飞飞机上有上万到两万个传感器、采样率千赫兹到兆赫兹；火箭八秒点火产生的数据就是整个公司的核心资产，一个点都不能丢。

最值得带走的三点：硬件数据平台的本质是把"事件、资产层级、数据谱系"做成一等公民；边缘侧的取舍是过滤、本地暂存与事后回填的分布式系统问题；以及 AI 改不动硬件的根本原因——反馈回路必须经过物理世界，而且 LLM 是在"人类翻译成英文的物理"上做推理。

## 主题正文

### 反馈回路以天计：硬件世界的 ground truth

Hoch 的联合创始人做过 NASA 任务操作，给他讲了一个问题：向木星发一个耗资超十亿美元的探测器，软件程序怎么部署、怎么提前测试才能不毁掉任务？他的第一反应是对比 CI/CD——单元测试分钟级，而硬件世界的"测试床"可能是一张花了百万美元搭起来的物理台架，台架本身还得先"预测试"，因为它只有一两套，坏了整个组织停摆（`00:05:12–00:06:46`）。最直观的例子是试飞飞机：落地、把硬盘拆下来、送到设计该系统的工程师手上、调试——一些客户这套流程要走一两天，而软件工程师的反馈循环是分钟级的。

数据丢失的方式也很"硬件"。采集数据的 schema 会随机载软件版本变化；现场疲惫的操作员（不是软件工程师，也不是设计者）在给飞机降级软件时忘了同步降级地面控制软件里的一个配置项，数据就全花了。有客户请他们去挖网络存储，结果发现只有约 10% 的数据能到达那里，其余都折损在前面的环节。Nominal 的解法是把"机上软件版本与本地软件版本自动同步、配置自动更新"做成后台动作，让操作员根本不用想这件事；再往下一步是架构迁移——装上 Starlink 收发器后数据从"落地拆硬盘"变成实时流，对软件资源都投在飞控上的团队来说，这种转变需要一个专门的平台来接（`00:07:11–00:09:20`）。

### 八秒点火的黄金数据与 pets 的世界观

数据的形状决定了架构。一颗卫星或一架试验机上可能有一万到两万个传感器，每个采样千赫兹到十千赫兹、偶尔兆赫兹——每秒一万到一百万个数据点，外加视频需要与时间序列做帧级精确对齐（他们低估过这件事的难度，最后有几个工程师成了视频编码专家，因为开源视频栈都是为社交媒体播放设计的、不是为帧寻址设计的）（`00:13:41–00:16:03`）。更根本的世界观差异是那句行业老话的反转：软件工程师被训练成"把基础设施当牛不当宠物"，而硬件客户的一切都是宠物——整个公司围着一两架飞机转，卫星发射失败就是几个月工期加几千万美元，"你愿意比软件人加倍多地反复检查"。极端例子是一家公司发现某零件有问题，要溯源到是哪台 3D 打印机打的——他们给每台打印机起了名字（`00:16:03–00:17:44`）。

Nominal 数据模型的三个支点因此是：事件（任何人圈出一段"这里发生了什么"的时间区间打上标签，全组织可见，无论对方在看哪个子系统）、资产层级（两架飞机各两台发动机、发动机还会互换成什么样，必须随时答得出"上周 100A 左侧装的是 2 号还是 3 号"）、以及标记/目录/数据谱系。回报是具体的：测试出了问题想和对应仿真叠在一起对比——数据标记好了就是"点几下"，没标记就是"写一大堆定制 SQL"。他们的目标不是取代 MATLAB，而是让那一个写 MATLAB 脚本的人把逻辑打包进平台，其余 200 个需要这份逻辑的人不必打开 MATLAB（`00:17:55–00:22:45`）。

### 热路径与冷路径：控制室和推进工程师是同一个平台

架构上最难的是让"热路径"与"冷路径"讲同一个故事：控制室里的人盯着大屏看安全检查是否失败（不能忍受公网上的 AWS 延迟，有的客户整个本地部署），推进工程师则在几千次飞行的历史数据里挖统计模式（OLAP 式分析）。Nominal 让用户把分析逻辑只写一遍，在两个场景间无缝切换。他们最早的流式架构其实很弱，是被一个"要在控制室大屏上显示"的客户需求逼着重做的，而分析界面意外地被用户当成监控面板用——两个用例就此都成了核心（`00:09:20–00:12:06`）。界面的教训也反直觉：专家用户每天盯十小时，他们要的密密麻麻像 Excel 的数据密度，而不是转化漏斗式的消费级 UI（`00:12:26–00:13:41`）。

边缘侧是标准的分布式系统问题集：网络受限环境里边缘 Agent 依然要过滤，但不丢数据——本地落盘、事后回填，总部和试验场各自有库、最终同步（mesh 概念）；要在"安全攸关信息、高优先级观测、其余一切"之间做优先级调度，背压思维完全适用。好消息是火箭点火一天就几次，把上传摊到足够长的时间窗里总能追平（`00:24:57–00:27:06`）。

### 硬件创新的黄金时代与 AI 改不动的部分

行业格局在变：25 年前真正的硬件创新集中在通用电气那样的大集团，它们花三四十年攒出了世界最好的自研仿真软件；如今创新在向小公司迁移，它们只能拼装现成工具——Nominal 想做的就是把仿真数据也接进来标记好，让"测试出问题就回头改进仿真"的组织愿景不再死于工具疲劳。 SpaceX 蹚出了路，而现在一批创业公司想比 SpaceX 更快：七到八个人的组织，100% 的工程师每周登录平台看数据，CEO 亲自看周环比——"我小时候不会想到核反应堆创新能由创业公司来做"（`00:22:45–00:24:57`、`00:27:06–00:29:29`）。大机构一侧同样重要：美国空军雇着两万名测试工程师，电弧加热器、风洞这些"国家实验室"资产的运转水平，直接关系到技术竞争的位次；Starlink 已有多代设计同时在轨、持续回传数据改进制造，Tesla 在内部数据目录上的投入会超出外人想象（`00:29:29–00:31:45`）。

那 AI 为什么还没改写硬件工程？Hoch 的对照很锋利：一个客户在造一台楼房大小的机器，已经是见过最快的速度，仍然以月计——但用了平台后 CEO 反馈"问题被更早发现，30 分钟修掉，而不是灾难后损失两天"。这是数量级的改善，但与"代码自己写自己、自己跑单测"的软件循环相比仍是不同物种（`00:32:20–00:34:52`）。差距的根子有两个。第一，硬件的反馈必须经过物理世界：打印、接线、开到沙漠里试飞，时间和人的协调省不掉，也没有人愿意对火箭点火或载人飞行像对 OpenClaw 那样 YOLO。第二，他怀疑 LLM 是在"人类把物理翻译成英文"的语料上做推理——你问它喷气机性能，它在合成英文概念，而不是在物理层思考；这跟软件里 Agent 原生工作在代码上完全不同。要让设计 Agent 在硬件上工作，需要能单元测试的硬件、需要积累"哪里反常但无害、哪里反常且危险"的人工标注数据集——火箭一周只点几次火，大量静止时间正好用来删掉无用区间、圈出关键区间，这些才是未来训练物理世界 Agent 的原料（`00:34:52–00:36:24`）。

平台已经迈出了务实的第一步：几周前上线的 workbook agent 把"搭一个飞行测试分析可视化要点一百次点击"变成用英语提问（速度是分量速度平方和的平方根这类公式，模型答得上来），再往路线图里还有时间序列上的异常发现研究。更远的愿景包括：用正经数据科学把认证测试的置信水平从一千个数据点压缩到一百个；空军伙伴梦想的"飞行员在空中五秒前动作的反馈改变下一步动作"——把绑在大腿上写死十件事的 kneeboard 变成动态的 iPad；供应商与采购方减少重复测试；以及 SpaceX 式的反转——从一百人盯一个资产变成一个工程师盯一百个资产（`00:36:40–00:42:33`）。规模光谱的另一端是机群：几百架无人机每天飞几十次，问题从"宠物"滑回"牛群"——昨天一千个异常先钻研哪一个；外卖无人机不需要 100% 可靠、需要 99.9%，那是一个经济学问题（`00:42:51–00:44:59`）。

最后是一个值得记住的警示：把多小时飞行画成一张缩略图时，降采样可能在说谎——真正致命的可能只是某半秒的异常。用户因为"数据里有个故事我没看到"而失眠，Hoch 对此的敬畏变成了产品里的谨慎，也是他对 AI 时代的担忧：如果 UI 由 Agent 生成、细致劲儿没了，误解会复利。"我们最好先在软件世界这种低风险领域把风险管理的课补上，再把它们带给航空航天和核电"——swyx 总结：你不想让 OpenClaw 设计你的火箭？他答：还不想，先从电子游戏开始（`00:48:13–00:50:11`）。
