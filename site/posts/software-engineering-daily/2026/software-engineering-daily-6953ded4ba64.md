## 速读

Capital One 开发者体验 SVP Catherine McGarvey（领导 14000 名技术人员）接受 SED 访谈（主持为 Sean Falconer），讲大型受监管企业如何做开发者赋能。最实用的两段：度量陷阱（每工程师 PR 数是坏指标——"最差的编码助手可能产出最多的代码"；开发者是"最擅长玩弄指标"的客户群）与受监管环境的标准化策略——"让做正确的事变得容易"，把最佳实践做成默认行为。

对 AI 转型最有用的判断：反对度量代码行数；收益正在"向栈的上层爬"；以及那个类比——不用 AI 工具就像"开卷考试却选择不用书"。

## 主题正文

### 从 productivity 到 enablement 的定义

Catherine 的经历覆盖初创、国防咨询到 Capital One。她的定义演进：过去关注 developer productivity（吞吐、速度、质量），15-20 年前产品经理角色兴起带来转向"我们是否在做正确的事"——"没有与价值连接的生产力就像一个垂死的产品"。enablement 的定义是速度与倾听用户的平衡——既给工具，也给信息。团队"泳道"要足够小才能有效交付；团队不应只是领取产品定义后执行，而应理解并改进整体体验。（`00:01:21–00:05:58`）

### 度量：time to first commit 与"玩弄指标"

对"该度量什么"没有唯一好答案：部署间隔时间、工具是否达成预期结果、NPS 满意度等。onboarding 的通行指标是 time to first commit 与 time to 10th commit；但要考虑"知道被测量会改变行为"——开发者是这一领域所有客户中最擅长"玩弄指标"的。糟糕的 onboarding 可能影响留任（主持人推测、她认同）。（`00:05:58–00:09:51`）

### 受监管环境下的标准化策略

策略是"让做正确的事变得容易"：把最佳实践做成默认行为，若不满足需求可走审批/例外流程。应由公司层面标准化的就标准化——这会带来迁移等额外工作，但能把控制措施放进标准、减少开发团队的工作量。没有标准时会出现多个类似工具，这反而促使公司较快建立标准。AI 领域刻意不锁定：每次 pilot 都标准化"成功标准"；用抽象层接入编码助手；"越是绑定一个模型或一种方法，越会被框死"。（`00:09:51–00:15:14`）

### LLM 编码助手的推出与"反 LOC"立场

推出流程：完整风险与合规评审 → POC → pilot → 规模化；配套做法是建 Slack 频道展示谁用得最多、分享成功与失败案例。主持人的两个观点值得记录：公司常低估工具的学习周期；即使编码助手完美工作，编码可能只占开发者时间的约 20%，按 100% 时间想象 ROI 会落空。

她明确反对度量代码行数："最差的编码助手或 agent 可能产出最多的代码，这完全不是价值的衡量"；更看重长期视角（团队一年的吞吐变化）、质量是否持平或变好。希望自动化低创造性任务：老版本迁移、解决 npm 依赖、漏洞修补。观察到的实际收益：对职业新人提升巨大（理解代码库、学新框架）；但结果"时好时坏"，因此坚持所有环节 human in the loop。（`00:15:14–00:23:13`）

### 工程为何是 AI 落地的先头部队

主持人的两个原因：工程有内建验证护栏（编译检查、单元测试、人工评审、canary 发布），而许多创意领域缺乏确定性验证手段；工程师历来善于投资自动化。她完全同意，补充：视觉测试、点击行为类功能级测试以前难写、agent 很擅长；但"不能让 agent 写所有测试和所有代码，那样的配置没有平衡"。资历差异仍处早期：初级者从"不够优秀但够用"的响应中也能获益；在 planning mode 等新工具上开始看到资深工程师获得更多提升——她称之为 "green shoots"。（`00:23:13–00:26:34`）

### "开卷考试却选择不用书"

开发者角色的变化："我认为它已经变了"——如同旁边多了一个人与你协作；人的价值将落在判断力、理解方向、清晰表达，以及足够理解代码以确保沿正确路径推进。以自身经历类比历史抽象跃迁：学汇编、学 C++——"不再需要担心内存泄漏的那些日子真好"；这次转变"可能比那些更大"。对抵制者的回应很直接："如果你是珍视解决 npm 依赖、或把老版本 Java 库迁移到新版本的工程师，那这个演化不适合你"——找到乐趣所在并转向能获得乐趣的角色。不用 AI 工具就像"开卷考试却选择不用书"。（`00:26:49–00:30:38`）

### 另外 80% 与峰值生产力愿景

开发者非编码时间包括：生产问题 triage、部署与测试覆盖、理解 Jira 中的需求、跨团队协调；公司层面在评估相应 AI 工具。她的因果断言："开发者花在 SDLC 其他方面的时间越多，花在代码上的时间就越少，我们要在每次机会中把他们推回代码。"峰值开发者生产力的定义：有了一个想法，当天就能放到用户面前——且在全部控制与验证就位的情况下安全一致地部署。（`00:30:38–00:34:00`）

### 度量陷阱与更好的指标

最常见的错误是追踪所有可能的指标、或追踪会驱动错误行为的指标；人会朝被追踪的方向努力并使其被游戏化——反面例子是每工程师 PR 数（"现在有了这些工具，我可以给你生成一大堆 PR"）。她感兴趣的方向："从 story 开始到 story 交付"的整体 cycle time，但也承认这个指标可能被游戏化。（`00:34:00–00:37:09`）

### 自助服务与"开发者喜悦"

主持人类比：最好的公司能做到落地页面后 3-10 分钟内成功调用 API，差的地方要数天——直接影响采用。这取决于团队的自助服务程度：知道工具在哪、权限是否正确、信息可发现性。她的玩笑表述："开发者永远不会快乐"，但她要负责的是提升开发者处于 flow state 的时间和对手艺的喜悦；最容易改进的切入点是"看不懂、不知道如何行动的错误信息"。（`00:37:09–00:38:53`）

### 给转入大组织的工程领导的建议

首先了解公司如何运作——沟通规范、什么信息在什么层面浮现、"坏消息如何被传达"很值得观察；还要弄清什么被庆祝。"不要假设大就意味着慢"（个人经验性判断）；但搭上既有模式能获得更大提升，而想在大公司做完全新的事物会难得多。结语：工程师将因其判断力和经验被重视；"这是一个成为开发者的激动时刻"。（`00:38:53–00:41:17`）
