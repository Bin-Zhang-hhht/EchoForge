## 速读

这期节目适合做推荐系统、Feed 流与大规模 LLM 推理的工程师，尤其适合想知道"前沿团队怎么在十亿级用户身上为 LLM 推理买单"的人。嘉宾 Tim Jurka 在 LinkedIn 工作十三年，从信息流最早的 AI 工程师做到消费产品线 VP of Engineering；主持人 Matt Merrill。LinkedIn 近期把信息流重构成"内容序列建模"问题——像 LLM 预测下一个 token 那样预测用户下一个想看的内容，节目覆盖了架构、评估、成本与组织四条线。

最值得关注的三点：一是从"每条候选内容独立打分"的特征交叉架构（DCN V2、deep and wide）转向序列模型后，系统学的是"看完某类内容的人接下来走向哪里"；二是内容质量管控变成了产品经理写在 GitHub 里的自然语言策略文件，由"品味官"人工评测与 Copilot CLI 自动评测组成主动学习循环，一周内就能迭代对"AI slop"的定义；三是成本工程的真实细节——GPU 原生架构先撞墙，然后语言过滤下放 CPU、20 分钟窗口批量、CUDA 级定制注意力核、微调模型替代通用前沿模型，以及"上下文压缩是一个整编 pod 的长期工作"。

## 主题正文

### 为什么重构：十亿会员、零样本会话与 AI slop

规模是重构的起点：2020 年以来会员从约 6.9 亿涨到 13 亿，每秒约 7 名新会员加入。新会员带着陌生的行业与诉求而来，LinkedIn 必须在会话的头几秒——他们称之为"零样本体验"（zero-shot experience）——迅速锁定其关心的事，因为多数人不是来无限刷屏的，是来办事的。老用户侧的问题则是生态性的：AI slop 与钓鱼式互动内容涌现，系统需要细粒度控制把高价值对话与真实、经认证的创作者顶上去。此外，LinkedIn 信息流历来偏重网络关系，但给你前沿洞见的人往往不在你的关系网里，"未连接内容"（unconnected content）的 topical 匹配精度因此同样依赖这套新基础。（`00:02:59–00:07:18`）

### 序列建模：推荐系统的"下一个 token"

Jurka 把新架构的类比讲得很直白：LLM 是语言的序列模型，预测给定 token 之后的序列；信息流可以对内容做同样的事——预测条目序列而非词序列。旧范式是 MLP 类架构加特征交叉（他点名 DCN V2、deep and wide），把海量特征塞进模型、逐条候选打分再排序；序列模型则学习"看过模块化反应堆内容的人接下来会往哪个方向深入"——可能从一篇 PyTorch 入门开始，沿着序列走十五步之后其实是在本地复现 LLM。这套东西不是现成可买的：他说据其所知这套"序列模型 + 排序 + 基于 LLM 的检索"的组合在这个规模上相当独特，内部大量自研，同时仍按实验决定哪些部件用开源、哪些自建。（`00:07:18–00:09:02`）

打分目标本身也是多头的：正信号（评论、转发、停留时长）与负信号（跳过、视口一扫而过）合并进多目标优化，而且所有动作的权重按用户逐人个性化——找工作的用户和运营粉丝的营销人看到的排序目标不同，"完全个性化"，不靠角色或人群包。（`00:11:20–00:13:44`）

### 策略即代码：PM 用文本文件管内容质量

评估环节最有启发的是"策略文件"机制：什么算高质量内容由产品经理定义，写成检入 GitHub 的文本文件——"几乎可以当成 prompt"。人工侧有熟悉产品策略的"品味官"（taste makers）评分；自动侧用 GitHub Copilot CLI 主动复评——模型看一批检索内容，指出哪里违背策略，与 PM 对话迭代措辞，形成主动学习循环。他说这正是新旧范式的分野：过去优化一个目标、祈祷"有趣"是模型的涌现属性；现在可以逐话题验证——"对核工程受众，你推出的真的是行业相关内容吗"。这套机制一周内就能看到对"非真实内容"（如 AI slop 式回复）定义的演进与微调。训练侧则是持续增量重训：新数据一到就更新模型，线上分流跑数百个实验，线下在历史数据上回放数千次。（`00:13:44–00:19:39`）

### 组织：通才、专家与"整编 pod"

"没有普通工程师"——他如此回答"平均工程师长什么样"的问题。走得最快的是能横跨栈的通才：既懂模型微调、蒸馏，也懂后端集成甚至 prompt 工程；但专家没有消失：nearline 管道把客户端行为事件实时灌进特征库、推理工程师在 GPU 集群上优化 QPS、AI 工程师训练部署。组织形态是小 pod——PM、设计师、基础设施工程师、后端工程师端到端负责一个模型。整个重构由几百人完成、系统性地干了 12 到 18 个月；一旦建成，日常运营所需团队小得多，基建团队随即转向下一个平台。（`00:17:38–00:21:39`）

### 成本工程：GPU 先撞墙，再一层层往下省

他复盘的成本路线图非常具体：先做 GPU 原生架构、在小流量（1%、2%、5% 会员）上验证价值，然后发现"这样撑不住"，开始系统性降本——能下放 CPU 的下放（如语言与分面过滤，不需要 GPU 的简单索引先砍掉不必要计算）；不需要全参数模型的判断用简单模型近似，"不必为每条候选都跑千亿参数模型"；嵌入生成批量化（约 20 分钟窗口聚合而非流式直灌）、特征计数批量写库（点赞数从 100 到 105 不值得毫秒级写库，十分钟合一次写）；推理侧做共享上下文批量（shared context batching）与定制注意力核——直接优化到 CUDA kernel 级别，由基础设施团队完成。

模型选择上同样分层：自有数据中心 GPU 集群上跑在 LinkedIn 数据上微调过的模型，比通用前沿模型更省更准（"为 Feed 排序用通用大模型是浪费"）；前沿模型留给对"接近人类智能"要求最高的策略评测，且只对抽样数据打分。（`00:22:09–00:25:09`，`00:27:18–00:29:05`）

### 踩坑：数值信号被当纯文本，上下文压缩无捷径

一个值得所有 LLM 应用者记住的坑：结构化数值（如文章热度计数）直接以纯文本进上下文，模型完全意识不到这是流行度信号。早期前沿模型数学也弱，通用做法是 RAG 挂计算器，但 Feed 的在线打分毫秒级完成、没有 RAG 的预算，于是他们保留传统计数系统并行计算热度与传播速度，再作为特征与序列模型交互。更大的长期工程是上下文压缩：成员画像、兴趣、最近几个会话的阅读、条目作者、正文、图像描述——什么都塞进去系统就爆了，要"压缩到最小但不损失精度"，连序列怎么采样、哪些条目更重要，都有一个整编 pod 专职研究。他给 agentic 系统的可靠性算了一笔直觉账：如果每个环节 99.5% 可靠，一个 20 步的工作流"端到端基本不可用"——误差跨步复利，所以必须用流行度信号、上下文与策略迭代持续为系统接地。（`00:30:11–00:35:13`）

### 负责任 AI 与剩下的老手艺

负责 AI 在他的描述里落在具体机制上：排序只用职业信号与互动行为，不用敏感人口属性；每个上线的 Feed 模型定期用统计检查审计不同受众与创作者的分布公平性；对低质、非原创内容与自动化脚本（浏览器扩展、第三方自动评论——违反服务条款）检测、限流，屡犯者可能封号。生态里还有一重天然护栏：1 亿认证会员，看到认证作者的内容时可信度天然更高。

他留给听众的职业判断是：agentic 工具不认识团队边界和仓库边界，职能的墙在融化——最有效的人能横跨语境把全局拼起来，基建专家也必须懂模型；决策变快之后，瓶颈变成"你能否自己拍板并立刻把它变成代码"。主持人的收束是：好奇心与批判性思维是关键，"等着被派活"在这个新世界里行不通。（`00:39:51–00:45:18`）
