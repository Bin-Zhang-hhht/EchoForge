## 速读

向量搜索已成 RAG 管线的标配，但生产系统对相关性的要求正在暴露"单一相似度分数"的天花板。Vespa 工程师 Radu George 在这期访谈里给出完整论证：混合检索仍胜过纯嵌入、整本书压成一个向量必然有损、两段式重排的瓶颈是效率；而 Vespa 的答案是张量检索——把所有数值信号统一成可快速运算的张量，让 ColPali 这类新技术"第一天就能支持"。

## 主题正文

### 从 Elastic 顾问到 Vespa：两种工程文化的碰撞

Radu George 的履历在检索圈很典型：在杀毒软件公司做日志集中化时接触 Elasticsearch,随后做了近 12 年 Elasticsearch、Solr、OpenSearch 的咨询与培训；加入 Vespa 更多是出于好奇——它不基于 Lucene,内部分布式模型与取舍都不同（`00:01:56–00:02:47`）。Vespa 的基因要追溯到被雅虎收编前的挪威搜索公司 FAST（Fast Search and Transfer,递归缩写），一直在做大规模网络搜索；今天它仍在服务雅虎内部大量大小不一的垂直场景（`00:02:48–00:04:05`）。这段历史解释了 Vespa 的"过度工程"倾向——张量就是最好的例子：不只支持向量和距离函数，而是在各种数值结构上支持各种数学，新用例来了直接组合现成能力（`00:04:18–00:05:31`）。他也坦承文化冲击：做咨询时习惯就事论事，在 Vespa 提方案时同事会先问"三个月后会不会推倒重来？能不能泛化？这个规模撑得住吗？"（`00:05:07–00:05:31`）。

### 向量相似度只是一路信号

"向量搜索到极限了"听上去大胆，他的论证却很朴素：人们要的是相关性，而向量距离只是其中一路信号——文档新不新鲜、词面匹配如何、哪个块更相关、取最高块还是前 10 块的平均、叠加什么业务规则——实践中大家最终都会堆出一套复杂的相关性算法。"向量相似度本身没有错，只是不够"；传统向量数据库其实也都在往上加东西（`00:06:25–00:07:39`）。

词面检索是最典型的例子。检索圈一直有"BM25 永不死"的梗：Vespa 近期的博客测评了大批嵌入模型——大多数模型的"开箱版本"确实胜过"开箱的 BM25",但现实中没人用开箱版本，大家两边都会调；而把 BM25 与嵌入模型混合的混合检索，又稳定胜过任何单一嵌入模型。结论：词面信号被一遍遍证明会一直存在（`00:07:53–00:09:03`）。另一个极限是长文本：一篇博客、一本书的含义塞进一个向量必然有损——向量维度有限，文本越长压缩越狠、丢失越多，这也是切块和块间组合存在的理由（`00:09:03–00:12:37`）。

### 向量化丢掉了什么：阈值与分面

把文档变成向量的代价还有精确过滤。词面检索的截止点相对直观——Lucene 系常用 minimum match:"三个词全中、十个词中七个就算合格"；而余弦相似度 0.7 算"相关"吗？这个分界随查询漂移，你很难说清阈值意味着什么。更麻烦的是分面统计（faceting）:没有人为截止点，向量搜索会匹配一切，结果集分析无从谈起（`00:09:57–00:11:14`）。

多模态让有损压缩问题更尖锐。PDF 的常见做法是逐页甚至逐块向量化——以 ColPali 为代表的模型把页面图像切成若干 patch、每个 patch 一个向量，文本查询与它们在同一向量空间，因此可以做"七月能耗在哪"这类图表定位（`00:14:26–00:16:16`）。

### 张量检索：把新技術变成"第一天就支持"

Vespa 对以上所有问题的答案是张量。向量是数字列表（浮点，可量化到 16 位整数甚至比特）；张量更灵活：可以是标量、数组、带命名维度的映射（比如 ColPali 的 patch ID 到向量的 map）、也可以是稀疏张量（把"黑裤子、蓝 T 恤"的偏好强度存成命名维度的权重）。在张量上可以做相似度搜索、用点积做个性化、对 ColPali 的 patch 向量做 maxSim,以及求和、取最大值等各种数学（`00:16:46–00:18:26`）。

这种通用性的回报是"新技术的落地速度"。ColPali 出现时，Vespa 只是把 patch 向量建模成张量、用张量数学实现 maxSim,"管道早就有了，写对表达式就行"；Bayesian BM25 这项把 BM25 分数归一化到 0–1 的新技术到来时，团队发现秩配置（rank profile）里连 sigmoid 都现成——"连论文作者都觉得意外"（`00:19:15–00:20:38`）。工程接口也齐备：在 schema 里定义张量的形状与类型，查询时构造查询张量，再用 rank profile 表达"文档分数怎么算"——点积、相似度平均、前 N 个向量的平均，想得到的数学基本都在（`00:20:40–00:22:05`）。

至于"我怎么知道该用哪个相关性函数"，他的答案很工程师：从词面检索起步，找到适合数据的嵌入模型，再逐步加入业务信号和元数据，全程用黄金评测集（golden set）盯着质量涨跌（`00:22:06–00:22:51`）。张量的学习曲线他也不讳言——"我的数学止步高中也能看懂"——配套有张量别名（x*y 即点积）、Tensor Playground 在线实验场、每年 12 月的"张量降临挑战"（用张量算圣诞老人要打包多少礼物），以及 GitHub 上可以拿来改的 sample-apps 仓库（`00:23:33–00:25:17`）。命名维度的价值在真实场景里最直观：汽车搜索把"昂贵、保险便宜、油耗、车龄"等属性做成张量，与用户偏好做点积即可——比跨字段取值再用脚本（如 Elasticsearch 的 painless）计算快得多；"其他引擎能力上也有，但在你的规模上用不起"，而张量运算快到可以在超大规模上真用（`00:25:31–00:27:39`）。

### 把计算搬到数据旁边，以及智能体的误差复合

Vespa 的架构哲学是"数据移动贵，让计算去数据所在的地方"。两层体现：第一阶段对全部文档的计算挪到外部根本不可行；第二阶段重排同样发生在内容节点上——可以跑 LightGBM 树模型或 ONNX 模型，把相似度、BM25、时效性等多路信号合成一个分数；只有更小的头部集合才会被送到无状态层做全局重排，那里可以上更大、可跑 GPU 的模型（`00:27:52–00:30:02`）。

对智能体时代"向量检索还重要吗"的追问，他的回答是：对智能体来说这只是"一次搜索"，但底层质量更重要——智能体会连续搜索多次，单次 90% 的准确率连做十次就按 0.9 的十次方衰减；而且模型拿到糟糕的检索结果会幻觉得更厉害，上下文越长注意力越稀释（context rot）,"它们会注意到你不想让它们注意的东西"（`00:30:02–00:31:51`）。

数据更新方面，Vespa 选择真·实时：更新确认返回的那一刻即可被搜索，代价是放弃其他引擎的提交缓冲；内存属性（价格、库存）改动极快，磁盘持久化、预写日志、多副本复制一应俱全，所有副本确认后才向客户端应答；批量更新用 HTTP/2 逐条发送、逐条确认（`00:31:53–00:34:37`）。

### 五年后：多模态、实时探索与十五年未解的黄金集

对未来他出言谨慎——短期工作太多，看不远。但有几件事可以确定：多模态检索会越来越重要；实时探索数据会变得重要——智能体不会满足于 top-k,它们想看结果集里"还有什么"，而这又绕回"相关与不相关的边界在哪"这个老问题。还有些问题从他入行前就在、现在依然无解：怎么得到好的黄金评测集、怎么有效度量搜索质量、怎么在不破坏其他指标的前提下提升相关性。他点破了其中的鸡生蛋困境：学术界的 SOTA 之所以可信，是因为有公认基准；而从零起步的电商或图书搜索，既没有黄金集，造出来也不知道它好不好。编码领域反而幸运——issue 跟踪器和历史代码就是天然的基准矿藏；而"好坏"远比单元测试主观的领域，黄金集既难造、更难验证（`00:34:38–00:38:16`）。
