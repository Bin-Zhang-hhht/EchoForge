## 速读

VS Code 工程负责人 Kai Maetzel 解释编辑器如何从补全走向前台、后台与云端 Agent，并拆解上下文装配、工具安全和人工审查的真实约束。适合做 AI 编程工具、开发者体验、Agent 平台和工程治理的读者：重点不是“IDE 会不会消失”，而是不同自主程度的工作怎样共存，以及团队如何判断什么已可交给 Agent、什么仍必须由人掌握。

访谈发生在产品高速变化期，Maetzel 同时谈到现有功能、内部实验、界面 mockup 和未来设想。本文按这四类分别呈现，不把录制时的计划写成后来已经发布，也不采用口径不明的内部指标或说明性数字。

## 主题正文

### 好的补全不只要生成正确，还要知道何时闭嘴

Maetzel 回顾，VS Code 在轻量编辑器与完整 IDE 之间找到定位后，AI 最先沿 IntelliSense 和补全路径进入产品。早期多行补全要求开发者一次审阅更多代码，容易打断输入节奏；团队因而转向更短的 ghost text。ChatGPT 出现后，团队通过内部 hackathon 得出另一个判断：AI 不应只是侧边栏里的附加对话，而要进入编辑器核心交互。（`00:01:25–00:09:39`）

补全的难题也不只是模型质量。展示得太少会错过帮助机会，展示得太多又会增加干扰；同一名开发者在熟悉的 TypeScript 仓库和陌生的 Rust 项目里，所需主动程度可能完全不同。团队会同时观察接受、明确拒绝和烦扰信号，并用小范围实验调整触发。节目中的比例来自未说明口径的内部观察，不能外推为行业基准；可迁移的结论是把“是否展示”和“展示多少”当成独立于生成正确率的产品问题。（`00:09:39–00:15:44`）

### Ask、Edit 与 Agent 对应不同的控制权和等待方式

传统编辑器交互追求即时反馈，而 AI 对话或 Agent 可能需要更久。Maetzel 认为，用户愿意等待的前提不是延迟消失，而是最终节省更多时间，并且等待期间仍有合适的控制和反馈。VS Code 因而提供或试验不同模式：有的用于提问和探索，有的执行范围明确的编辑，有的让 Agent 自主调用工具，还有的先规划再实施。（`00:15:44–00:21:04`）

这不是单一能力阶梯。开发者可以先用快速模型交互研究，再把边界清楚的任务交给后台；也可以让能力更强但更慢的模型规划，再用更快的模型实施。不同模式在响应速度、自主性、可操控性与审阅成本之间交换，产品不能只用“能解决多少任务”概括体验。（`00:17:42–00:21:04`）

### Agent 框架的核心资产是工具、指令和停止条件

Maetzel 将 Agent 循环概括为工具、工具说明、附加指令和停止条件。仓库指令可以补充项目约束，自定义 Agent 也可以限制可用工具；他举例说，若没有明确约束，模型可能为了让测试通过而改动断言，而不是修复实现。这个例子说明上下文不仅提供知识，也界定什么动作被视为成功。（`00:21:04–00:26:41`）

评估同样不能只看 SWE-bench 等任务是否解决。团队还会关注耗时、工具调用数、token 消耗以及 Agent 是否采用符合 IDE 工作方式的工具。不同模型家族可能需要不同主提示；大量 MCP 工具也不宜一次全部塞进上下文，VS Code 会把工具分组并按需展开，在可发现性、提示长度和缓存利用之间权衡。（`00:26:41–00:35:11`）

这里有一条重要边界：录制时，一些更细的模型专属工具说明仍是计划，不应视为已发布功能。更稳妥的工程原则是承认模型行为和工具接口存在耦合，并用自己的任务、成本和交互指标持续验证。

### 前台、后台与云端 Agent 需要不同的工具面

前台 Agent 能利用当前编辑器状态、选择区、终端、任务和差异快照，适合短小、需要即时指导的改动。后台 Agent 若随意操作界面，会干扰用户正在进行的工作，因此应减少 UI 工具、在隔离环境中执行边界清楚的任务；云端 Agent 还依赖容器能否构建、测试并重现项目环境。（`00:35:11–00:43:10`）

Maetzel 的产品判断是，模型选择通常比多暴露几个 IDE 工具更影响结果，额外工具更多改善用户体验。这不是跨模型基准。对历史悠久的 VS Code 代码库，团队还要区分不可随意改动的核心抽象和可以放手生成的外围工具，并以测试、仓库说明和代码审查表达这些边界。（`00:40:40–00:49:44`）

后台任务完成后如何让人形成“待审阅意识”仍是交互难点。标题栏提示在访谈中只是 mockup，外部通知也只是备选；不能把它们写成已交付功能。这一问题提示，异步执行的产品价值取决于结果能否被发现、理解和及时审阅，而不只取决于 Agent 是否跑完。

### MCP 扩大能力面，也把不可信内容带进上下文

Maetzel 认为 MCP 当前最常用的价值是工具调用，但工具能力增加也放大了输入与授权风险。外部网页、文档或远程 MCP 返回内容进入模型上下文后，可能包含提示注入或错误信息；即使用户批准了某项工具，工具的输出仍不能自动被视为可信。（`00:49:44–00:55:48`）

VS Code 提供按单次、会话或命令模式审批工具的机制，但逐项审批在 Agent 和任务数量增加后很难扩展。容器或虚拟机能够限制执行环境，却不能消除外部输入、安装命令、授权数据和输出通道的风险。节目以 Context7 作假设说明，并明确不是在指控其存在具体漏洞；可迁移的结论是同时治理执行权限和信息来源，而不是把沙箱等同于完整安全方案。（`00:53:10–00:58:40`）

### 当生成扩张后，人的理解和审查会成为系统约束

对跨仓库、跨部署的纵向功能，Maetzel 预计主 Agent 会委派其他 Agent，并把进度写入 issue、变更跟踪或规划板，而不是只留下一个 Markdown 报告。这属于未来协作设想，不是微软产品承诺。它真正指出的问题是：并行执行会增加待解释的状态和结果，团队需要共享的工作记录与责任边界。（`00:58:40–01:03:24`）

他把人的理解和审查能力视为潜在瓶颈，但这一判断有明确前提：Agent 生成的代码首先要达到足够质量。移动端更适合启动任务而不是深度审查，语音、绘图和大屏多模态协作也只是他对未来交互的个人判断。无论界面如何变化，开发工具仍要帮助人理解计划、检查差异、验证结果并承担最终责任。（`01:03:24–01:06:46`）
