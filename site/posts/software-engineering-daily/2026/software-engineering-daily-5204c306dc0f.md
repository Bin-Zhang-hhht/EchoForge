## 速读

Software Engineering Daily 邀请 Metalab 工程副总裁 Wesley Yu（本期主持人为开源开发者 Josh Goldberg，TypeScript ESLint 维护者）。Metalab 是服务过 Apple、Slack、Uber、Instacart 的设计+工程工作室。这期谈的是设计工作室如何把"人们喜爱的软件"落到实处：为客户选"最无聊、最稳定的技术"，愿意交付"丑陋的应用"以跑通迭代，以及设计-工程协作的核心产物"服务蓝图"。

对独立开发者与产品团队最有用的是三条：技术栈决策本质是招聘、入职与"凌晨 2 点谁来支持"的计划；端到端先看全貌比逐块完美更容易调整；以及 AI 时代"人工痕迹（human touch）将越来越重要"——AI 生成的内容有同质性，人很快能识别，价值随之下降。文中欧洲技术栈偏好的观察受访者自述是轶事性的。

## 主题正文

### 从 Neopets 到 Metalab：沟通背景的价值

Wesley 的编程起点是 1999/2000 年代初玩浏览器游戏 Neopets，通过改 HTML/CSS 定制虚拟店铺入门，纯试错；大学学的是商业与媒体研究而非软件工程。首份工作是电台新闻制作人，约 2010 年代进入科技业，2013 年随一家 Y Combinator 创业公司搬去 Sunnyvale；后来上编码训练营学 Ruby on Rails，以实习身份进入 Metalab，在 Slack、Coinbase、Instacart、Uber 等客户项目中"学到行业本事"。他自认沟通背景（把复杂概念讲给外行）在 agency 尤其有价值。（`00:02:03–00:06:24`）

Metalab 的定位是"为非常有雄心的公司设计并构建数字产品"，帮早期团队定义产品 DNA；与 in-house 的差异是：in-house 优化已取得市场牵引的业务，agency 早期是定义业务、寻找市场。Slack 案例很有代表性：当年业内都用 HipChat，Slack 来找 Metalab 做定位与品牌以区别于普通聊天应用，重点是 UI/UX 的 look and feel。"feel"的工程含义包括响应速度与从用户交互中读出的意图（悬停频道时后端预加载内容、切换时闪电般快），设计侧则指 Slackbot 这类"业务价值很小但带来快乐"的功能。来找 Metalab 的客户本就重视设计与体验、形成自我选择，而不是被说服的；反而常常需要 Metalab 说服客户放弃一些 delight 功能——"加入一个愉悦功能 = 省略某个功能功能"是权衡，要先保核心功能。（`00:06:24–00:10:43`）

### 技术栈方法论：无聊、稳定、按客户能力决策

Wesley 的核心判断：在 agency 干得越久，越倾向为客户选最无聊、最稳定的技术。早年在 Metalab（2010s 仍是 Rails 店）追逐过 CoffeeScript、Knockout.js、Ember、Backbone、React、GraphQL + Relay。决策树按"客户能力 → 产品需求"顺序：客户团队已具备什么技能、在本地能否招到人；团队成员还把这套做成了 CLI 工具（对话式问答后生成技术栈和样板代码）。地理因素上，欧洲客户通常要求 Java 系后端（Spring/Spring Boot），因为当地大学产出这类人才——他自述这是轶事性观察。非技术因素上，技术栈决策本质是招聘计划、入职计划，以及"凌晨 2 点谁来支持"的问题。产品维度：如果速度上线是主要关切就考虑跨平台工具，当性能仍是产品核心则 native 仍然胜出（跨平台买的是日历时间）。他明确表示喜欢 Expo，是核心技术栈的一部分。新技术"除非客户强烈主张，否则很少选"，偏好模块化单体做 MVP，新东西放进侧车（如实时 WebSocket 用 Elixir/Phoenix）——隔离、可更换、把风险集中在小范围。（`00:10:43–00:16:03`）

### 工程领导：管线匹配与项目串链

VP 层面主要看客户管线，把现有技能与行业专长跟进线客户匹配；刻意把同技术栈（如 React Native）或同行业的项目连着排给同一批人，以积累效率。行业专长的理由：医疗行业 EHR 系统数量有限且偏好固定；如同换掉 Rails 再回来会忘掉框架细节，跨行业一年回来会失去"哪里有边缘、有哪些解决方案"的直觉反射。（`00:16:03–00:18:31`）

### 迭代与"丑陋的应用"

Metalab 做大量 V1/MVP，好技能是愿意交付"丑陋的 app"：先把完整流程跑通，中间屏幕可能只渲染 JSON 加一个按钮，再与设计迭代"如何呈现这些数据"。很多开发者执着于完美、想呈现最好的自己，"这是必须跨过的一道坎"。客户其实欣赏丑陋 app，但需要提前准备（sprint demo 时问"屏幕上方括号是什么"）；只展示最终成品，客户得不到"教育的价值"、不理解背后的工作量，打开帘幕展示过程本身是 Metalab 的价值。端到端先看到全貌更容易看出初始方案的缺口、更容易调整下一步；"逐块做到完美再拼起来"会留很少的调整空间。裁剪类比：迭代像垂坠裁剪（把布料挂上身体再按垂感调整），瀑布式像先剪裁纸样再切布。（`00:18:31–00:22:39`）

### 项目"家长心态"与交接

Metalab 规定开发者一次只做一个项目以保证全身心投入，很快会对作品产生强烈依恋。交接回客户团队时很煎熬——面试接手人像"为孩子找最好的寄养父母"，价值观要合；接手者改动时会"心碎"，因为每个人的偏见与使用习惯不同，很难用文档传达全部决策过程。他们避免"冷交接"（不知道谁会维护、只能靠代码注释与文档），偏好让接手人一起跑 3-4 个 sprint、参与 PR 评审和技术决策，做"热/温交接"；并建议客户尽早招聘未来维护者。（`00:22:40–00:26:36`）

### 服务蓝图：设计-工程协作的核心产物

设计-开发协作的核心 artifact 是 service blueprint（服务蓝图）：列出从用户首次认证/建号到价值链末端的所有用户动作、后端动作、后台事务。项目早期先对齐核心体验、大节拍、如何被技术支撑、驱动它们的用户意图；有时在客户签约前做估算时就先草拟。他用电视制作季类比：编剧先定整季大节拍（无对话、只定事件序列）再写各集，设计与工程团队因有结构而各自知道去向。他也提醒类比不一定一一对应，"硬套会弄砸"。（`00:26:36–00:29:31`）

### 美与实现成本、触觉体验

一个"美到要 3 年才能实现"的例子：为收藏品应用，设计师想要"翻卡册"的体验，React Native 开发者说不知道怎么做；解决靠紧邻协作加迭代——开发者给约束，设计师再推边界，最终落在"设计师脑中极致体验"与"开发者默认实现"之间。电子化时每个交互要有"物理反应"，要把物理性重新建回体验里（如开包亮卡片的视觉刺激）；但对 haptics 他有保留：试过触觉反馈，"开包时手机振动、灯灭"会出戏——"我的手机在振？跟这个应用有什么关系"，所以更依赖视觉。这是对"曾有一段时期每个 app 交互都振动"潮流的温和反对。（`00:31:35–00:34:45`）

### AI 时代的设计与工程：人工痕迹的价值

Wesley 看好设计师用代码做原型：Figma 的画布"只能走到一定距离"，要点/点击界面才懂 ergonomics；正在建设脚手架让设计师能提交真实代码，开发者仍做评审，"设计师也去让 Claude Code 生成 PR"。但他强调前端开发者的工作会存在：重要的不只是 prompt 出来上生产，而是出问题时代码库要可审查、可检查、可改；目录结构、清晰边界、基础架构仍依赖开发者多年经验，"我个人不认为有失业风险"，只是协作媒介从 Figma 转向代码。（`00:34:45–00:36:52`）

设计师的护城河判断最有观点：Claude Design、Figma MCP 等工具产出的东西有同质性，人是"模式识别机器"，很快能看出哪些是 AI 生成的；一旦消费者能识别，价值就大幅下降。"这是人做的、AI 绝不会这么做、有瑕疵、从没见过"——人工痕迹将越来越重要。但他被问"是否有刻意不完美/有瑕疵的设计实例"时坦承"没有具体例子可指"，只是"直觉上觉得"高付出、非量产的东西价值更高，瑕疵是手工制作的标记。（`00:37:07–00:38:47`）

### 未来 5-10 年：前沿构建与人性化

在前沿构建很难：投入大、风险高，花大量时间做的定制东西常因行业标准化而废弃。例子是 LLM 的 eval 框架——现在会直接用 LangChain/Langfuse 而不再自研；MCP 刚发布时自建了大量 Notion、Figma 定制 MCP，后来官方 MCP 出现且更好，基本弃用自研。职责因此是判断"该投资什么、该等行业替我们解决什么"。他用日本面包店类比：烘焙店用视觉模型识别托盘上的糕点自动计价，店员岗位转为纯人际服务；Wesley 想复刻这种"自动化非人事务、把人力留给与人对话"的做法——写规格、文档、会议纪要用工具转成 tickets 进 Linear。主持人复述确认："用 LLM/agent 减少生活中的机械感、腾出时间关注重要的事"，他确认"没错，清理跑业务的杂事，把真正好玩的事（和人协作）浮出来"。（`00:38:47–00:42:21`）

结尾的彩蛋部分他把魔术与写代码相通：魔术是用没人会想到你付出那么多努力的手段做出看似不可能的效果（如 book test 把书每一页做标记），"把全部努力投进一个让人愉悦的微小瞬间，而观众看不到背后的生产过程"。（`00:43:03–00:46:11`）
