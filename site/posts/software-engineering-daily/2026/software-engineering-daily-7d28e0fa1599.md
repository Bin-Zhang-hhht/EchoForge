## 速读

这期访谈适合正在为 agent 系统设计数据接入的工程师、数据平台负责人，以及被"RAG 结果不稳定"困扰的团队。嘉宾 Jörg Schad 是 Pinecone 工程副总裁，与主持人 Kevin Ball 讨论 Nexus 背后的模式：与其让 agent 在每次查询时临时检索、临时整理，不如把上下文当作像数据库物化视图一样预先计算、带版本的一等资产，让它自带 schema、元数据、权限和血缘。

最值得关注的三点：一是把可复现性和审计作为预计算上下文的核心收益，而不只是省 token；二是面向 agent 的回答应是"数据加元数据"的组合，低置信度信息对会规划的 agent 仍有价值；三是嘉宾坦率划定了边界——从约束违反中自动学习整理策略目前仍是设想，他估计标准化至少还需要两年。Nexus 发布约两个月，许多判断属于早期经验而非定论。

## 主题正文

### 从"每次查询都检索"到预计算上下文

Schad 先回顾了检索的演进：RAG 的价值在于让 LLM 结合企业自有数据，向量数据库带来稠密检索、稀疏检索，再叠加全文检索，最后形成 agent 可以反复调用的检索系统。但他指出，实践中 agent 拿到检索结果后还要做类似 ETL 的整理，而且这些工作在每次查询时都被重复执行。

Nexus 的思路是借用数据库的物化视图：把上下文预先整理、编译成一个带版本的产物。这样做的直接收益有三层。第一，上下文成为系统的一等公民，可以施加权限、可以共享；第二，结果更可复现——RAG 在查询时现场检索，而 LLM 和 agent 本质上是概率系统，"去年收入是多少"这类问题需要的是跨时间一致的答案；第三，产物自带血缘，能说清它是用哪天下午两点的数据集生成的、为什么包含这些内容。他回忆过去为排查生产问题在特征存储上重建血缘的经历，认为这种可追溯性对可观测和治理是重要资产。需要说明的是，Schad 的背景是数据库系统，他自己在节目中多次提醒听众他在反复使用数据库类比。（`00:04:38–00:10:37`）

### 把上下文当一等公民：权限、分层与元数据

作为一等实体，上下文可以分层组织：个人的、部门共享的（如整个财务团队）、公司级的，再按任务组装成一组相关上下文。权限也进入画面——可以为敏感财务数据建一个只含月度聚合的物化视图，让 agent 只能通过这个接口访问。

元数据部分谈得最具体的是新鲜度与语义层。Schad 建议，上下文的描述不应只是一段长字符串，而可以是结构化描述：里面有什么、新鲜度如何、血缘是什么；与 MCP 工具的静态描述不同，上下文描述可以随版本动态更新。他举了一个例子：想查最新销售数字，而上下文元数据显示两周没更新，LLM 就能据此判断不宜使用。他还认为 LLM 本身是好的规划者，只要不给太多工具、必要时辅以渐进式工具发现，就能选对信息源。（`00:11:16–00:14:09`，`00:16:12–00:18:03`）

### 制作与质量：spec、版本化与评测集

制作流程分两种模式：不知道问题是什么时，做通用上下文——分析数据集、识别关键实体、建立带固定 schema 的结构化视图；已知问题域（例如邮件或预估的问题）时，整理可以更聚焦。执行上是两步：先决定"怎么整理"并把这一步本身版本化——早期它就是一个 Python 程序，如今多由模型生成；再执行编译得到上下文产物。因为数据集几乎都是动态的，版本化让整理策略可以随数据演进迭代，旧版本也能帮助 agent 生成新的整理工具，理想情况下还能产出评测集。

质量维护上，Schad 给出的路径是：先有规格说明，再从规格生成代码；对通用场景尽量寻找真值，对已知问题则用少量真实问题样例生成更大的评测数据集，持续迭代，并确保数据集更新后结论仍成立。质量资产应与上下文一起存放在系统层面，供财务、市场等不同消费方共用。

他同时坦率划出边界：约束表达可以借鉴知识图谱世界（RDF 把 schema 层与事实层分离，SHACL 等可表达约束），例如"会议参会人数不能为负"；发现数据集冲突时先标记、由人介入，长远看希望系统能从约束违反中学会应对滞后数据源。但他明确说明这部分是展望，"目前还不知道有任何系统在这样做"。（`00:18:15–00:20:42`，`00:25:00–00:28:12`）

### 面向 agent 的暴露：数据加元数据的组合回答

这一段是全期最有操作性的讨论。Schad 认为 agent 与人类用户的关键差异在于迭代能力：人和仪表盘发出一次查询、拿一个结果就走；agent 拿到"答案是五，但我只有 5% 的置信度"这样的元信息，可以调整下一步计划，比如改问"哪些事实的置信度高于阈值"。由此出现两种立场：治理视角下，低于 50% 置信的内容根本不该给到 agent；信任 agent 的视角下，则应尽量多给，让低置信度元信息参与规划。

接口层面，Nexus 提供把结构化查询与元数据组合的方式（逐字稿中记作 NoQL）：agent 可以在查询里声明输出 schema，例如要求以美元计价而非欧元；响应侧除了表格结构，还自动执行约束校验，例如价格字段应为低于一万的正数。他强调 agent 交互不是一次性的，数据与元数据成对返回才能让双方持续对齐；代价是循环的 token 开销，而预计算上下文的作用正是把昂贵的发现循环前置成一次性的整理。（`00:30:07–00:36:09`）

### 边界与展望：抽象层次与标准化节奏

Kevin Ball 把讨论引向工程方法论：LLM 擅长线性描述的任务，嵌套的子循环既贵又不可靠；Schad 用软件工程的组合性作比——把整理做成独立子过程，如同抽出公共函数，接口稳定、内部可替换，他还提醒这类抽象不能做过头。

关于证据与引用，Schad 确认上下文始终保留指向原始文档的指针，并建议在上下文不大的情况下把原文一并取回——这与传统检索"先找相似向量、再取原文"的模式一脉相承，只是结构化表示降低了取原文的必要性。他展望的另一个方向是持续整理：夜间空闲的 GPU 算力可以回头修正知识图——收缩、扩展、用图机器学习发现新连接、按问题流做贝叶斯更新——即使初始数据没变。

对于这层能力应独立成层还是垂直整合，他的判断是：Pinecone 目前受益于端到端拥有全栈，新鲜度元数据不必重复维护、治理更容易；抽象层会出现多种方案，标准大概率先在查询与响应格式上形成，而血缘最难穿过通用抽象，"至少再给两年迭代"才谈得上通用规范。作为参照，Nexus 发布约两个月，用例已经在反过来塑造内部实现。（`00:43:15–00:45:42`，`00:48:19–00:50:14`）
