## 速读

Chroma CTO Hammad Bashir 与主持人 Gregor Vand 长谈一场：检索正在从"一次向量搜索、塞进上下文"的 RAG，变成 Agent 以机器速度发起多轮并行查询的 agentic search，检索基础设施被迫重造。Chroma 从给计算机视觉模型挑训练数据的主动学习起家，因为市面检索系统都不适配 AI 负载而自建了 ChromaDB，如今产品栈是数据库、sync 数据管道加 Context-1 检索模型三件套。

最值得带走的三点：Context Rot 论文用极简实验证实上下文利用率越高模型越钝，且三代模型迭代后依然存在；20B 的 Context-1 不靠压缩上下文，而是训练模型随手删掉自己上下文里的无关内容（prune 准确率从 80% 练到 97–98%），以 400–500 tokens/s 对标前沿模型的检索质量、低一个量级的成本；Chroma 把数据库整个建在对象存储上，恰好接住了 Agent 每一两秒五六路并行的查询洪流。

## 主题正文

### 从"给视觉模型挑数据"到 ChromaDB：为 AI 负载重造检索

Hammad 在湾区做了近十年软件工程师，方向横跨机器学习、计算机视觉和数据系统。Chroma 的起点不是数据库，而是计算机视觉的主动学习：线上模型每天看大量数据，全标注成本高到不可行，所以要先选出"哪些数据值得标注"——这是个训练期的数据策展问题（`00:02:25–00:03:35`）。语言模型兴起后，他们意识到同一个问题换到了推理期：怎么为模型挑选要放进上下文的数据？这就是搜索（`00:02:25–00:06:18`）。

今天的 Chroma 平台由三块组成：核心是 ChromaDB——他称其已是"与语言模型配合使用的最广泛使用的数据库之一"，支持向量、全文、元数据多种检索；其上是 sync，一个托管 ETL 管道，负责把各来源数据清洗、转换成可向量化、补元数据后灌进库——多数开发者不想自建这种高吞吐管道；再加上今年早些时候发布的 Context-1，一个做 agentic search 的模型（`00:03:48–00:06:18`）。所谓 agentic search，是让模型把一个高层查询分解成一组低层查询、读文档、再发查询、迭代到自认为可以下结论为止——像人做研究一样，而不是"谷歌一下看完前十条链接就收工"（`00:03:48–00:06:18`）。

他们最初并不想造数据库：试过市面上的向量检索方案，发现为传统搜索设计的系统都围绕"一个巨型索引"构建，加数据要扩节点、再平衡，运维沉重。AI 应用恰好相反——索引极度分区：每个客户、每个团队、每段聊天记录、每个 Agent 一个索引。向量检索在单一索引里做分区过滤效果很差，正确做法是索引时就硬分区成大量逻辑独立的小索引（`00:06:50–00:10:24`）。让这件事在经济上成立的关键是对象存储：S3、GCS 等相继支持条件写（AWS 到 2024 年才支持；逐字稿把 conditional writes 误写作 "conditional rights"），使他们能在对象存储上直接建库，让"每个客户一个索引"不再烧钱（`00:06:50–00:10:24`）。

Agent 化进一步放大了这套架构的价值：Agent 不只发一个查询，而是五路并行，查询频率也不是人的"最快每 30 秒一次"，而是每 1–2 秒一次，读侧压力剧增。Chroma 的核心架构是无状态计算加共享存储层，可以随意加节点承接读流量——他说这种弹性收益是当年没预料到的意外之喜（`00:10:38–00:11:47`）。

### Context Rot：上下文越满，模型越钝

2025 年 6、7 月间（主持人提及的时间），Chroma 发布了 Context Rot 论文。Hammad 的定位很直白：这是把大家"凭感觉都知道"的退化做成实证研究——随着塞进上下文的 token 越多，模型执行任务的能力如何退化（`00:12:14–00:14:45`）。实验设计刻意极简：比如反复注入同一个词再问模型"这个词在哪里不再出现"，或对 needle-in-a-haystack（大海捞针）任务做各种扰动。结果是在数万 token 处出现急剧掉落；论文发布后模型又迭代了三代，退化依然存在（`00:12:14–00:14:45`）。

主持人提到论文覆盖了 18 个模型，既有 Anthropic 等大厂的也有大量开源权重模型，Hammad 确认属实；当时开源与闭源前沿差距明显，但一年过去差距收窄得很快，个别任务上开源模型甚至反超（`00:14:45–00:16:30`）。他给出的机制解释是：随着干扰信息增多，模型分辨"看起来相关其实无关"的能力下降——两个不矛盾但指向同一事物不同侧面的事实，模型很难消歧。经典例子是问"佐治亚的人口"，文档里同时有国家格鲁吉亚和美国佐治亚州的信息（`00:16:44–00:19:05`）。真实世界处处是这种坑：检索出两个同名同事的文档，把一个人的工作安到另一个人头上；编码 Agent 找认证系统，代码库里恰好有两套，一头扎进错误的那套（`00:16:44–00:19:05`）。

由此他接受了"上下文工程"这个说法：怎么挑选、组织、提示要进上下文的信息，直接决定下一轮成败。而且即便解决了退化，成本也不允许把上下文无限拉大——精细管理上下文本身就是经济学（`00:12:14–00:14:45`）。

### Context-1：把检索拆给一个会自编辑上下文的小模型

Context-1 的定位是"给任何大型推理模型用的通用搜索子代理"：编码 Agent（Codex、Claude Code、Cursor 及各开源 harness）已经普遍会派生子代理干活，Chroma 认为搜索这个窄任务恰恰适合交给小模型——它主要是理解意图、分解查询、判断文档相关性、迭代执行，需要的不是原始智力而是速度（`00:19:30–00:22:08`）。大模型做编排者和规划者、调度一群小模型，是他明确押注的范式，并预期一年内渗透到几乎所有 Agent（`00:21:31–00:22:08`）。

工具设计上，任何 agentic search harness 的标配是两件套：给搜索入口、给抓取入口——"给它谷歌的前十条蓝色链接，再给它点开链接的能力"。Chroma 加的第三件是 prune chunks：让模型回头把自己上下文窗口里的文档删掉（`00:22:26–00:26:37`）。这是对主流"压缩"（compaction）范式的反动——长上下文快满时让模型总结压缩，对小模型来说太容易丢失有价值的信息；自编辑上下文是在 KV cache 一致性和 token 用量之间做交易，而模型本来就要做相关性判断，顺手删掉判断为无关的内容并不额外（`00:22:26–00:26:37`）。训练的难点在于"早期看似无关、后来变关键"的文档，需要足够多样、有扰动的训练案例教会模型何时该删、何时不该删（`00:22:26–00:26:37`）。

数字层面：底座是 GPT-OSS-20B，一个 200 亿参数的开源权重模型。训练前模型删对文档的准确率约 80%——这意味着 prune 工具形同虚设；训练后达到 95% 以上，最新内部 checkpoint 接近 97–98%。因为上下文始终保持在约 32,000 token 界内，prefill 和 decode 都快，反复 prefill 的代价也付得起（`00:22:26–00:26:37`）。他还在探索把延迟本身作为训练目标，让模型自己学出兼顾准确与延迟的删除策略（`00:22:26–00:26:37`）。

为什么 20B 能打平前沿模型？他的核心答案：搜索行为的价值大于推理——搜索是一串很窄的子任务（分解查询、判相关性、决定追问、汇总筛选），可以分阶段课程化训练：先只给一跳两跳的简单题，再逐步加难（`00:27:04–00:30:22`）。训练是 SFT 加强化学习两段式：SFT 用合成数据和从开源权重模型蒸馏的行为，光是把 GPT-OSS-20B 教会并行工具调用（它原生不会），在 RL 之前就带来大幅收益（`00:27:04–00:30:22`）。他也保留边界：更大的模型在稳态下大概率仍更强，世界知识对发查询确实有帮助；但小模型便宜到可以用 LoRA 在窄语料上快速微调，把"语料的地图和词汇"教给它——就像人搜自己的 Google Drive 之所以快，是因为知道里面有什么（`00:27:04–00:30:22`）。

效果口径全部来自厂商：他称对比 Opus 4.6，Context-1 跑在约 400–500 tokens/s，而 Opus 约 40–80 tokens/s，同质量下成本低一个量级、快一个量级（`00:03:48–00:06:18`）；主持人引述 Chroma 的说法，20B 的 Context-1 在其多数自建基准上对标 Opus 4.5、Sonnet 4.5、Gemini 3.1 Pro（`00:26:37–00:27:04`）。这些是厂商自报数字与基准，本文未独立验证。

### 开源与 BYOC：一家基础设施公司的两个"反直觉"决定

Context-1 的权重以 Apache 许可开源。Hammad 给出的理由很务实：开源能最快学到反馈、让更多人集成到他们够不着的地方；模型够小可以本地跑，而 Chroma 起家靠的正是本地版数据库——"在开发者所在的地方与之相会"，让人低成本玩到接近前沿的技术（`00:30:44–00:32:41`）。他也承认未来未必每个模型都开源，但认为 AI 仍处早期，现在不是零和思维的时候；而且他们自己就是开放权重生态的受益者——Context-1 的训练就直接受益于此（`00:30:44–00:32:41`）。

采用路径上，多数人从本地嵌入式版本起步：pip 装个包，Jupyter 笔记本或本地进程里就跑起来了；原型完成后用 CLI 把整理好的知识库推上云端——这类应用确实存在"从 staging 推数据到生产"的真实需求。上云后有两条路：直接用数据库，自己控制分块策略与嵌入模型等细节；或交给 sync，把数据丢进 S3 桶、上传文件或接上 GitHub、网站等来源，自动保持同步。他总结的最佳实践：用 SPLADE 稀疏向量，配一个质量够用但别太大的稠密嵌入模型——不需要很大维度，精度几乎不吃亏，成本低得多（`00:33:32–00:35:33`）。

BYOC（bring your own cloud，主持人语）是另一个容易被低估的决定：Chroma 把代码部署进客户 VPC，拿回可观测性以运营系统，控制面留在自己一侧；客户获得托管服务体验，又不用真去跑基础设施，配好 Terraform 和 Helm chart 即可（`00:37:32–00:41:11`）。他从第一天就主张做 BYOC，因为整个架构都建立在这上面——半年后再想补装是补不上的；代价是开发速度大打牺牲，还要在架构上画一些"当下觉得不自然"的边界（`00:37:32–00:41:11`）。他转述 Databricks CEO 被问"最想改变的两件事"时的回答之一就是不做混合部署模型，但补了一句这可能是幸存者的后见之明（`00:37:32–00:41:11`）。他的建议很直接：除非这是业务增长的核心，否则别做；真要做，"确保你能因此赚到很多钱"；同时承认买家正在主动推动这一部署形态，因为它好过安全与合规审查（`00:37:32–00:41:11`）。

客户对"控制面在你手里"的疑虑，他们的化解方式有三层：存在 Chroma 侧的只有元数据（系统里有什么数据、利用率、版本与 epoch 计数器），不含隐私内容；控制面代码本身开源，可以直接发给客户读 schema 自己判断，甚至用 Slackbot 代理现场遍历代码回答"你们到底存了什么"；数据面默认不开任何端口，一切走反向隧道由数据面主动外连，运维操作也是数据面内的服务拉取待办再执行（`00:41:21–00:44:01`）。他承认这种"拉取式运维"是 BYOC 的组织税——本可以一个 POST 解决的事要绕很多弯，好在基于 Kubernetes 可以复用其声明式机制（`00:41:21–00:44:01`）。

### 终局想象：智能搬进数据库

面向未来，他的判断分三层。第一层，需求恒存：语言模型永远需要有人回答"它此刻该知道什么"——今天即使接上各种 MCP，模型还是常常调不对工具（`00:44:59–00:49:02`）。他反复用的类比是 CPU 与磁盘：语言模型是 CPU，旁边需要一个子系统决定它看到什么、存什么、更新和合并什么——今天它长得像数据库，但 Chroma 真正想建的是那一层；一个数据库公司自研模型，正因为未来"我有数据库、我有智能"会变成"智能跑在数据库里"（`00:44:59–00:49:02`）。

第二层是速度曲线的推论：去年大家还在用 100 tokens/s 的模型，今年 1000 tokens/s 会很常见，几年内 10,000 tokens/s 未必不可想象——到那时，"搜索系统多一次网络调用没关系，反正模型慢"的假设失效。他设想索引直接与 GPU 同址，语言模型不经 CPU、直接在 GPU 上发起子内核就地检索再把数据喂回模型（`00:44:59–00:49:02`）。

Agent 优先也在重塑产品形态：有客户因此让用户不再直接编辑信息，一切编辑都经由模型完成——他们相信模型遍历信息空间、把各处改到位的能力比人更可靠；他预期交互会逐渐摆脱复选框、表单和滑杆，一切交给自然语言与 Agent（`00:35:37–00:36:29`）。

第三层是终局形态：一个能装进任何非结构化数据、又能满足任何查询的系统，"不会长得像 Postgres"，会和今天的东西差别巨大；Chroma 想先把正确的抽象和积木做出来，"争取未来有资格去建那个系统"（`00:44:59–00:49:02`）。对想上手的开发者，答案是 `pip install chromadb`、`chromadb run`，再进阶到 chroma.com（`00:49:18–00:49:25`）。
