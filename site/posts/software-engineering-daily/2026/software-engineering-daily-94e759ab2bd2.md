## 速读

Featureform 被 Redis 收购后，创始人 Simba Khadder 负责公司的 AI 战略。这期访谈给出了 Agent 时代数据层的一张完整地图：为什么朴素 RAG 已经封顶、上下文引擎的四根支柱、物化视图加语义层的架构，以及"记忆其实就是一种新型 ETL"的判断。

最值得带走的三点：Agent 可信无人作业时长已到约 1 小时且每 6 个月翻倍——预训练基本持平、后训练在进步，所以"唯一重要的是上下文"；别让 Agent 直连生产数据库，用物化视图加语义层和检索服务替代；记忆的正确心智模型是异步的提取与压缩——一种特殊的 ETL，而不是一个"万能记忆服务器"。

## 主题正文

### 为什么朴素 RAG 封顶了

Khadder 给出的行业坐标很清晰：两年前你能放心让 Agent 无人监督跑几分钟，现在已经能跑约一小时——Anthropic 的说法是这个数字每 6 个月翻倍。变化不在预训练（模型的内在知识大体持平），而在后训练：模型能"保持连贯更久、推理更长时域的任务并端到端解决"（`00:05:00–00:07:37`）。推论很直接：朴素 RAG——知识库切块、嵌入、把"延误常见原因"塞进上下文——已经到顶，"它不会变得更好，因为瓶颈根本不在模型注意力，而在你能不能持续把相关的东西放到它面前"（`00:06:24–00:07:37`）。他由此提出上下文引擎的四支柱：Agent 能自主导航并检索所需上下文（形式可以是 CLI、MCP，工具只是实现细节）；数据永远最新；检索要快（"如果每个工具调用都是 3 分钟的 Spark 查询，那根本不像个 Agent"）；上下文要随时间变好——这可能是个性化，也可能是记住决策与错误以免重犯。"推理能力每年翻倍的世界里，护城河就是谁能建起上下文护城河——这正是 Anthropic、OpenAI 与其他所有人的差别"（`00:08:30–00:10:26`）。

### 别给 Agent 直连生产库：物化视图与语义层

客服 Agent 是最好的解剖样本。"为什么我的订单晚了？"朴素 RAG 会检索"延误的常见原因"——很糟。正确的做法是让 Agent 去查这张订单、查配送信息、查政策，它们分散在不同系统。于是大问题来了：要不要让 Agent 直连 Postgres 跑查询？Khadder 的回答是一段黑色幽默："为什么生产库没了？""你说得对，别这么干"（`00:11:25–00:12:21`）。业界正在收敛的架构是：用 ETL 同步层（Redis 的 RDI）把系统记录的数据做成物化视图，控制视图里有什么、规定访问规则、不用为海量 Agent 流量扩展一堆原始系统；再在视图上加一个语义层——描述"这些信息是什么"，编译成一组工具、一个 MCP 端点或 CLI。粒度可以做得很细：行级 ACL 加 Agent 层的 RBAC，不同 Agent 看到不同切面（`00:12:20–00:15:08`）。

语义层这个概念以前"在 Redis 上做毫无道理"，现在成立的原因值得玩味：Redis 的数据结构（set、hash、JSON、HyperLogLog、向量）本来就是按人类头脑里的概念组织的，不像"列、主键、外键、级联删除"那套需要推理的东西——以前语义藏在应用代码里（代码自解释数据是什么），现在需要让 Agent 也能看懂，所以语义层显式化了（`00:15:38–00:18:36`）。他把设计思想拆成两个概念的合并：ORM（不是写、而是映射——人和 Agent 都更容易推理）加 GraphQL（Agent 其实会喜欢 GraphQL 那种"自由灰度"来精确取所需，但 GraphQL 服务器撑不住 Agent 的规模、Agent 也写不好 GraphQL 查询）——取两者之神，落在"缓存视图、建语义层、必要时回源系统记录"的上下文引擎（`00:18:53–00:21:06`）。

### 记忆是一种新型 ETL

第四支柱"随时间变好"的机制是访谈最有原创性的部分。Khadder 的判断是：大部分改进不是 Agent 自己写记忆，而是异步发生。类比是 spec 驱动开发——你到处写 markdown、prompt 其实只是指向文件，麻烦在于时间长了要压缩、要保证仍然准确。客服 Agent 同理：学到的东西越攒越多、还会互相冲突，所以需要"一边运行一边提取信息、一边压缩信息"的系统（`00:21:28–00:22:06`）。他的口号是"每个向量数据库其实都是物化视图"——原始文档经切块和嵌入投影出来；记忆也会走同样的路：把对话、决策等原始 trace 做成可调的投影。"我不相信存在一个'万能记忆服务器'，一定会有面向不同用例的不同引擎"。Redis 开源的 Agent Memory Server 的实现方式是让用户定义不同类型的"转换"——本质是 prompt：追踪决策、捕捉季节性、抓取事实、为个性化优化——可自定义（`00:22:06–00:24:50`）。

对"记忆引擎能否自我改进"的追问，他先讲了那个行业笑话：LLM judge 不好怎么办？再叠一个 Agent 去评审 judge，然后一直求导下去？答案是会有"自愈记忆"，但今天的现实是你可以调记忆引擎的旋钮。可控性他用自家槽点举例：用 ChatGPT 筹备婚礼，婚都办完很久它还在说"既然你的婚礼要到了"——"LLM 对时间的处理很糟"。需要的机制是记忆随时间衰减、新记忆与旧记忆冲突时取新、个人/团队/组织分层——而分层马上带来隐私设计问题："Agent 把你的个人偏好记到组织层，全公司都知道你喜欢 Katy Perry 怎么办？"（`00:26:27–00:28:39`）

### 组织如何改变：人人都是 dev，架构 review 同步化

Khadder 观察到的组织变化有两条主线。第一是"人人都会成为开发者"：他现在和 PM 合作时不想读 PRD——"把 PRD 变成原型的时间和读它一样，那就做原型"；_feature happy_（"就一个 prompt，加上这个、加上那个"）成为新风险，品味变得空前重要。他妻子做营销、一行代码没写过，用 Claude 给活动数据建了个带图表的完整网站分享给团队——"这已经不只是边缘案例"（`00:31:27–00:33:13`）。第二是工程流程的重构：团队写大量 spec 并互相评审，每天同步做设计会（他讨厌 standup，站会异步），有人上来讲"这是我在建的系统"，展示接口与验收标准——"接口定义清楚、验收标准写全，我有 98% 的把握 Agent 能把它建出来；如果错了，那是设计问题"。行为测试被提到最高优先级："黄金路径加错误路径、能高确定性证明这个东西端到端该做什么的行为测试，我会亲自每一单都看。如果行为测试是对的且通过了，代码就是对的"——速度、性能这些关切"那就为它们写行为测试"（`00:34:30–00:44:00`）。另一个反转：他一度还用审自己代码的强度去审 Agent 代码，结果 Bugbot 这类工具反复抓到他漏掉的 race condition——"我放弃了，这种东西我不可能把这些线索拼起来"。架构一致性才是 Engineer 剩下的高价值工作：Agent 能一周产出 10 万行代码，乘以团队规模会"被生产力压垮系统"，问题整体下游化了（`00:40:19–00:46:36`）。他给管理者的建议火药味十足：对 AI 的默认答案应该是 yes——"不让工程师用这些工具的公司，你不知道自己落后多远"；同时要分清 agentic 工程与 vibe coding——"demo 可以 vibe，数据库代码不行"（`00:46:36–00:48:00`）。

框架选型上他的标准出奇地朴素：与生态兼容最重要。逆着 MCP 另造一套协议也许更快，但"你唯一要避免的就是在每个东西前面立专有关卡"——标准让任何人都能构想和构建任何 Agent。具体工具里他提到 LangGraph 的 Deep Agents 和 Google 的 ADK；而作为一年没手写代码、自称"100 个 tmux 窗口"的 Vim 党，他提醒工程师别陷入工具焦虑（`00:37:51–00:40:19`）。收尾的判断浓缩了全期："Attention is all you need 把我们带到了这里；但对构建真实产品的人来说，别人的系统会处理 attention，你只需要记住：上下文就是一切"（`00:48:11–00:48:48`）。
