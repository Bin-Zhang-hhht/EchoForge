## 速读

Comet 联合创始人兼 CEO Gideon Mendels 与 Kevin Ball 聊 LLM Agent 的生产化。Comet 从 ML 实验追踪起家，服务 Uber、Netflix、Etsy、Shopify、Autodesk 等 AI 团队，全球约 15 万工程师在用其产品；2024 年 9 月他们为 Agent 时代单独推出了开源的 Opik——评估、优化与可观测平台。

最值得带走的三点：Agent 开发夹在软件工程与 ML 之间——不能字符串匹配断言，还要考虑泛化，大多数团队卡在评估数据集"痛到难以构建"上；提示词优化本质是搜索问题，把失败样本与 trace 喂给 LLM 生成候选提示词再重测，20–30 个样本就够用（LangChain 的结构化输出提示词两轮从 12% 优化到 96%，成本不到一美元）；以及提示词终将被当作"带版本、可回滚、有 SLA 的运维配置"来管理，而不是烤死在仓库里的常量。

## 主题正文

### 从"有数据有算力有聪明人还是做不成"说起

Mendels 的路径是软件工程师转 ML：2016 年在 Google 做语言模型（transformer 之前的前夜），团队做 YouTube 评论区的仇恨言论检测——"有人管那儿叫互联网最糟糕的地方"。他记得当时最深的困惑：有数据、有算力、有聪明人，模型还是做不出来，而这甚至不算难题——问题出在驱动项目的过程本身。他打电话给 Comet 的联合创始人（两人此前一起做过处理数十亿聊天的 NLP 创业公司）："你以前老笑话我把 ML 工作流缝缝补补，我在 Google 看到的还是同一套，只是规模更大。"Comet 因此从实验追踪起步：超参数、数据集版本、结果全都记不下来、协作无从谈起，此后长出数据集版本管理、模型注册表与监控。约两年前客户开始说"这个用例我们不训模型了，直接建在 OpenAI API 上"——相似但足够不同，2024 年 9 月他们为 LLM 应用单独发布了开源的 Opik（`0:02:24`）。

与训模型的对照很能说明问题：训练时代算法基本是商品，你花时间打磨数据集与超参数；LLM API 时代你完全控制不了权重，能玩的只有温度等少数参数——但系统提示词就是你的权重，此外还有工具调用、上下文、向量库、分块策略、工具描述。变量变了，"在变量组合里找最优解"的骨架没变，但日常形态完全不同，所以值得另起一个产品（`0:06:22`）。

### 非确定性：单元测试的类比哪里失效了

对来自传统软件背景的工程师，非确定性最硌人。Mendels 指出其实有好几层：温度设为零"理论上"确定，但实际上主流部署（混合专家）让它并不严格确定——"说到底是矩阵乘法的组合，输入相同本应确定"（`0:08:52`）。更重要的是测试范式的失效：不能对输出做字符串匹配（语义相同、字面完全不同的输出太常见），断言本身成了难题；还要引入 ML 的泛化概念——测试集要有足够的覆盖与方差，才敢说"这个东西是好的"。他的结论被主持人反复引用：Agent 开发夹在软件工程与 ML 中间，"两个范式的经验各取一半，才能把东西发布上线"（`0:08:52`）。

### 评估：不是不知道好，而是数据集痛到建不起来

评估的基本形制不难：一列输入、一列期望输出、一个距离度量（确定性指标如 BLEU 分，或 LLM-as-a-Judge），汇总成分数。投了真功夫的团队"明显在把 Agent 成功跑进生产的那一拨里"。但大多数团队不做，他的论点很直接：构建数据集极其痛苦。第一层是领域知识鸿沟——软件工程师给 HR 团队做工具，他哪知道"在挪威工作两年半的员工年假政策是什么"？第二层是要测"该调哪个工具"就得构建整条图执行上下文，苦工（`0:11:10`）。

Comet 的解法是产品性的而非算法性的：反正你把东西放进生产后总会收到投诉，负责的工程师或 PM 反正要去修——那就把你本来要做的动作变成评估数据集的种子。HR 机器人的例子里，专家用自由文本写一条规则"如果员工在这个国家、司龄如此，应当看这份文件/答案应当是 X"，系统就多了一条带断言的测试样本；下次你改模型、改系统提示词、改工具调用，整套评估自动重跑（`0:11:10`）。分层的建议是：从端到端的系统级测试起步（数据集最容易攒、价值大），再补"该不该调这个工具"的分类式数据集（最常见的失败模式是工具没调对——"工具再完美，调错了照样白搭"），最后才隔离测单个工具或子 Agent（`0:15:35`）。至于类似 TDD 的用法——有 SME 建好的真评估集后，先随手写两句系统提示词、跑测试、按失败样本加工具迭代——他坦承"还很少见到团队这么做，但方向在那"（`0:17:26`）。

### 提示词优化是个搜索问题

Mendels 做了一个行业级类比：神经网络早期人们手工调权重，反向传播出现后回头看不可理喻——"我们现在手动看 trace 找失败步骤，几个月后回头看也会觉得荒唐"。他主张把 Agent 当优化问题看：系统有一组可调变量（系统提示词、工具描述、分块策略、向量库返回条数……），另一端有评估套件的分数，搜索的就是全局最优（`0:19:06`）。路径从暴力枚举（不可行，提示词空间太大）到随机搜索、贝叶斯优化，再到 LLM 进环：把 10 个失败样本连同 trace 交给 LLM，总结共同失败模式、提出新的系统提示词候选，整包重测。斯坦福的 GEPA（逐字稿作 "JEPA"）走进化路线，提出多个候选再合并最优者。最惊人的是样本效率：传统 ML 要几千样本，这些算法"20、30 个样本就能走很远"（`0:22:46`）。

真实案例是 LangChain 的结构化输出兜底提示词（当模型不支持原生 JSON 输出时让它按 schema 返回 JSON）：Comet 用一组 JSON schema 加随机取值的输出构建数据集，原提示词通过率约 12%；跑优化器，两轮迭代到 96%。度量是确定性的（schema 是否匹配），成本"不到一美元，用的还是前沿模型"。PR 提给 LangChain 当天就被合并——对方回复"太感谢了，这事一直很折磨"（`0:25:27`）。

对比的现状是 vibe check："测几个输入，看着不错，上生产。"他认为这正是市面上成功的 Agent 屈指可数的原因。至于成本焦虑：token 单价三年里陡降（他后来给出约每年降九成的口径），评估带来的额外开销在快速贬值（`0:27:31–0:28:13`）。

### 生命周期：从一次性优化到每日重训

今天的现实：客户不每天、不每周、甚至不每月跑优化——花力气建一次评估套件，开发环境里优化几轮到"够好"就上线；而评估套件此后增长缓慢，"这是一切的瓶颈"。他预期的 6–18 个月后会像 ML 团队一样：生产反馈（用户反馈、LLM-as-a-Judge 标记的边缘案例）经人工环节进入评估数据集，每天或每周重优化一次 Agent。核心论据是 ML 的基本等式"更多数据等于更好模型"在 Agent 身上失效了——"你上线那一刻起它就是陈旧的，一个用户还是十亿用户都一样，不做事它不会变好"。把生产数据的环闭上，"天空才是上限"（`0:28:48`）。眼下还没有客户做到全自主的在线闭环，Comet 的优化 SDK 也才发布五六个月——整个品类都是襁褓期（`0:31:00`）。

### 提示词的运维化：配置管理器与蓝图

一个被低估的部署问题是提示词怎么发：多数团队把它烤进仓库的 YAML 或源码，改一行提示词要重新部署整个应用；AB 测试/金丝雀那套框架对一个这么小的组件也太重。Comet 的路线是应用在推理时从平台拉取生产提示词，新候选下次推理即生效——这打开了"生产表现与评估套件表现相互印证"的空间（比如看下游动作：用户到底订没订机票）（`0:31:43`）。主持人给出了精彩的框架：LLM 是台虚拟机，提示词既是代码又是数据——当代码管就要版本控制，当数据管它又有独立生命周期。Mendels 坦承这个问题"没有成熟答案，整个领域才一岁，连最前沿的团队都是边做边想"（`0:34:06–0:35:26`）。MLOps 的历史提供了一个参照：模型二进制当年因 Git LFS 撑不住而没进仓库（虽然"理应住在仓库里"），最终落在模型注册表——对象存储的封装，处理耦合、支持生产热切换，模型团队与部署团队不必互相等待（`0:35:35`）。

一年半摸索后，Comet 的答案是"配置管理器 + 蓝图"：一个蓝图打包十来个相互依赖的提示词与全部影响 Agent 行为的配置（用哪个模型等），SDK 侧以 `Opik.getprompt("名字.latest")` 之类的方式在 invoke 时拉取。产品经理——往往才是 Agent 的实际 owner——可以在 UI 里改配置；版本、回滚、防误操作的流程、对外 SLA 一个不能少。由此才能做夜间优化、Agent 版本的金丝雀发布（`0:37:17–0:39:23`）。路线图上还有两件：让非技术角色也能轻松搭建评估/回归套件（他称之为当前一切的最大阻塞），以及"优化产生新蓝图变体→按流量比例在生产测试"的闭环，全部开源（`0:40:54`）。

### 自由与约束、生成的 UI，以及给同行的四条建议

收尾的展望里有两处值得记录的行业观察。其一，模型与 harness 要分开看：12 月前后的 Claude Code 让所有人感到跳变，KBall 猜"Opus 4.5？"，Mendels 说大概率是，但"Claude Code 作为一个 harness 极其令人印象深刻"——它测过嵌入方案，最终大部分检索靠 grep，而且用得聪明、不撑爆上下文；SWE-bench 之所以不是好基准，正因为它只测模型不测 harness（`0:40:54–0:42:39`）。其二，他观察到一种反直觉的趋势：团队遇到 Agent 瓶颈后的本能是加结构（用户流、按流注入上下文），但方向可能恰恰是"给模型更多自由而非更多约束"；KBall 补充这取决于问题本身——边界清晰的问题适合锁死流水线，开放问题就得让它流（`0:42:39–0:44:00`）。再往后，两人对聊天 Agent 的界面畅想了一会儿：未来的 UI 会不会按需生成、与聊天会话保持同步（数据表这种东西还是按钮筛得好）；生成的 UI 又怎么评估——大概率还是"人类评审对齐 LLM-as-a-Judge"的老路（`0:44:00–0:47:55`）。

给同行的建议有四条。第一，市面有几十上百个 Agent 框架，但他见到的成功者里八成哪个都没用——"最成功的那些基本是原味自酿"，别把月份花在选型上。第二，烦人但有效：先建一个 20 个样本的迷你评估集，"回报巨大"，然后你就可以放心地 vibe code 了。第三，别过早优化成本：token 每年降约九成是行业设计使然，先用前沿模型跑通，再考虑降级到小模型。第四，别被 Twitter 上的叙事压垮——"人人都有上万个 Agent 员工"的段子背后，全行业（包括刚发了数据 Agent 博客的 OpenAI）都在同一条船上（`0:50:20`）。
