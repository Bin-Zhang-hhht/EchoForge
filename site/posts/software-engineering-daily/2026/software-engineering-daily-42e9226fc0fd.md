## 速读

RAG 管线的复杂度（向量库、切块策略、嵌入模型、索引设施）劝退过很多人。Google DeepMind 把一套全托管 RAG 直接做进 Gemini API——File Search 工具，上传文档即可提问。产品经理 Ivan Solovyev 与工程负责人 Animesh Chatterji 在访谈里讲透了他们的反共识判断：质量八成来自嵌入模型而非配置；默认返回约 5 个块就够；重排序和微调大多不值得做；长上下文模型没有杀死 RAG，反而扩大了它的用武之地。

## 主题正文

### 产品哲学：少给你 knobs，把复杂度收走

File Search 是内置于 Gemini API 的托管 RAG：把大量文本、PDF、代码直接上传到 Gemini,就能开始就数据提问。市场上不缺 RAG 管线（Google 自己还有 Vertex RAG Engine）,他们的差异化押在"可及性与简单性"上：做了一系列有主见的决定，砍掉配置成本——不用建数据库、不用搭基础设施，上传即用（`00:02:36–00:03:45`）。定价同样做减法：市面方案通常要分别为存储、推理、索引付费，他们只保留两项——上传时按索引处理（嵌入等）付费、查询时按 token 付费，存储免费；整体比市面便宜不少，也契合 Gemini API 一贯的"简单"定位——开发者对多产品、多计费模式的抱怨太多了（`00:03:45–00:05:03`）。

### "RAG 已死"？长上下文反而扩大了它的地盘

面对流行语境里的"有了智能体还要不要 RAG",两人的回答是：RAG 是基础能力，从大模型流行之初就是标配，炒作周期起落而 RAG 始终在（`00:05:37–00:06:11`）。长上下文确实改变了局面——小数据集直接塞进上下文效果很好，他们也推荐这么做；但企业级场景（庞大代码库、成堆法律文档）里 RAG 依然显著更优：可以面对整个数据集工作，而不必为"数据进出上下文"搭建复杂管线；成本优势更明显，把所有东西塞进上下文"很快变得昂贵"，用 Pro 档模型尤其如此（`00:06:11–00:07:21`）。Animesh 的观察更进一步：长上下文反而鼓励 RAG 覆盖更多用例——比如学生想就整学期的文档提问；而且长上下文检索仍有"上下文腐烂/迷失中间"综合征，模型对位于上下文中部的信息检索不佳。去年有篇叫 Refrag 的论文：不再把切块原样塞给模型，而是先把块变成嵌入喂进去，让模型自己决定展开哪些（`00:07:30–00:08:39`）。嵌入模型本身的进步——语境理解更好、英语以外语言表现提升——则是 RAG 作为产品持续变好的底层动力（`00:08:39–00:09:00`）。RAG 与工具调用也不是竞争关系："RAG 就是我们递给模型的一个工具"，需要私有语料信息时调用它；他们刚开启公开预览的个性化功能，背后同样是用类似 RAG 的方式检索相关块、为模型补充用户画像（`00:09:02–00:10:20`）。

### 机制：检索几个块才够？约 5 个

工作流并不复杂：上传时切块、用最新的 Gemini 嵌入模型向量化、建索引；查询时把问题同样向量化，从语料中取回相关块。团队用大量评测找延迟与质量的平衡点，并调教系统指令让模型"只在真的需要更多上下文时"触发工具、而不是滥触发（`00:10:20–00:11:26`）。返回多少块合适？"低位两位数"，具体数字不对外文档化；但从伙伴集成看，返回约 5 个块就足以覆盖法律文档检索、代码库检索辅助补全等各类场景（`00:11:27–00:12:44`）。

最反直觉的判断在这：多年来大家围着块重叠、块大小这些旋钮较劲，但"质量的 80% 来自嵌入模型，配置只占 20%"。只要嵌入模型是最好的——"我们相信我们是"——其余配置对结果影响甚微；与其调参，不如把时间花在构建自己的应用上。他们的立场也很克制：不说"别用别的 RAG 管线"，而是"File Search 是你该先试的最简方案"；真正高复杂度、强结构化（特定表格、特定图谱）的场景，再去用可配置性更强的管线（`00:13:17–00:14:24`）。

### 支持什么、更新怎么办、检索怎么做

目前索引的对象以文本为主：PDF、文档、代码文件；图片会走 OCR 抽文本进入上下文；原生多模态（图像、视频、音频检索）在路上——Gemini 本来就擅长对图像视频做推理，缺的是"找到相关图像再放进上下文"的检索能力（`00:14:20–00:15:12`）。切块策略对不同文本类型没有做太大区分，代码表现良好；图表是薄弱点——但解法不是换切块方式，而是预处理：把表格的行列在转成文本时对齐好（`00:15:14–00:16:43`）。

更新与一致性是 RAG 系统的老大难，他们的答案是"并行化加强一致存储"：摄取在块级别高度并行；底层用 Google Spanner（对外即 Cloud Spanner）的强一致性保证，写入后几乎立即可读索引和嵌入（`00:17:15–00:18:31`）。文档更新采用"插入新版本"语义——旧版本不会自动消失，系统不做数据 diff,删除旧内容靠开发者调用文档管理 API（`00:18:31–00:19:26`）。检索本身目前是纯向量语义检索；用户想要关键词检索，已列入路线图考虑（Spanner 的索引能力让它成了自然的扩展）；GraphRAG 评估过但"对我们想做的产品太复杂"，他们更倾向让两个独立系统互补——更复杂的场景可以转向 Vertex RAG Engine（`00:19:28–00:21:27`）。引用的实现在于训练：模型被训练为对每句生成内容标注它引用的块索引（每轮的索引可变），后处理再把索引映射回文档、附上引用元数据（`00:21:28–00:22:57`）。

### 实战数据、重排序与微调的"不推荐"

博客里提到的客户 Beam 是个 AI 游戏生成平台：大量新手开发者要学着做游戏，Beam 把引擎代码库加全部文档索引进 File Search,用户与智能体对话时自然提问，相关文档即时进入上下文——"教育闭环"就此跑通（`00:22:58–00:24:27`）。性能上：检索延迟约几秒，与模型延迟同量级；检索质量视用例最高约 85% 的正确命中——任何 RAG 都难做到 100%（`00:24:28–00:25:00`）。质量的三个杠杆依次是：嵌入质量、检索策略（延迟与质量的权衡）、模型本身（何时触发检索、不幻觉答案）。有开发者在文件搜索之外做后处理：用子智能体再调一次 Gemini 验证结果与对话上下文是否匹配、过滤不合格的返回（`00:25:00–00:26:37`）。

要不要上重排序模型？他们的实验结论是"不值得"：只增加复杂度；只要上下文没被撑爆，让模型自己判断哪块相关更好。系统内部对块有质量分阈值——低于阈值的块不返回——但阈值之外不给模型提供排序信息，因为"没看到给排序带来任何优势"（`00:26:37–00:27:37`）。微调的判断更直接：DeepMind 内部约一年前的通用建议是大多数情况下不要微调——模型迭代的速度远快于小团队能微调出的增益；等你微调完，它大约只能领先一两个月，下一代嵌入模型就会在所有基准上全面反超（约 15%）；六个月后微调基本失效，而且换了底座模型就得从头再来。例外是极小众、自己独占、大厂不会覆盖的数据集（`00:27:39–00:29:23`）。

### 嵌入模型的进步与硬问题

他们判断：随着模型变强，RAG 周边的很多配置终将消失——"嵌入、搜索、拿到好结果"一步到位。嵌入侧的具体进步有两项：多模态嵌入支持（现为公开预览，GA 在即）；Matryoshka 式嵌套表示——嵌入向量的前段比后段携带更多信息，约 3000 维的向量可以在任意点截断仍保持足够精度，未来可能开放成"存储换质量"的旋钮（`00:29:39–00:31:46`）。剩下的硬问题清单：多模态检索、更好地捕捉结构（表格图表）、多语言国际化——英语已很强，其他语言仍有差距；以及持续提高命中率。容量限制方面：最高档总存储 1 TB,单文件 100 MB,单个语料（file search store）建议控制在约 20 GB 以保证检索延迟，查询时可并行指定多个语料 ID（`00:31:47–00:36:36`）。迁移建议务实而克制：先用独立的 Gemini 嵌入模型在一部分数据上对比现有管线的结果，再上传小部分数据到 File Search 跑评测，逐步切换（`00:33:15–00:34:18`）。产品状态：对 Gemini 2.5 系列模型与工具组合均已 GA;Flash 3、Pro 3 模型仍在预览，但 File Search API 本身 GA（`00:33:37–00:34:48`）。上手路径：AI Studio 的 file search applet、Gemini API 示例，AI Studio 里的"氛围编码"环境也已原生支持——直接让模型生成使用 File Search 的代码即可（`00:36:37–00:37:13`）。
