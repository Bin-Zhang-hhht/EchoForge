## 速读

Coinbase Staff Software Engineer Manjiri Moghe 接受 SED 访谈（本期主持人为 Josh Goldberg），讲 React Native 在一家金融公司的规模化实践：2021 年入职时公司刚完成原生到 RN 的重写，至今五年。这期最扎实的是一套"可观测性先行"的方法论——性能分四桶（冷启动、屏间导航、错误量、端到端旅程）、指标太多等于"煮沸海洋"、以及护栏（ESLint 规则、性能预算）优于文档与宣讲。

对移动团队最有用的三个判断：原生双端开发的"80% 用户在 iOS"失衡使 RN 的价值成立；某个性能指标改进后"约两年"会回退，因此自动化护栏是唯一"修一次就永不复发"的手段；以及 Coinbase 超过 50% 的代码已由 AI 生成，个人产出从一天 1 个 PR 变成同时开 5 个。

## 主题正文

### RN 与原生的取舍：适用域与价值

Manjiri 的经历横跨整个混合开发史：2011-2012 年第一份工作学 iOS/Android 原生，经历了 PhoneGap/WebView 时代（"感觉完全不原生"），2015 年 React Native 发布、"2016 年起再没回头"；2021 年加入 Coinbase，当时公司刚完成原生到 RN 的重写。RN 的核心价值：保留原生观感，底层用与 Web 相同的 JavaScript/CSS 技术栈，Web 工程师能较快上手。（`00:02:09–00:04:52`）

从公司视角她给出因果判断：原生双端开发速度慢，业务总催上线日期，往往"80% 用户在 iOS"（她的经验说法）就先做 iOS、Android 跟进，永远无法维持双端功能对齐；RN 一次编写双端发布。但适用域有明确条件："取决于你所在的领域"——做游戏她不推荐 RN（动画和所需性能不到位）；金融类 App 且行业变化快需要高 velocity，则 RN 合适。（`00:04:52–00:07:23`）

### 转向 RN 的三条建议

建议一，可观测性：很多团队把它当 P1/非功能需求，她认为应是第一件事——"不度量就无法改进"，人们说 RN 慢，但"慢"是什么、不度量永远无法改进。建议二，护栏：文档、演讲、学习课程都不如"写代码时直接拦截并告知原因"有效，点名 ESLint，特别是 exhaustive-deps 类规则——"这样一条简单 lint 规则能拦住很多性能回退"。建议三，把纪律内置到平台：定义性能预算（"这个屏加载该在 2 秒内还是 3 秒内？"）、导航（React Navigation 是关键也常是最大痛点）、列表行为；要"打进攻性"，一开始就建共享组件库而非事后补。（`00:07:23–00:11:18`）

设计系统方面，Coinbase 的设计系统已开源，Web 与 RN 用同一套元素，"有时意识不到自己在另一个 repo"；大量抽象组件（lists、modals、trays）让性能优化开箱即得。她给性能下的朴素定义：打开 App 完成想做的事的感受，以及是否出现太多 loading 态。（`00:10:04–00:11:29`）

### 性能四桶与"两年回退周期"

性能分四个桶：冷启动（App 被杀后到主屏的时长）、屏间导航体验、错误量（是否全屏报错挡住用户）、端到端旅程（从打开到完成一笔加密货币买入的总时长）。她的方法论强调克制："试图改进每一个指标就像煮沸海洋"，聚焦必须极窄。关于持续性，她给出一个被主持人反复引用的经验数字：某个指标改进后"约两年"会回退——代码堆积、新成员不了解当初的指标约定；自动化和护栏是"修一次就永不复发"的关键，但性能领域做不到这点，是不断重复踩同样的坏模式。（`00:11:29–00:14:29`）

冷启动调试用 React DevTools 做 profiling：看哪些 API 调用耗时、JS 线程上是否有可推迟的长任务、是否过度重渲染、审计冷启动请求的数据；"有时升级 RN 版本或迁移到新架构能改善冷启动——不总是你的代码，也可能是依赖和基础设施"。线程模型上可回落到原生线程（她称之为 native escape），把重计算交给原生。（`00:14:31–00:16:53`）

### 错误率监控与全球设备差异

错误率是最大指标，分两类：阻塞用户（凡用户无法完成其预期旅程即算）与不阻塞用户；每分钟监控，值班时这是最大责任——因行业受加密资产价格微小波动影响，错误率一抬升就立刻启动根因分析（价格波动？流量尖峰？）。（`00:16:53–00:19:08`）

用户行为驱动大部分优化："用户规模放大必须跟着扩容"，且她认为"用户行为由我们发布的 UI 驱动"。大胆变更一律藏到实验后面（control/treatment 对照），看效果和基础设施能否承接再决定全量；她个人经历过实验回退到 control、删除代码"非常令人沮丧"，但认同"用户是最终裁决"。全球化设备差异：美国以外设备的 P75/P95 指标"看起来很糟糕"，必须优化，理由是"时间就是金钱"——极简单操作要"六七秒"用户会换 App。排查手段：iOS 用 Network Link Conditioner 模拟用户网络、第三方工具在指定设备上跑端到端测试、外部 QA 团队的设备农场。（`00:19:08–00:23:35`）

### 数据获取：过度拉取、轮询与预加载

两个坏模式的批评很具体。过度拉取：React 的重渲染特性下，拉取不必要的数据会让 App 持续重渲染导致卡慢；设计数据层时应只取必需数据（美国用户不需要拉取英/欧合规字段；不参与实验的用户不该为实验拉数据）。微服务扇出："一个服务调 10 个服务、再各调 10 个，客户端一个请求最终变成 100 个下游请求。"轮询是她自称"软件工程里最大的 pet peeve"：RN 导航栈机制下，屏幕一的轮询进入屏幕二后若不显式处理会继续打服务，只有退完整个导航栈才停。（`00:23:35–00:29:13`）

预加载有代价（用户可能根本不去那个屏），只有强指标支持（如"99% 用户都会去那个屏"）才值得预加载。一个有趣的坦白：她 2024 年曾试图把"开发时反馈拉取代价"自动化（设想示例：多取一个字段 = 多 10 个请求 = 多 40ms 延迟），承认"没成功"，至今仍在找方案；退而求其次靠上线后小流量灰度（1%、2% ramp up）。AI 辅助护栏：PR 打开时由 AI 找 footgun 模式，如每次查询都绕过缓存就询问作者能否改用缓存策略。（`00:23:45–00:29:19`）

### GraphQL、Suspense 与新架构

GraphQL 只取所需字段且支持 defer：一屏一个大 query 加 fragments 下传子组件，非关键数据延后加载、先渲染关键数据。Suspense 被她列为最喜欢的 loading 态：不再有巨大 spinner，上下文化的局部加载"让用户保持参与"；且自带度量——Coinbase 用 suspense instrumentation 计算组件/整屏渲染耗时，被称为 "huge win"。GraphQL 的取舍是"取决于你在做什么 App"，Coinbase 重度使用，"像所有数据层一样有优点也有缺点"。（`00:29:13–00:31:53`）

新架构方面（文中只说 new architecture，未提 Fabric 一词），她很兴奋：JSI 去掉了旧的 native/RN 桥接——早年支付模块、银行集成在 RN 侧不可用，必须桥到 native 再桥回来，"这个通信耗时很长"；Turbo Modules 让摄像头、keychain、原生存储等交互更快。她补充 Coinbase 用的原生功能不多，主要就是这几类。（`00:31:53–00:34:01`）

### AI 与工程效率：一天 1 个 PR 到同时 5 个

一个引人注目的数字："Coinbase 超过 50% 的代码是 AI 生成的"（她称两天前刚看到）。个人效率对比：过去一天约能开 1 个 PR，现在用内部 agent 给出 prompt 和计划，可同时开 5 个 PR，"巨大的 velocity"；成功关键在于"给 AI 正确的上下文"。内部重度使用 Claude，通过 agents.md 约定文件让 AI 生成的 UI 组件开箱即带屏幕名（用于渲染指标）等约定，减少人机来回。主持人问 agent 是否会写出 Web 版 React 的惯用写法而非 RN 惯用写法，她答 "Not really"——因为设计系统、React 和 lint 规则两端一致。她也提醒 AI 修 lint 违规"必须检查产出"：有些违规一眼即对，有些需要人工核对。（`00:34:01–00:37:19`）

运营卓越：几乎每个团队都运行自己的复盘——错误率、性能预算、过去一周的事故并总结预防措施；指标向上汇报到 leadership 层，"不是分配 20% 时间应付，而是每位工程师的头等大事"。运营也在用 AI 做重活（跑查询、找共性主题）；分类标准是"同一根因的事故两周内不再发生才算赢"。面对"稳定团队突然涌入大量用户叠加领导层要新功能"的假设场景，她的答案是优先级排序：先评估影响面，Coinbase 有 severity 机制；单用户问题也重要，"但取决于是谁"——如果用户是高净值个人，"今天就得处理"。（`00:37:19–00:41:13`）
