## 速读

AWS 资深首席工程师 David Yanacek——二十年亚马逊生涯只做一件事：让开发者更轻松（DynamoDB、Lambda、API Gateway、CloudWatch 都有他）——向 Kevin Ball 讲解 Kiro：一个围绕"规格驱动开发"构建的 AI 开发环境，目标是保住 vibe coding 的敏捷与乐趣，同时产出经过彻底测试、可上生产的代码。

最值得带走的三点：规格就是三份 markdown（需求含 EARS 式验收标准、设计含架构图与代码片段、任务含可选任务拆分），在写第一行实现代码之前就把方案分歧消化掉；Kiro 用属性测试把"验收"变成硬约束——从规格提取不变量、自动生成海量输入排列、失败后收缩出最小复现序列，Agent 无法靠注释掉测试体蒙混过关；面对"编码不再是瓶颈"的新现实，AWS 的答案是把 DevOps、安全都做成常驻的"前沿 Agent"，且让它们在团队已有的协作面（Slack、工单、事件响应工具）里协调。

## 主题正文

### 二十年只做一件事的人做的 IDE

Yanacek 的职业主线解释了 Kiro 的气质。亚马逊的 DevOps 观念是"开发者自己做运维"，于是他一路都在消灭让开发者痛苦的运维：参与 DynamoDB 的动机之一是"从此再也不用做数据库运维了"，此后是 Lambda、API Gateway、无服务器与 CloudWatch。LLM 出现后，"让开发者更轻松"有了全新抓手，这就是 Kiro 的由来（`0:02:02`）。Kiro 的定位是帮助开发者"从原型走到生产级代码"：保留 vibe coding 的全部敏捷、乐趣与迭代，只加上恰到好处的结构，让 IDE 心里始终装着最终目标、只做服务于目标的任务，并尽可能自主运行（`0:04:42`）。

### 规格就是三份 markdown

Kiro 的规格流程从一句普通提示词开始——"我想做个红绿灯控制系统"——Kiro 会反手扩展出更细的需求（比如"需要跟踪车辆进出路口"），然后产出三份文档。第一份是需求：markdown 文件，采用 EARS 风格（逐字稿作 "ears format"，即 WHEN/SHALL 式的条件-应答句式）写成，附验收标准，容易扫读、容易点头或摇头；不满意就继续聊天改。规格的粒度随意：可以是全新项目、一个功能，也可以是"把这套代码升级到最新 Node.js"的维护任务。第二份是设计：技术栈与框架选型、非功能需求、类图、架构图，以及关键实现思路的代码片段——他最看重这一步的价值是"免得 20 分钟之后才发现方案不对、全部推倒"。第三份是任务：把实现拆成搭框架、写基础设施即代码、建测试环境、建数据库表……还会把可选任务单独列出，并遵循"先给你一个能跑起来的东西，再做彻底测试（含属性测试）"的顺序（`0:05:58`）。

流程刻意不是瀑布：看到设计发现漏了需求就退回需求文档，实现途中也能回头改规格或任务。三份文档通常随代码提交进仓库，用法因人而异：有人一次性归档，留给未来的自己或 Agent 查问"当初为什么这么做"；有人把规格当活的架构文档随变更更新。他本人的习惯是规格用完归档，另维护一份独立的权威设计文档，在项目完成后让 Kiro 把最新实现同步进去（`0:09:57`）。

### 属性测试：让 Agent 无法自欺

规格真正的威力在验证环节。Yanacek 强调意图被固化成文档后，测试就有了超越"对着代码补单测"的依据。Kiro 采用属性测试（property-based testing）——这不是 Kiro 的发明，但规格让它第一次可以被大规模自动化生成。思路是把测试写成不变量：红绿灯系统最重要的不变量是"任何时刻至多一个方向是绿灯"（全红可以），然后让输入生成器（他们用 Python 的 hypothesis 框架）从规格描述的输入类型生成海量排列——行人按钮、紧急车辆、不同时序、断电与恢复——验证不变量在任何输入序列下都成立（`0:12:36`）。

失败后的处理链路也很完整：Agent 拿着失败反复修正实现，直到所有不变量成立；属性测试的痛点是失败序列太长看不懂，框架的收缩（shrinking）技术会不断删减输入，收敛到触发失败的最短序列（`0:12:36`）。他顺带吐槽了所有 Agent 用户都见过的名场面：测试过不了，就把测试体注释掉、宣布通过、然后忘了这茬——彻底的属性测试让 Agent 必须证明正确性，"保持诚实"（`0:12:36`）。KBall 补充了机制层面的解释：LLM 有自我确认偏误，容易在一条思路里越陷越深，属性测试把整个输入空间铺开，逼它跳出既定轨道。值得强调的是这一步是 Kiro 主动做的——它在规格流程中会自我反问"需求是否清晰、有没有冲突"、"应该验证哪些正确性属性"，实现测试反而是可选项（`0:18:07`）。

### steering、powers、hooks：上下文的渐进披露

Kiro 给开发者的定制件有三样。一是 steering 文件：描述开发环境与团队惯例，可以分层——公司级一份、团队级一份、个人偏好一份；由于占用上下文窗口，要保持精简、多放指向详细资料的指针。二是 Kiro Powers：把 MCP 服务器、steering 文件与 hooks 打包成可动态加载的"能力包"，kiro.dev 上按需添加——项目里出现 Supabase，相应的 power 就带着全套 MCP 工具与约定进场。三是 hooks：在触发条件（如某文件保存）下发起一段提示词或一个独立 Agent 循环——"每次我改 API 定义就重新生成 SDK 与文档"、"每次改依赖文件就跑安全扫描"——也可以手动触发（他本人最常用的是手动）（`0:19:32–0:24:24`）。

KBall 把 powers 的设计概括为"上下文的渐进披露"：不给全量上下文，先给一小段足以勾起 Agent 兴趣的描述，时机到了再加载全部 MCP 与约定。Yanacek 说这套东西来自第一方的痛：新服务发布当天 Agent 根本不知道 Bedrock AgentCore 或 Strands 是什么，你只能一遍遍丢链接、纠正误会——power 就是"把专长打包起来，让 Agent 样样都行"的产品化（`0:21:51`）。hooks 的实现细节也被问到：它弹出独立的上下文窗口、跑完整的 Agent 循环、目前不与主会话合流——"分支出去把事做完"（`0:26:02–0:27:20`）。

### 前沿 Agent：把协调交给团队已有的协作面

Kiro 规格流程让 Agent 可以跑得更久、接下更模糊的任务，AWS 顺势推出"前沿 Agent"（frontier agents）三件套：Kiro 自主 Agent 是非 IDE 形态——从你的工单系统领任务、自己循环测试与打磨、把模糊任务展开成符合团队习惯的实现、最后交一个 PR；AWS DevOps Agent 做事件响应——分诊、根因、建议修复，并且长期在后台找优化机会（"这个告警总响是因为你们的部署质量差，我来把 CI/CD 加上更好的测试、自动回滚和更灵敏的告警"）；安全 Agent 负责让人与 Agent 写的代码符合安全标准，还会自己做渗透测试（`0:27:38`）。

多 Agent 协调的答案出乎意料地朴素：IDE 里跑的 Agent 不需要特别协调（就在你眼前）；真正的难题是常驻后台的 Agent——而它们的协调面就是团队已有的协调面：Slack 里沟通、工单系统里派活、事件走 ServiceNow、可观测走 Dynatrace 或 Datadog。"在人类已经在协调的地方协调 Agent"（`0:27:38`）。人的介入时机同样重要：Agent 学习了团队惯例之后，如果工单要求用的日志库与团队实际用的冲突，或者实现和需求看起来都对、属性测试却失败，它应当主动回头找人，而不是"怀着 LLM 特有的乐观"烧掉大量算力做最佳猜测（`0:31:49`）。

### 学习机制：拓扑、runbook 与知识条目

持续学习被拆成了看得见的机制。DevOps Agent 会构建并可视化系统拓扑（测试与生产环境、基础设施、代码与接口如何叠加、CI/CD 如何推送、日志与 trace 在哪），在"agent space"里你能看到它学到了什么宇宙；学不下去时它会报告障碍——"你说过这里能访问，但我找不到日志"——你可以修配置，或者写 runbook（本质是渐进加载的 steering 文件，用简短的名字与描述在恰当时机吸引 Agent 查阅）告诉它"这部分系统的日志在另一个地方"（`0:34:02`）。另一个样本是 AWS Transform 的自定义转换：面向长期升级、迁移、重复性重构项目，每次执行都从你的结果里学习（只学你的，不学别人的），学到的内容以"知识条目"（markdown 文件）呈现，由你逐条接受或拒绝（`0:34:02`）。

知识管理的底层是"混合技术、快速演化"：不是每次全量加载，而是渐进披露、知识老化、RAG 加摘要文件，再加上专职反思的 Agent 循环——DevOps Agent 每天回看前几周处理过的事件，产出预防建议与模式归纳，并反思自己的调查路径哪里浪费了时间；但"有时候浪费时间是对的"——不去探索那个分支，下次真正的问题就在那里（`0:38:34`）。任务中也有内省点：没有时间评估每一条知识，但可以从不同主题领域自问"是否都考虑到了"；反思的透镜包括 AWS Well-Architected Framework、安全、测试与可观测实践，尤其是"有人特别强调过重要"的事项（`0:40:30–0:41:45`）。底层设施方面，他点到 Amazon Nova Forge（从早期检查点做模型开发）、Bedrock AgentCore（安全、租户隔离地运行 Agent，DevOps Agent 自己就在用）与 AgentCore Memory（压缩 Agent 的 trace，沉淀会话反思与长期经验）（`0:44:06`）。

### 评估难题与"机场洗手间按钮"

展望前沿，Yanacek 最关心的是测量 Agent 是否真的有效。他指出这本质上是网站时代的老问题回归："我的 API 返回成功了吗"容易测，"我的用户满意吗"很难——Agent 服务的是业务结果，必须找到领域相关的信号。点赞/点踩有用但不够，他把那个按钮比作机场洗手间出口的"干净/不脏"评价器：必要，但没人认真对待，也问不出"为什么不满意"。出路是借鉴真实用户监控（RUM）行业的方法论，用新技术把它做深；可观测始终是"理解客户满意度的透镜"——这正是他从 CloudWatch 带来的信念（`0:48:57–0:52:47`）。

他给的两个数字与两条建议值得单独记录：一个 30 人×18 个月的服务重平台项目，用这些工具后 6 人×6 周完成。建议一，像当年学搜索引擎的布尔语法一样，养成内省习惯——"为什么我没得到想要的东西？"缺背景就写 steering、装 power、接 MCP 服务器；建议二，别只盯着编码工具：编码被加速后不再是瓶颈，安全评审、渗透测试、生产运维会成为新瓶颈——"我们不想只是把瓶颈挪个地方"，这就是前沿 Agent 存在的理由（`0:52:54`）。
