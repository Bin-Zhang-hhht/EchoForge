## 速读

在 Data + AI Summit 现场对 Databricks 两位联合创始人 Matei Zaharia 和 Reynold Xin 做的双人访谈，信息密度极高：一半讲 Omnigent——他们开源的"元 harness"，坐在 Claude Code、Codex、Cursor 之上统一会话、安全与协作；另一半讲数据库——为什么 CDC 管线会让工程师凌晨三点起床，以及为什么"只统一存储层"的 LTAP 可能终于把 HTAP 圣杯变成现实。

最值得带走的观点：Agent 安全的正确粒度是"情境化策略"——不是允许或禁止某个工具，而是跟踪会话状态后再判断（读了机密文档又装了可疑 npm 包就拦下来）；以及"把数据放对地方、上面随便贴个 Agent，传统软件就会被重写"这条重写论。

## 主题正文

### Omnigent：编码 Agent 和企业 Agent 需要同一层

Omnigent 的起源是两条线的汇合。一条是内部开发基础设施：Databricks 的开发工具团队做了个叫 Isaac 的东西包住 Claude Code 和 Codex，结果高级工程师们各自在上面搭自己的工作流和 UI；另一条是他们自己的数据科学 Agent Genie 和各种内部 Agent，全都困在同样的问题里——每隔几个月要换模型和 harness，而且不能分享会话、没有历史和搜索的 Agent 基本没用。Matei 的判断是这两类问题同构：都需要"把 Agent 交付出来、按需控制它、并让它可移植"的那一层（`00:02:22–00:05:42`）。

Reynold 补了一个体感细节：他有整整一周不停歇地写代码，开着笔记本、用手机热点，去见医生路上红灯都要瞄一眼 Agent 跑得怎么样，"感觉回到了编程的黑暗时代"。这个痛点直接变成了产品需求清单——云端沙箱要能不关机地持续跑会话，能开自己的 shell、tail 日志、渲染 Markdown；也是 swyx 当周亲测后写给 Matei 的愿望清单（`00:05:46–00:08:39`）。架构上 Omnigent 刻意保持克制：核心是一个公共 API——Agent 会话可以收消息或文件、吐出流式文本和工具调用、可以取消一轮——底下把 Claude Code、Codex、Pi、OpenAI SDK 全映射到同一接口，免得你自己维护的编排层在 harness 改 API 时丢消息；安全控制、UI 都是可插的组件而不是一个大一统 stack（`00:14:06–00:15:20`）。开源周六上线，几天就有约 400 个合并 PR、近半来自社区：Kubernetes 支持、各种云沙箱、Cursor CLI 和 Antigravity 的 harness 接入都进来了（`00:11:42–00:12:34`）。

为什么开源？Matei 的框架直接继承自 Spark 时代：如果某个层有网络效应、会因众人协作受益，就该开放——Spark 当年让所有机器学习、图计算框架都变成库、连接器由社区写，双方都受益；反过来，"流式作业半夜不丢数据"这种事需要运营团队值守，只能做成服务。他反问：如果闭源的 Agent 托管和开源的对手长期竞争，谁赢？（`00:09:45–00:12:34`）

### Agent 安全的 correct 粒度：情境化策略与花费上限

Matei 花了大量时间访谈内部用户、安全团队和客户，结论是今天的编码 Agent 权限模型太粗糙：只支持"允许/禁止某个工具模式"的是非题，把人逼进两难——Agent 能读机密文档吗？能从 npm 装新包吗（万一被投毒）？能发布到公司官网吗？单独看每个答案都是"看情况"，真正的危险是组合：读了机密文档又被提示注入、把内容发出去（`00:18:03–00:20:25`）。Omnigent 的答案是状态化、情境化的策略：跟踪会话状态，"它刚装了个可疑的旧包、或读了一千份机密文档？那就别让它再干危险的事"。另一个设计是策略分层：Google Drive 的 MCP server 有 60 个 API 调用，没人分得清哪个会把文档共享到外网，所以策略层支持函数库——由社区把低层事件映射成高层语义，策略只写高层规则；这也是开源的又一个理由。状态里还包含花费：他自己的 Agent 调试一次烧过 500 美元（读了太多日志），现在可以设"这次任务上限 5 美元，超了来问我"（`00:20:25–00:24:00`）。Databricks 内部政策是不限额，但用自家产品分析全部 trace，还顺带得出"哪些模型更擅长 Rust 哪些更擅长 TypeScript"这类洞察；他提醒咨询公司才是最痛的——十万工程师每人每月多花一千美元不是小数目（`00:22:10–00:23:34`）。

顺带给出规模感：Databricks 每天在三朵云上编排约 5000 万–6000 万台虚拟机，"看你在哪个时区，早饭前就处理了 EB 级数据"；Neon 现在每天要启动 1300 万个数据库，很大程度归功于 Agent 的分支实验（`00:16:52–00:17:54`）。

### LTAP：不统一引擎，只统一存储

下半场是 Reynold 的数据库布道。世界分 OLTP（事务，Postgres/MySQL/Oracle）和 OLAP（分析）两半，应用一旦认真起来就要把数据从事务库复制进分析系统，靠的机制叫 CDC（变更数据捕获）。CDC 无处不在又极其脆弱——OLTP 侧改个 schema，下游管线就崩，数据工程师半夜三点被叫起来；他们开玩笑说 CDC 应该叫"持续数据损坏"（continuous data corruption）。十年前行业就梦想 HTAP：一套系统同时干两件事，但至今都是妥协——新引擎两边生态都接不上，性能两头不讨好，"两边都烂"（`00:27:39–00:32:39`）。

Databricks 的 LTAP（Lake Transactional/Analytical Processing）论证是：放弃统一查询引擎，只统一存储层。让 Postgres 兼容的事务库直接把数据以列式格式写进开放数据湖，分析侧零延迟直接读——没有中间管线，事务数据立刻可用于分析（`00:31:12–00:32:39`）。为什么现在才可行？Lakebase 架构（源自收购的 Neon 团队，存算分离）本来在往湖里写 Postgres 页，Ali 和 Reynold 争论能否改成列式，吵了很多次会议后，一位工程师直接做了原型：用存储集群闲置的 CPU 做行转列的转码——转码后压缩率更高、写 S3 反而更快，性能无损。"这么战略级的事没有设计文档、没有立项流程，就是吵不完的会之后有人去试了一下"（`00:34:05–00:36:47`）。价值在 Agent 时代被放大：Reynold 本来不信自己的营销话术，直到一个澳大利亚客户说他们的 Agent 只能看到服务遥测、看不到订单本身是谁在下、在干什么——能读到实时业务数据会让 Agent 强十倍。Matei 补充的场景是事故排查：以前不能对生产库跑大查询（会把库压垮），现在可以另起一队分析机器随便查（`00:32:40–00:34:05`）。

他还顺带判了向量数据库"死刑"：它本不该是独立品类。而 LTAP 特意不合并查询层——Agent 对用 Postgres SQL 还是 Spark SQL 毫无压力，"只要数据在，Agent 不会搞混"；这对人类可能是问题，对 Agent 不是（`00:51:02–00:52:36`）。

### 快速原型的公司文化与"数据库工厂"

文化段有几个可复用的原则。一是克制地少做产品但做透：公司理论本来就是"别让用户拼 20 个服务，用一套 API、一套语义、一份数据"，存储（Delta Lake）、SQL、机器学习平台是一次加一件（`00:36:47–00:38:33`）。二是极致贴近客户：Reynold 问团队的第一个问题永远是"目标客户是谁？你能叫出他名字吗？会跟他发短信吗？"存储层当年就是为最大的客户单独打造的（网络安全隔离的事件存储与查询），Clean Room 起初只为两个客户做——"过拟合到一两个客户的下行风险，远小于好高骛远一无所有的风险"（`00:38:43–00:41:02`）。三是对企业客户与科技公司的差异要保持清醒：治理、安全、合规、采购流程完全不同，企业说"我永远不想自己造这个"反而是最好的客户（`00:41:03–00:43:40`）。

最野心勃勃的是"梦想引擎"：现有分析型数据库引擎几乎都十岁了，为窄场景而生、靠围绕初始抽象打补丁长成庞然大物——"包括 Databricks 自己"。重写从零开始当然有"第二系统综合征"的风险，但这批工程师的应对是先造"造数据库的工厂"：用十年积累的 trace（万亿次级数据点）训练一个机器学习模型，高保真预测任何算法/实现在任何负载上的表现，再据此选型并在运行时按负载特征分发不同实现。特征可以细到"字符串是纯 ASCII 还是含 Unicode"——密集字符串（比如国家码）可以直接用数组替代哈希表（`00:43:40–00:49:47`）。发布策略是增量的：新端点先吃下"几十毫秒内完成"的低延迟负载，不指望五年磨一剑（`00:49:47–00:50:29`）。

### 开放格式、专项模型与"贴个 Agent 就行"的重写论

对标 Snowflake 的问题，Reynold 给了两个结构性差异：格式开放（从 Parquet 到 Delta/Iceberg，从未有过私有格式）和 AI 基因（ChatGPT 之前就一直以"数据+机器学习"平台自我定位）。Matei 的版本是"我们从上游开始"：先做大规模、低成本的摄取，再向下衍生出快而好用的小数据服务比反过来容易；两家曾互为伙伴，直到客户问"为什么不能直接查你的表"。对经历过 Oracle 锁定的企业 CTO，开放格式已经是默认要求——当年 Snowflake 创始人那篇《Choosing Open Wisely》反开放的文章现在是反例教材（`00:52:36–00:57:48`）。

模型侧的取舍同样清晰：收购 Mosaic、发过 DBRX 之后，他们决定不追通用前沿模型（"那件事的配方主要是堆算力"），而是让聪明模型变得有用——第一方 Agent Genie（虚拟数据科学家，官方口径称准确率是通用 Agent 的三倍）就是载体。真正持续投入训练的是高量场景的专项模型：文档解析视觉模型把一页 PDF 变成结构化 JSON，比调前沿模型便宜约百倍还更准；以及源自 Berkeley 论文的 advisor models 思路（Harvey、Anthropic 也在采纳）。Matei 的判断是模型定制会越来越容易——基础模型更聪明所以 trace 质量更高、合成数据管线更成熟，他们的开源模型自生成训练环境自训练后已能在特定任务上打赢 Opus 和 GPT-5.5；RL 微调作为服务加 AI Runtime（按需 GPU 集群）就是对外的两条通道（`00:57:48–01:03:11`）。收尾呼应 Satya 的"前沿生态"论：数据让一切更值钱，而"把数据放对位置，上面贴个 Agent，传统软件将被重写"——他们新发布的面向安全团队和营销团队（客户数据平台）的两个产品都是这个论点的注脚（`01:03:11–01:07:09`）。
