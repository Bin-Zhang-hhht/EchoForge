## 速读

Notion 联合创始人 Simon Last 与 AI 负责人 Sarah Sachs 首次公开 Custom Agents 背后的全部历程：这个功能是第四、五次重建的产物——从 2022 年底拿到 GPT-4 访问权就开始尝试"给助手全部 Notion 工具让它在后台干活"，经历自研工具调用框架加微调的失败，直到 Sonnet 3.6/3.7 一代的解锁才达到可用可靠性。

最值得带走的三点：五次重建的最大教训是"给模型它想要的，而不是给你方便的"——从无损映射 Notion 区块的 XML 改为 Notion 风味 Markdown，从 JSON 查询格式改为 SQLite 式查询，从 few-shot 提示全面转向工具定义与渐进披露；他们的评测体系分三层——CI 里的回归测试、上线质量报告卡，以及刻意只求约 30% 通过率的"frontier/headroom 评测"（"Notion 的 Last Exam"，与前沿实验室合作共建），并由一个独立职业路径的"Model Behavior Engineer"岗位运营；以及代理组合哲学——不做特殊的记忆或消息概念，"记忆就是页面和数据库，给它一个页面加编辑权限就行"，30 个代理被 70 条通知淹没的答案是一个管理代理。

## 主题正文

### 五次重建：给模型它想要的

Custom Agents 是 Notion 史上最成功的发布（免费试用与转化计），但 Simon Last 透露它已是"第四或第五次重建"。起点在 2022 年底刚拿到 GPT-4 访问权时——"那时还没有 agent 这个词，我们叫它 assistant"——想法与今天无异：给它全部 Notion 工具，让它在后台干活。失败的原因清单：没有工具调用标准（他们自研了一套工具调用框架并尝试微调模型，与 Anthropic、OpenAI 都做过合作）、上下文太短、"模型就是太笨"。真正的解锁是 Sonnet 3.6/3.7 一代（逐字稿作 Sonic 3.6 or seven），此后核心 Agent 得以上线，而 Custom Agents 又多花了很久——"因为它真的在后台运行"，加上权限的产品化难题：一个 Custom Agent 被分享进 Slack 频道、能访问的文档又各自有不同的可见人群，如何让管理员理解这套交集，反复改了多轮（`00:00:26–00:03:35`）。

Sarah 总结 Notion 的两种关键能力：一是迅速识别"你是在对抗模型能力，还是没把正确的信息喂给模型、没搭对基础设施"——不要逆流而上；二是看清河流的方向，提前把产品建好，等能力到位时你已经就绪。转录/会议笔记就是"多次尝试才对准方向"的例子（`00:05:32–00:06:58`）。她把 Agent Lab 论点讲给每个候选人听：Notion 之于模型，如同 Datadog 之于 AWS——"Datadog 离不开云存储，AWS 也有 CloudWatch，但 Datadog 是理解用户想如何观测自己产品的专家；我们的专长是理解人们想如何协作"（`00:07:02–00:08:07`）。团队纪律则锚在用户旅程上：每个周五，全员一起看"P99 最昂贵的 Custom Agent 轨迹"，逐条分析它为什么没做好——"邮件分诊就应该能行"（`00:09:22–00:10:29`）。

### Token Town 的组织学：低自尊、西蒙漩涡与"demo 而非备忘录"

Sarah 的管理哲学："我的工作不是当点子王或技术专家，而是让每个人理解目标、有资源排优先级、有渠道推动自己认为重要的事。"最好的想法来自原型，如果都要经过她和 Simon 的"嗅探测试"就是巨大的浪费。重建了三四次 harness 之后，第二条领导力法则是"团队必须乐于删除自己写的代码、低自尊、由公司利益驱动、不为晋升写设计文档"——这种文化来自 Simon 与 Ivan 的开放心态。Simon 补充自己的角色是"每六个月循环一次地推倒重来"：新东西出现了，如果全部重写会怎样？（`00:10:54–00:13:16`）围绕他高速旋转的"Simon Vortex"不需要黑客松，需要的是可信赖的资深工程师随进随出——管理边界刻意松散（"你向他汇报，但现在为她工作"），组织结构在发布之后才成形。公司级黑客松（1.5 天）则是为了提升大众：最近一次的主题是让所有人从零手写一个工具调用循环，"用你喜欢的编码 Agent，理解这个基本功"。安全团队被刻意最早拉入——Sarah 在 Robinhood 的岁月教会她合规的代价（`00:13:16–00:16:02`）。一个典型故事：数据库团队有人想做封面图生成，"你想做？请便"——给了 Gemini 资源、评测支持，最终成了正式项目。"这就是为什么当领导不能有自尊。"（`00:16:02–00:16:39`）

组织规模：Sarah 管理的"核心 AI 能力与基础设施"约 50 人，做产品包装的伙伴团队 30–40 人，而更根本的机制是"每个拥有产品面的团队都拥有代理使用的那个工具"——做离线 CRDT 的团队负责两个代理编辑同一区块的冲突，写 SQL 引擎的团队负责代理的查询性能。"随着时间推移，我们的大部分流量将来自代理而非人类，所以整个产品组织都在为代理而建。"（`00:16:39–00:17:40`）内部的原型文化已被 agent 改写：设计团队维护一个"design playground"仓库，不做 mock、直接给可用的 URL；工程师的原型标准是"一个真的能用的 feature flag"；实验性聊天界面里有一百来个开关（`00:17:40–00:20:25`）。"demo 而非备忘录"（设计师 Brian Levin 的说法）的反面压力是：什么都能被 demo 的时候，PM 与设计师必须有强信念选对要爬的那座塔，而不是堆出一片平缓的矮丘。

### 评测三层与 Model Behavior Engineer

Notion 的评测分三层：CI 里的回归测试（必须在随机误差率内通过）、上线质量报告卡（各用户旅程需达 80–90% 才能发布），以及最有意思的"frontier/headroom 评测"——刻意设计成只有约 30% 通过率的考试。"我们曾到达评测饱和的顶点，除了'没变差'之外给不出任何有洞察的反馈——这对合作伙伴没用，对我们判断河流方向也没用。"于是他们与 Anthropic、OpenAI 合作打磨"Notion 的 Last Exam"，有全职的数据科学家、模型行为工程师（MBE）与评测工程师专门维护（`00:20:25–00:25:56`）。MBE 是 Notion 发明的职业路径：起点是 Simon 需要人肉检查 Google Sheets 输出好坏的"数据专员"（团队里有语言学博士肄业与斯坦福应届生），如今他们在构建"能自己写评测的代理"与 LLM judge；角色是"数据科学家 + PM + 提示工程师"的混合体，需要理解模型的能与不能、定义 headroom、判断好坏、分析失败——"有手感与品位的成分，不是软件工程"，因此"不需要工程背景也能做到最好，我们欢迎 misfits"（`00:25:56–00:27:37`）。

更进一步，他们把评测系统本身当作代理 harness："一个代理应该能端到端地下载数据集、跑评测、迭代失败、调试、实现修复，人类只观察外部系统。"实现上就是 Claude Code 之类的编码 Agent 加 CLI 工具，刻意不锁定任何一家；监督由 MBE 完成——"就像让编码 Agent 写单元测试，也应该让它写评测"。对 swyx 的尖锐问题"是不是已经没有软件工程师了"，两人的回答是"我们正沿着抽象阶梯上移"：人在观察和维护外部系统——一串代理在流动，哪些 PR 出轨了、需要我批准什么、记忆机制是否有效——"这是一个艰难的工程问题"。Sarah 的版本更扎心："今年夏天每个 Notion 工程师都经历了管理者式身份危机：你写代码的能力不再重要，重要的是委托与上下文切换。"Simon 补充关键差异：与管人不同，代理系统可以像严格的工程系统一样对待——PR 可以有阻塞状态、可以定义阻塞后发生什么，"这本质上是技术设计问题"（`00:27:37–00:30:42`）。"软件工厂"的设计原则由此推出：尽量少的人工干预但守住要紧的不变量——一个可提交的 markdown 规格层（"自然归宿就是 Notion"）、强大的自验证测试层、以及"出现 bug 后如何流入系统、子代理如何认领、PR 如何被评审"的流程（`00:30:42–00:32:18`）。

### 现场演示与代理的组合学

Alessio 现场展示了他花 15 分钟为共享办公空间搭的 Custom Agent：监听收件箱里的租户申请、自动建数据库记录、用网络搜索丰富申请人画像。"不是 AGI，但我不想亲手做这些事。"Sarah 分享的最大内部用例同类：Slack 里的 bug 分诊代理——带着自己的"路由宪法"判断该归哪个团队、建任务、回帖——"它改变的是流程而非人头，Notion 之所以还是 Notion 就是因为几乎没有事情会漏掉"（`00:32:18–00:34:44`）。代理的组合有两种方式：经由数据原语（一个代理写数据库、另一个监听数据库）的松耦合，以及即将发布的直接互调——设置里可以授权一个代理调用任何其他代理（有递归上限，"总会有人搞出回形针"）。最生动的故事：GTM 团队某人搭了 30 多个 Custom Agent，每天被 70 条"代理被阻塞"通知淹没——答案是再造一个管理代理，能调用所有代理、观察它们、把 70 条通知压成 5 条，还能帮其他代理调试修复。实现上没有任何特殊概念："给他们一个内部 issue 数据库用于报障，管理代理有读权限"；记忆同理——"我们没有内置记忆概念。记忆就是页面和数据库：给它一个页面和编辑权限，人类与代理都能编辑，这个模式运行得极好"（`00:34:45–00:38:15`）。

### MCP 与 CLI：分层而非圣战

 swyx 抛出 MCP vs CLI 的必答题。Simon 立场鲜明地 bullish CLI：它活在终端环境里（分页、翻阅长输出）、天然渐进披露（只见 CLI 包装与 help 命令，不见全部工具）、而且最关键的是"自举"——出了问题，代理可以在同一个环境里调试并修好它。"我看到今早有个推文：某人的代理没有浏览器，就让它自己造了一个——100 行代码包了一层 Chromium API，有 bug 它立刻自己修。反过来，Chrome DevTools 的 MCP 一旦传输层坏了，代理毫无办法——浏览器没了，就是坏了。"但他也承认 MCP 的缺点可被 harness 修复（渐进披露不是协议固有的，是包装方式），且 MCP 有 CLI 不具备的优势：天然的强权限模型——"你能做的只有调用工具"；CLI 则模糊得多——token 的再加密、防外泄，都是真实且难解的问题（`00:39:43–00:42:12`）。Sarah 补充两个商业视角：Notion 作为企业协作的记录系统会永远维护 MCP（"只要别人在用"）；更重要的是"价值与定价要对齐能力"——"要求语言模型去执行确定性的第三方对接任务是浪费；让代理通过 CLI 确定性地调用代码是一次性成本，而反复用语言模型走 MCP、在缓存窗口之外一遍遍付费，既浪费又不必要"（`00:42:43–00:43:36`）。Simon 的总纲是"分层而非冲突"：MCP 是获取长尾工具的开放协议（Linear、GitHub 走 MCP），Slack、邮件这些高频集成则自研并配了 MCP 协议里不存在的"触发器"（trigger）；内部有 tool/agent/completion/chat-archetype 的统一抽象，"MCP 只是 integration 的一种类型"（`00:44:10–00:47:43`）。

### 五次重建史与渐进披露

应 swyx 要求，Simon 考古了 harness 的演变史。第一版是编码代理："不造工具了，一切都是 JavaScript，给它 JS API 让它写代码"——当年模型"写代码就是烂"。第二版转向工具调用（彼时不存在，他们自创了 XML 表示）：最大的教训是"过度迎合 Notion 的数据模型而非模型想要的"——他们造了能无损映射 Notion 区块的 XML 格式与变更操作，结果模型不认识这套 XML，还得用提示词教。于是第三版：Notion 风味 Markdown——"核心必须是朴素的 Markdown，加一些增强，不必无损"。数据库层同理：Notion API 的 JSON 查询格式对模型不友好，干脆全改成 SQLite 式查询——"模型超级擅长"；幸运的是 Notion 内部早已把数据库查询落在 SQLite 集群上（那篇著名的工程博客）。之后是 research mode（尚非完全代理式）、全面放弃 few-shot 转向工具定义，以及正在酝酿的 Agent 2.0（`00:47:43–00:51:34`）。整个弧线被 Simon 总结为："逐渐剥掉一切，看起来越来越 AGI"——从单 prompt 加 few-shot，到工具加 few-shot，到纯工具。

最近的两次大变化：其一，工具数量突破百个后撞上渐进披露的瓶颈——此前"说声 hello 都要消耗成千上万 token"，而且任何工程师为小众功能加一个工具都可能"削弱"整个模型（引发过度调用）；解决方案是 harness 级的渐进披露。其二，从 DAG 到真正的反馈系统：放弃 few-shot 后，工具按目标描述定义，工具的所有权得以分散给各业务团队——few-shot 时代所有人编辑同一个字符串、顺序与选择都影响效果（"并非所有上下文生而平等"），全公司只有五六个人有权碰它，无法随公司规模扩展；现在有正确的评测体系，人人拥有自己的工具定义。意外发现也很有趣：两个同名工具会让某些模型直接崩溃，而 GPT-5.2 表示"我能搞定"——这是一次 SEV 事故中的收获。Sarah 强调这次转变并不立即带来速度："拥有 few-shot 的 AI 卓越中心团队必须一夜之间变成平台团队，那并不自然"——但这是除编码工具之外"我们扩展代理贡献的最大杠杆"。系统提示词如今被奋力压到最短；全部 100 多个工具完全公开（"问代理就知道"）："我们不认为系统提示词是我们的秘方。作为运营者，你需要能审问这个系统：有哪些工具、怎么工作、该怎么提示。"Sarah 甚至说得更狠："我们并不力求让它尽量易用——越把可解释性抽象掉，越会削弱代理的能力。"Custom Agents 期间的一次集体对齐就是："我们不是在为所有人Build，不为让任何人都能看懂——那会削它的能力。"（`00:51:34–00:56:40`）

### 自设置代理、flippy 与定价

Custom Agent 的"元提示生成器"其实就是代理本身：它不仅有工作工具，还有设置与调试自己的工具——让它写系统提示词，就是它在干这件事；失败了可以问"为什么失败"，再让它更新自己的指令以防再犯（自动自愈在路线图上）。这里藏着一个微妙的权限设计：Custom Agent 默认无任何权限，一切都要显式授予——这正是你能信任它后台运行的原因；而"自我修复"会破坏这一点（它不允许编辑自己的权限），所以修复按钮进入的是一种管理员模式：同步聊天、可以看到它的动作、改动前确认。swyx 点赞的设计细节是"编辑聊天与使用聊天是同一个聊天"——团队内部管这个叫 flippy：最初设置页为主、测试为辅，AGI pilled 的想法是"一切皆代理"后翻转——主视图是聊天，设置只是旁边预览变更的侧栏，理想状态是永远不必手动碰设置。为此发布痛苦地推迟了一个月，实现者是来自三个不同团队的三名工程师——"公司已经到了这种事没人抱怨的程度"（`00:56:40–01:01:12`）。

定价采用 credits 作为 token 之上的抽象，因为成本结构不均匀：自研与开源模型跑在自己的 GPU 上、网络搜索是另一种计价、未来的沙盒又是一种；还有模型档位与服务层级（优先 vs 异步、缓存率差异）的权衡。出发点是"客户为合理的用量付费"，企业买 credit 包有折扣也顺了销售流程。价值差异化定价被讨论过但被否决——"市场还没到那一步，而且定义什么算复杂本身就复杂"；更现实的动机是margin：如果数据库自动填充的每个单元格都跑一个 Opus 代理，"那是几十亿美元"——必须让重度用户有出口，而不是把高成本摊给所有人。产品里甚至有悬停提示告诉用户某个选择"更贵也更慢"，因为"异步场景里人们不在乎 Haiku 更快"。而"auto"档要向用户解释的不是"最便宜的蠢模型"，而是"最适合该任务的模型"——Sarah 的类比是 robo-advisor："你可以天天盯市场，也可以买指数基金。"另一个反驳实验室的观察是：前沿实验室的 SKU 只会越来越强、越来越贵，而"reasoning 模型半年前所在、nano-haiku 们还没追上的那个无人区"正由开源模型填补（Notion 已提供 MiniMax，并与开源实验室合作优化 Notion's Last Exam）——"智能-价格-延迟的三角形还没有被填满，模型都聚在两个角上"（`01:01:13–01:09:01`）。

### 不训练基础模型、为代理重造检索与会议笔记

为什么不训练自己的基础模型？Simon 的坦白是"我烧过大量时间在训练实验上，非常诱人"，Sarah 则是"来找他谈预算的人"。结构性原因是错配：Notion 的工具每天都在变，为工具微调一个模型等于"赌前沿能力不会覆盖它，赌你能在那之前建好"——而"99% 的问题其实只是某个工具里的 bug，修 bug 就行；训练只是一个实现细节。真正值得想的是外环：怎么提升速度与稳健性、造更好的工具、更好的 harness、验证它有效"。他们真正加码模型训练的地方是检索与排序——企业 AI 套餐的搜索流量 majority 已来自代理而非人类：查询的结构不同、返回结果的要求不同，"位置排序的重要性下降，进入 top-K 更重要"（用点击率训练的排序模型与这种需求错位）；snippet 的取舍也变了；新内容类型（代理 setup 生成器、会议笔记）甚至打破了块状嵌套索引模型。他们在招排序工程师与模型训练工程师（以排序为主），并把"排序"与"并行穷举查询"视为通往同一用户结果的两个工具；查询多样性本身也交给模型（一次并行 8 个不同角度的查询）。"我们不再花时间优化向量嵌入的选择——那已经不是正确的优化杠杆了。整个旅程叫 agentic find。"（`01:09:01–01:17:12`）

Meeting Notes 被重新框定为"数据捕获"而非转写：起初他们担心要教用户一种新工作方式，结果它成了最大的增长杠杆之一（采纳的病毒性与留存都极强）。Sarah 自己的用法是：所有 1:1 与会议都有 Meeting Notes，写绩效自评时回看与经理的全部对话——"没在 1:1 里提过的事，多半与绩效无关"——这为系统记录增添了强优先级信号，也为代理与搜索带来了内容爆炸（compaction 机制正是被"会议笔记进上下文"倒逼出来的）。内部的工作流已经闭环：站会前由 Custom Agent 扫 Slack 与 GitHub 生成 pre-read 会议笔记，会上讨论，会后由挂在日历上的代理落任务、发 Slack 跟进——"我们的会议已手不离键盘，专注问题本身而非问题的簿记"。Simon 最被震撼的新功能：总结时会 app mention 被提及的人（用代理推断"哪个 Simon"+人员相似度缓存与生成的个人档案），于是他如今会在有人会议里谈到他时收到通知。组织上，Meeting Notes 是 Notion 少有的完全垂直的团队（质量+产品+UX 的老虎团队）。至于硬件——OpenAI 都在做设备了，Notion 会做吗？Simon 的答案是"大概率不会"：可穿戴是"深度个人"的问题切片，"你的公司不会强迫所有人戴腕带"；Sarah 的表述是信条级的："我们的工作不是做出最好的 agentic harness，而是做人们协作的最佳场所；不是造最好的会议捕获硬件，而是让会议笔记住在最好的地方。"可穿戴伙伴们反而都找上门来要求接 Notion 的搜索与上下文（`01:14:07–01:23:45`）。
