Latent Space 本期是 AIE CODE 大会（AI Engineer 旗下，2026 年 11 月 10–12 日，旧金山）的前瞻节目：Warp 创始人兼 CEO Zach Lloyd 与主持人 swyx 对谈他反复布道的「软件工厂」——一个运行在云端、由代码定义的智能体系统，任务从 Slack、Linear 等入口进入预定义工作流，全程留痕，用打分器与重放基准持续度量，把「选模型、配 harness、调工厂」从凭感觉变成靠工程度量。（`00:00:46–00:01:31`，`00:02:23–00:03:06`，`00:13:06–00:14:06`）节目最有信息量的三块：一是 Warp 的完整参考架构——从 Terraform 式声明定义、集中数据层、可插拔沙箱与开放推理，到编排器与多入口；（`00:19:31–00:26:08`）二是内部实战数字——单个 PR 成本从约 80 美元压到 15–20 美元、月吞吐提升 40% 而回滚率未升；（`00:24:02–00:24:48`）三是坦率的适用边界与成本账——5 到 10 人以下别上这套、API 计费比订阅贵 5 到 50 倍、纯编码智能体生意难做。（`00:27:14–00:27:51`，`00:31:06–00:32:21`）适合正在搭建内部编码智能体平台的平台团队、DevX 与技术管理者。

## 主题正文

### 软件工厂是什么：把「一堆自动化」变成一个可运行的实体

主持人片头介绍，Warp 已演进为一座开源的软件工厂，Zach 在 AI Engineer 大会关于软件工厂的演讲正在走红；他还给出一个判断：这套东西正在成为「桌面筹码」——你会想要云、控制平面以及团队与安全等基本特性。本期是 AIE CODE 大会（11 月 10–12 日，旧金山）的前瞻内容，Zach 将在会上做软件工厂主题演讲、回顾这一年并预告下一步。（`00:00:12–00:01:31`）Warp 落地页首行写的是 open infrastructure for cloud software factories——为云端软件工厂而生的开放基础设施。（`00:02:06–00:02:11`）

Zach 给出的定义是：软件工厂是一个运行在云端的智能体系统，你在其中定义各个智能体在为团队或产品构建软件时的角色；系统带有一定自主性——智能体可以自行做事；并且应当是可度量、闭环的，团队可以随时间对它调优、测量、做基准，逐步建立起对这种智能体开发方式的信心。（`00:02:23–00:03:06`）他观察到的常见误区是：来找 Warp 的公司大多在把不同的自动化串起来，或者把「大量使用智能体交付软件」直接称作内部软件工厂。Warp 的主张是把它具体化——工厂应当用代码定义，工作流、技能、MCP 都是其组成部分，是一个能在某个时点真正跑起来、并可测量表现的对象；Warp 的口径是每个产品面对应一座工厂。（`00:03:08–00:04:30`）

结构上，工厂作用于某个产品面（比如移动应用或服务端应用），操作一组仓库，配备所需的技能与 MCP，并挂一条与团队现有实践大致对应的工作流——例如分诊（triage）、规格化（specing）、实现等步骤；整条工作流用一个 YAML 文件定义，声明可用仓库、MCP 与接入的集成。（`00:04:30–00:05:35`）使用方式上，做产品工程的人不需要直接操作工厂本身，而是通过既有工具投递任务——在 Slack 里派活、用 Linear/Jira 任务、经 GitHub 交互，或通过 API 与 MCP 调用；工单进入工厂即触发预定义的代码化工作流，服务器报错这类自动化事件同样汇入同一系统。（`00:05:35–00:06:40`）

### 闭环的第一半：全量留痕、成本度量与 LLM 打分器

工厂跑起来后的第一个收益是可观测：无论智能体在哪里运行，你都能拿到全量 trace——Warp 内部用它观察自家各团队如何使用工厂；这不仅是「看看大家在干什么」，而是把全团队的智能体会话与产物集中起来，而这些记录正是闭环系统得以改进的关键输入。他以内部一位成员在 Slack 中开发移动应用的任务为例：从完整会话记录、计算机操作截图到编排智能体每一步动作都有档案——而且不只一条任务如此，每一件事都如此。（`00:06:45–00:08:07`）他对比的行业现状是：多数公司还没有这种中心化，工程师大都在本地终端里各自使用 Claude Code 或 Codex；有了中心化才能对全公司的智能体编码做数据分析。（`00:08:07–00:08:41`）

度量维度包括团队侧的传统 DORA 指标（交付时长）、自动化程度——对每个合并的 PR 统计人工介入了多少次、吞吐与成本；他强调成本尤其重要：要用合适的模型与技能把单个 PR 成本逐步压下来，并支持按人、按自动化环节、按软件开发生命周期阶段切片。（`00:08:41–00:09:27`）质量侧是他们称为 scorers 的在线评测：从很通用的问题看起（智能体是否太啰嗦、是否高效、代码质量如何），平台提供开箱即用的一组，企业也可以针对自己的特定失败模式自定义，同样全部用代码定义。（`00:09:27–00:10:29`）机制上，打分器背后是对存储下来的历史智能体会话（runs）做事后评分，形态类似 LLM-as-a-judge——选定评审模型、评审提示词与采样率，因为智能体一直在跑，必须顾及评审本身的成本。他举的典型失败模式是冗余测试：编码智能体常在摸索实现的过程中顺手写一堆并不需要的测试并留在代码里，撑大代码库、浪费 token；对应的打分器就能把这类问题找出来。（`00:10:29–00:11:48`）

这套工具的主要使用者并非一线工程师，而是平台团队/DevX 团队与工程管理者——他们要回答的是「我们公司怎么把 Claude Code 或 Codex 用到最好」。（`00:12:16–00:12:53`）他把通用原则总结为：一切被存储、一切可观测、一切可测量，只有这样才谈得上用工程化的严谨来改进编码智能体；围绕新模型新 harness 的社交媒体争论（Pi、Claude Code、Codex、Cursor……）应当从凭感觉转向靠度量——公司会想要一套这样的系统，无论用不用 Warp 的产品。（`00:13:06–00:14:06`）

### 闭环的第二半：会改进自己的工厂与跑在自己数据上的基准

在打分器之上还可以再挂一层自动化与「自我改进」：人们除了在 Slack 派活，也会配置各种触发器向工厂投递工作；另有一类智能体盯着工厂评分，寻找表现不佳的地方并建议改动。内部实例是自我改进智能体审查分诊（triage）步骤后，找出 54 个「如果分诊智能体能派生子智能体做调查会更好」的失败案例；由于整座工厂由代码定义，这些编码智能体可以直接对工厂定义提交 PR 来改进工厂本身——一条内建在系统里的学习回路。他同时明确了条件：把任何建议改动拿去重放历史 runs、验证它确实带来改进的能力还没有做，属于下一步计划。（`00:14:06–00:16:02`）

最后一块是基准测试（benchmarking）：把系统里跑过的编码智能体任务加入基准套件——比如精选一批前端编码相关的 runs——然后把这批任务重放到「模型 × harness」的配置矩阵上。他强调不应只换模型，也要能换 harness：Warp 有自家 harness，但支持对 Claude Code、Codex 或 Pi 做基准对比，模型自选；产出的结果形态类似 SWE-bench 或 Terminal-Bench 的公开结果，只是跑在公司自己的真实运行上。（`00:16:07–00:17:18`）演示图是一张成本-正确率散点图（目标在左上角：更低成本、更高正确率），数据来自「已稍旧」的模型：GPT-5.6 在该任务集约 95% 正确、平均成本约 6 美元，GLM-5.3 Flash 约 93% 正确、约 2 美元；这些信息再反哺按你自己的工作流与代码库定制的模型/ harness 路由策略。（`00:17:18–00:18:02`）他把这个大方向命名为工厂工程（factory engineering）：用真正的工程思维回答「作为团队与公司，我们是否以正确的方式部署了编码智能体」；他说这种思路正在引起很多想自建同类系统的公司共鸣。（`00:18:02–00:18:42`）主持人打趣：这场思想运动的极致是让所有人最终都在试图造一个 Warp——哪怕用的不是 Warp。（`00:18:49–00:19:00`）

### 分层参考架构：把工厂当基础设施来设计

抛开 Warp 自建的话，Zach 建议把它看作一个栈。栈底是基础设施：以声明式代码定义工厂，类比 Terraform，但收益更多——除了整个开发生命周期的版本化视图、开分支测试、改坏回滚这些版本控制的常规好处，还有一条特别的：因为定义在代码里，编码智能体可以对工厂本身提出改进建议，这正是自改进软件工厂的地基。（`00:19:31–00:20:38`）

上一层是汇聚智能体产出信息的地方：你需要智能体会话、智能体工件，以及从所有工具到结果的完整交互记录——典型链路是会话从 Slack 开始、在 Linear 继续、到 GitHub 出现代码评审评论，最终合并代码，甚至上线后引发服务器崩溃；要能事后（多半用智能体，也可以人工）回溯诊断哪里本可以做得更好、失败出在哪。（`00:20:38–00:21:52`）同时要有把数据接进来的方式（插入 MCP）；公司变大后还要按组织切分访问权限——市场、销售、工程团队各自能访问哪些 MCP。（`00:21:52–00:22:20`）

算力层应视为独立组件且保持可插拔：市面上已有多家智能体沙箱供应商，Warp 主用 Namespace，但换成 Daytona、Modal 或 E2B 在架构上也应当可以；按需覆盖不同平台，默认多半是 Linux 类沙箱，而涉及计算机操作（比如他们测试 iOS 应用）就要能起 Mac 虚拟机、跑模拟器并点按操作。（`00:22:20–00:23:11`）推理层的态度是开放：很多公司手握与 Anthropic、OpenAI 或 Google 的既有合同额度要消化，所以 Warp 既允许自带推理供应商，也可以直接向 Warp 购买推理；甚至可以插入自己的 harness——他认为这是件大事，可编排 Pi 等以及任何 ACP 兼容的 harness；再往上是改进层，即演示里展示的、整个系统真正的威力所在。（`00:23:11–00:24:02`）

他给出 Warp 内部数据作为佐证：刚采用工厂方式时单个 PR 成本约 80 美元——Opus 用在了不该用的地方、分诊智能体配了过强的模型、子智能体数量也过多；经过一轮内部调优与测试，成本降到约 20 或 15 美元；最近一个月 PR 吞吐提升了 40%，回滚率没有上升。他表示对「观察、度量、调优」这条总路线很有信心。（`00:24:02–00:24:55`）

栈的上层还需要一个编排器（orchestrator）：拿着工厂定义代码，把工作沿各阶段推进——调用正确的模型、装载正确的技能、触发正确的自动化；有人把编排器说成整个平台，他认为它只是其中一块。（`00:24:55–00:25:22`）最后是接入点：Warp 的哲学是把工厂带进公司既有的知识工作工具——最明显的是 Slack（Warp 约 60% 的任务从 Slack 发起），有时从任务管理工具发起更合理，习惯终端里 Claude Code 的开发者也可以在那边做完后把 spec 提交进工厂；整体做成 API 驱动、MCP 驱动，工厂本身像一块带多个入口的无头（headless）基础设施。（`00:25:22–00:26:08`）这套栈式视图在与公司交流时反响很好：它是开发者基础设施栈里的新一层，位置在 CI/CD 再往后一层，多数公司都会长出类似的东西。（`00:26:08–00:26:29`）

### 适用边界与成本现实：谁该建、谁别建、以及订阅补贴下的生意经

主持人以「一家 B2B SaaS 的 CTO」的视角追问：这些层是否每层都需要、这套东西到底为谁而设。（`00:26:49–00:27:06`）Zach 的回答很直接：最有共鸣的是有一定规模的公司；只有几个人的小团队上这套是过度工程——别这么做，直接用 Claude Code 或 Codex 的订阅反而更快。（`00:27:06–00:27:27`）规模下限他估计在 5 到 10 名工程师左右，上限到大公司都适用；公司越大，落地所需的实施工作越多——在企业自己的基础设施里立起这套东西并不是纯即插即用。（`00:27:42–00:28:15`）他描述了一个相对自服务的区间：约 10 到 100 名工程师的快速成长期公司，只要用的是 Slack、Linear、Jira 这类他口中「happy stack」的常见组合，接入就能很快见效——主持人当场追问「你刚才是叫它 happy stack 吗」，他解释这是他对初创公司常见集成组合的叫法。（`00:28:15–00:29:01`）他补充说，团队不必很大就能受益：服务器崩溃频道、用户反馈频道的信息可以直接喂进工厂开工，工厂还能按谁熟悉对应代码把相应同事拉进来；即便是 Devin 这类产品，在 Slack、Linear 这类原生多人环境中也能获得部分类似体验。但他也重申，小团队不适合，它真正适合的是想趁模型与智能体持续演化时，先立起一套可持续依托建设的基础设施的公司。（`00:29:02–00:30:00`）

不适合的客户画像有两类：基础设施非常定制的公司，以及他点名的 Uber、Ramp——它们自建这套东西，内部开发团队非常庞大；对很小的团队，用订阅确实更经济，这又回到规模问题。（`00:30:24–00:31:06`）

经济学部分是这期访谈最坦率的段落。很多人直接按 API 计费，而按他的说法，API 计费比买一堆订阅贵 5 到 50 倍。（`00:31:06–00:31:23`）节目讨论中提到，确实有小团队靠轮换一批 200 美元档的订阅过活（有人数过多达 17 个）；是否违反服务条款，说话人坦言并不真正清楚——只要能这么做，那是最便宜的方式，代价是失去中心化带来的种种好处、不可扩展，公司长到一定规模后也必然不会再被允许。节目中还给出了一组数字：200 美元的订阅计划约折合 8,000 美元的 API 用量。（`00:31:23–00:32:21`）

由此他给出生意层面的判断：从商业角度看，这是他不想做「纯编码智能体」生意的原因之一——你没法在一个成本高得多的底座上造出有竞争力的编码智能体；在他看来 Cursor 很出色、做到了（其后关于退出与转向的评价转写含糊，本文不采用）。Warp Factories 的定位因此不同：不做转售 token 的产品，而是做编码智能体优化平台与生产力平台——这反而是优势。（`00:32:21–00:33:13`）至于还独立存在的编码智能体，他数了数：基本就是 Cognition 和 OpenCode，「哦，还有 Factory」。（`00:33:13–00:33:24`）

收尾是预告与行动号召：他将在 AIE 的演讲里谈「工厂工程」越来越普遍的世界里工程师意味着什么——工程分两种：产品工程与工厂工程，后者要回答用什么工具、如何修炼技能去工程化那个建造软件的系统，而不只是直接建造软件；Warp 正在招聘工程师、市场、数据与设计岗位，他也在 X（@zachlloydtweets）上持续分享关于工厂的思考。（`00:33:37–00:34:40`）
