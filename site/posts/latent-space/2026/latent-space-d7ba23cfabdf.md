## 速读

一年前 Cognition 发过著名的《Don't Build Multi-Agents》；如今他们的合并 PR 两个月涨了 7 倍，Devin 在自家仓库的 commit 占比从 1 月的 16% 涨到 3 月的 80%，而工程 headcount 只增加了约 10%。这期节目请来 Walden Yan 和开源后台 Agent 系统 OpenInspect 的作者 Cole Murray，把"背景 Agent"从概念拆到螺丝钉级别。

最值得带走的三点：brain 与机器分离不只是安全偏好，而是权限治理的干净解法；测试远比 computer use 难，真正的功夫在跨服务编排；以及一个所有团队都该记住的警告——不审计 AI 代码的团队，代码库会退化到"最差工程师"的水平。

## 主题正文

### 2025 年 12 月的转折与 7 倍增长

Cole 把行业分水岭定在 2025 年 12 月：Opus 4.5 和 GPT 5.2 的能力跨过了一条线，从"扶着模型走"变成"基本可以放手"——只要规格说明写得够好，就能从 spec 一路到完成的 PR。这个范式让后台 Agent 第一次变得实用（`00:00:43–00:01:41`）。Walden 回忆 Sonnet 3.7 时代那一跳时说，当时"一夜重写 Devin"的很大一部分其实是删掉——模型变聪明后，大量补偿性脚手架不再需要；而最近几个月的增速比 2025 全年还陡（`00:01:57–00:03:01`）。两个内部数字被主动公开：合并 PR 数月环比 7 倍，而工程 headcount 只涨了约 10%；Devin 提交在所有 Devin 仓库中的占比 1 月 16%、3 月 80%。这也是"人人都在自建 Devin"的背景——Shopify、Stripe 到 Ramp 都在造自己的后台 Agent（`00:03:01–00:03:49`）。

OpenInspect 的由来很轻：Cole 的客户们在 Slack 里用 Claude，痛点是会话属于发起者——PM 发起的会话工程无法接入，只能复制粘贴结果，这本身就被判了死刑。Ramp 发布自建 Agent 的博客后，他把已有的零件拼起来，让 Claude 和 GPT 照着博客现场搭了一套，全程直播推文，然后开源（`00:03:49–00:06:16`）。为什么不商业化？他的账很清楚：不想去竞争 20 美元一个席位的生意——核心部件很容易被复制（他自己很快就建成了），而且你不拥有全栈：沙箱层（Daytona、E2B）在赚钱，模型层在赚钱，夹在中间卖基础设施和集成是个尴尬的灰色地带（`00:06:36–00:07:59`）。Walden 顺着补了 Cognition 实际卖的三样东西：不用你操心的算力层（两年前用 EC2 裸 VM，休眠唤醒要冷等 10 分钟，只能自己造）、企业采用与 onboarding 服务（大企业里想做的人很多，但项目规划和 AI 素养跟不上，需要一支工程师团队帮你接集成、建自动化），以及产品本身（`00:07:59–00:09:56`）。

### 架构：brain 与机器分离，repo setup 是永远的痛

后台 Agent 系统的第一个架构决策是 harness 放箱内还是箱外。放箱内的问题主要是安全：Agent 在沙箱里跑，secret 就得进沙箱，AI 行为不可预测，很容易意外外泄；放箱外则把"大脑"放在控制平面的 worker 里，沙箱只是被工具调用操纵的"双手"——代价是状态管理复杂得多（`00:10:11–00:12:08`）。Devin 从第一天就选了分离，理由很实用：机器上只放最小作用域的 secret，机器上的一切都默认可被用户/Agent 自由操纵，而大脑从机器不可达——这样"给每个用户一个 GitHub App、权限各不相同"的多租户场景就干净了，还能复用已有的开发机基础设施（`00:12:08–00:13:49`）。Cole 认为箱外是更好的架构但要付复杂度的代价，OpenInspect 目前在箱内、长期会迁出（`00:13:49–00:14:07`）。

其次是如何管理"箱子里有什么"——Cognition 内部叫 repo setup，是公司创立以来的常青难题：仓库在变、依赖在变，Agent 的工作环境怎么保持最新、凭证怎么配。Cole 的咨询业务里一半工作就是这个：多数团队的 dev 环境根本不存在或靠"去找 Bob 要 secret"，这对 Agent 是死路（`00:14:07–00:15:48`）。关于 Docker，Walden 的判断是它不适合做这层抽象：容器本就不是真正的安全边界，而真实应用自己还跑在 Docker 里，套起来就成了怪异的 Docker-in-Docker。Devin 因此用了完整 VM（底层是 Firecracker 虚拟化）——现在有真实价值的原因是 Agent 要真的把应用跑起来、点一遍、给你录屏；Android 支持则需要 VM 里再嵌套一层模拟器，坑还很多所以仍在 beta（`00:15:48–00:18:08`）。Cole 的建议朴素有效：本地开发者用着舒服的环境，天然就是 Agent 好配置的环境；OpenInspect 用 setup 脚本预装、预快照秒起、恢复钩子把微服务状态拉回来（`00:16:57–00:18:08`）。

### 测试比 computer use 难，难在编排

Walden 纠正了一个流行误解：大家把"AI 测试应用"等同于 computer use——发对坐标点对按钮，但那是最简单的部分。真正的测试是推理问题：一个横跨前端、后端和更深服务的改动，要先想明白怎么把这几个服务用正确的版本跑起来并互相配合，然后怎么触发要测的行为——可能需要管理员权限、需要打开某个 feature flag、甚至要开两个会话往其中一个发特定关键词。这需要大量代码库上下文和专门做的编排，有些场景连一个 frontier 模型都端到端搞不定，他们见过必须把多个 frontier 模型编排起来才能完成的案例（`00:19:13–00:20:58`）。产出物是那段著名的演示：PR 完成后点"testing approved"，Agent 回传一段视频，画面底部有它标注的"我现在在测什么"，光标在页面上移动——swyx 说这是"少数 AGI 时刻"之一：看完视频就不需要看代码了，"我想直接在 Slack 里合并"（`00:22:40–00:23:19`）。

围绕合并体验的打磨占了大量工程：Devin 可以直接在 GitHub 上被评论并响应；Devin Review 会在自己的 PR 上发评论然后自己去修——听起来像死循环，实际上靠"评论必须高信号"+"Agent 判断哪些该立即修、哪些该回怼"来避免。Walden 最喜欢的时刻就是 Devin 告诉他"你错了"（`00:23:19–00:25:06`）。集成侧同理：给 Agent 一个 Slack MCP 只能让它发消息，而 Devin 在 Slack 里是当同事用的——webhook 回调、自然回复、不刷屏，这些都要在 MCP 之外自建。Walden 的结论是希望有比 MCP 更有表达力的双向协议，但 MCP 一复杂就失去"一步连接"的承诺，最后还是回到自建第一方集成（`00:25:42–00:28:43`）。

### 记忆、多 Agent 与"两周定理"

记忆被 Cole 直言"尚未解决"。Devin 的 Knowledge 系统走了几年弯路后的形态是：不指望用户主动教，而是在你纠正它时主动问"要不要记住这个"，一键批准——约 95% 的记忆来自自动生成。难点两头都有：生成端要区分"这次要 draft PR"和"Cole 一般喜欢 draft PR"；检索端要在几千条记忆里精准取用而不撑爆上下文，靠大量 eval 维持跨模型的稳定。记忆还可编辑更新，下一个探索方向是让记忆更像文件系统、让 Agent 自己导航维护（`00:28:59–00:33:01`）。延伸出的玩法是"常驻 PM Devin"：在 DeepWiki 的 Slack 频道里放一个永不休眠的 Agent，自带 memory.md 维护优先级清单、定期 at 人——把 Agent 用到工程流程的上游（`00:33:01–00:34:00`）。

对多 Agent，两人的立场是"务实地冷却"。给 Devin 开了 MCP 让它们互发消息、随意创造同伴的结果是"一个非常混乱的世界"，日常最佳实践仍是单个 Devin；并行要靠隔离——每个 Devin 自己的盒子、不共享机器，把冲突空间挤掉。sub-agent 倒是真实有用：让子 Agent 去找文件、查实现，token 和工具调用折叠成一个答案回到主 Agent——但这更像工具调用而非"两个协作者在对话"（`00:36:16–00:40:53`）。让 Walden 对多 Agent 重燃信心的信号反而是行为层面的：Devin 会反驳用户了——两个看过不同信息的 Agent 能辩论出谁对，而不是互说"You're absolutely right"，这是多 Agent 世界的必要条件。另一个反直觉实验：让单个 Devin 长时间自管理上下文去干疯狂任务（比如重建一个 Windows OS 级别的系统），比 swarm 成功率更高（`00:40:53–00:42:25`）。而纯 vibe coding 的极限他们真的测过：内部用"全自动合并、零 code review"的方式做真产品，2025 年 12 月的状态是最多撑两周——之后你会发现一个按钮的颜色在十个地方有十种实现，漏改一处就穿帮，"还是得回到 code review 和定期清理"（`00:43:55–00:45:03`）。

### 代码库会退化到最差工程师的水平

Cole 的警告值得每个团队贴在墙上：拥抱 AI 原生编码的团队最常见的失败模式，是那个对 AI 最狂热、最不审计代码的工程师——他的模式被 AI 当成"这里就是这么写的"的范例，然后指数级繁殖 slop。你会收获 12 个格式化日期的 helper。对策是定期清理（人力或专门找重复的系统）加上 swyx 说的架构纪律：模块边界要硬，黑箱内部随意，边界契约必须人签（`00:44:54–00:46:44`）。具体的"AI 味"与防线：Python 里 Agent 爱写 `getattr`——本质是 reward hacking，不想让代码报错，Claude 侧已经把"出现 getattr 就让 PR 挂掉"设成 lint 规则；GPT 系爱"不惜一切代价向后兼容"，为不改模块名做奇怪的 import/export；还有满屏的 `dict[str, Any]`。有趣的是 Opus 4.7 的新习惯：在每个函数头上写 PRD 式长注释——但内容是推理过程、备选方案与取舍，"信息过量，但方向可能是对的"，甚至可能是自维护系统的雏形；GitAI 那类把 prompt 存进 git metadata 的做法是同一主题的隐蔽版（`00:52:25–00:55:01`）。

企业落地清单里最被低估的一条是本地可测性：Agent 要能不碰生产凭证就跑通全流程，就得有本地 DB、本地 Docker Compose、Postgres 和 mock server——"公司越老，要改的越多"，好在如今可以靠 AI 来做这次迁移（`00:56:10–00:58:30`）。用例侧，Cole 看到最多的三类：SRE 自动分诊（Agent 作为告警的第一响应人，接好生产日志与只读数据库，报错到 PR 全自动）、非工程师写代码（PM 遇到小 bug 不再建 issue，直接在 Slack 里说一句，PR 就出来了）、客服支持（客户问题在 Slack 里 @ 一下，全上下文就绪，工程介入时无需再问"能提供更多信息吗"）。预算的经验值是每工程师每月 1000–5000 美元；Walden 预测今年的大主题是混合系统——sub-frontier 模型做快速大部分、按需升级到 frontier，拿住性能与成本的两头（`01:00:45–01:06:10`）。招聘口味也随时代：Cognition 最想要"有高品味的产品工程师"，标准是"你端到端交付过让自己骄傲的产品吗"（`01:06:51–01:07:45`）。
