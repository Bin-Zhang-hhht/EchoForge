## 速读

Latent Space 邀请 Legora CTO Jacob Lauritzen（ASR 转写作 Lauridsen，官方页为 Lauritzen）谈法律 Agent 的工程化：从「ChatGPT 加瑞典法律检索」起步，到 Tabular Review 单日处理近百万格的尽调审阅，再到不能查看任何客户数据时如何靠评估近似真实用量。这期最值得听的不是单点功能，而是一家垂直 Agent 公司如何用少数核心原语拼出大量产品、如何在模型供应商迭代中保持 Pareto 前沿，以及对法律行业合伙制与计费模式松动的判断。（`00:00:36–00:01:05`）

## 主题正文

### 起点：法律检索 Agent 与被行业「借用」的命名

Legora 的起点极其简单：一个内置瑞典法律检索的 ChatGPT 式工具，「这就是全部的起点」。法律研究本身是个大市场——律师要花大量时间找相似判例、确认法律先例，早期的形态就是一个可以提问、查询法律的 Agent。（`00:02:14–00:02:39`）此后能力逐步扩展：起草文件、编辑 Word 文档、整理归档、跑复杂分析。（`00:02:46–00:03:03`）

其中一个功能叫 Tabular Review——Bulk 提取与审阅大量协议，用于尽调或融资场景。Lauritzen 有点得意地提到，Claude for legal 已经在用他们的术语来命名同类功能。（`00:03:03–00:03:12`）产品从「做工作」扩展到「编排工作」：Lists 定位类似 Linear，Intake 用于与客户协作，Portal 则覆盖律师与律师、客户与律师、甚至 Agent 与 Agent 之间的协作。（`00:03:27–00:04:06`）

公司节奏上，Legora 参加了 YC 2024 批次，而嘉宾本人此前是 YC 2023 的创始人；从助手形态切换到 Agent 形态大约是一年前。（`00:04:15–00:04:33`）公司原名 Leia，西班牙报纸曾把缩写解释成「Legally Efficient Yoda Assistant」——他笑着补刀：「幻觉不只是 LLM 的问题，记者也会。」（`00:18:13–00:18:53`）

### Tabular Review 与 Lists：少数原语撑起大量产品

Tabular Review 的用户流程以尽调为例：把一万份雇佣合同放进去，每一行是一份合同，每一列是一个问题——解约通知期多久、有没有 IP 归属条款、解雇要赔多少。（`00:34:31–00:35:17`）也可以直接丢给 Agent 一句「做尽调」，它会自己拉起 Tabular Review、跑完全部、分析结果并标出红旗——比如 CEO 薪酬异常或奇怪的奖金结构——再起草给客户的备忘录。（`00:35:17–00:35:46`）所有产出都带回到源文件的引用，可以逐层点下去核验。（`00:35:54–00:36:12`）

规模上他们单日最多处理过约一百万个单元格。工程上的关键习惯是「先跑前 10 行」：先小规模验证提取结果符合预期，再全量铺开。（`00:37:16–00:37:53`）底层用的是 ag-Grid，用户乐意直接住在表格里而不是导出 Excel。（`00:36:21–00:37:10`）

Lists 是另一个核心原语，定位接近 Notion 数据库：可以配置触发器与自动化，Agent 能创建列表、列表能触发 Agent、Agent 也能读列表——「Agent 集群就这样活了起来」。（`00:39:15–00:40:07`）Intake 则是法律专用的 Slack 入口：请求进入特定列表，律师与 Agent 在 Legora 里处理完再回流到 Slack。（`00:37:53–00:38:52`）Lauritzen 把这层灵活性视为内部加速器——即使不暴露给最终用户，法律工程师也能用它极快地拼出「自定义产品」，比如基金管理仪表盘；收购的英国公司 Wexler（诉讼场景的事实情报）也构建在同一原语上。（`00:40:21–00:41:39`）

他的扩张哲学由此而来：客户要的东西很多，竞争激烈，纯靠拒绝会输。他的工作是「搭建一个系统，让客户觉得我们造了很多东西，而我们实际只造了少数几件」。（`00:50:20–00:51:25`）Agent 本身就是当年没人主动要求、但团队判断行业方向而下的注之一；协作内嵌是另一个。（`00:52:00–00:52:39`）

### 评估热图：模型会回退，跟踪要自己动手

Legora 有一支专职评估团队，按法律细分领域 × 任务类型追踪各模型表现，形成一张大热图。（`00:08:44–00:09:16`）评估的构造方式是「世界」式的 RL 环境：给一个一万文件的数据室做尽调，定义一份好报告长什么样、要含哪些红旗、要简洁。（`00:09:23–00:10:07`）

团队构成是三工程师加三律师，外加一个约百人的「法律工程师」池——在大所做了三四年、有 CS 学位、转向技术的一线律师。这是他们最难招、也最有杠杆的人才：既做评估又参与产品塑造。（`00:10:07–00:11:03`）

两个观察值得所有应用团队参考。其一，模型发布常「部分提升、部分回退」，所以热图必须自己盯。（`00:09:06–00:09:16`）其二，在模型快速进步期，复杂评估可能不值得投入——曾经有个引用格式问题，他们什么都没做，下一次模型发布直接从 70% 跳到 99%。（`00:11:09–00:11:42`）子 Agent 的扇出式检索查询则是从「之前很难」进化到「现在非常好用」的典型。（`00:08:44–00:08:55`）

### 法律行业的未来：能力分布、合伙制松动与计费转向

对「模型够不够好」的答案是能力分布：约六成工作现在就能做好，剩下的是成本与时延问题；但对极复杂的分析仍需要更强的智能，而且律师的工作范围会随智能扩张。（`00:07:48–00:08:14`）

宏观判断是他谨慎范围最大的部分（开场即声明「我不知道」）：律师整体生产力会大幅提升，把时间转向风险判断、策略与客户关系，减少翻文档找「冒烟枪」式的琐事。（`00:13:24–00:14:18`）合伙制存在的原因是律所唯一的资本就是人力资本，合伙制让人力资本所有者留下来；他希望帮律所把「某律所的做事方式」固化成可自改进的知识图谱、判例库这类持久 IP，但现在合伙人缺乏固化经验的激励——离开时拿不到自己建的资产的分红，激励结构需要改变。（`00:14:18–00:16:34`）

计费模式已在松动：美国市场越来越多按项目收费而非按小时，低端审阅有的免费做（换取客户关系）、有的走固定费率。（`00:19:02–00:19:36`）至于开场那句标题党式的「律师助理消失了、初级律师消失了」，他承认是夸张的喜剧效果——实际观察是「这并没有发生」，优秀初级律师的价值反而更高，只是两极分化更严重。（`00:16:43–00:17:55`）

### 隐私约束下的工程：看不见数据，也要把产品做好

这一行最独特的工程约束是：Legora 几乎不能看任何使用痕迹——数据室里的数据大多属于客户的客户，高度保密。（`00:27:02–00:27:39`）替代方案是多层收敛：把失败模式归类到已知的十到二十种、把任务与执业领域分类，用便宜的 LLM 消息做在线评估指标，配合功能开关对比新功能上线的升降。（`00:26:25–00:28:42`）对客户提供的材料，他们选择「最安全的方式」——尽量彻底匿名化复现问题。（`01:00:24–01:00:44`）

云选择的历史也很有行业特色：早期律所不信任 AWS 与 Google，「微软已经审过我们 365 了」，于是全部基础设施放在 Azure。这个转变只用了三年，本地部署的声音已经基本消失。（`00:28:50–00:29:44`）

模型策略上他称之为「模型套利」：按任务在能力、时延、成本、治理与区域可用性之间寻优。部分任务用开放权重模型，部分做后训练，部分直接用前沿模型。（`00:30:11–00:30:36`）具体例子：早期某版 Gemini 对转写与说话人归属极好；微软的转写模型也「比老版 Gemini 好」；Eleven Labs 反而不用——数据处理协议（DPA）的供应商名单必须收得很紧。（`00:30:47–00:31:39`）转写在法律领域仍是硬问题：某澳大利亚法庭称谓被稳定转写成不堪的词，Whisper 与 Eleven Labs 至今把 Claude Code 转成「Cloud Code」。（`00:32:33–00:33:25`）

### 原语、API 与「Agent 即 API」的边界

数据与模型策略的边界同样清晰：至今没有微调过任何模型，因为之前「所有模型都在变好，投入复杂评估不如把 harness 做好」；现在开放权重模型已经足够强，会对法律检索这类扇出检索任务做后训练——快、便宜、低时延——但不会去训练自己的主力 Agent 模型，「我们赢不了 Anthropic」。（`00:53:09–00:54:00`）检索与 RAG 研究仍有大量低垂果实，团队成员 Song 甚至推动 TurboPuffer 支持多向量以实现后期交互。（`00:54:10–00:54:43`）

起草复杂合同也不是纯生成问题：先找到对的判例文书——「相似」可以是同行业、同类型公司——再决定从哪份取哪部分，这本质上还是搜索问题。（`00:55:32–00:56:25`）模型侧的坑是 Fable 与 Opus 话痨、冗长；Astra 反而精炼且写作质量好，团队会把这些反馈直接给到供应商。（`00:56:25–00:57:07`）幻觉治理靠引用系统：每句话都要能点回来源，甚至能从 Agent 结论点到 Tabular Review 的单元格再点到底层文件；律师的核验行为分化得和工程师审代码一样——有人逐字读，有人只抽查关键点。（`00:57:07–00:58:16`）

长文档推理仍是模型短板：百万 token 的合同跨处编辑、定义随改动变化，目前靠分块与编排解决。有趣的是行业重心在迁移——主持人自己已从 MapReduce 转向「全部塞进上下文」，而 Legora 的两难是分块会丢跨块的细微关联。（`00:58:30–01:00:24`）嵌入方面他认同「别用默认embedding」的观点，Voyage 或定制嵌入有大量红利，但欧洲多语言场景是额外约束——Mistral 目前帮不上忙。（`01:01:54–01:02:44`）

对未来的判断是两者并存：大型企业可能用 Claude 等通用助手再调 Legora 的 API，律所则直接住在 Legora 里——「就像我用 Claude 操作 Linear，但我还是会去 Linear」。他类比法律领域的 Open Evidence，并判断前沿实验室不会像对待编码领域那样切断法律垂直伙伴——知识工作还有太多方向要覆盖，做不了 Legora 这样的深度。（`01:02:53–01:04:18`）

API 策略本身是一段治理故事：API 约 6 个月前才启动，此前长期抗拒——产品迭代太快，20 个工程师时维护旧 API 版本会拖死节奏；现在 100 人规模才接得起这个成本。（`00:47:27–00:48:35`）更远的一步是「Agent 即 API」的设想：有些调用方其实只想触发一件事，让 Agent 去完成即可——代价是非确定性与成本时延，这件事还在他的头脑推演中。（`00:49:28–00:50:01`）

组织层面，嘉宾曾放话要做「300 勇士」：20 个工程师打天下。现实是竞争逼着扩张到 100 人还觉得太小。（`00:50:28–00:51:25`）交付侧则分化为两层：法律工程师以高级用户方式配置产品、不写代码；前置部署工程师向生产写代码、做集成——他们不碰客户数据，必要时才会被律所以员工身份入职。（`00:44:43–00:46:40`）法学院的配合项目已经启动，他个人更激进的建议是给 CS 背景的人发法学院奖学金。（`01:04:25–01:05:20`）
