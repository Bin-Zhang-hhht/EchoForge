## 速读

这期讲 Anthropic 如何安全地发布最强模型：把「大脑」（模型）与「双手」（执行环境）分开的安全架构、反蒸馏的产品取舍、逐模型的数据保留与验证计划、Fable 下架催生的一键回滚与概率化路线图，以及 Managed Agents 的凭据保险库与出口代理，最后回到 Messages API 的 Rust 重写。

访谈录制于 Opus 5.5 发布次日，正值 Anthropic 递交 S-1、IPO 在即；两位嘉宾是 Anthropic 的产品与工程负责人 Angela Jiang 和 Katelyn Lesse（据节目简介）。开场的 S-1 数字（每员工收入 660 万美元、首个 GAAP 盈利季度利润率 19% 等）与 Rust 重写收益（CPU 节省 40%–50%）均为节目中的说法。嘉宾保留了明确的条件与分歧：蒸馏被反复强调为安全问题而非商业问题；回退拦截仍有误伤，「对齐 vs 个性化」被承认「做得不好」；模型发布的反馈机制自认「仍很非结构化」，靠评测过硬的早期客户加 vibes。适合关心 Agent 安全工程与平台架构的人听。

## 主题正文

### S-1 当口：两万亿估值、660 万美元人效与两个飞轮

本期是 Anthropic 递交 S-1 后的系列节目之一。主持人开场交代语境：IPO 预计两周后进行、估值说法为 2 万亿美元，并转述这家公司一生累计融资超过一千亿美元、累计烧钱不到一百亿美元（`00:00:06`–`00:00:28`）。以下均为主持人转述、无法独立核验：过去 12 个月每员工收入 660 万美元，一年前还是 140 万美元（`00:01:28`–`00:01:43`）；2025 年 Q2 时每一美元收入亏约 0.5 美元，如今每一美元成本赚约 2 美元（`00:02:01`–`00:02:13`）；刚录得第一个 GAAP 盈利季度、利润率 19%，而一年前亏损相当于收入的 129%（`00:02:40`–`00:03:10`）。

主持人把效率的「第一归因」概括为 S-1 里的两个循环：改进循环（Claude→更好的模型→更多用例→更多反馈→更好的 Claude）与投资循环（采用扩大→增长→更多投资→更强能力），两者「一起旋转、构成无限循环」（`00:03:10`–`00:03:59`）。S-1 把 Claude 平台称为「comprehensive agentic development environment」，向客户开放原语以构建、部署、扩展自己的应用，并将其列为「扩散 Claude」的支柱之一（`00:04:05`–`00:04:31`）；过去 12 个月收入在 10 万美元以上的客户中，超过一半在用 Claude Platform——Anthropic 正从模型实验室走向「超大规模云平台」（`00:04:44`–`00:05:18`）。IPO 叙事被概括为「从聊天机器人到副驾驶再到虚拟协作者」：不用 agent 这个词，但要素相同——长期自主工作、判断力、自我修正、迭代与工具访问（`00:05:31`–`00:05:50`）。

最后是当天的引子：访谈录制于 Opus 5.5 发布后一天（`00:07:31` 起），主持人称其接触的「高品味测试者」几乎一致认为它是当前世界最强模型，并推测（自称无内幕消息）Anthropic 手上的 Fable 5.5 可能在两周内发布（`00:06:00`–`00:06:26`）。

### 「事故发生在训练箱里」，不是生产线上

这是全期的题眼，嘉宾在节目中完整讲了两遍。人们读到、听到的那些智能体「越狱」事故，大多发生在训练中的模型身上：把模型放进一个箱子，命令它「解决不可能的任务，我要给你加压」，而智能体天然被激励「逃出箱子」去完成任务。但当用户在生产环境调用 API 时，跑的是另一套环境：有在线防护在运行，而且架构和基础设施把组件分开——「线束（harness）在这边，双手在那边」——「这根本不是一个你需要去考虑的问题」（`00:06:26`–`00:07:16`，`01:08:50`–`01:09:49`）。

嘉宾的第二个回答是：长时运行的智能体本身还是个新鲜事物，全行业都在边跑边补控制。谈到「给前沿踩刹车（pacing the frontier）」时，他们的做法是把这套安全工作同时用于 Anthropic 内部的所有智能体、并把这些能力开放给客户，让「正确的护栏默认就在那里」（`01:10:08`–`01:10:55`）。

### 反蒸馏：安全理由先于商业理由

Opus 5.5 发布背后有一块没有大张旗鼓的工作：让 API「更难被蒸馏」。嘉宾列举的措施包括 prefix lock thinking、跨模型重放思考 token 等，并承认这是一场「穿针引线」——既要照顾压缩策略等正当用例，也要防范坏行为者（`00:08:24`–`00:09:19`）。主持人提到论文《Stealing Reasoning Traces from Proprietary LLMs》；嘉宾确认研究者做了「非常负责任的披露」，并表示这一直是已知的缺口（`00:09:19`–`00:09:52`）。

核心判断是：思维链抽取是最强的模型蒸馏方式之一，「跨轮保留思维块并设为必需」这件事已经探索了很久，难点始终是用户体验与防蒸馏之间的取舍（`00:09:59`–`00:11:24`）。为什么在乎？嘉宾给出的理由完全是安全性的：Anthropic 存在的理由是「让 AI 安全地为世界创造正面结果」，平台在自产 token 上运行大量防护分类器；如果模型被蒸馏出去、脱离这些分类器运行，「世界上可能出现坏结果」（`00:10:37`–`00:11:10`）。

落地时他们把「用户体验损失」分成两层：需要改集成但能力等价（可以接受），和再也做不到原来能做到的事（要极力避免）。最近几代模型用增量变更强制跨轮保留思维块；团队主动联系开源 harness 维护者与大客户，并为压缩策略会被破坏的客户在 API 内新增了官方压缩特性——用嘉宾的话说，「我们没有蛮干（YOLO）」（`00:11:34`–`00:13:09`）。效果方面，以他们能测量的维度看，蒸馏「显著更难」了（`00:13:15`–`00:13:45`）。

Angela Jiang 补充了一个外界常见的误读：把蒸馏当「商业化问题」——偷走模型就能便宜地跑。「这其实不是我们很在乎的事」；「你从我们这里蒸馏，实际上是在给我们付钱」；真正的担心是安全——被派生的 Claude 若走向负面，「那才是不幸」（`00:13:45`–`00:14:26`）。

### 每次发布的安全清单：政策、数据保留与验证计划

嘉宾把「安全地发布模型」称为团队当下最重要的工作：智能体安全、在线防护、离线防护（`00:17:43`–`00:18:06`）。每次发布从政策决定开始（离线与在线安全各一份）：近期最受关注的是数据保留——面对「一张巨大网络里的大量账号」，在线逐 token 的风控根本抓不住恶意使用或蒸馏，必须留存数据才能做自动化与人工复查（`00:19:33`–`00:20:29`）。这是逐模型的决策：前一日发布的 Opus 5.5 就没有 Fable 那样的数据保留要求；一旦某个模型要带这些政策，就要做相应的执行工作（`00:20:29`–`00:20:56`）。

第二块是验证计划：既有网络犯罪验证计划，也有新设的生命科学验证计划——进入这些计划的用户面对的是不同的在线防护（`00:20:56`–`00:21:11`）。嘉宾直言，如今模型发布的大部分工作是防蒸馏、在线防护、离线防护与政策，「这些是我们以前发布模型时根本不用想的事」（`00:21:18`–`00:21:31`）。

配套的是授权体系：允许使用某模型或「放宽防护计划」的授权，必须「一路贯穿系统、值得信任」——「不是发你一个 API key、翻一个 feature flag 就完事」，而要确保只有你本人以预期方式使用该模型（嘉宾以记音为 Mythos 的受限访问模型举例）（`00:21:31`–`00:22:01`）。能力越强、在特定领域「冒尖」，就越要额外注意；评估会区分「进攻主导/防御主导」的能力并采取不同策略。编码是最明显的正向场景；生物与网络则是典型双用途——可能是找漏洞的合法研究者，也可能是坏行为者，验证计划就是给双用途开的一道门，条件是必须说明用途（`00:22:01`–`00:23:13`）。

### Fable 下架之后：一键回滚与概率化路线图

主持人点题：Fable 曾被回滚，加上蒸馏攻击公开、「Fable 上没有零数据保留」的吐槽，「你们想得太多——而且方向是对的」（`00:23:17`–`00:23:40`）。嘉宾回应说，团队为此专门立了一条工作项：「做一个系统，让对所有人的模型访问可以一键收回」；这也是平台工程的常态——一次事故之后「为不再发生而过度准备」（`00:23:40`–`00:24:31`）。它不是孤立功能，而是把管理验证计划与模型访问的那套原语「垫到所有人的模型访问之下」，以备万一（`00:24:31`–`00:24:51`）。

这件事改变了路线图方法论。传统产品管理是「下具体的注」，而 Fable 被政府触发下架（de-deployment）这件事「没有一个人料到会是真实发生的用例」——但概率显然非零。路线图从此「深度概率化」：对冲、构建组合式下注；事后看，「大多数时候我们真的用上了那个东西」（`00:24:51`–`00:26:10`）。

验证计划本身是这套方法的好例子：想在某模型上使用高级网络能力做防御研究的用户可以申请；获批后，其版本模型的防护会被调低以便执行任务——但前提是逐用例理解、逐用户限定，「我们不会普遍这么干」（`00:26:10`–`00:27:09`）。设计时他们刻意选择了「更通用」而不是只贴着当前验证场景做，结果这套原语在管理可信访问计划、处理模型下架等场景反复复用，「红利越来越大」（`00:27:16`–`00:28:12`）。

### 信任授权（trust grants）：Anthropic 自己的 IAM

主持人（AWS 背景）拿 IAM、Zanzibar 这类授权架构对照发问。嘉宾的答案是：trust grant「其实没什么特别的，就是一种授权形式」——「是 IAM，但是 Anthropic 自己的 IAM」；含义是「你被授予了对某个特定模型或某个特定计划的访问」，排列组合很多，「我们不停地用到它」（`00:28:32`–`00:29:15`）。一个具体用例：Fable 5.1 上线「保留思维块」时对存量客户设置了宽限期并登记造册，然后靠一个跑在请求热路径上的服务逐请求检查「你有没有这个 grant」——本质与普通授权无异，只是要插进自家系统（`00:29:15`–`00:30:07`）。

### Managed Agents：大脑与双手分离的工程实现

产品栈分两层：Messages API 是「裸 token 访问」；Claude Managed Agents（CMA）是一组 API——定义一个 agent、启动一个会话，是让用户跳过自建 harness 与基础设施的高阶抽象（`00:42:39`–`00:43:15`）。它与第一方产品共享大量底层基础设施但不同 harness；平台团队还运营着同时支撑 Managed Agents 与第一方产品的沙箱机群（`00:43:15`–`00:44:06`）。

安全在挤压功能的空间。记忆与 dreaming 仍在做，但团队的大部分精力已经转向安全：「把模型的能力送出去、并且安全地送出去」才是最重要的事；与年初相比，skills、dreaming、memory 的投入相对放缓（`00:44:44`–`00:45:28`）。官方提供的 harness「刻意简单」、不预设立场，差异化留给上层策略：dreaming 就是一个在 CMA 之上爬坡的多智能体系统——再起一个 managed agent 去检查前一个 managed agent 并向其写入记忆，「managed agents all the way down」（`00:45:48`–`00:46:45`）；此外还有 best-of-N、verifier agent 等策略，平台很快会开放底层原语让人自建多智能体策略，并附上 dreaming 的起步模板（`00:46:55`–`00:47:42`）。

架构本身是这期的核心图景。CMA 发布时的博客提出「大脑与双手分离」：harness（大脑）跑在 Anthropic 自家的持久服务器上，「双手」是按需拉起的沙箱或容器（`01:03:28`–`01:03:58`）。这样做的第一动机是延迟与可靠：不必先启动沙箱和 Claude Code 才吐出第一个 token；沙箱死了智能体不死，状态单独存放。第一版方案「把 Claude Code 扔进沙箱再套一个 API」正是因为这两点被否掉（`01:03:58`–`01:04:52`）。

但事后被「平反」的，是最初坚持「这个架构最重要的属性是安全」的那位产品经理——嘉宾笑说前一天刚向此人道歉。凭据存放在完全独立的保险库中，智能体只看到占位符；出口处由代理取出正确凭据注入——智能体与凭据「永远不在同一个地方」，用嘉宾的话说，这是一堵「字面意义上的基础设施墙」；旧世界的做法是把凭据送进箱子里，然后再想怎么擦除、防止它拿凭据干坏事（`01:04:52`–`01:06:30`）。沙箱层还有出口控制：域名白名单，或干脆完全断网——「不可信代码执行了，也只能连到你说它连的地方」。这些设计让 CMA「默认安全」，并且随着 Anthropic 自己的认知升级，客户「免费」获得升级——「九个月前，没有人会说大脑、双手、凭据注入、出口这些词」（`01:06:30`–`01:07:50`）。给自建智能体的客户，嘉宾给出的两条最重要建议是：架构上让智能体「字面上不可能」做不该做的事，再加上沙箱配置（`01:07:17`–`01:07:38`）。

### 三个安全维度，与「无理由回退」之痛

主持人提出表面的矛盾：倡导给前沿踩刹车，却 11 天后就发布新前沿模型；嘉宾的回答是——「说明它通过了我们的安全检查」（`01:10:55`–`01:11:19`）。检查落在三个维度上：架构与基础设施安全、模型工作时运行的在线防护、对静态数据的离线防护分类；Opus 5.5 在三个维度上都表现很好，「因此我们才放心发布」（`01:11:19`–`01:12:01`）。代价是误伤：团队在追求「最佳用户体验」的同时继续爬坡降低假阳性，但「被切到另一个模型」对用户来说仍然令人沮丧（`01:12:01`–`01:12:16`）。

主持人替用户追问到底：Anthropic 的回退判定像一个独立的在线分类器，而非完整的 Fable，「明显不如 Fable 聪明」，会造成「无理由回退」——「我只是写生物作业，提了一次 bio 就被切」；这与「聪明路由还是笨路由」是同一类难题（`01:12:16`–`01:13:27`）。还有中途截断的情形：让 Fable「分析这份材料里有什么有意思的东西」，五分钟后进入网络安全内容被切、回退到 Opus——判定看的不是原始提问，而是「推理与整条链路的组合」（`01:13:57`–`01:14:46`）。

嘉宾把「判定」与「用户体验」分开作答：更理想的 UX 是一致的统一体验——在树中设「逻辑切点」，而不是连环回退；分类器应当聪明到能识别善意场景，「把答案更具体地写给你，同时说明该能力的负面用途」（`01:14:46`–`01:15:42`）。API 侧已经给出了一组光谱选项：撞到拦截后可以不在回退模型上继续对话（官方应用的做法，已做成 API 特性）、服务端配置自动回退、SDK 客户端助手，或改写提示词继续用原模型（`01:15:42`–`01:16:37`）。至于路由类比的根本困难——对任务和对模型都没有完备信息，无论分类器多好都有误差——他们更看好「一致的模型+动态 effort」的方向，而不是在不同模型间跳来跳去（`01:16:37`–`01:18:23`）。

### 「双手」的底层：CPU 紧缺与 Messages API 的 Rust 重写

嘉宾把团队的时间概括为两件事：scale 与 safety。多数人谈算力只谈 GPU 加速层，而 CPU 这一「老派层」如今是同样大的瓶颈——VM 和沙箱「永远不够」，代码变多导致 CI 变多（`00:53:28`–`00:54:33`）。对 Anthropic 整体而言 CPU 是零和游戏：与云服务商谈下来后，在研发沙箱、产品沙箱、API 与应用之间内部分配；「只要预算够就能按需扩容」的时代结束了，现在必须提前做容量规划（`00:54:33`–`00:55:32`）。

于是有了这期最「疯狂」的工程故事：截至录制时的「上周」，Messages API 已全部以 Rust 上线。当时这个决定很激进——团队里没有一个 Rust 开发者；人类负责设计系统，代码由 Claude 写，最重要的两件事是「做的计划」与「对结果的验证」。做法是把整个 API 完整复刻一份 Rust 版，灌影子流量对比 Python 与 Rust 的输出，再逐步放量——「一次性整体移植、慢慢打开，而且成功了」（`00:56:05`–`00:58:18`）。收益的量级（嘉宾口径）：CPU 节省约 40%–50%，首 token 延迟（TTFT）改善约 10%–20%，长任务上收益更高（`00:58:27`–`00:59:11`）。

纪律同样值得记：这是一次「纯移植」而非重构，团队抵抗了「顺手加新功能」的冲动；一支特遣小队边移植边用静态分析盯着其余团队的功能开发。下一步才做面向用户的架构改造，例如由服务端暂存会话状态、免去来回传递完整对话历史（`00:59:21`–`01:00:39`）。至于 CPU 从哪来，嘉宾给出的门槛是最小机群规模、SOC 2、企业级与全部隐私承诺；原来为加速器算力做安全的团队，现在也把大量时间花在 CPU 采购上（`01:02:10`–`01:03:09`）。

### 发布机器：自用、早期客户与负反馈

除安全外，模型发布已经「成了机器」：安全测试、评估、必要的取舍、切出多个版本，内部「自用」（逐字稿记音 ant fooding，即 dogfooding）最早暴露问题、区分哪个变体更好（`00:30:31`–`00:31:25`）。候选版本或先走第一方产品（Claude Code、Cowork），或交给进入早期访问计划的 API 客户——被点名提到的有 Cognition、Hers 等——对方改自己的 harness，回报评测结果与 vibes（`00:31:25`–`00:32:01`）。

嘉宾坦承反馈机制「仍很非结构化」：基本是公司之间的 Slack 频道；由于在「抢时间窗」，只挑评测体系过硬的客户参与，其余靠 vibes（`00:31:59`–`00:33:04`）。主持人补充：世界上很多 agentic 产品并没有像样的 evals——「两年前 Boris 在节目里说 Claude Code 没有 evals」，如今已经变了（`00:33:13`–`00:33:31`）。

API 客户之所以宝贵，是因为他们把 Claude 放进不同的 harness，而「我们希望 Claude 非常通用」，这类反馈是自用得不到的新信息；最有用的永远是负反馈。「懒惰 vs 主动」就是典型：有人嫌它偷懒，有人嫌它抢跑，「让所有人满意在字面上就是不可能的」——遇到过太懒的早版本，就「放回炉里再炼一次」（`00:33:50`–`00:35:28`）。更深一层是「对齐 vs 个性化」的难题：默认人格与个人 CLAUDE.md 定制互相拉扯，嘉宾直说「我们做得不好」；宪法（constitution）有帮助但解决不了指令级偏好，只能靠更多参数按客群微调、给 API 客户建议，以及在相互冲突的品味之间做判断（`00:35:37`–`00:38:39`）。具体到参数：effort 默认值改为 medium（Claude Code 设置），默认值还会按免费/专业/Claude Code/Cowork/企业/API 等分段调整；原则是「温和的默认+始终可调」，不想让人觉得无法自定义 Claude（`00:38:48`–`00:40:05`）。

### 收尾：更长的任务、内部文化与多智能体建议

工作负载观察：部分工作负载的智能已趋饱和，仍远未饱和的一类（嘉宾认为比人们预期的多）要靠「极长时运行的智能体任务」去啃历史上无法暴力求解的问题；今天多见于编码与企业流程自动化，生物、网络这类硬科学问题也在出现（`01:19:06`–`01:20:43`）。内部文化与 slop 的讨论同源：人负责系统设计、Claude 负责实现，「大部分代码只需要快速盖章」，靠整体验证保证质量；Tariq（记音）在推上的提醒是「用模型能力的正确方式，不是往生产环境多塞 10 倍功能」（`01:23:47`–`01:24:52`）。当天的博客是个注脚：目标两周给 Claude AI 提速，13 项目标 3 天达成 12 项（`01:26:29`–`01:26:41`）。

给听众的收尾建议：去 Opus 5.5 上构建——更省钱、更少啰嗦（`01:43:29`–`01:44:38`）；试多智能体时守住两条——任务大体可并行、子任务共享同一上下文且异步互不阻塞，「其他的放手让 Claude 自己设计」（`01:45:16`–`01:46:16`）。
