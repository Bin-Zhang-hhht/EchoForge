## 速读

OpenAI Frontier 团队的 Ryan Lopopolo 带着那篇引发全行业讨论的 Harness Engineering 长文来做客首次播客。他的实验数据令人瞠目：三人团队、五个月、一个内部 beta 产品、仓库超百万行代码、约 1500 个 PR——其中人工编写的代码为零，合并前经过人工评审的代码也为零。他的每日 token 消耗超过 10 亿（按市价与缓存假设约合每天 2000–3000 美元），并认为用不满这个量"近乎失职"。

最值得带走的三点：他的方法论是系统思维而非提示词玄学——模型搞不定时，不催它"再努力"，而是问"缺了什么能力、上下文或结构"，把它拆成更小的积木再组装；人类同步注意力是唯一真正稀缺的资源，因此一切工程投入都指向"让代理可自测、可自审、可自合并"；以及那套把团队品味"编译"进代理的方法——文档、测试、评审代理、质量分，全都是把工程师脑子里"什么是对的"翻译成代理能读的文本。

## 主题正文

### 一个刻意的约束：我自己不写代码

Ryan 在 OpenAI Frontier Product Exploration 工作——为企业级安全、可治理地部署 Agent 的新产品探索团队，背景横跨 Snowflake、Brex、Stripe 与 Citadel。实验的起点是一个刻意为之的约束：他不写任何代码。"如果我们要把 Agent 部署进企业，它们就得能做我做的所有事。用了六七个月编码模型与 harness 之后，我认为模型与 harness 的能力已经与我同构。"于是唯一的完成方式就是让 Agent 替他完成工作（`00:02:20–00:03:46`）。起步用的是最早的 Codex CLI 加 Codex Mini——"让模型给你造一个产品功能，它就是拼不起来"，这种挫败感反而定义了方法论：模型搞不定时，把任务摊开、double click、造更小的积木，再组装成大目标。头一个半月比他自己写慢 10 倍，但因为付了这笔学费，最终团队的生产力超过了任何单个工程师——"我们造好了 Agent 的装配站"（`00:03:46–00:04:43`）。

跨过 GPT-5、5.1、5.2、5.3、5.4 多代模型，每代都有新的"怪癖"需要适配代码库。最有趣的案例是后台 shell：5.2 时代的 Codex 没有后台 shell，可以靠阻塞脚本跑长任务；5.3 有了后台 shell 后模型变得"没耐心"、不愿阻塞——于是整个构建系统被重构到一分钟以内，构建工具从手写 Makefile 换到 Bazel、Turbo、nx。"这在一个人们有意见的代码库里是不可能发生的事，但我们唯一的目标是让 Agent 在一周内保持高效。"一分钟内环成了纪律的棘轮：超时不是杀掉，而是"再次拆解构建图"的信号——token 便宜、并行度疯狂，他们可以永远"园艺化"这些不变量，从而让代码库的离散度更低、更依赖不变量（`00:04:43–00:07:45`）。

### 人类是瓶颈：从写代码到造系统

三人团队产出百万行代码、上千个 PR，人做什么？Ryan 的答案分几层。首先是翻转默认：人类的评审大部分发生在合并之后（post-merge），再往后的使用阶段甚至谈不上评审——"模型是可以平凡并行化的，有多少 GPU 和 token 我就有多少产能，唯一真正稀缺的是团队的同步人类注意力——我们总得吃午饭、睡觉，虽然不盯着机器的时候它一直引诱你喂它"（`00:07:46–00:09:00`）。其次是可观测性先行：本地可观测栈（VictoriaMetrics 一族加少量 Python 胶水）只用了一个下午；更关键的是"倒置"——不是搭好环境再spawn编码代理，而是 Codex 本身就是入口，通过 skills 和脚本赋予它自行启动整套栈的能力。他把这归为推理模型与前代（GPT-4/4o）的本质区别："以前的模型不会思考，你得把它们放进预定义状态转移的盒子里；现在 harness 就是整个盒子，给它足够的选项和上下文，它会聪明地选。"（`00:09:35–00:11:28`）

"把品味编译进代理"的具体形态包括：一个 100 行以内、带目录结构的 agents.md；core-beliefs.md 里写着团队是谁、在造什么产品、终端客户与试点客户是谁、未来 12 个月的完整愿景——"这些都是影响我们怎么写软件的上下文，所以也必须给代理"；markdown 表格式的 tech tracker 与质量分，作为 Codex 自查业务逻辑是否匹配护栏、并给自己提出后续工作的钩子；票据系统出现之前，后续工作就记在 markdown 里，随时可以拉一个代理去 burn down。他总结的元规则是："模型从根本上渴望文本。我们做的很多事就是想办法把文本注入系统。"最生动的例子是：半夜被告警吵醒（缺了超时），他会在 Slack 里 @ Codex——"我会修这个，同时请更新我们的可靠性文档，要求所有网络调用必须有超时"——一次性完成点修复与流程知识的持久编码，这些文档还能反过来蒸馏成测试或评审代理的评分依据（`00:12:24–00:13:51`）。

### 代理互审、自治合并与"降级为 500 人组织的 tech lead"

代理互相评审的初始版本闹过笑话：写代码的 Codex 会被 PR 评审代理"霸凌"，无限往返不收敛。修正方案是给双方都加弹性：评审代理被要求"偏向合并"、只报 P2 以上的问题（P0 的定义是"合并它就等于静音整个代码库"）；作者代理则被明确允许"defer 或 push back"评审意见——因为人类评审里大量批注本来就是 FYI 性质，"下个 fix-it week 再说"。完整的委托链是一个 /land 技能：推送 PR、等人类与代理评审、等 CI 变绿、修 flake、合并；有冲突就进 merge queue 处理冲突直到进 main——"这就是完全委托的含义，我唯一要做的就是把笔记本开着"。人类还剩什么？因为做的是原生应用而非持续部署，切发布分支和"经人类祝福的冒烟测试"仍在人手里（`00:13:51–00:16:30`）。Ryan 对自己角色的描述颇具启发性："我像一个 500 人组织的 group tech lead——不适合陷在每个 PR 里。我看合并后的代码样本，推断团队在哪里挣扎、哪里需要帮助。"他的关注点不在业务逻辑怎么写，而在"是否用了那个自带追踪、指标与可观测性的命令式原语"——用对了原语，杠杆自然来。团队甚至给 Codex 配了生成 Grafana 面板 JSON、发布面板、响应告警的能力，于是告警、日志、代码在它的世界里是互相索引的——一次未触发告警的故障，它也能自行发现面板与指标的盲区并补齐，"像全栈工程师从后端开到前端"（`00:17:00–00:21:00`）。

 swyx 总结这套哲学为"软件要为模型而写，如同为人而写"——agent legibility 优先于 human legibility。Ryan 补了一个生态反馈：文章发布后，很多人直接把链接丢给 Codex 说"把我的仓库改成这样"——"效果出奇地好"。Brett Taylor（他的董事会主席）发文称"软件依赖即将消失、可以被 vendor 进来"，Ryan 百分百同意：几千行量级的依赖，一个下午就能内化，而且"大部分代码你根本不需要——内化即抽象，可以剥掉通用部分只留你要的"；Codex Security 对内化依赖的深度审查，远比给上游提 patch 等发布再升级省事。他给这条路线标注了当前的能力边界（"低到中"）与反方论据：规模测试与"many eyes"的开源安全红利（`00:25:57–00:28:00`）。一个反直觉的教训是"人类可读性有时是错的"：首位内部用户报性能问题后，值班工程师花一下午用 Codex 造了个漂亮的拖拽 trace 可视化工具——而其实"直接把 tar 包丢给 Codex，五分钟就能得到答案"，为人类可读性优化反而让人滞留在环路里（`00:28:00–00:29:36`）。

### 幽灵库与 Symphony：把仓库蒸馏成规格

"幽灵库"（Twitter 的叫法）是发布方式的革新：Symphony 以规格而非源码分发——用自家仓库作参考让 Codex 写出 spec，然后 spawn 一个断连的 Codex 实现 spec，再 spawn 另一个 Codex 对照上游实现评审并修订 spec，Ralph 式循环直到 spec 能高保真复现整个系统。 swyx 抛出了那个哲学问题："Agent 能不能想象出它做不到的事？"Ryan 用四象限作答：简单/困难 × 成熟/全新——"又难又新"仍然需要人类驱动，但其余三个象限在正确的 scaffold 下基本已被解决，"这恰好意味着时间与注意力有限的人类可以去啃最难的部分：纯白空间的问题、你不知道接口该长什么样的深度重构"（`00:29:36–00:32:00`）。

Symphony 本身是 Elixir 写的编排层——模型自己选的，因为 BEAM 的进程监督与 gen server 天然适配"给每个执行中的任务拉起一个小守护进程并驱动到完成"的编排形态；而且"环路上没有人类，我个人会不会写 Elixir 不会污染工具选型"。诞生的契机是 12 月底的 3.5 PR/人/天，1 月初 5.2 发布后飙到 5–10 个——人被 tmux 窗格间的上下文切换榨干，于是造出"让人离开终端"的系统。它的 rework 状态机值得所有团队抄写：升级给人评审的 PR 应该是"便宜的评审"——可合并或不可合并；不可合并就整个丢弃工作树与 PR、从头重来，但要先回答"它为什么被扔掉、Agent 做错了什么"，把答案修进上下文再重新入列（`00:32:46–00:36:00`）。团队为此付出的代价是混沌：45 分钟的每日站会用于"扇出当前状态的理解"；仓库被拆成约 500 个 NPM 包——"为 7 人团队设计这种架构是过度的，但当每个人实际是 10 到 50 个人时，深度分解与边界就合理了"。Bearish 的教训也有：playwright 的 MCP 会强制注入大量 token、干扰自动压实、Agent 还会忘记怎么用（其实只需要 3 个调用）——后来某个同事"vibe"了一个本地守护进程，暴露一个极小的 CLI shim，而 Ryan 完全不知道这件事发生过，"我只知道 Codex 变得更好用了"（`00:36:00–00:37:00`）。

### 六层自我改进与"别把代理关进盒子——把盒子装满"

swyx 把 Symphony 的机制归纳为六层：策略、配置、协调、执行、集成、可观测，外加"第零层"——我们协作得好吗？能改进协作本身吗？Ryan 的答案是"当然可以"：代理有完整权限，可以自己开票（甚至在票据里写明"请把你的后续工作开成票"）。团队真的在把全员 Codex 会话日志 slurp 进 blob 存储，每天跑 Agent 循环寻找"团队层面如何做得更好"并回灌仓库——"每个人都免费受益于所有人的行为"。PR 评论与失败的构建同理："这些都是信号，说明代码写下的那一刻，Agent 缺了某段上下文——把它吸出来，放回仓库。"swyx 指出这就是 on-policy 与 off-policy 的区别：护栏要在模型已有的输出分布内构建（跑测试本来就是可靠软件的一部分），如果你另起一个 Rust 脚手架去限制 Codex 的输出，那才是容易被废弃的 harness（`00:40:39–00:43:00`）。

工具层的经验高度可操作：模型热爱文本工具，"我的工作就是想办法把文本从一个 Agent 漏斗到另一个"；对 UI 这类非文本对象，与其指望模型的视觉感知（"它看到的不是一个红色方块，而是 latent 空间里的 red box button"），不如把界面栅格化成 ASCII 喂进去，图文双喂更佳。CLI 维护者被点名："CLI 天生 token 高效，而且很容易变得更高效"——prettier 应该有 --silent（Agent 只关心格式化与否）；pnpm recursive 输出的日志山应该被包一层只输出失败用例；gh CLI 的 "gh pr view --web" 已是他使用 GitHub 网页版的唯一方式。Symphony 的规格被刻意设计为蓝图而非宪法：Linear/GitHub 写在 spec 里但可替换成 Jira/Bitbucket，而 ID 格式与每个 Agent 的 Ralph 循环被严格固定——"对成功标准越有主见、越严格，部署成功率越高，我们就不用接票"。面向企业的 Frontier 平台由此顺理成章：让 Agent 可观测、安全、可控、可识别地进入企业，接上原生 IAM 与安全工具链；Agents SDK 提供"开箱即用的 harness"；GPT-OSS 的 safeguard 模型带"安全规格"接口，让企业定义自己最在意的防泄露与内部代号；控制台的用户不是 CEO 而是 GRC、治理、安全团队与 AI 创新办公室，可以下钻到单个 Agent 的轨迹（`00:50:04–01:02:00`）。

两段收尾的细节为这场实验定调。其一，core-beliefs.md 里甚至有"如何生成 deep-fried 梗图、维持 Slack 的 meme 文化"的技能——"Codex 可以替我 shitpost"，而幽默被他视为困难的智能测试（用极少的词压缩大量上下文），5.4 在这方面是"巨大的提升"。其二，关于 harness 与训练的张力，他的立场是：团队的成功恰恰意味着"模型获得了更好的品味，因为我们指了路"，而且他们造的东西没有一件在降低模型表现——"跑测试本来就是写可靠软件的一部分"。数据点收尾：Codex 周活突破 200 万、周增 25%；5.3、Spark、5.4 在一个月内相继发布；OpenAI 的 Bellevue 办公区在录制前一日开张，而 Ryan 正是西雅图办公室的第一批工程 hire。swyx 的结语成了整期节目的标题句："You can just do things."（`01:02:05–01:12:29`）
