## 速读

这期在 OpenAI 录制的对话，嘉宾是前沿评估团队的 Olivia Watkins 和研究副总裁 Mia Glaese——她们的团队正是当年 SWE-Bench Verified 的缔造者。全期围绕一篇同日发布的博文展开：为什么 OpenAI 决定停报这个曾被视为"北极星"的编码基准。最有信息量的部分是污染证据（GPT-5.2 的思维链自己暴露了"题外知识"）、对失败案例的公平性深挖，以及她们对下一代编码评估的期待清单。

## 主题正文

### 为什么停用：饱和且被污染

嘉宾给出的核心论点很直接：SWE-Bench Verified 曾是全行业衡量编码进步的"北极星"基准，但进步已经停滞——因为这个评估实际上已经饱和，且污染严重，如今已不能很好地衡量编码能力的改进；领域应当转向 SWE-bench Pro 这类新基准（`00:01:04–00:01:29`）。主持人补了一个行业观察式的玩笑：各大实验室像在同一个群里轮流把成绩提高 0.1%，"领先 0.1% 就是最好的编码模型"已经没什么说服力（`00:01:30–00:01:45`）。前沿模型在这个基准上的成绩普遍到了 80% 出头（`00:09:53–00:10:00`）。

### Verified 的出身：一项重投入的清理工程

两位嘉宾先回顾了 Verified 的来历：它是对普林斯顿 SWE-bench 的一次清理——给智能体一个真实仓库和 GitHub issue，要求解决任务，以测试是否通过来评分（`00:02:08–00:02:28`）。OpenAI 在准备为"准备度框架"追踪这个评估时，发现智能体的失败常常源于题目本身有问题，而不是模型笨（`00:02:32–00:02:49`）。于是有了那次大规模人类数据工程：雇了近 100 名真实世界的软件工程师逐题审查——任务是否定义清楚、测试是否公平——最终筛出 500 道质量更高的任务（`00:02:49–00:03:06`）。Mia 强调成本高昂的"三重独立评审"是必要的：审题要在代码库语境里同时理解问题与补丁，单看一遍根本靠不住（`00:03:22–00:03:54`）。

她们并不否认这个基准当时很出色：发布时是强基准，它教会了 OpenAI 和整个行业很多东西。问题在于基准的共同生命周期——从只有 20% 通过率、大家有抓手改进模型，到成绩极高之后每 +0.1% 都变得没有意义；此时基准测的已经不再是"编码能力"，而更像"猜对某个函数该叫什么名字"的能力（`00:08:40–00:09:51`）。

### 污染的证据：思维链里的"题外知识"

污染在开源数据来源的基准上几乎无法杜绝：常规做法是给自建评估加 canary 字符串以便训练时过滤，但取材于开源 GitHub 的任务天生没有 canary，何况 Django 这类热门仓库的实例在全网到处都是（`00:04:39–00:05:17`）。最直接的证据来自 GPT-5.2 的思维链：某题要求实现某个功能，题目并没有说测试会检查一个特定参数，而模型的推理过程里出现了"我记得这个仓库后来的版本实现了这个参数，也许我该加上"（`00:05:18–00:05:46`）——没有污染知识几乎不可能通过这道题（`00:05:46–00:05:52`）。这触发了对自家模型和市场上一线模型的全面调查：在 OpenAI 模型、Claude Opus 4.5、Gemini Flash 等模型上都发现了污染迹象，包括复述标准答案、甚至直接给出任务 ID（`00:05:52–00:06:08`、`00:11:32–00:11:55`）。

上限可能已经到了：GPT-5.2 发布时，有人检查了那批"没有污染知识就应该极难解决"的题目，发现它解出了 31 道（`00:10:09–00:10:26`）——嘉宾认为无污染的真实上限可能已经被触及，虽然很难断言。

### 公平性深挖：过半"失败"另有原因

团队还做了一次公平性深挖：把 O3 无法可靠解决的问题集合拿出来，再次动用大量人力逐题排查"到底是题坏了还是模型不行"（`00:06:16–00:07:09`）。结论是：被调查的问题里超过一半存在这样那样的问题（`00:07:10–00:07:17`）。最常见的是"过窄的测试"——测试检查某个实现细节，但题目描述里根本没写；比如要求实现某功能，测试却硬性检查参数或函数的命名，换个同样合理的名字就判失败（`00:07:17–00:07:44`）。另一类是测试要求题目从未提及的额外功能（`00:07:45–00:07:53`）。主持人的总结很到位：通过测试当然说明做得不错，但没通过绝不等于实现不好——基准只接受了极窄的解法空间（`00:07:51–00:08:10`）。

### 下一站 SWE-bench Pro 与更远的评估议程

OpenAI 将停止报告 Verified，转向 Scale 主导的 SWE-bench Pro。吸引力有三：更难——Verified 约 90% 的题目据估计对专家工程师来说不到一小时，Pro 的题目则在 1–4 小时和 4 小时以上两档，空间大得多；更多样——仓库、语言、题型都更丰富；污染更轻——用"污染审计代理"（给代理任务描述、补丁和任务 ID，让它开放式提问套出模型可能记住的东西）检查后，Verified 里多家模型污染明显，Pro 只有极轻的熟悉痕迹（`00:10:27–00:12:13`）。嘉宾同时提醒：Pro 将来也照样会过时，领域必须不断去找更难、更有代表性的问题（`00:12:15–00:12:31`）。

往远处看，她们想测的东西正在变化：从"能不能修好一个小 issue"走向以小时甚至天计的长任务；也走向更难量化的品质——设计品味、代码是否干净可维护，"我们不知道怎么测"（`00:13:43–00:15:27`）。测量手段有两条路：雇大量承包商做人工标注，或者用对齐过的 LLM 做代理评分，两者都要（`00:15:27–00:15:46`）。她们拿 GDPval 举例：由人类数据团队与前沿评估团队合作的这个评估覆盖大量真实白领职业，评分极依赖领域知识，所以请了各行业的专业人士出题、写标准答案和评分细则；把这套思路搬到代码上就是一个方向（`00:15:47–00:16:58`）。同时她也肯定"测试通过与否"这类极简评估的价值——跨行业可比、无需人工即可快速运行——只是它回答不了"开源维护者会不会合并这个 PR"（`00:17:23–00:18:15`）。

至于把分数换算成金钱的做法（如 SWE-Lancer、VendingBench 一类），Mia 认为金钱、时间、复杂度是同一件事的不同度量，彼此相关：真正要追踪的是"我们敢把多复杂、多长程的任务托付给智能体"；METR 用时间做度量，OpenAI 也与 METR 在这些评估上合作（`00:19:45–00:21:34`）。这一切都连回准备度框架：它是 OpenAI 公开追踪前沿风险的框架，目前覆盖生物风险、网络安全、研究自动化与模型自主三类；编码虽不等于科研自动化，却是其中关键组件——Verified 正是为模型自主工作流而建，下一步要看的是模型能否真正自动化科研提案（`00:21:49–00:23:03`）。

节目后半段 Mia 提前离场，Olivia 留下三个请求：真正困难的任务（顶尖工程师要数月、团队要数周的那种），配上经领域内多人校验的可靠评分细则；端到端做出产品的基准；以及严格说不是评估的东西——追踪 AI 真实使用情况的指标：到底被用了多少，是在替代工作还是增强人类（`00:24:15–00:25:08`）。
