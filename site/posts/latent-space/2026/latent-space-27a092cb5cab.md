## 速读

GitHub 在 2026 年春天经历了一轮非常公开的可用性风波，背后是 Agent 带来的增长冲击：2025 年全年 10 亿次 commit，如今每周 2.75 亿次、年化 140 亿。COO Kyle Daigle（GitHub 十三年老兵、webhooks 和 Actions 的缔造者之一）在这期访谈里罕见地摊开了工程细节：为什么垂直和水平扩展同时失灵、哪个数据库是最后的痛点的来源。

同样精彩的是非工程部分：他如何用"回顾式"Agent 工作流运营公司、为什么 GitHub 坚持"绝不隐藏代码"、以及当 80% 的 PR 来自 Agent 时，"信任"如何变成一个必须重新设计的社交问题。

## 主题正文

### AI 让 COO 重新开始写代码，方向是"向后看"

Kyle 的 commit 图表有个十三年的空洞——管理岗期间几乎不写代码，如今靠 AI 满血复活。他的用法和多数高管不同：不是"帮我写篇博客"这种简单调用，而是把一堆异构数据源连起来的回顾式工作流——"把今天所有 PR 过一遍、把我们网上发的所有东西过一遍、把过去三个月做了什么过一遍，翻我的 Obsidian 笔记里所有相关内容，调 WorkIQ 的 MCP server 拿全部 Teams 会议记录，再过一遍 Slack，然后告诉我这周的传播主线到底是什么"（`00:03:40–00:07:04`）。他的心得是这波 AI 对他最大的价值不是向前构建，而是"递归地向后看"：LLM 极其擅长从海量痕迹里找模式、做短期复盘——这对远程分布式团队尤其重要，办公室里天然存在的那些信息，远程就是会漏。

内部推广的原则同样反直觉：绝不让任何人改变工作方式。他试过的大部分工具都死了，因为"得先教会你怎么用"；最后跑通的是给非技术同事发 CLI 和一套共享技能——连上 GitHub、Teams、邮件、Slack 的读取权限，配上 WorkIQ MCP server，就形成了公司级的上下文层（`00:07:04–00:10:26`）。技能生态的演化方向是从"巨大完美的 mega-skill"退回到原子化 micro-skill："每条推文都在让你下载那个完美编排一切的东西，但几周过去需求一变，你的 mega-skill 就废了。现在我们谈的是乐高块，说明书大家自己拼。"swyx 用 Postel's law 总结（对输入宽容、对输出严格），Kyle 补充了真正的矩阵难题：同一个"总结"，对分析师、对客户会议、对 Gartner 简报是完全不同的东西，那点排列组合的差异恰恰是"读起来像不像人写的"的分界线（`00:10:26–00:15:00`）。

### 周六的 15 个 Agent 与"做得不像 AI"的汇报

对"这是不是前开发者领导者的黄金时代"，他的答案是肯定的，逻辑在于复利：模式识别与解决问题本来就是他的核心竞争力，如今再加上十年积累的业务判断和重新获得的写代码能力——"周六孩子在打长曲棍球，我同时跑 15 个 Agent"。他举了年度营收规划的例子：用技能收集全部上下文、建了个 SQLite 小应用看数据，最后整套汇报直接拿去给 CRO、CFO 和他们的团队——他还专门写了个技能让排版"看起来非常不像 AI 生成"，全程无人起疑，也无人关心（`00:15:00–00:20:20`）。Chief of staff 的角色没有被取消，而是换了内容：不再有人给他做幻灯片，但"找出这些人脉连接、该见哪个团队"的人类连接工作反而更值钱了——就像总管不拆信件改处理邮件一样（`00:20:20–00:21:45`）。

### 从 webhooks 到 npm：平台不想替社区做决定

平台史部分信息量很大。他在收购完成前夜（2018 年 10 月）发布了 Actions 第一版；最早的 webhooks 时代是个 Ruby 仓库替所有人执行任意代码，隔离只靠服务器层面——演化到今天的容器化和新的 Azure Dev Compute（快速拉起小 VM 跑工具调用），就是"运行任意代码"这件事的安全债逐步还清的历史（`00:21:45–00:26:07`）。npm 收购的动机被一句话概括：它当时就在给整个互联网供包、已经在遇到扩展问题，GitHub 想的是"别让它死"。此后逐年补课：改 2FA 政策、发现泄露的令牌就主动作废——每个安全动作都会弄疼一批人，"但安全是头等大事"（`00:26:07–00:28:45`）。

对" slop fork"和"干脆取消包管理器、让 Agent 读源码然后 vendor"的激进设想，他的回应是历史感：2013、2014 年大家就是 vendor 一切的，"一切旧的都是新的"；缩小依赖确实有帮助，但解决不了根本问题——Agent 照样能被说服把危险的东西当安全的拉进来，静态分析和运行时检测才是要持续投入的那一步（`00:28:45–00:31:35`）。GitHub 的生态哲学是不替社区拍板：几乎从不主动推一套流程，而是等 RFC 和社区共识形成后再固化。Mitchell Hashimoto 的 vouch 系统是好例子——他的社区喜欢，别的维护者不买账；GitHub 的做法是给维护者工具去控制 AI PR 的摄入量，哪个方案成为事实标准就内置进去，但绝不强制（`00:31:35–00:34:02`）。他给 PR 的未来下了个判断：当 80% 的 PR 来自 Agent 时，PR 流程的本质是"把信任编码化"——过去"Sean 审过的我就信"依赖人的信号，现在 Agent 写、Agent 审、人最后看一眼，信任被稀释了；多数新工具其实在做验证流，但"我能不能信这个 PR"终究是社交问题。他用 Waymo 作比：信任既需要可验证的证据（事故率、数据），也需要人坐进去的感受，两者缺一不可（`00:34:08–00:38:18`）。

信任的信号设计里有个精妙的反直觉：stars 和 commit 数都是被动信号、天然可被操纵——设"账号要 90 天"的门槛，攻击者就批量养号；要 star 数，就互刷 star。所以他更看重"有代价的信号"（比如 Sponsors 花真金白银支持），以及把每个项目自己写在贡献指南里的启发式变成可配置的 Agent 规则（比如"只接受在多个项目有被合并 PR、且绑定了老社交账号的提交者"）（`00:38:37–00:41:18`）。对 stars 通胀他并不悲观：最快的破十万星纪录里确实有水分，但更大来源是"软件开发的入口变宽了"——GitHub 注册开发者已超 2 亿，其中大量是 AI 时代才第一次写代码的人；对"他们算开发者吗"的争论，他的立场很硬：他自己入行时也没人叫他开发者，"只要你有个想法并把它做出来了，就是同路人"，gatekeeping 毫无价值（`00:41:18–00:45:19`）。Spark 的教训与之呼应：低代码外皮可以加，但"永远不向你隐藏代码"是铁律——开发者真正离不开的是那个简单的运行时（`00:45:19–00:47:38`）。

### 14 倍增长撞墙：老系统的"新式崩溃"

然后是最难的部分。Octoverse 发布时（去年 10 月）他们说那是史上增长最快的一年；如今"我们一个月干完去年一年的量"——commit、PR，几乎每个指标都是。崩溃的方式是新的：不是 webhooks 那种老毛病（已重写、稳定），而是"只在全体量级下才会出现的、新颖的权限问题"。swyx 追问为什么 14 倍增长没有 14 倍的准备，Kyle 的答案很工程：Actions 需要更多构建就意味着更多 CPU——现在缺的是 CPU 不只是 GPU，所以一边加自建数据中心一边上 Azure 云计算（`00:47:38–00:51:53`）。最深的痛点是权限系统：大量权限数据仍住在内部代号 MySQL One 的数据库里，多年持续用 Vitess 等技术往外搬迁（PlanetScale 正是这套实践的产物），而 GitHub 还要同时服务企业版黑盒部署和数据驻留场景——几次全面性故障都出自这里。另外行业风向掉头：monorepo 回潮、仓库变大变肥，逼着 Git 底层继续优化；任务队列也在换底层技术。他的总结非常精准：过去十五年只有垂直和水平两种扩展手段，现在进入"对角线"困境——垂直到头了，水平又受 CPU/供给约束，只能打开跑了十年的服务重写，因为"这条管道里流过的东西的尺寸已经变了"：以前一次 git push 是个稳定尺寸，现在平均尺寸完全不同（`00:51:53–00:58:30`）。

对恢复路径他给出的是可检验的承诺：最近几周可用性已好于之前几周，未来三个月逐月改善；关键改进（数据库拆分、额外算力）是"重量级改变"，需要时间但会带来阶跃式的好转，而不是小修小补。至于对外沟通，他把这归结为 GitHub 的老传统："这是我们的 uptime，是我们的问题"——团队现在的做法是修完之后写博客、让工程师出来讲清楚改了什么（`00:58:30–01:02:04`）。

### Copilot 的下一章：一个 SDK、环境智能与"让它像 Kyle 希望的那样行动"

Copilot 部分坦率得少见。他承认走过的弯路：代码补全爆红之后，团队花了一年半押注微调（整体模型微调加按客户微调）来提升正确性，然后新一代模型横空出世，"所有这些投资一夜之间过时"。如今的答案是一个统一的底层 SDK 和 harness：新的 CLI、新的桌面应用、云 Agent 全部共用，也支持自带密钥用任意模型（`01:02:04–01:06:22`）。更重要的定位转变：编码 Agent 不只服务写代码——安全修复、每个新 issue 挂一个 Agent 试试、全库文档与实现的一致性检查，都是同一套自动化。"现在你可能不再建 issue 记录想法了，你直接说'把这个做了'"（`01:06:22–01:07:44`）。他心中 GitHub 的"终极形态"是环境智能：他关心的是修 webhooks 时，Agent 知道每一份 spec 文档、每一封相关邮件、每一次相关讨论，并把团队的品味与判断带进实现——他点名 OpenClaw 的启发正在于此：它证明了"连接你全部信息的 Agent"有多能干，而软件开发的下一程是把这种连接度带进工作流。他自己愿意让 OpenClaw 提醒喝水，但不想让它改他的行车路线——控制反转的边界要划清楚（`01:07:44–01:13:05`）。

Microsoft 设 OpenClaw 方向的 CVP 一职也因此顺理成章：Claw 类对象要能安全地跑在员工的 Windows 工作设备上，就需要 OS 级沙箱——"我需要用得了 Claw，而且不被开除"；Microsoft 大量全职投入上游开源项目却刻意不揽功，是因为他们要卖的是平台组件（沙箱、云沙箱、上下文引擎），而不是又一个垂直产品（`01:13:05–01:16:23`）。收尾是两个实用推荐：M365 生态里的 WorkIQ 和 FoundryIQ——两个"上下文引擎"，前者横跨你的会议、邮件、聊天，后者接进既有数据存储，"不用换工具，把已有的接进来"，而且企业级权限让它不会成为泄密事故；以及他建议 swyx 采访 Satya 时问的问题——"你认为两三年后什么是真的？"（`01:18:03–01:23:16`）
