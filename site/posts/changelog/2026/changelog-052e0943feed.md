## 速读

Burke Holland 以个人体验回看 Opus 4.5 带来的能力转折，并与 Adam Stacoviak 讨论 Agent 编程为何仍要经过规划、验证、生产化和质量判断。

标题里的「changed everything」不是一项行业基准。Burke 讲的是自己长期测试 GitHub Copilot 和不同模型后的体感：过去的 Agent 常能做出 demo，却会在错误处卡住；Opus 4.5 则让他第一次看到一个原生 Windows 小工具较完整地生成出来，代码结构也比预期更好，但他仍明确说结果并不完美。更重要的是后续边界：写出代码不等于把软件送进生产，Agent 声称完成不等于已经验证，个人自用工具也不能拿来代表承担安全、维护和 SLA 的平台。（`00:08:18–00:11:10`，`00:18:46–00:20:41`，`00:27:20–00:30:31`，`00:39:37–00:41:49`）

这期值得看的地方，是两人没有只停留在「模型更强」的兴奋中。他们一面想象更多人能够成为 builder，一面担心软件开发的 craft、深层知识和质量标准被快速生成稀释。节目没有解决这种矛盾，也没有证明某套 Agent 工作流已经普遍有效；它提供的是一位深度使用者正在采用的方法，以及对方法失效位置的坦白说明。

## 主题正文

### 一次能力转折，仍只是个人测试经验

Burke 先限定自己的观察位置：他在 GitHub Copilot 的开发者关系岗位跨多个产品组工作，长期试用模型和工具。他回顾较早的 Agent 时说，它们已经会调用工具、运行终端命令和查询资料，能够把项目推进到 demo 或原型；问题是遇到错误后可能停住，而使用者又没有亲手写那段代码，双方都未必理解故障。对他而言，低可靠性不是偶尔多改一次那么简单，而是让人很难把工作放心交出去。（`00:08:18–00:10:09`）

Opus 4.5 的转折来自一组很小、很具体的尝试。Burke 在假期测试一个用于按指定宽高调整 Windows 窗口的原生工具；按他的描述，模型一次完成了主要实现，使用了原生 WinUI 库，代码结构看起来也相当清楚。他紧接着补充「并不完美」。因此，这个案例能证明的只是 Burke 在该任务、该工具链和自己的审阅下获得了明显不同的体验，不能外推成模型对任意代码库都能一次交付，也不能把「结构看起来不错」改写成经过维护性、安全性或缺陷率评测。（`00:10:11–00:11:10`）

节目后面多次使用「step function」一类强烈说法，但它们仍属于参与者的体验与判断。本文不采用节目中未经展示的产能倍率、成本估算或第二手名人案例来强化标题，也不把不同模型版本的主观比较写成排行。真正可复用的问题不是某个版本是否「改变一切」，而是能力提升以后，人怎样定义任务、检查结果并承担上线后的责任。

### 从提示词到工作流：先规划，再要求可验证证据

Burke 描述的工作流并不是把需求写成一句提示词后离场。他会先在 plan mode 中与 Agent 往返多轮，让它提出遗漏、推荐方案和其他选项；任务达到可接受的计划后，才进入实现与迭代。简单问题可以直接回答，复杂构建则需要规划、拆分和委派。这种按难度改变流程的做法，比「所有任务都多开几个 Agent」更关键，因为并行只扩大吞吐，并不会自动补齐目标与约束。（`00:27:20–00:29:37`）

复听补回的一段话给出了更严格的完成条件。Burke 说，多个子 Agent 产出后仍需要审查；他希望自定义 Agent 在另一端交付「可验证」的东西，并回答：你凭什么认为它有效，有什么证据证明它有效？对于浏览器应用，可以让工具实际操作界面、检查自身工作；到了原生应用，这件事就难得多。Agent 可以写单元测试，但他认为仅靠单元测试不足以说明软件在真实使用中确实工作。（`00:29:37–00:30:31`）

这段讨论没有把自报的置信度当成正确性。循环运行到高置信、自动分派工作和模型自检，都只是编排机制；最终证据仍要对应产品行为与风险。Burke 也明确说自己没有全部答案。编辑归纳：可执行的原则是让每项委派同时带回验收方法，把「实现完成」和「证据成立」设为两个条件；但采用什么证据，仍取决于浏览器、原生应用、后端服务等不同运行环境。

### 代码生成变容易，生产交付的责任没有一起消失

当 Adam 担心高性能开发是否会变成需要持续付费才能进入的「收费站」时，Burke 没有只回答模型效率。他的判断是，要真正 ship，仍需理解架构、安全以及应用如何进入生产；写出代码相对容易，把系统送进生产仍然困难。他以大量 vibe-coded 项目没有上线作为个人观察，但节目没有统计样本，因此这只能保留为他的解释，不能写成对所有此类项目的数量结论。（`00:18:46–00:19:37`）

关于初学者是否还应学习编程，他同样保留了摇摆。一方面，他认为 REST API 等概念层层相连，不理解底层使用方式会限制判断；另一方面，他立刻拿编译器反问自己：开发者过去也曾需要理解一些底层细节，如今未必再关心。最后他没有给出学习边界的确定答案，只坚持当时还不能把一个非技术人员直接放进通用 AI 工具，就期待其交付完整生产软件。这个结论有明确时点和工具条件，不是「新人永远不能开发」。（`00:19:38–00:20:41`）

另一段实验把差异说得更具体：一个长期自动运行、不断给游戏添加行为的 Agent 可以产生有趣结果，但 Burke 不认为它最终会自然成为可玩的、可发布的软件。他随后区分个人游戏与可销售、可维护、承担 SLA 的系统：两者都叫软件，基准、要求和期望却不同。即使 Agent 能生成浏览器或编译器规模的代码，真正发布仍是另一件事。这里讨论的是完成定义，而不是贬低实验项目；个人作品可以用「对自己有用」验收，平台则必须面对其他用户、兼容、安全、运维和长期演进。（`00:39:37–00:41:49`）

### 人人都能成为 builder，也可能让 craft 更稀缺

两人尝试重写「AI 会取代开发者」的命题：未来也许不是开发者消失，而是更多人在某种程度上参与构建。Adam 觉得把所有人都叫 developer 有困难，builder 更合适；对话同时承认，传统开发者掌握的知识与技能具有经济价值，开放工具会引发职业身份和守门心态上的不安。把这种心理说出来，并不等于证明专业门槛已经消失。（`00:49:36–00:51:06`）

支持 builder 视角的例子，是业务人员为自己即时构建仪表盘之类的小工具。这里的验收者和使用者可能是同一个人，适用范围非常窄；只要解决自己的问题，就可能已经足够。两人随后又把软件分成个人定制工具、即时业务软件和真正的平台或生产系统，承认后者仍需要更深的系统知识。因而「更多人可以构建」与「所有人已经具备同等工程能力」不是同一句话，降低表达和实现成本也不自动降低系统责任。（`00:51:06–00:53:58`）

节目主动给这份乐观意见安排了反方。Burke 说，写了几十年代码的人会把它看作 craft；快速生成可能像批量商业建筑一样实用，却让精细手艺变少。他和 Adam 用老建筑、稀缺工匠与成本上升作类比，担心人们逐渐失去建造「大教堂」的能力，也担心作品因人人都能快速做出而失去令人惊叹的过程。这个类比表达的是质量焦虑，不是对建筑史或软件质量的测量。（`00:54:10–00:58:46`）

两种判断可以同时成立：Agent 扩大了能把需求变成软件的人群，也提高了区分「能运行」「对一个人有用」「可交付」「值得长期维护」的必要性。节目真正留下的开放问题，是团队会不会把节省的实现时间投入设计、验证和维护，还是只用来制造更多难以理解的代码。工具可以降低动作成本，但产品判断、证据标准和后果归属仍需要人来定义。
