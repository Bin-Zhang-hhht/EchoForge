## 速读

Techno Tim 与 Adam Stacoviak 从硬件稀缺谈到自托管软件、文档识别、Proxmox Agent 接口和一体化存储，重点不在堆设备，而在保留原始数据、约束自动化与控制故障半径。

这期 Changelog & Friends 适合正在经营家庭服务器、文档知识库或 Agent 自动化的读者。Techno Tim 把“2026 是自托管软件之年”明确说成自己的预测；硬件价格、视觉模型识别质量和家中系统表现也都来自两人的购买经历与实验，不是市场调查或对照测试。官方逐字稿没有收录付费赞助口播，本文省略开场闲聊、嘉宾自我推广和与核心判断无关的产品罗列。

## 主题正文

### 硬件越难买，越要重新发现已有机器

Techno Tim 用“availability”概括家庭实验室的变化，但这个词有相反的两面。他观察到服务器级 CPU、主板、内存、GPU 和二手设备更难买、价格更高，并怀疑大型客户的数据中心订单挤压了小额采购及其后续二手供给；这只是他对当时市场的解释，节目没有供应链数据来验证因果。他举出的具体价格也是个人样本：一块 14 TB 翻新硬盘一年前花 159 美元，录制前查看同款时贵了约 70 至 100 美元，不能外推为所有地区或型号的涨幅。（`00:02:03–00:28:52`）

另一面是软件能力更容易获得。Tim 因此预测 2026 会成为“自托管软件之年”：既然新硬件难得，就在已有机器上运行更多软件；本地 Ollama、Open WebUI、文档处理工具和编码 Agent，让过去因时间或开发能力搁置的个人需求变得可尝试。他同时保留了限制：在他的使用感受里，开放模型仍不如付费闭源模型，但已足以承担不少聊天、RAG 和文档辅助任务。这里的“年份”是方向判断，不是说家庭实验室必须新增 AI 负载，更不是购买更大服务器的理由。（`00:02:03–00:28:52`）

### Paperless 的关键不是只换一个更强 OCR

Tim 把 Paperless-NGX 描述为自托管文档扫描与管理系统：传统 OCR 先把扫描件变成可搜索文本，再由 Paperless GPT、Paperless AI 一类附加工具调用视觉或多模态模型提取更丰富的信息。他用设备铭牌做了一个小实验：传统 OCR 只读出少量文字且序列号错误，小型视觉模型则在这张图片上给出了明显更完整的结果。这个案例能说明为何值得试验视觉模型，却不能证明模型对书籍、表格、低质量扫描或所有语言都能稳定达到同样精度；他提到的高准确率也是估计，没有给出数据集与评测方法。（`00:02:03–00:28:52`）

讨论随后从“识别”转向“可重做的处理链”。Tim 提到文档结构化工具可以区分标题、页脚和表格，使输出不只是扁平文本；Adam 则把它放进 ETL 与 medallion 的思路中：bronze 层保留每页原始图像，silver 层做识别和清洗，gold 层才进入面向使用的 Markdown 或数据库。保留原图的价值在于，视觉模型、提示词或结构化方法变化后仍可从原始证据重新处理，而不是被第一次 OCR 的错误永久锁死。Tim 赞同这个架构，同时提醒 LLM 输出本质上仍是每次可能不同的“best effort”；所以原始资产、转换结果和生产数据不应混成唯一副本。（`00:02:03–00:28:52`）

### PXM：先给 Agent 一条受约束的确定路径

Adam 展示的 PXM 是他为 Proxmox 编写的 Go CLI。它把创建 VM 所需的 IP、CPU、内存、磁盘、cloud-init 和 SSH key 收进一个命令，并让 `info` 返回便于继续交给 Agent 的连接信息；保护参数还会提高误删 VM 的门槛。这里真正可复用的设计不是“让 Agent 随便 SSH”，而是先把反复操作压缩成可测试、输入输出清楚的窄接口，再让模型调用它。（`00:30:03–00:38:17`，`01:04:05–01:30:01`）

他设想下一层做 Proxmox MCP：自然语言由模型理解，MCP 优先调用 PXM 里已经收束的常见动作，必要时再触达原生 Proxmox API。Adam 给出的理由是模型具有非确定性，而 CLI、API、测试与 skill 可以为常见路径增加确定性。这里必须区分成品与设想：PXM 能满足他自己的需求，但已经约三个月未改，仍有“warts”，尚未达到他认为可以开源发布的状态；用户模板移到独立仓库、重写 CLI 以及 MCP 都是计划，不应读成已经交付的工具链。（`01:04:05–01:34:02`）

节目还给出一个反例：Adam 曾让 Claude 通过 SSH 进入 UDM Pro，并直接读写其 Mongo 数据库来修复 VLAN 规则。他说自己过去做过、愿意承担这种操作，但 Tim 当场提醒不要直接碰生产数据库。这个成功案例没有证明内部数据库是稳定接口；相反，它说明把模型接到基础设施之前，需要先决定哪些动作可以暴露、哪些资源必须保护，以及出错后如何恢复。（`00:28:52–00:30:03`）

### “一台大机器”减少依赖，也集中故障

受硬件稀缺影响，Tim 的另一项预测是家庭实验室会回到“一台大机器”：存储、应用、转码、本地 AI 与部分计算共享同一台主机。他自己的“home production”运行在 TrueNAS 上，Plex、NAS 和其他必须持续可用的服务靠近数据存放；其推理是，应用主机与 NAS 分开时，任一重启都可能让服务不可用，合并后少了一个运行依赖。这是以家中可用性和管理负担为目标的取舍，不等于故障域消失：主机维护、存储故障或配置错误反而会同时影响更多服务。（`00:38:17–01:00:01`）

他的性能方案是在 ZFS 中用多组镜像硬盘承载容量，以 NVMe special vdev 保存元数据和部分小文件，再利用 RAM 的 ARC 缓存提高响应。Tim 明确说出最重要的风险：special vdev 一旦丢失，整个池的数据都可能丢失；他的应对是四块 NVMe 组成镜像并另做备份。节目没有基准测试来证明“接近 NVMe”的描述适用于其他工作负载，也没有把镜像等同于备份。对读者更有价值的判断顺序是先确认需要哪些服务、可接受怎样的停机与恢复，再考虑共置和分层存储，而不是照抄硬件清单。（`00:38:17–01:00:01`）

Tim 也没有把大机器当作入门门槛。他建议先用闲置旧电脑确认自己是否真的愿意在家承担系统管理，并称多数自托管容器需要的计算资源很少；他的基础需求只是存储、媒体串流、一些计算与必要的转码。更大的机器来自需求和兴趣逐步增长，而不是开始家庭实验室前必须完成的采购。（`01:04:05–01:30:01`）

### 用角色划 VLAN，用测试保存意图

VLAN 部分没有给出一份普适网络拓扑。Adam 与 Tim 最终采用的判断轴是设备扮演的角色、需要访问什么，以及设备失陷后愿意承受多大的 blast radius，而不是看到“智能设备”就一律放进 IoT 网段。Adam 保留 trusted、kids、IoT 和 guest 等角色；Tim 还把摄像头与网络设备分开。Home Assistant 一类需要跨设备通信的服务尤其体现取舍：放在哪个网段都要在规则数量、信任程度和横向移动范围之间选择。（`01:40:08–01:44:15`）

到了生成代码，Techno Tim 给出的底线同样是为长期保留的东西补测试。他认为测试不只检查当前行为，也记录作者当时的意图，让未来接手的 Agent 更容易理解代码。测试不能证明生成实现安全或完全正确，但它把“能运行”提升为可重复验证的行为契约；这与 PXM 的保护参数和 VLAN 的故障半径思路一致：自动化可以更快，边界仍需由人定义并留下可检查的证据。（`01:46:21–01:50:27`）
