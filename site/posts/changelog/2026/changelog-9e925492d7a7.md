## 速读

Nicholas Zakas 分析 npm 为何不能只把安全责任推给维护者，并从 Trusted Publishing、发布时检测、安装脚本和 JSR 的取舍提出改进方向。

这期 The Changelog 邀请 ESLint 创建者和长期维护者 Nicholas Zakas，讨论 npm 安全措施为何不能只围绕维护者凭证展开，以及注册表可以在发布环节承担什么责任。Nicholas 肯定 Trusted Publishing 用按需短时 token 取代长期存储凭证的方向，但指出它在平台覆盖、双因素认证和逐包配置成本上仍有限制；他借信用卡反欺诈说明，验证持卡人只是第一层，平台还应在每次交易或发布发生时检测异常。节目随后把同一思路落到 preinstall、postinstall 脚本，并以 JSR 展示从一开始收紧安全边界所得到的好处，以及与 npm 生态互操作不足带来的迁移阻力。适合维护 JavaScript 包、管理软件供应链，或评估 npm 替代方案的读者。（`00:00:17–00:00:42`）

## 主题正文

### Trusted Publishing 减少 token 暴露，却增加逐包迁移工作

Trusted Publishing 要求维护者在 npm 中为单个包指定获准发布的源码仓库和具体工作流；工作流运行时由 GitHub Actions 向 npm 请求 token，该 token 只在本次工作流期间使用，之后即失效。这减少了长期 token 留存在配置中的风险。（`00:13:27–00:14:30`）

Nicholas 同时强调适用条件：按节目当时的讨论，这套路径适合使用 GitHub，或使用同样支持它的 GitLab 的项目，未使用两者的发布者不能直接获得同样方案；Trusted Publishing 当时也没有双因素认证。按 Nicholas 在节目中的转述，OpenJS Foundation 针对关键包给出的建议是不要采用 Trusted Publishing，因为一旦攻击者取得 GitHub 仓库访问权，便可能获得发布能力。这是他对 OpenJS 建议的转述，不应扩展成针对所有包的普遍结论。（`00:12:19–00:13:23`）

迁移成本也没有消失，而是转移到了包级设置。Nicholas 说，当时缺少批量更新操作，维护者需要逐个包配置并经历多次双因素认证确认；他听说批处理工具将会推出，但在谈话时尚未可用。因此，短周期细粒度 token 和 Trusted Publishing 虽改善了凭证处理，却在配套工具到位前给维护大量包的人增加了工作。（`00:14:44–00:16:27`）

这套机制之所以可信，是 npm 预先知道哪个仓库中的哪一个工作流获准为指定包发布；其他工作流即使请求 ID token，也不能据此发布该包。Nicholas 因而把它评价为一个有价值但仍受平台与 2FA 条件限制的系统，而不是完整终点。（`00:16:40–00:17:50`）

### 从信用卡反欺诈转向注册表侧异常检测

Nicholas 的信用卡类比把责任分成两层：CVC、芯片和 PIN 等措施用于确认操作者有权使用卡片，但发卡机构还会检查每笔交易是否偏离日常模式，并在可疑消费发生时询问、阻断和调查。对应到 npm，保护维护者凭证是必要的，却不能假设任何人都能百分之百避免凭证失窃；注册表也应分析发布行为，在恶意内容扩散之前介入。（`00:17:51–00:20:17`）

他依据 npm 曾在识别出某类凭证窃取攻击特征后阻止带有同类特征的新包上传，判断注册表已经具备某种发布时实时分析能力；但攻击以相似方式反复出现，让他认为这项能力尚未被充分用于更主动的防护。这是 Nicholas 根据公开响应和攻击频率作出的判断，不是对 npm 内部系统的独立确认。（`00:20:22–00:21:33`）

至于为何没有做更多，Nicholas 明确表示自己没有内幕信息：资源不足是他的猜测，大量积压和人手有限是他与 npm 工作人员交流后形成的印象；他关于相关措施可能早已列入路线图、只是被安全事件推动优先落地的解释，也被他明确称为个人解读和理论。（`00:21:34–00:22:52`）

因此，这期节目的可执行主张是把检测前移到注册表的发布路径，而不是把这些资源和路线图推测写成已证实事实。

### 安装脚本既支撑原生模块，也能执行任意代码

npm 的 preinstall 和 postinstall 脚本允许包在安装过程中执行额外命令。它们对原生模块尤其重要：某些包的源码需要针对用户机器编译，postinstall 可以在本机生成可运行形式；生态中已有相当一部分包依赖这种机制，因此直接禁止脚本会破坏现有用途。（`00:38:08–00:40:29`）

风险并不来自编译本身，而是这些脚本可以运行任意命令。Nicholas 举例说，节目所讨论的攻击包曾下载安装并执行 TruffleHog，以搜寻用户机器上的 secrets 和 token。（`00:41:57–00:42:19`）使用 `npm install --ignore-scripts` 可以阻止这些脚本执行，但如果依赖树深处存在必须编译的原生模块，使用者可能事先并不知道，结果会表现为意外安装失败，而且这类深层依赖问题很难调试。（`00:40:31–00:41:19`）

节目中的缓解办法都还是提案。Nicholas 偏好的方案是：如果一个包原本没有 preinstall 或 postinstall，后来新增脚本，注册表应要求发布 major 版本，而不允许只发 patch 或 minor 版本；这样多数依赖者不会自动升级，可为 npm 或安全工具识别恶意版本争取时间。（`00:43:44–00:44:59`）主持人另行提出，对新增或已有安装脚本的包持续进行针对性审查，检查编码混淆、网络请求或额外安装行为；Nicholas 赞同在审慎实施的前提下给予这类脚本额外关注。（`00:45:18–00:46:24`）

另一条提案借鉴 Deno 的权限模型：包要访问网络或文件系统时由用户明确授权。Nicholas 提到 npm 曾有相关实验，但不确定这些权限是否覆盖 preinstall 和 postinstall；他也承认，为安装脚本增加联网等能力的选择加入授权，实施起来可能比描述中复杂。（`00:42:19–00:43:44`）

### npm 的惯性与 JSR 的安全、互操作取舍

Nicholas 认为 npm 的生态惯性已经大到很难摆脱：JavaScript 包的 README 通常直接告诉用户从 npm 安装，使用者也习惯到 npm 查找包。替代注册表面对的不只是技术设计，还要改变维护者的发布路径和用户的发现习惯。（`00:34:10–00:34:37`）

JSR 展示了从起点设置更严格边界的做法。Nicholas 介绍，它会保留可能引发冒用或混淆的 scope；他申请 ESLint scope 时必须证明自己与项目的关系。JSR 从一开始支持 Trusted Publishing，本地发布则要求双因素认证，并且不提供 preinstall 或 postinstall 脚本。（`00:34:38–00:36:06`）与此相伴的取舍是，JSR 不处理需要安装时编译的包，而 Nicholas 认为一个从零设计的注册表可以选择这种边界；若要支持原生编译，安装脚本则成了难以完全回避的代价。（`00:41:20–00:41:48`）

真正阻碍迁移的还有 npm 互操作。Nicholas 报告，JSR 不能像 npm 那样安装 ESLint 后直接把它作为命令运行；而替代注册表若不能单独覆盖全部依赖，就必须允许项目混用两边的包。他们曾尝试在一个准备发布到 npm 的 ESLint 包中使用 JSR 标准库包，最终因为流程过于困难而把源码复制进自己的仓库。按他的实操描述，仅部署应用时可以工作，但把混合依赖的包再发布回 npm 并不可行。（`00:55:30–00:57:17`）

因此，节目呈现的不是简单的安全功能清单：JSR 的保留 scope、Trusted Publishing、2FA 和无安装脚本设计减少了一些攻击面，但 npm 的分发惯性、命令行包能力和跨注册表发布兼容性决定了这些优势能否被现有生态采用。
