## 速读

The Changelog 688 期，Snowflake Postgres 负责人 Craig Kerstiens 重访节目：数据库的「无聊」是刻意的产品决策——核心保持稳定、可预期，创新留给扩展生态；pg_lake 把 Iceberg 目录与 DuckDB 装进 Postgres，直面把数据在 OLTP 与 OLAP 之间搬来搬去的 ETL 之痛。（`00:00:01–00:00:16`，`00:13:02–00:14:23`，`00:17:50–00:18:47`）

最值得停留的三段：Postgres 19 被他称为十年来最酷的版本，repack concurrently 从专家级扩展变成核心能力（`00:11:49–00:12:03`，`00:34:24–00:36:04`）；ETL 被他同事吐槽「E 代表 evil」，而 pg_lake 让一条 CREATE TABLE ... USING ICEBERG 就能写出 Parquet、交给内嵌的 DuckDB 查询（`00:17:50–00:18:47`，`00:22:41–00:23:21`）；AI 生成的 PR 正涌向全球约 50 名核心提交者，维护者负荷与安全披露被同步放大。（`00:48:35–00:49:07`）

## 主题正文

### 「无聊」是刻意的产品决策

开场介绍里，Craig Kerstiens 现任 Snowflake Postgres 负责人，此前在 Heroku、Citus Data、Microsoft 和 Crunchy Data 搭建过数据平台（`00:00:01–00:00:16`）。他回忆「Postgres 之年」的文章已经连写了五六年，而自己当年在 Heroku 押注 Postgres 时没人看好，「没别人想赌」，那时它一点都不酷（`00:04:27–00:05:07`）。如今他提醒的是另一面：工程师选型常常自称理性、其实是跟风，真正拉开差距的是并发索引创建、事务性 DDL、LISTEN/NOTIFY、JSONB 这些底层能力——「我们是跟风粉，不总去剥开看看它到底好在哪」（`00:07:38–00:08:13`）。

繁荣也不只是运气。据他介绍，Heroku 曾为核心功能开发直接出钱、雇人，他后来在 Citus、Microsoft、Crunchy Data 和 Snowflake 延续了这种投入；Oracle 对 MySQL/MariaDB 用户的「衬托」也帮了忙（`00:08:56–00:09:25`）。而这套开发机制按现代开源标准几乎不该成立：没有 issue tracker，补丁寄到邮件列表，GitHub 上的仓库只是镜像；他直言「按所有标准看这都不该成立，但它持续变好」，项目已超过 30 年（`00:09:42–00:10:34`）。

他对好数据库的定义贯穿全场：像银行一样的服务。做了十来年客户支持的体会是，用户说「没什么反馈」往往是要走了；理想的数据库是让人不去想它——做好且无聊，没有意外、没有戏剧性（`00:39:03–00:40:35`）。

新一代开发者则常常在不知不觉中用上 Postgres。主持人 Adam Stacoviak 说，他接触的一些 Supabase 用户答不上「用什么数据库」，因为「未来不是选 Postgres，而是选了 Postgres 的那个东西」；Craig 把 Supabase 类比为 Firebase 式的易用 API/工具层，多于直接的数据库供应商（`01:40:26–01:41:09`，`01:41:43–01:41:58`）。他给出的评估标准是：这些 Postgres 公司是真在深挖并反哺上游，还是「贴个 Postgres 标签」——他认为 Supabase 与 PlanetScale 属于前者，否则「潮水退得很快，地基可能不在」（`01:43:16–01:43:59`）。

### 扩展生态：把 Postgres 当平台用

Craig 反复强调的公式是：核心保持无聊、可预期、安全、快，新能力交给扩展。文本搜索是典型例子——BM25 类搜索（他称 ParadeDB 先做，Timescale 又开源了一个）把 Elasticsearch 的核心能力搬进 Postgres；PostGIS 则庞大到他形容为「平行路径」，地理空间的处理与核心差异太大（`00:12:09–00:13:02`）。

主持人的类比更进一步：有扩展的 Postgres 像一个 OS 或 runtime，「能为它写扩展，就能在它上面做事」，甚至让整个团队收敛到一个数据库底座；Craig 的说法是「Postgres 不只是无聊的关系库，它是一个 data platform」（`00:26:45–00:27:47`）。节目里给出的取舍是：如果一个扩展能做到专用系统八九十的功能，而省掉运维、监控、备份和多套凭证，省下的不只是成本，更是「痛苦」——不必为了一个任务学五种工具（`00:28:39–00:29:12`）。

### pg_lake：把 Iceberg 目录和 DuckDB 装进 Postgres

先看问题。Craig 把 OLTP 与 OLAP 称为三十年的学术分野：前者行存、单行插入更新、毫秒级返回，后者列存、批量摄入分区、可以等几分钟；两拨人「几乎从不同时出现在一个会上」（`00:15:34–00:17:50`）。他同事调侃 ETL 的「E」代表 evil——从行存库上批量抽数会压出负载甚至故障，数据进分析系统有延迟，搬数据本身就是巨大的痛点源，「聊到这个有人几乎要哭」（`00:17:50–00:18:47`）。

他给了三个类比：DuckDB 之于分析，如同 SQLite 之于嵌入式事务——适合桌面分析，而不是 Postgres 的替代品（`00:19:56–00:20:45`）；Parquet 是为列式分析设计的「CSV」，Iceberg 则是在 Parquet 之上叠加更新集、删除集的元数据目录，让各家数据仓库引擎都能连上来查（`00:20:45–00:22:35`）。

pg_lake 被他形容为「12 个扩展合一体」：先在 Postgres 里放一个 Iceberg catalog，再内嵌 DuckDB 做查询引擎；DuckDB 语法不同，就加语法转换扩展；函数不同，就加函数扩展；GeoParquet 要转成 Postgres 地理类型，也有扩展；最后还有一个管理扩展版本本身的扩展（`00:13:02–00:14:23`）。结果是，不必再靠机柜上的 Python 脚本搬数：用 pg_cron 在库内调度，S3 桶里出现新 Parquet 文件就能直接查（`00:14:29–00:15:15`）。

用法上，CREATE TABLE ... USING ICEBERG 即自动以 Parquet 写入 S3，可正常 INSERT 和查询，查询由 DuckDB 执行；Spark、Snowflake 等能讲 Iceberg 的分析引擎也可直连同一份数据（`00:22:41–00:23:21`）。他举的客户案例颇有说服力：一位用户用 Athena 等搭了三个月的管线、即将上线，看完 pg_lake 演示后决定整条推倒重写，理由是本来就担心上线后怎么运维它，「能删代码反而高兴」（`00:29:16–00:30:15`）。

入手方式：在 GitHub 搜索 pg_lake 自行安装扩展，或在 Snowflake Postgres 上 CREATE EXTENSION 即用；他强调项目 11 月才开源，但此前已有约两年研发（始于 Crunchy Data 时期），目前仍在持续投入（`01:28:21–01:29:08`）。Snowflake 自己的答案则是 database mirroring：一条命令把 Postgres 库双向镜像，不用想 CDC 和 ETL，表近实时持续复制（`01:29:49–01:30:32`）；他描述的智能电视客户把观看数据实时写入 Postgres，经 pg_lake 或镜像进入 Snowflake 分析，再由其 AI 层 Cortex 决定广告投放，结果回到 Postgres 作毫秒级查询服务层（`01:30:32–01:31:40`）。

### Postgres 19：他口中十年来最酷的版本

观点先行：如果有一个版本让他觉得「wow」，那就是 Postgres 19——「可能是十年里最酷的发布」（`00:11:49–00:12:03`）。他刚在 Snowflake 博客发文盘点，发出去仍有人留言「漏了我最爱的特性」（`00:31:12–00:31:23`）。作为参照系，他回溯：9.2 引入 JSON 时其实是「作弊」——校验合法后整个塞进 text 字段，没有索引，却贡献了「Postgres 现在是文档数据库」的头条；两年后的 JSONB（同事说 B 代表 better）才是磁盘上的二进制表示、可建 GIN 索引；他因此称 19 是 JSONB 以来十年最大的发布（`00:32:44–00:34:23`）。

旗舰特性是 repack。Postgres 底层是 append-only：删除只做标记不回收空间，膨胀要靠持锁 vacuum 清理；pg_repack、pg_squeeze 扩展多年来在线重写表，但需要额外磁盘、有一定风险，属于「专家模式」。19 把 repack concurrently 收进核心：不持锁、后台运行，不必再去装扩展（`00:34:24–00:36:04`）。

第二件是查询计划固定。Postgres 长期「信任规划器」，靠统计信息和启发式选索引、定计划，通常可靠；但数据分布一变，计划可能悄悄更换，让成熟生产库的运维措手不及。新能力让你把计划「钉住」——不是绕过规划器手写 hint，而是要求它「别在未来换计划给我惊喜」（`00:36:59–00:38:44`）。

其余改进密度同样很高：autovacuum 改进与逻辑复制增强（`00:40:35–00:40:52`）；SQL 标准的图属性让他看到单个 Postgres 里出现图查询能力（`00:42:05–00:42:26`）；GROUP BY ALL 免去逐列罗列，也治好他自嘲的 group by 1,2,3 坏习惯（`00:42:37–00:43:42`）；UPSERT ... ON CONFLICT 终于能返回那一行已有数据，ORM 少一次往返（`00:43:41–00:44:14`）。企业侧的信号是：不止开发者，企业也开始问「为什么继续付 Oracle/SQL Server 的高许可费」，把 Postgres 当可长期下注的对象（`00:44:41–00:45:08`）。

条件必须说清：19 的功能集已冻结但尚未发布，他预计几个月后落地，20 的开发已经开始，他点到数据类型灵活性与文本搜索的丰富度（`01:26:38–01:26:56`）。他的建议是到时候「别怕数据库」，上手把玩（`01:38:45–01:39:13`）。

### AI 时代的小社区：约 50 个提交者与被放大的责任

节目前后两次给出同一个数字：全球真正向 Postgres 提交代码的 committers 不到 100 人，更接近 50；开场预告则说「大量 agent 生成的 PR 正涌向他们门口」（`00:00:48–00:00:58`，`00:48:35–00:49:07`）。Craig 解释为什么数据库比前端更难被 AI 快速贡献：模型靠公开代码语料训练，而高质量的大型公开 C 代码不多；UI 上按钮放错是一回事，「我损坏了数据」是另一回事，正确性验证本身就是难题（`00:49:09–00:50:07`）。

主持人补充的判断是：提交吞吐量与软件质量不是一回事——他转述推特上「Spotify 日均部署约 7500 次」引发的议论，认为应用没有因此变好（`00:50:24–00:51:03`）。两人对生产边界的共识明确：在 R&D 里尽管探索，核心生产库另说；Craig 以银行为例，AI 可以帮你找优惠、换套餐，但「我的核心数据库，我觉得还没到那一步」（`00:51:31–00:52:35`）。

主持人把开源的未来概括为一场注意力问题：PR 本质是对维护者注意力的需求，用户变多、问题变多、PR 变多，单个 PR 可能淹没在成千上万个同类里（`00:53:29–00:54:28`）。Craig 的宏观担忧是结构性的：十五二十年前一切变更走 DBA，后来开发者绕过 DBA 自建库、DBA 被动接锅；如今「人人都是公民开发者」，却从未有过「DBA 训练营」——按他的说法，开发者与数据库专家的比例从 10:1 到 100:1，即将 1000:1（`00:54:29–00:56:11`）。主持人顺势提议把 DBA 理解为 database agent：在规划器旁边放一个模型做即时的计划权衡；Craig 认为方向成立，「肯定有人该去做，问题是生产什么时候跟上」（`00:56:18–00:57:03`）。

安全是 AI 放大效应最直观的地方。主持人指出开源「因可见而默认安全，也因可见而默认不安全」——现在的模型能以前所未有的速度扫描和甄别代码（`00:59:41–01:00:04`）。Craig 的回应分几层：把 Postgres 从 C 移植到 Rust 基本不现实，邮件列表每隔几年就有人重提，「祝你好运」（`01:00:21–01:00:37`）；社区确实挖出过潜伏 10 到 20 年的老 bug，但正因 Postgres 无处不在、盯它的人多、扫描结果在回馈上游，他仍信任它的状态（`01:01:03–01:01:29`）；大型公司都在下注——Amazon、Microsoft、Google，世界 500 强几乎都有 Postgres 足迹，.org 顶级域就运行在 Postgres 上（`01:01:36–01:02:16`）。他举的最生动例子：PostGIS 主维护者 Paul Ramsey（在他团队）提到有模型找出潜伏 15 年的小内存泄漏——「大概是我当年第一次提交时就埋下的」（`01:02:29–01:02:57`）。

支撑这一切的是一套朴素的测试体系：Postgres 基金会自建 build farm，C 代码可跑静态分析，他所在的 Crunchy Data 时期参与编写过 STIG 与 CIS 基准；发布流程靠 CommitFest 分阶段测试评审，「最缺的是测试者」；社区之外，Amazon、Microsoft、Snowflake 各自加测（`01:04:56–01:07:12`）。

负责任披露则是小社区与大厂商协作的样本。按他的描述，Snowflake 接入新扩展前先用模型做自动化安全评估，发现漏洞先打电话问维护者希望怎么报告，然后带着补丁和 PR 上门，而不是「提个 issue 祝你好运」；按项目意愿决定是否发 CVE，在修复发布前不公开（`01:08:40–01:10:11`）。历史坐标是：Postgres 近 15 到 20 年大约只有 2 个 zero-day；修复需要社区与 Amazon、Snowflake 等交付方提前协调，让对方第一天就能滚动自己的机群——他认为 Postgres 在负责任披露上做得很好（`01:12:16–01:13:39`）。而 AI 把这件事的利害推高：「任何人都能发现漏洞、知悉漏洞并利用」的今天，风险比以往任何时候都高（`01:14:26–01:14:52`）。

展望收尾：他把 pg_lake 形容为「还早、还新」的东西，认为 AI 接入 Postgres 是自然方向——「它是所有人底层都会用的数据库」，帮大多数并不擅长数据库的开发者做调优的数据库 agent 也会到来（`01:26:03–01:26:32`）。
