## 速读

Apache Airflow 的维护者 Jarek Potiuk 与 Amogh Desai 打开一个真实的大型 Python monorepo：节目称其有超过 100 万行 Python、120 多个概念上的包，并以 uv workspace、`pyproject.toml`、prek 和一套共享库机制来管理相互依赖的发行版。重点不是“monorepo 必然优于 multirepo”，而是把源码边界、开发环境和发布方式拆开处理（`00:00:00–00:02:58`，`00:18:12–00:19:43`，`00:33:09–00:34:05`）。

这期适合维护大型 Python 项目、正在拆分内部包，或需要同时管理多个发行版的工程师。最有用的部分是可操作的开发路径：进入要工作的子项目运行 `uv sync`，让 workspace 按声明加载本地依赖；在模块内运行 `prek` 钩子；通过 IDE helper 自动发现源目录和测试目录。与此同时，Airflow 的共享库、符号链接和构建时 vendoring 是该项目为解决版本并存而做的定制，不能直接当作所有 monorepo 的通用默认方案（`00:36:24–00:37:43`，`00:43:27–00:44:34`，`00:48:52–00:50:17`，`00:51:48–00:52:50`）。

## 主题正文

### Monorepo 的价值在于一起开发，不等于单体应用

嘉宾把 monorepo 和 monolith 区分开：一个仓库可以包含许多相对独立的组件，每个组件拥有自己的构建产物、依赖和发布节奏；仓库统一提供一起测试、一起开发和跨组件协作的边界。组件仍可拥有自己的 `pyproject.toml`，甚至自己的虚拟环境。这里的关键是集中源码位置，不是把所有功能变成一个不可拆分的运行时（`00:08:46–00:10:10`）。

这套结构对 Airflow 的现实压力来自集成规模。节目提到，项目每周约有 310 个活跃 pull request、约 200 个已合并、约 100 个仍开放，并称有 120 多个发行版或分布；这些数字是录制时主持人与嘉宾对 GitHub pulse 和项目结构的口头概述，不是稳定的项目规格。嘉宾还说，项目有约 120 万行 Python（去掉注释后约 918,000 行），另有约 200,000 行 reStructuredText、81,000 行 YAML 和 16,000 行 TOML；YAML 主要用于 provider 规格，部分 YAML 与 TOML 是生成后提交进仓库的（`00:12:47–00:13:12`，`00:18:12–00:19:43`）。

因此，节目并没有建议所有项目都改成 monorepo。Potiuk 的个人结论是，现代工具消除了他过去认为必须拆成多个仓库的许多理由；但这仍是 Airflow 团队的经验判断。可迁移的原则是先问清楚组件之间是否需要频繁联动、共同验证和共享演进，再决定仓库边界，而不是把“微服务”“多仓库”或“单仓库”当成架构目标本身（`00:59:18–01:00:00`）。

### uv workspace 把声明变成实际的开发隔离

Airflow 的当前做法是由顶层 `pyproject.toml` 声明 workspace 成员和路径，各子项目再声明自己的运行时与开发依赖。进入某个发行版目录后，开发者运行 `uv sync`；uv 会为这一工作区同步所需环境，workspace 内的传递依赖优先使用本地源码而不是从 PyPI 安装。随后可以用 `uv run pytest` 在对应环境中运行该项目的测试（`00:38:01–00:38:29`，`00:36:24–00:37:43`）。

这里真正重要的是“缺什么就不暴露什么”。如果 `airflow-ctl` 没有把 `airflow-core` 声明为依赖，运行 `uv sync` 后，core 的源码不会因为同在一个 monorepo 就自动出现在该环境中；离开一个子项目再进入另一个子项目，环境会随声明重新对齐，未声明的依赖和源码也会被卸载。这让错误的跨包导入更早暴露，并把 `pyproject.toml` 变成依赖和边界的单一事实来源（`00:39:17–00:40:58`，`00:41:41–00:42:56`）。

这也是一个配置例子，而不是“只要装 uv 就自动完成架构治理”：团队仍需为每个发行版写清依赖、在顶层列出 workspace 成员，并接受同步环境会移除未声明内容的行为。节目提到 Hatch 也在支持相近的 workspace 概念，但 Airflow 尚未实际尝试把它作为一对一替代；因此这里能确认的是 uv 在 Airflow 的真实使用状态，不是其他工具已经完全兼容的结论（`00:34:50–00:35:21`）。

### prek 让检查规则跟着模块走

Airflow 过去把所有 pre-commit hook 堆在顶层 YAML 中，还曾用超过 10,000 行 Bash 脚本手工维护部分 monorepo 行为；后来团队把一些脚本转换为 Python，并与 uv、prek 的作者协作，把需求反馈到工具中。Potiuk 与 Desai 都强调，工具本身的演进和维护者之间的直接合作，是这次迁移能够落地的重要条件（`00:22:45–00:23:19`，`00:24:20–00:25:10`）。

在录制时，prek 是用 Rust 编写的、可运行多语言 hook 的 pre-commit 框架。Airflow 可以把 hook 配置放在对应模块中，进入该子项目运行 `prek run`，只执行与这个发行版相关的检查；它还提供 shell 补全，减少从 CI 输出反查失败 hook 名称的麻烦。嘉宾把速度、模块化配置和补全列为相对旧方案的实际收益，并提到 prek 也被 CPython、FastAPI 等项目采用，但没有给出 Airflow 与旧方案的基准测试（`00:42:28–00:44:50`，`00:46:38–00:47:13`）。

另一个配套变化是 PEP 723 的 inline script metadata：脚本可以携带自己的依赖元数据，配合 `uv run`，使用者不必先在全局环境中手工准备依赖。节目也讨论了 PEP 735 的 dependency groups，以及用 `dev`、`test` 等组组织开发依赖；这些是标准和工具支持带来的能力，具体组名和命令仍取决于项目的 `pyproject.toml`。主持人举出的“给别人一个脚本，让他用 `uv run` 执行”的例子，不能理解成脚本绝对不需要任何运行时，只是 uv 可以进一步处理 Python 和依赖的安装（`00:28:50–00:31:38`，`00:32:04–00:32:31`，`00:47:55–00:48:22`）。

### 共享库解决重复代码与版本耦合的两难

Airflow 想复用日志、配置等公共代码，却不想让所有发行版永远锁定同一个共享库版本。团队尝试过基于 pip 的 vendoring 工具，最终采用符号链接加构建预处理：共享代码在源码树中通过 symlink 提供给目标发行版，prek 自动维护需要生成的 `pyproject.toml` 片段和相关一致性；构建发行版时，这些代码被自动 vendored 进包中（`00:50:19–00:52:50`）。

结果是，不同时间发布的发行版可以各自携带共享库的快照：一周前发布的包保留当时的配置实现，今天发布的另一个包可以带今天的版本，二者仍可一起安装。嘉宾用静态库作类比，但这套方案不是 Python 打包标准的既定功能，而是 Airflow 围绕自身发行版布局组合出的混合做法。它需要 symlink、构建配置和自动检查协同工作，也增加了发布流程的隐含复杂度（`00:52:50–00:54:29`）。

节目称 Airflow 当时已有约 11 到 12 个共享库，目标之一是支持 Airflow 3 的控制平面与执行平面拆分；这些是项目当前的架构方向，不应当被写成所有 Python monorepo 都应拥有的数量或分层方式。嘉宾给出的可迁移部分是：若确实需要版本各自演进，可以考虑构建时嵌入；若不需要，普通独立发行版依赖仍然是更标准的路径（`00:55:41–00:56:05`，`00:56:10–00:57:11`）。

更值得注意的是架构副作用。共享库迫使团队减少循环依赖和导入时初始化，把配置改为由调用方注入，并让每个组件拥有更清晰的入口和初始化顺序。嘉宾认为这改善了 Airflow 内部架构，但这是迁移过程中形成的设计收益，不是符号链接本身自动保证的属性（`00:57:18–00:58:50`）。

### IDE、社区协作与采用边界

多包仓库的开发体验不会仅靠包管理器自动完成。Airflow 提供 IDE helper script，自动发现 monorepo 中的包；对 IntelliJ/PyCharm，它为每个模块把 `src` 标记为 source root、把 `tests` 标记为测试目录；VS Code 也有由社区贡献的对应脚本。节目没有声称这些脚本是 IDE 的通用标准，而是项目为“顶层有 120 多个源目录”这一现实提供的辅助层（`00:48:52–00:50:17`）。

这段迁移史也说明，真实部署经验和普遍建议要分开。Desai 回忆，过去切换分支或 rebase 后重新组装环境很痛苦；现在进入目标目录同步几乎不费力。Potiuk 则说，早期很多行为由 Bash 手工实现，团队后来与 uv、prek 构建者共同测试、提交问题并推动功能。这证明持续维护者参与能改善工具，但不能推出其他团队会得到同样的迁移成本或速度（`00:23:51–00:24:19`，`00:24:20–00:25:40`，`00:45:29–00:46:26`）。

给准备采用这套思路的团队，节目最稳妥的建议是从真实边界出发：把组件依赖写成声明，让同步和检查在本地尽早暴露越界，再根据发布需求决定是否做共享库嵌入。Airflow 的 symlink 方案可以作为研究案例，而不是复制粘贴的起点；工具在录制前后仍可能变化，Hatch 的相近实现也尚未由嘉宾在 Airflow 上验证（`00:34:50–00:35:21`，`00:56:10–00:57:11`）。
