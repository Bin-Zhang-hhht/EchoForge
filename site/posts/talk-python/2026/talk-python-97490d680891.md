## 速读

这期节目解释 Ray 如何把熟悉的 Python 编程模型扩展到多进程、多节点和 GPU 集群：从强化学习研究的起点，到如今用于 LLM 后训练和多模态数据处理的分布式执行引擎。它适合正在面对单机内存、CPU、GPU 或跨机器编排瓶颈，却不想把开发环境和生产集群写成两套代码的 Python、数据和 AI 工程师。

最值得注意的是，Ray 的价值不只是“把函数丢到更多机器上”。嘉宾把它定位为协调异构资源和复杂 AI 流水线的底层层，Ray Data 则用惰性数据集、map 操作和资源声明，把 I/O、CPU 预处理与 GPU 推理串起来。节目也没有把它包装成万能替代品：Pandas、Polars、Dask 等在表格或科学计算场景各有重点，集群版本管理仍属于外层编排系统。文中的性能和规模数字均保留节目中的条件与归属，未作独立复现。

## 主题正文

### 从强化学习研究走向 LLM 后训练

Ray 起源于 UC Berkeley 的 RISE Lab。Edward Oakes 说，他约从 2018 年末或 2019 年开始参与 Ray，当时还是 Berkeley 的研究生；Richard Liaw 则回忆，实验室同时聚集分布式系统、机器学习、网络与安全方向的人。这样的交叉环境让研究者既能看到模型需求，也能获得构建集群系统的能力（`00:03:21–00:04:29`，`00:08:48–00:12:08`）。

直接动因是强化学习研究。Robert 和 Philip 等更偏机器学习的研究者试图用 Spark 做强化学习，却发现 Spark 面向较静态的数据处理，而强化学习需要更动态的组件协作，于是团队开始构建更适合自己需求的工具。受访者把这描述为“工具不符合问题，就做需要的工具”，而不是把 Ray 简单称为 Spark 的继任者；两者来自相近的 Berkeley 实验室谱系，但解决的问题不同（`00:03:45–00:04:05`，`00:09:37–00:10:34`）。

后来强化学习一度被认为不够实用，Ray 早期最成功的库 RLlib 也随之降温。ChatGPT 之后，强化学习重新成为语言模型后训练的一部分：先用预训练得到包含大量信息、但尚未针对具体用途调整的模型，再用强化学习等方法把它塑造成更适合聊天或编码代理的系统。嘉宾明确说，OpenAI 至少训练 GPT-3 时使用了 Ray 作为计算框架；他没有确认 GPT-4，因此这里不延伸为更广泛的版本归因（`00:14:04–00:15:57`）。

### Ray Core 的位置：跨节点的 Python 编排层

受访者用两个维度区分并行工具：一个是 API 对特定工作负载还是通用，另一个是只能在单线程、进程或主机内扩展，还是能够跨机器扩展。`asyncio` 适合大量等待数据库、HTTP 或文件操作的 I/O 并发，但仍在单线程内；多进程可以利用一台机器上的多个核心；当内存、CPU 或 GPU 超过单机能力时，才需要 Ray、Dask 这类集群框架。节目中的“64 核”“1 TB 数据”是主持人用来说明单机边界的假设，不是 Ray 的基准条件（`00:18:57–00:22:40`）。

Ray 可以在单机运行，管理自己的进程，让主程序把工作交给 tasks 和 actors；这种模式与 multiprocessing 相似，但带有自己的 API 和观测能力。受访者同时强调，Ray 真正的价值在多节点集群，而不是声称单机上一定比 multiprocessing 更快（`00:23:10–00:23:47`）。Ray Core 的底层能力也不局限于 AI：嘉宾提到金融机构用它做并行回测和时间序列分析，但这只是访谈中的使用案例，不是行业覆盖率或性能证明（`00:27:03–00:28:09`）。

在使用体验上，开发者可以用一个 Python 脚本启动原本需要多个容器和入口的组件，在本地机器上联调，再用同一套代码连接集群。Ray 的任务、actor 与资源声明负责把工作交给合适的进程；KubeRay 则以 Kubernetes operator 的方式把 Ray cluster 或 job 变成自定义资源，由 Pod 组成集群、互相连接并接受健康检查。也可以使用 cluster launcher 创建 AWS、GCP、Azure 或自有机器上的集群，或选择 AnyScale 等托管服务；launcher 本身并不等于完整托管体验（`00:28:31–00:31:36`）。

### Ray Data 把 I/O、CPU 与 GPU 串成惰性流水线

示例从 `ray.data.read_parquet` 读取对象存储中的数据开始。调用本身不会立即把数据加载到某一台机器，而是先构造惰性计算；真正执行时，数据可以由整个集群中的进程直接从 S3 读取，并利用已经分片的文件或行来分配工作。对数据调用 `map` 时，传入的是处理函数，Ray 再决定怎样把它分布到集群中；示例中，重采样函数可能在数百个进程上执行，这是嘉宾对该流水线形态的说明，不是固定的吞吐保证（`00:34:34–00:37:31`）。

这个例子先用 `torchaudio` 把音频转换成更适合后续处理的数组，再用 Whisper 做推理。由于加载 Whisper 模型本身可能耗时，示例把它封装为 class，让多个进程各自预加载模型；如果需要 GPU，可以为该算子声明 GPU 资源。嘉宾描述的核心不是某个模型的速度，而是同一条程序可以表达 I/O 密集、CPU 密集和 GPU 密集的阶段，并让 Ray 按资源协调它们（`00:37:31–00:39:59`）。

资源声明也让调度不只看 CPU。嘉宾举的配置例子是“每个 GPU 可能需要 4 个 CPU 才能保持 GPU 忙碌”，并称 Ray Data 会据此自动调整资源使用；这是为解释调度机制的假设性配比，不是所有模型或硬件都适用的最佳值（`00:40:10–00:40:42`）。Ray Data 更想解决的是数据与 GPU 相交处的非表格、异构处理，以及把 vLLM 等模型推理阶段插入数据管线；它并不把交互式表格体验作为重点，Pandas、Polars 和 Dask 的表格能力不能由此推断为等价或劣于 Ray（`00:40:42–00:42:50`）。

流水线可以把结果分区写回 S3 或 NFS，而不是先汇总到一个进程再写出。对于多模态数据，嘉宾还提到可在处理链中使用开放权重的本地模型，也可以调用 Anthropic 等 API；具体选择取决于模型、数据隐私、硬件与成本，节目没有给出统一的性能比较（`00:42:08–00:43:19`）。

### 可观测性、调试与部署边界决定生产体验

分布式程序的难点不仅是启动更多进程，也包括知道每个节点和任务正在做什么。Ray Dashboard 提供集群层视图，可查看节点、CPU/GPU 资源消耗及运行内容；在任务和 actor 视图中，可以看到例如数据读取任务提交了多少、完成了多少、哪些失败以及相关堆栈摘要。更高层的视图则面向数据处理和训练库，帮助使用者理解流水线，而非只看到底层进程（`00:43:19–00:45:14`）。

VS Code 调试扩展把类似 PDB 的体验带到远程函数：开发者可以在可能运行于另一台机器的函数中设置断点，遇到异常后附加到远程进程，查看回溯和局部变量。这解决的是“本地正常、上集群后某条数据出错”的定位问题，节目没有声称它支持 PyCharm；嘉宾说录制时主要是 VS Code 及其衍生环境，并邀请贡献者扩展（`00:47:17–00:49:08`）。

集群管理与应用版本管理需要分开看。Ray 可以通过 runtime environment 自动打包本地代码：提交任务时把本地文件压缩并上传到集群协调进程，任务和 actor 按内部 ID 拉取对应代码。嘉宾报告，在只改 driver script、重新提交任务的条件下，更新耗时“不到 1 秒”；这是一项关于代码同步路径的访谈陈述，不是整套集群重部署的端到端基准。如果更换 CUDA 版本等底层环境，仍然需要重新部署集群，嘉宾把这种变化描述为通常数月才发生一次的低频事件（`00:54:41–00:56:00`）。

正在运行的工作流如何版本化，Ray 留给外部编排层处理：Kubernetes 用户可能把自定义资源定义提交到代码仓库，也有人使用 Airflow；AnyScale 则把代码产物、集群配置和基础设施配置组合成可复现或版本化的 job 单元。这个边界很重要：Ray 提供执行和资源协调，但不会替应用团队决定发布、回滚和长任务的版本策略（`00:56:05–00:56:59`）。
