## 速读

Django 的异步接口已经成形，但采用策略不该是全面改写；这期把渐进部署、数据库边界、Tasks 后端抽象与自由线程的机会放进同一张工程地图。它适合正在评估 Django 异步视图、长连接、后台任务或 6.1 数据库改进的开发者，也能帮助团队先判断瓶颈究竟在 I/O、CPU、连接池还是查询本身。

前 Django Fellow、现 Django steering council 成员 Carlton Gibson 的核心判断是：旧版异步主题文档留下了“尚未完成”的印象，但 ORM、缓存、认证、会话与信号等面向用户的异步 API 已经具备；剩余难题更多属于 Python 异步编程和扩展生态，而非 Django 独有。与此同时，他没有把 async 描绘成万能加速器：数据库连接数、事务线程归属、事件循环上的 CPU 工作和部署复杂度仍然决定实际收益。（`00:30:53–00:31:24`，`00:41:13–00:45:13`）

## 主题正文

### 文档改写纠正的是过时风险叙事

Gibson 解释，Django 的异步主题指南写于早期支持刚加入的阶段，当时第三方库覆盖不足，文档也反复强调功能未完成与性能代价。随着 Python 和 Django 演进，这种表述没有同步更新：`sync_to_async` 一类线程切换过去可能需要毫秒量级，而他称在较新的 Python 上已降到数十微秒；在一次本身耗时数毫秒的请求中，这通常不再是显著成本。这个比较是他的量级判断，不应理解为所有应用都可以忽略切换开销。（`00:28:31–00:30:49`）

更重要的是功能面。Gibson 列举 ORM、缓存框架、认证、会话和信号，称这些部分都已有异步 API，因此从用户角度看主要接口已经齐备。团队仍会继续修复和扩展功能，但文档不应再用“故事没有完成”的口吻劝退用户；这也是性能警告被降为说明的原因。（`00:30:53–00:31:24`）

### 渐进采用比整体迁移更符合真实负载

异步视图并不要求先把部署切到 ASGI。Gibson 说明，Django 可以在 WSGI 下运行单个异步视图，例如在一个请求里并发调用五个外部 HTTP 端点，再聚合结果；Django handler 会为它运行事件循环。真正需要 ASGI 的典型条件是长连接，例如 Server-Sent Events、WebSocket 或流式响应：在 WSGI 的 worker 模型里，每条长时间占用的连接会消耗一个 worker，而 ASGI 可以让许多等待 I/O 的连接共享事件循环。（`00:31:28–00:35:25`，`01:01:27–01:01:37`）

部署也可以分阶段。对于低流量小应用，他认为单个 ASGI worker 可能已经足够；对更大的既有系统，他观察到较成功的做法是保留成熟的 WSGI 主应用，再用一个 ASGI sidecar 承担特定异步路径。Gibson 建议先借此熟悉运行特征，再逐步扩大范围，因为正确处理阻塞事件循环、死锁等问题，比同步代码复杂得多；“Django 已准备好”并不等于“应用应一次性异步化”。（`00:35:27–00:36:17`，`00:56:09–01:00:29`）

性能诊断仍应从瓶颈出发。Kennedy 建议在因请求慢而增加并发前，先检查查询计划和热点路径的数据库索引；Gibson 补充，Psycopg 在数据库 I/O 阶段已经释放 GIL，而查询编译和 ORM 对象构造才是 CPU 工作，因此增加 async 或 worker 未必会改善由数据库查询主导的延迟。两人的建议有明确条件：先测量，再决定是否需要异步、更多 worker 或数据库优化。（`00:58:06–00:59:44`）

### 数据库边界不会因 async 自动消失

异步并不能突破连接池容量。Gibson 指出，一条数据库连接仍按顺序处理查询，无论 Django 用线程、其他 ORM 用 greenlet，还是应用运行在 WSGI 或 ASGI 下，可并行数据库工作的上限仍受连接池约束；需要扩大吞吐时，要评估连接池大小和使用效率。（`00:41:13–00:42:01`）

Django 的事务还有更具体的线程条件。因为连接和事务状态绑定在线程上，Gibson 认为 Django 不会支持在 `atomic` block 内任意 `await` 的那种异步事务：恢复执行时若落到不同线程，事务状态就可能错位。这不代表异步代码不能使用事务；可行模式是把完整事务封装为一个同步函数，再通过一次 `sync_to_async` 调用，使它在同一线程内完成。（`00:42:02–00:42:49`）

Django 6.1 在录制时仍处预发布阶段，节目讨论的两项数据库能力因此应按当时时点理解。其一是数据库级级联删除选项：历史实现会由 Python 遍历关联对象并依次删除，大规模关系树可能带来内存压力；新选项把工作交给更擅长集合操作的数据库。其二是 queryset fetch modes，其中 `FETCH_PEERS` 可在首次访问某个相关对象时批量取回同组对象，像延迟触发的 `prefetch_related`，减少常见的 N+1 查询及手工预取维护成本；Gibson 同时提醒，它不是应对所有查询都默认开启的魔法方案。（`00:07:02–00:08:32`，`00:19:36–00:20:01`，`00:20:07–00:22:32`）

### Tasks 解决的是队列抽象，不是事件循环

Gibson 特意区分两种“异步”：Django async 支持主要服务于并发 I/O、多连接和长请求，后台任务则需要队列、独立 worker、结果与重试语义。例如密码重置邮件不必阻塞 HTTP 响应，可以先把任务写入后端，迅速告知用户请求已接受，再由另一进程发送邮件。（`00:51:00–00:52:42`）

Django 6.0 的 Tasks framework 提供的是统一后端 API。第三方包可用同一接口入队、查看结果，而项目通过 settings 选择实际后端；Celery、RQ 等系统只有实现相应 adapter 才能接入。Gibson 说录制时 Celery adapter 尚未完成，但已有 Redis 和基于 ORM 数据库存储的后端可用，因此不能把框架本身等同于内置的完整 worker 系统，也不能假设任意现有队列已自动兼容。（`00:00:24–00:00:36`，`00:52:42–00:54:06`）

他的实践建议是从需求最小的后端开始：多数项目可先用 ORM 数据库队列，已有 Redis 且确有需要时再选 Redis。不要仅把工作扔给事件循环 executor，因为那样缺少队列控制、结果记录、失败检查和重试恢复。对于 Celery，他肯定其能力，但把监控、beat server、worker 和值班恢复等运维负担视为采用前必须核算的条件，而不是所有项目的默认起点。（`00:54:24–00:55:51`，`01:00:30–01:01:23`）

### 自由线程可能兑现 Django 的线程路线，但生态仍是门槛

CPU 密集工作若直接运行在事件循环上会阻塞其他任务，移到线程后又会在传统 Python 中遭遇 GIL 竞争；移到进程则需要启动进程、序列化数据和处理返回值。Gibson 因此把自由线程 Python 视为重要机会：Django 长期使用线程承接同步工作，当多个 Python 线程能真正并行时，这条路线可能减少依靠多进程扩展所带来的内存和运维成本。（`00:42:49–00:47:29`）

但这仍是条件判断，不是现成收益承诺。Gibson 说架构基础已经存在，剩余工作主要在生态：应用的模块级缓存或共享属性是否线程安全、扩展和第三方库是否使用了不安全模式，都需要通过测试逐项确认。他预期单进程并行可释放更多性能，但把“随着自由线程在生态中成熟”作为前提。（`00:47:31–00:50:03`）

这也解释了异步文档的新定位：GIL 竞争、数据库池扩展和 CPU/I/O 分工同样出现在 FastAPI、Flask 等 Python 栈中。Django 有自己的事务与线程约束，却不该为整个 Python 并发模型的问题单独背上“异步未完成”的标签。（`00:47:56–00:48:29`）

### Mantle 展示类型边界，而非要求重写 ORM

在主线之外，Gibson 介绍了自己的 Django Mantle 项目，尝试为 Django 提供更现代的序列化方式。他认为 Django REST Framework 的 serializer 需要逐字段动态查找，而 attrs、cattrs、Pydantic、msgspec 等现代工具能生成接近手写属性访问速度的代码；但 Pydantic 本身不了解 Django ORM，不能自动判断所需字段、关联预取和 N+1 风险。Mantle 的目标是在这两者之间提供 ORM-aware 的 typed wrapper。（`00:13:32–00:15:43`）

其设计不是给动态 ORM 强行覆盖静态类型，而是在上层建立“静态岛”：开发者定义纯 Python shape class，查询只取需要的字段并处理相关预取，领域逻辑也可从 active record 模型中分离。Gibson 强调这是应用复杂度增长后的演进路径，而不是新项目一开始就应采用的重型架构；过早使用同样会造成过度设计。（`00:15:44–00:19:25`）
