## 速读

这期节目把 OWASP Top 10（2025）翻译成 Python Web 开发者能检查的日常问题：权限是否逐请求验证、生产配置是否加固、依赖和发布链是否可控、输入是否始终与命令分离，以及失败时有没有可调查的证据。Tanya Janca 与 Michael Kennedy 还讨论了 AI 生成代码为什么常常把安全当成可选项，以及如何把安全要求提前写进开发流程。

它适合维护 Django 或其他 Python Web 应用、管理 PyPI 依赖、配置 CI/CD，或正在使用代码生成代理的团队。最值得注意的不是背诵十个名词，而是理解每项风险的边界：OWASP Top 10 是基于数据和社区调查的 Web 应用风险认知文档，不是所有软件风险的精确排名；节目中的比例、事件和工具体验是嘉宾在节目中的陈述或案例，不能替代本组织的威胁建模、测试与事件响应。

## 主题正文

### 1. 2025 版的重点是可行动的风险类别

节目介绍，OWASP Top 10（2025）在 2025 年 12 月 31 日发布；它面向 Web 应用风险，许多问题也适用于其他软件，但不能把它误读成覆盖一切场景的漏洞清单。嘉宾把榜单解释为根据收集到的数据和多次社区调查形成的 awareness document，条目是风险类别而不是单一漏洞；团队也因为无法在第十位附近取舍，额外提到 vibe coding、记忆安全等值得关注的议题（`00:02:02–00:02:13`，`00:11:24–00:12:16`）。

2025 版一个明显变化是把“软件供应链失效”从只关注易受攻击或过时组件，扩展到开发者工作站、浏览器插件、沙箱、CI 设置、依赖来源与传输完整性等整条链路。节目也强调，榜单应当帮助团队采取具体行动，而不是用“代码质量差”这样的宽泛桶状标签替代可执行的检查（`00:13:22–00:14:12`，`00:23:52–00:24:18`）。因此，榜单更适合作为评审清单的入口，不能单独证明某个应用安全。

### 2. 权限与配置：登录成功不等于有权做事

第一个风险类别是失效的访问控制。节目将它描述为每个页面、每条记录和每次操作都要验证当前角色是否获准访问；只在前端筛选，或返回整个数据集再“整理”，都把关键边界交给了不应信任的客户端。嘉宾还用 Django 的 `login_required` 说明常见误区：它可以确认用户已登录，却不自动确认用户具有管理员权限（`00:22:20–00:23:55`，`00:25:09–00:25:35`）。对 Python 服务而言，授权检查应在服务端、靠近具体资源和动作的位置执行，并覆盖读取、修改、删除等不同操作；这是对节目建议的工程化整理。

第二个类别是安全配置错误，包括未按生产加固指南配置、忘记补丁、暴露不必要的调试信息或错误设置。节目以 Django 的生产 `DEBUG`、HSTS、内容安全策略和其他安全响应头作例子，也提到容器端口发布可能绕过主机上原本以为有效的防火墙边界。这里不应照搬某个环境的开关，而应在部署检查中验证调试关闭、公开监听面最小化、默认凭据已替换，并让扫描器和清单把这些要求变成发布门槛（`00:26:55–00:32:16`）。

### 3. 供应链治理要同时处理版本、来源和完整性

节目把供应链定义为“创建和维护软件所用的一切”：不仅是 Python 包，也包括浏览器、插件、CI、CI 权限和包的获取方式。对 Python 项目，嘉宾建议在开发阶段更新到经过选择和测试的版本，再用 `pip-compile` 或 `uv` 锁定，使测试、验收和生产不会因环境间的意外更新而分叉；锁定不是永远不更新，而是把更新变成有审查的动作（`00:33:11–00:34:31`，`00:38:47–00:39:40`）。

对“最新版本”的自动跟随，节目给出的更谨慎方案是考虑短暂冷却窗口，例如只接受几天前或一周前的版本，让扫描、社区报告和下架流程有时间发挥作用。与此同时，嘉宾明确承认冷却会阻挡刚发布的漏洞修复，也可能与严格锁定或特定平台约束冲突；是否采用、等待多久，应按漏洞修复优先级、镜像能力、部署节奏和可回滚性决定。节目中的“超过 95%”和“99.9%”是嘉宾对 PyPI 漏洞检查与可达性情形的口头估计，不是本项目可独立验证的行业统计，不能当作普遍保证（`00:34:38–00:37:13`，`00:39:43–00:41:17`）。

完整性是供应链的另一面：下载的软件、第三方脚本和输入数据是否仍是预期内容，是否在途中或发布环节被篡改。节目建议对依赖和外部资源做完整性校验，并指出 CDN 场景可使用子资源完整性；同时承认深度受损的构建链可能让恶意代码通过既有检查，因此这些护栏是降低风险，不是绝对保证。CI 工作流应持续扫描权限与触发器；发布链则可迁移到 PyPI Trusted Publishing，并在迁移完成后删除不再需要的旧 token（`00:50:55–00:54:15`，`00:58:23–01:03:21`）。

### 4. 加密、注入与设计问题要在代码前后分层防护

节目将密码存储、过时算法、错误的加密覆盖范围和密钥管理归入密码学失败；对密码，嘉宾强调应使用带盐的单向哈希，盐不是秘密，pepper 则是系统级秘密，并以 Argon2 作为比老旧算法更合适的方向。具体算法、参数和密钥托管仍要结合框架和组织标准验证，不能只凭 AI 的一句“已安全处理”（`00:41:21–00:42:40`）。

注入的核心不是某一种数据库，而是把不可信输入混入将被执行或解释的命令。节目以 SQL、把 JSON 转成查询条件，以及不安全反序列化说明风险类别，但防御建议停留在原则层：优先使用参数化查询或预编译机制，对输入采用明确的允许列表，拒绝不符合预期的值；必须保留的特殊字符应按正确上下文转义，而不是依赖容易绕过的黑名单。这里的重点是把输入当数据处理，不提供可直接复现的攻击载荷（`00:43:24–00:46:50`）。

不安全设计则发生在代码看起来“写对了”之前：没有威胁建模、安全需求或设计审查，可能遗漏限流、服务端业务规则等关键控制。节目把它与实现缺陷区分开来，并提醒客户端校验不能成为 API 的唯一约束。团队可以在设计阶段记录信任边界、滥用情境、权限和恢复要求，在代码评审与测试中验证这些要求；这是降低后期补洞成本的流程建议，不等于为所有产品预设同一套架构（`00:46:54–00:49:01`）。

### 5. 认证、证据链和 AI 代码都需要人工负责

认证失败包括自建认证、无法抵抗撞库或暴力尝试、允许弱密码或缺少第二因素等问题。节目认可 Passkey/WebAuthn 相比一次性验证码更具抗钓鱼能力，也讨论了在受信设备、网络和高风险动作之间分级挑战的可用性权衡；更强的认证控制可能增加 VPN 切换等场景的摩擦，设计时应按操作风险和恢复流程校准，而不是简单宣布“启用 MFA”就结束（`00:49:01–00:50:54`）。

安全日志和告警的目标是留下可调查的证据，尤其包括安全控制的成功与失败、相关用户标识和时间。嘉宾用一个没有应用日志、无法追查支付卡事件的案例说明：没有证据，就难以判断影响、改进防护或支持后续调查。异常条件处理不当则会让错误被吞掉、把完整堆栈暴露给用户，或在没有事务保护时留下损坏状态；因此错误处理既要对用户隐藏敏感细节，也要让系统可恢复、让内部日志足以定位问题（`00:55:04–00:58:45`）。

节目最后的 AI 演示说明，生成模型可能在很短的代码中遗漏大量控制，原因之一是训练材料中公开示例和演示代码并不等于经过安全团队审查的生产代码。嘉宾的防御性做法是把安全要求写进提示或代码技能，让模型先列出安全假设，再按通用、场景化、具体功能三个层级检查；但这只能作为开发辅助，生成结果仍需测试、人工审查和发布门禁。对高风险功能，不应因为模型给出“安全”结论就跳过威胁建模（`00:59:08–01:03:36`）。
