## 速读

Zensical 试图用 Rust 运行时、差分构建和模块化架构接替 Material for MkDocs；本期也讲清迁移兼容、alpha 限制与尚在规划的能力。它适合维护技术文档、评估静态站生成器，或关心 Python 与 Rust 如何协作的工程师。Martin Donath 没有把 Zensical 描述成已经完成的 MkDocs 替代品：录制时项目仍在 alpha，当前重点是保持 Material 用户能逐步迁移，而不是要求整个生态一次性重写（`00:15:25–00:16:18`，`00:47:02–00:48:30`）。

这期最有价值的地方，是把“更快、更现代”背后的工程代价说具体了：插件编排、依赖边界和兼容性都需要重新设计；作者还用自己从周末副项目走向可持续开源产品的经历，解释了为什么项目的技术方向与资助模式会一起变化。下面区分录制时已经存在的能力、面向迁移的建议、作者的个人经验，以及明确仍属于路线图的设想。

## 主题正文

### 1. 当前产品：面向 Docs as Code 的静态站工具

Zensical 的基本模型很朴素：把 Markdown 等文本文件生成静态 HTML，不需要数据库或应用服务器；主持人和嘉宾提到 GitHub Pages、Cloudflare 等免费托管场景，并强调静态文件服务通常具备较低的运维负担。项目采用 MIT 许可证，目标用户首先是写文档的人，而不是希望从头处理 HTML、CSS 和 JavaScript 的前端开发者（`00:05:39–00:06:28`，`00:07:43–00:08:32`）。

产品当前的重点是技术文档。它沿用 Docs as Code 思路，让文档使用版本控制、代码评审和与软件相近的变更流程；内置能力包括 admonitions、标签页、代码块、表格、Mermaid 图表和来自 Material for MkDocs 的代码注释。代码注释可以在代码行旁放置气泡，并在展开内容中使用列表、表格和图表等 Markdown 内容，这是项目希望保留的特色（`00:13:30–00:14:22`，`00:45:22–00:46:20`）。

“快”来自构建模型，而不是一句泛化的性能承诺。Zensical 的 Rust 运行时 ZRX 会尝试只重建发生变化的部分：如果只改页面标题，节目中给出的例子是重建该页面以及使用这个标题的相关位置，因此目标是让反馈达到毫秒级，而不是每次从头构建。嘉宾同时说，构建系统是 100% Rust；这说明实现方向，不等于对所有项目都保证固定的构建时间（`00:17:59–00:18:44`）。

### 2. 迁移建议：先看兼容层，再核对插件和平台

Zensical 诞生于 Material for MkDocs 与 MkDocs 基础之间的张力。Donath 说，Material 已被数万项目使用，而 MkDocs 的演进速度和插件编排能力逐渐跟不上需求；多个插件之间的兼容性与配置顺序也反复制造问题。后来 MkDocs 2.0 的方向被描述为主要依靠模板、不再提供现有的插件 API，这会让 Material 和约 300 个生态插件难以继续工作；这些判断是嘉宾对生态影响的说明，不是本文独立测量的兼容性报告（`00:22:37–00:23:17`，`00:33:18–00:36:55`）。

直接 fork MkDocs 看起来更省事，实际却会把依赖关系一起带走：现有插件依赖名为 MkDocs 的包，若改成 fork，插件也要迁移到新依赖，作者把它比作“同时搬动一整座城市”。因此团队选择从头实现，并优先优化兼容性。录制时 Zensical 可以读取 MkDocs YAML 配置，仍使用 Python Markdown 以维持 Markdown 和 Material 的兼容；但生态插件尚未整体支持，只覆盖了部分插件，例如 mkdocstrings。迁移时不能只看配置文件能否读取，还要逐项盘点插件、扩展语法和自定义主题（`00:38:39–00:40:22`，`00:46:20–00:48:01`）。

插件兼容的承诺也要按时态理解。团队的目标是把 MkDocs 的插件配置映射成 Zensical 模块，并最终提供命令帮助迁移，但嘉宾明确把这说成正在进行的工作，且 2026 年的主要任务就是让 Material/MkDocs 用户更容易切换。更稳妥的实践是先用真实文档仓库做试迁移，检查自定义插件、HTML、相对 URL、代码注释、主题和部署流水线；不要把“能读取 mkdocs.yml”当成“生产项目已完成迁移”（`00:09:58–00:11:16`，`00:46:20–00:48:30`）。

Rust 也不是迁移使用者必须学习的新门槛。Zensical 用 PyO3 把 Python 模块接到 Rust 运行时，计划让用户继续用 Python 编写模块，而调度、线程、缓存和并行化由 Rust 负责；不过模块系统在录制时仍接近完成阶段，项目整体仍是 alpha。因此这更像是兼顾运行时性能与 Python 扩展习惯的架构选择，而不是已经稳定的第三方模块 API（`00:15:25–00:16:53`）。

### 3. 个人经验：开源产品的边界由使用者和维护能力共同塑造

Donath 的经历解释了 Material 为什么会从主题变成框架。他 2015 年为一个 C 库寻找比 README 更好的文档方案，选中 MkDocs 并把 Material 做成副项目；当时他只在周日投入时间，随着用户、功能请求和维护工作增加，项目逐渐侵入工作日早晚。他还坦言，最初只检查了许可证，没有进一步做依赖尽职调查，后来才意识到把职业工作建立在自己无法控制的基础之上，会形成长期约束（`00:23:38–00:25:55`）。

转折发生在 2020 年。一次用户调查显示，Material 用户中只有 7% 是前端开发者；Donath 原本以为自己在做主题，实际却意外做出了技术写作者愿意使用的产品。这里的 7% 是节目中调查结果，不能当作整个文档行业的统计。之后他尝试 SponsorWare：赞助者提前获得功能，功能达到资金目标后向所有人开放；他称该模式最终做到每年约 20 万美元，并让团队得以建立。数字和模式均来自嘉宾回顾，适合作为一个开源项目的个人案例，而不是普适商业预测（`00:29:37–00:31:14`，`00:32:04–00:32:48`）。

这段经验还带来一个实际的维护教训：Donath 后来学习 Python、写出第一个插件，并累计写了 12 个 MkDocs 插件；但插件越多，编排和相互兼容越难，项目最终需要新的基础。Zensical 因而不是简单换皮，而是把过去近十年的产品和维护经验重新投入运行时、模块边界和依赖控制的设计（`00:32:34–00:33:17`，`00:33:18–00:34:43`）。

### 4. 路线图：知识管理、可扩展主题与可持续支持仍在路上

Zensical 的远期目标不止是文档生成器。团队希望把它发展成完整的知识管理和文档解决方案，作为 Confluence、Notion 等 SaaS 的开源替代方向；为此需要 WYSIWYG 可视化编辑器，让非技术用户也能参与。嘉宾把这列为 stretch goal，并没有表示录制时已经交付，所以不能据此判断它今天已经适合非技术团队直接使用（`00:12:38–00:13:23`）。

主题系统同样要区分现状和计划。录制时主要是现有主题及其变体，重点仍是 feature parity；未来计划是让 Markdown 使用组件、让模板引擎建立在组件之上，并提供主题的资源管线，使样式、TypeScript 和主题安装流程可以纳入构建，而不是由主题作者预先编译。差分渲染也被列为计划的一部分。社区主题生态和更容易配置的主题开发体验因此是方向，不是已兑现的交付清单（`00:54:47–00:56:15`）。

可持续性方面，团队表示会告别 Material 中“赞助者提前获得额外功能”的方式，改为从一开始就把 Zensical 全部开源、免费使用，再通过 Zensical Spark 提供企业参与方式。Spark 包括围绕问题空间的讨论、共同塑造提案、专业支持和直接接触团队；提案被称为 ZAP（Zensical Advancement Proposal），由团队先写出详细方案，再根据参与组织的反馈迭代。它更像协作式产品支持和路线塑造，不应误读成付费版功能已经锁定（`00:57:57–01:00:23`）。

截至录制结束，嘉宾给出的采用建议仍然克制：Zensical 已有组件、客户端搜索和移动端友好的静态站能力，可以直接试用并通过月度 newsletter 跟进；但项目处于 alpha，生态插件迁移和模块系统仍在演进。对现有 Material/MkDocs 用户，合理路径是保留原项目作为基线，拿一套真实文档做试迁移和构建对比，再决定是否扩大范围，而不是因为“毫秒级”或“Rust”就立即替换生产链路（`01:01:08–01:02:08`）。
