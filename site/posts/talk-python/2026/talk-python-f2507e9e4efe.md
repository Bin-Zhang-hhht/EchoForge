## 速读

PyCon 首个全天安全专题把钓鱼事件、依赖冷却、SBOM、CI 权限和 Rust 迁移放进同一张供应链防御图，并诚实呈现每道护栏的代价。节目由 Python Software Foundation 的安全从业者 Seth Larson、Mike Fiedler 与开源安全研究者 Juanita Gomez 回顾该专题，不是提供攻击操作手册，而是解释维护者、包索引、构建工具和使用者分别能承担什么防御责任。

这期适合维护 Python 包、管理依赖或设计 CI/CD 的开发者。最值得听的不是某个“一键安全”工具，而是贯穿全场的分层思路：抗钓鱼认证仍需配合会话约束；依赖冷却能争取检测时间，却可能挡住刚发布的漏洞修复；SBOM 要在构建发生时记录才更可靠，运行时分析又受 Python 动态性的限制；工作流扫描和可信发布可以缩小长期凭据与高权限自动化的暴露面。所有方案都依赖持续投入和人工判断，没有哪一项单独解决供应链安全。

## 主题正文

### 安全工作需要专职投入，也不能挤掉志愿者空间

Mike Fiedler 说，从志愿 PyPI 管理员转为全职安全工程师后，他才有条件持续识别缺口、先做能立即改善安全的工作，再逐步建设长期能力。专职岗位可以集中推进那些需要连续责任的任务，但也有双刃剑效应：志愿者可能因为“已经有人受薪”而减少参与，有限的全职人员随之承受更大压力。他的结论是，付费的聚焦投入确实能带来安全成果，但容量和时间仍然不足（`00:05:00–00:08:23`）。

Larson 对角色边界的处理是把精力放在高影响、又不容易吸引志愿者的基础事务，例如漏洞编号体系与安全响应团队管理，同时给适合社区贡献的任务留出空间。他还会把流程与经验公开，让第三方项目能复用，而不是把安全知识锁在组织内部。这既是人力分配策略，也是在培养开源社区长期承担安全工作的能力（`00:08:38–00:11:45`）。

专题本身也暴露了教育缺口。Gomez 认为安全贯穿包维护和开发流程，但很多维护者缺少时间或专业知识；当届议程覆盖面较广，却仍欠缺面向刚起步项目的“安全 101”，例如基础仓库配置、日志与限流。她把这类入门内容视为未来专题值得补上的层次，而不是假定所有参与者已经具备成熟安全团队（`00:12:38–00:16:08`）。

### 钓鱼事件说明认证必须分层，而不是责怪使用者

Fiedler 复盘的事件利用了维护者公开联系方式和近似官方的登录体验，使邮件看起来像平台过去发出的正常操作通知。他明确不责怪受骗者，因为他们只是按看似合理的通知行动。防御重点因此不是要求人永不犯错，而是让一次判断失误不至于直接变成持久控制权（`00:23:16–00:26:06`）。

事件也显示“启用 2FA”并不是完整结论。节目指出，基于一次性验证码的 TOTP 仍可能在钓鱼流程中连同会话被滥用；WebAuthn、Passkey 或硬件安全密钥把认证绑定到站点，抗钓鱼能力更强。PyPI 随后增加了一层会话约束：通过 TOTP 获得的会话若从不同 IP 使用，会要求重新确认身份；代价是 VPN 切换或移动网络变化也可能误触发。也就是说，更严格的控制提高防御性，同时会引入真实的可用性成本（`00:26:06–00:29:14`）。

按 Fiedler 的审计结果，PyPI 当时有超过一百万个用户账户，确认有 4 个账户完成了受骗登录，已知只有 1 个包被接管并重新发布；他也保留了“可能仍有未发现行为”的不确定性。被选中的包位于热门项目的间接依赖链上，说明使用者即使审查直接依赖，也可能被更深层的薄弱环节影响。这些数字是事件响应者在节目中的回顾，不代表对事件影响的独立审计（`00:29:58–00:32:18`）。

### 依赖冷却能买时间，但不是无条件安全默认值

依赖冷却的核心是主动放弃“刚发布的最新版”：终端使用者可以等待 3 天或 7 天，让扫描器、社区报告者与 PyPI 审核流程有机会发现恶意版本并将其隔离。Fiedler 将它定位为普通使用者尤其容易采用的护栏；Larson 则认为，对没有私有镜像和专职安全团队的个人或开发机，设置一次后持续受益很有价值（`00:34:13–00:39:09`）。

但冷却窗口会和漏洞修复发生冲突。主持人描述的实际问题是：审计工具要求升级到刚修复漏洞的版本，固定的冷却策略却把这个新版本排除在候选之外，最终产生“版本不存在”或不可解的依赖提示。Larson 因此暂不主张把冷却直接设为默认；理想的安全默认值还需要识别精确锁定、企业镜像、漏洞修复等不同情境，单靠客户端工具很难同时覆盖所有使用方式（`00:39:50–00:43:21`）。

PyPI 当前是上传后立即可用、扫描随后发生，原因是包量太大，无法逐个预审。部分长期保持极低误报的社区报告可先把可疑版本自动置于不可下载的隔离状态，再交给人复核。这个机制说明冷却为何可能奏效，也说明它只是借用检测和下架能力争取时间，并不保证窗口结束后版本一定安全（`00:36:24–00:37:34`，`00:42:44–00:43:21`）。

### SBOM 要记录真实构建，运行时证据仍有边界

节目讨论的构建期方案不是仅从声明文件反推依赖，而是在构建过程中记录网络访问、命令调用和安装行为，再导出 SBOM 与可验证记录。Larson 认为，这种信息在行为发生时采集远比事后补全容易，未来可用于包构建服务或推荐构建环境；但 Gomez 同时提醒，现有 SBOM 生成工具的准确性仍不足，离真正可用还有工作要做（`00:50:25–00:53:44`）。

SBOM 的另一项价值是跨语言表达来源：Python 包可能包含 C、Fortran、Rust、JavaScript 等成分，生态无关的清单比只观察 Python 依赖更能描述实际软件构成。运行时分析则补充“声明了什么”和“真正加载了什么”的差异，可以观察模块与函数是否实际使用，为事故调查和漏洞影响判断提供证据（`00:54:19–00:56:23`）。

不过“依赖存在漏洞”与“当前程序会触达漏洞代码路径”之间很难自动画等号。开放漏洞数据库正在尝试提供更细的受影响路径信息，但 Python 可以动态导入模块，静态判断不一定完整。Fiedler 把目标限定为提供足够信息以支持有把握的决定，同时避免给出误导性的安全结论（`00:56:23–00:58:18`）。

### 缩小 CI 与发布权限，比长期保存秘密更可靠

GitHub Actions 把外部贡献、缓存和发布权限连在一起，错误的触发器或权限配置会放大供应链风险。节目推荐用 Zizmor 扫描工作流，并特别提醒对来自 fork、又以目标仓库较高权限运行的 `pull_request_target` 保持谨慎。这里的行动重点是持续审计自动化配置、修复工具指出的问题，而不是依赖维护者记住所有平台细节（`00:58:23–01:00:47`）。

对包发布，Fiedler 的单项建议是把至少一个项目迁移到 PyPI Trusted Publishing，并在迁移后删除旧 token。这里最明确的防御动作是淘汰不再需要的长期发布令牌；“删除旧 token”是迁移完成不可省略的一步，而不是把新旧机制长期并存（`01:02:51–01:03:21`）。

节目也把更底层的内存安全放进长期路线：Rust for Python 团队提出先尝试用 Rust 重写一个标准库模块，长期才可能扩展到更多部分。Larson 认为从处理不可信数据、边界较清楚的压缩模块起步有安全价值，但技术集成、工具链和 CPython 社区协作都很困难；这是仍在讨论和验证的长路，不是已决定的全面重写（`00:45:47–00:50:24`）。

最终建议仍回到资源。Larson 提醒，语言、包索引和第三方项目的安全改善需要工程时间与资金，依赖这些生态的组织可以贡献安全工作或提供资助。工作流扫描、可信发布、冷却和 SBOM 都是可组合的护栏，但它们持续有效的前提，是有人维护基础设施、处理报告并推动项目采用（`01:03:25–01:04:41`）。
