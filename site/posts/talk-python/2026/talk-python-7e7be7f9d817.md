## 速读

EVE Online 自 2003 年上线起运行在深度定制的 Stackless Python 2 上，如今正把约 240 万行 Python 代码整体迁往 Python 3.12：约 6,500 行含除法的逻辑决定战斗胜负，约 100 GB 的 pickle 对象必须在跳跃中完好存活。（`00:00:00–00:00:33`，`00:03:29–00:03:56`）嘉宾是正在执行 EVE Online 迁移的 Jamie Bannister、先行完成 EVE Frontier 迁移的 Thomas Dähling，以及十年前到访过节目、现任 EVE Frontier 玩法工程总监的 Kristinn Þór Sigurbergsson。（`00:00:34–00:00:56`，`00:04:26–00:05:03`）

这期适合正在维护大型遗留 Python 系统、关心不停机升级和依赖打包困境的开发者。最值得关注的三个判断：语法 valid 不等于语义正确，除法语义就是反例；解释器与原生扩展必须"全有或全无"地切换；以及先用 EVE Frontier 试错、再用混合模式增量替换节点的推进方式。（`00:51:48–00:53:04`，`01:01:21–01:02:02`，`00:57:16–00:57:53`）

## 主题正文

### 一个没有回档键的单一宇宙，把二十多年押在 Python 上

Jamie Bannister 介绍，EVE Online 是 2003 年上线、运营至今的经典 MMORPG：开放世界沙盒，玩法覆盖采矿、贸易、海盗与战斗；它以"完全损失"著称，被击毁的飞船会永久移出游戏，没有任何找回机制。（`00:06:03–00:06:54`）经济系统记录了每一笔交易，Jamie 说其数据的准确与详细程度超过现实经济学研究能拿到的水平，因此曾被经济学家研究。（`00:07:13–00:07:36`）整个宇宙跑在单一分片（single shard）上，任何两名玩家到同一地点就会相遇；Jamie 估计最大的玩家组织约 15,000 个角色，并说他们大概握有两项"最多人参与 PVP 战斗"的吉尼斯世界纪录——他原话带有 I think 的保留。（`00:08:49–00:09:19`）

技术栈的历史同样久远。Kristinn 回忆游戏 2003 年发布、开发始于 1999 年前后，当时 Python 还相当新；Jamie 说明物理引擎 Destiny 与图形引擎 Trinity 这类核心库用 C++ 编写，而全部玩法逻辑、网络栈与集群栈都建在 Python 上。（`00:21:06–00:22:25`）Kristinn 补充选型动机：.com 时代程序员稀缺而昂贵，选 Python 是为了让初级开发者甚至设计师能写顺序代码、加速开发——一切为了开发速度。（`00:22:25–00:23:04`）Thomas 说，正因如此团队引入 Stackless Python 并在其上构建抽象，开发者写的是看似顺序的代码，感觉不到自己写出的是异步；他认为这让游戏扩展到数千人同处一个恒星系统。（`00:23:21–00:23:47`）

Stackless 被 Thomas 形容为"Golang goroutine 的 Python 版"，远早于协程模型流行；（`00:28:21–00:28:35`）但模型有学习曲线：代码看似顺序执行，实际会在数据库调用等位置让出主线程，连资深开发者也会忘记要加锁。（`00:28:35–00:29:06`）更大的问题是它是 CPython 的深度定制分支，CCP 又为实时游戏叠加了指标采集、内存分配控制等改动，导致难以及时跟进上游版本——移植原生扩展时，他们发现还有代码停留在 Python 2.3 时代就不该再用的写法上。（`00:29:22–00:30:12`）Thomas 还指出 Stackless 在生态中已边缘化：Python 3 有了基于 twisted 模型的 asyncio，即便在 Python 2 时代 gevent 都比它更有名；它实质上是自带运行时，通过 monkey-patch 线程与 socket 模块实现非阻塞。（`00:31:24–00:32:12`）主持人 Michael 补充，GitHub 仓库页面显示 Stackless Python 已于 2025 年归档——按他的说法，"不是每个项目都要永续"。（`00:32:48–00:32:57`）

### 没有 pip 的二十年：依赖、原生扩展与打包分发

Thomas 说，因为没有 pip（也没有今天的 uv），他们无法随意引入公开包；Kristinn 回忆早年还有自研 importer，第三方库很难用，后来才修复。（`00:20:08–00:20:53`）每接纳一个 Python 包都要仔细评估如何整合进技术栈：没有包管理器，只能从包索引下载 zip 解压进环境再看结果；一旦涉及原生扩展就更麻烦——要确认它支持最低规格环境、能跑在所有环境上、还要兼容他们那份分叉解释器。（`00:33:21–00:34:00`）Thomas 举过一个代价高昂的例子：为 2.7.18 构建的模块会损坏内存，因为 2.7.6 改变了 PyType 对象的内存布局，而他们的分叉版本没有这个改动。（`00:34:00–00:34:16`）

平台组合加剧了复杂度：Jamie 说明服务器集群跑 Windows，玩家绝大多数在 Windows，Mac 是少数，Linux 支持则已停止。（`00:34:21–00:34:51`）分发方案是过去二十年把解释器嵌入自研二进制，定制解释器可见的路径与环境变量，再把所需内容打包成匹配布局——Thomas 自评这仍是"75% 方案"，因为 Python 构建过程依赖系统特定路径，他们不得不大费周章地打补丁。（`00:35:31–00:36:17`）Kristinn 说连给内部开发者分发 Python 工具都头疼多年：环境变量一改、版本一错就出问题，新员工头几天常花在装机上，有时还要禁用 Windows 自带的 Python 才能用上指定版本。（`00:36:44–00:37:31`）被 Michael 问到 uv 与 uvx 时，Thomas 回答正在探索，希望将来能"把包装进游戏环境"，但原生扩展要找到合适的构建环境，这件事并不简单。（`00:37:36–00:38:45`）

Thomas 还提到他们最近开源了基本意义上的游戏引擎，可以想象别人把它 pip/uv 装进自己的解释器；而引擎自 2011 或 2012 年起就有解释器模式，加特殊标志即可启动接近标准行为的 REPL。（`00:39:03–00:39:49`）硬币的另一面是 Kristinn 的观察：加依赖麻烦客观上减小了供应链问题的暴露面，也避免同一件事冒出三个互不兼容的库，但代价是升级更少被做——Michael 附和说他们的依赖风险确实比有 200 个依赖的项目小。（`00:39:56–00:40:53`）

### 为什么必须升：原生 Mac 客户端、类型与性能

Thomas 说引擎侧推动升级的主因是 2020 年代初的原生 Mac 客户端工作：macOS 在 Unicode 与系统调用上的行为和 Windows 差异很大，此前 Mac 客户端要经过类似 Wine 的转译层；若不升到 Python 3，就得一直养一个只维护解释器的小团队。（`00:41:13–00:42:07`）作为玩法程序员，Jamie 期待的是正规的类型声明——2.7 时代靠特定 IDE 部分弥补、并不一致——以及语言级的 dataclass 支持。（`00:42:19–00:42:59`）Michael 补充，在 240 万行代码的规模上，Pyrefly、TY 这类类型工具可以自动化回答"代码是否仍一致"；Jamie 认同：测试覆盖"合理但远非完整"，语言层的正确性杠杆越多越好。（`00:43:00–00:43:41`）

性能上已有即时回报：Thomas 给出的数字是大多数场景获得 15% 到 20% 的全面提升，相当于"免费"拿到；字符串处理因全面 Unicode 化不可直接与 Python 2 比较。（`00:45:08–00:45:33`）但 asyncio 被明确排除：函数需要 async 标注，而 240 万行代码不是照这个思路写的，Thomas 说这条路"出局"。（`00:45:35–00:45:55`）底层他们并不缺异步——I/O 本来就跑在多个后台工作线程上，当年 Stackless 的角色正是把数据从工作线程同步进主线程的同步点；Michael 提到的一个 Rust 写的多线程异步运行时项目，Thomas 也认为难以直接整合进他们的栈。（`00:45:56–00:47:06`）

free-threaded Python 在关注清单上：Thomas 说很多代码位置隐式依赖 GIL 做同步、需要逐一识别，资源加载系统这类场景可能受益，但它未必是最大的性能提升来源。（`00:44:08–00:44:56`）Michael 则担心大量默认 GIL 存在的第三方库藏有潜在竞态，等发现后加锁又变成潜在的死锁；Thomas 回应单线程场景也不能出现性能回退，并提到社区有一个追踪 PyPI 各库 free-threading 兼容状态的项目，他自己也在关注——Michael 观察到该项目的覆盖偏数据科学，两人都认为又是数据科学家在领跑。（`00:47:10–00:49:11`）

### 迁移路线：先把 240 万行推到"语法 3"，再整体跳跃

Jamie 介绍，第一步叫 legacy to 2.7：把 240 万行代码里停留在 2.4/2.5 习惯用法的部分先抬到 2.7 标准，因为许多改动随后对 Python 3 前向兼容；录制前几周他们已发布并部署了这一阶段的首批成果。（`00:49:43–00:50:38`）工具上是 Futurize 的修复项中"保持 2.7 兼容"的子集，例如把 has_key 用法全部换成 in 运算符。（`00:50:38–00:51:43`）度量结果是：起点时 94% 的代码在语法上已是 Python 3 valid，现在到了 99.8%——Jamie 强调这只是语法 valid，不保证在 Python 3 下行为正确。（`00:51:48–00:52:07`）

语义风险的头号例子是除法：作为大量处理数字的游戏，代码里约有 6,500 行含除法运算；Python 3 把整数除法改成浮点除法，伤害计算只要结果一变，就会出现"我本该赢的战斗结果输了"。Jamie 说这是下一阶段的重点。（`00:52:13–00:53:04`）当前阶段他们把 Python 2 分支 fork 出 Python 3 分支，所有测试变红——内部叫 Python 3 unstable；并行的 2.7 unstable 分支放 shim 与适配器，让还在写 2.7 代码的功能团队保持前向兼容，代价是更慢，定位是兼容性验证而非可发布版本。（`00:53:12–00:54:14`）

不只是运行时代码：Jamie 说大量静态数据与网络传输数据是序列化的 Python 对象，Python 2 的老式类发给 Python 3 节点根本无法识别。（`00:54:18–00:54:53`）最具体的一块是游戏里的 NPC agent——他特意说明与 LLM agent 无关：这些角色的任务记忆以 pickle 形式存进数据库已 20 年，估计约有 100 GB；SQL 脚本无法反序列化这些对象，方向是改成 protobuf 或 flatbuffer，内部与外部 API 本就大量构建在 protobuf 上。（`00:55:17–00:56:47`）

上线策略叫 mixed mode：对约 200 个节点的集群和全部客户端做选择性替换，把单个组件逐步换成 Python 3 等价物，而不是选一个大部署日一次性切换，把风险和负载摊开；Jamie 说这批配套工具还带来异构部署等额外选项，比如部分节点 Linux、部分 Windows。（`00:57:16–00:58:19`）Thomas 另外在节目里提到，他们已有在当年晚些时候升级到 3.15 的计划。（`00:03:53–00:03:56`）

### Frontier 先行、"全有或全无"与三条建议

Kristinn 认为先在 EVE Frontier 落地帮助巨大：Python 代码依赖 C++ 模块可导入，C++ 模块又需要 Python 粘合，单边推进没有意义，而 Frontier 破坏风险低得多；其首次发布曾经历"每小时宕机"——运行一两个小时就有进程停止响应，最后发现原因"蠢得很"，他形容那是一段非常紧张的日子。（`00:58:31–00:59:28`）他们还靠 TeamCity 构建系统一路往真实构建深处跑：游戏年代久远，本就缺乏成体系的自动化测试，增量验证只能这样逼近。（`00:59:36–01:00:09`）

EVE Online 的约束更硬。Jamie 说它是每天都要在线的游戏，不能接受每天停机几小时，Frontier 先跑一步正是在 24/7 之前把很多东西验证完。（`01:00:51–01:01:15`）Thomas 补充，Python 3 迁移是"全有或全无"——不能只把解释器升到 3、原生扩展留在 2，必须一步到位；这正是当初最大的顾虑，也是先走 Stackless 3.8 中间步的原因：只改 Python 大版本，不同时更换底层异步库，避免代码里残留的时序依赖一起出问题。（`01:01:21–01:02:02`）

给后来者的建议有三条。Kristinn：他们请了承包商 Recon Digital 完成大部分 Python 代码迁移，因为功能团队一旦被拉回特性开发，迁移必然脱轨——所以要锁定资源、不许动用，一旦开始就必须做完，暂停几乎等于白干。（`01:03:15–01:03:58`）Jamie：功能开发还在 2.7 上继续，本周刚上线新的 linter 并将逐步收紧严格度，用代码质量工具保证新代码尽量前向兼容。（`01:04:00–01:04:39`）Thomas：老生常谈的好测试覆盖之外，要在独立分支上迁移、同时保持从 2 侧到 3 侧的高频持续合并，尽早暴露新痛点——频率低了很痛，双周一次曾要花一整天解决积压问题，总之"勤做、常做、保持小块"。（`01:04:44–01:05:36`）
