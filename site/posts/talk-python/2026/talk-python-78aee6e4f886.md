## 速读

TonIO 不只加速 asyncio，而是借自由线程 Python 重做多线程异步运行时；这期从调度模型讲到死锁边界、生态兼容与仍处 alpha 的现实限制。它适合关心 Python 并发、Web 服务内存占用或新运行时设计的人，也能帮助听众判断 TonIO 目前更适合试验还是生产采用。

核心矛盾是：更快的事件循环仍然只有一条执行线程，不能自动利用多核；TonIO 则把任务真正分配到多个线程，但也把竞态、锁和第三方库兼容问题重新交还给开发者。项目作者 Giovanni Barillari（节目中常称 Joe）反复强调 TonIO 在录制时仍是 alpha，API、上下文变量默认值和 Windows 支持都可能变化，因此这里呈现的是设计方向与试用边界，而不是成熟替代方案。

## 主题正文

### 自由线程改变的是资源模型，不只是事件循环速度

Barillari 把自由线程称为 Python 诞生以来最重大的变化之一，这是他的判断而非社区共识。他看重的不是语法变化，而是 Python 代码终于可以用真实线程利用多个 CPU 核，不再为了绕开 GIL 而默认诉诸多进程或 C 扩展；但他也指出，原生 C 扩展必须修到线程安全，年代较久的扩展尤其不容易迁移，这解释了采用速度为何没有他的期待那么快。（`00:17:05–00:20:00`）

Web 服务场景把代价表现得更具体。Barillari 以 Sentry 的 Django 单体为例，称为了利用一台 GCP 虚拟机的多个 vCPU，单个 Pod 往往要启动多个进程，并可能占用约 4、5 或 6 GB 内存；Michael Kennedy 补充，多进程还会复制 LRU 缓存等进程内状态，指标汇总也更麻烦。这是两位受访者描述的实际架构痛点，不是所有 Python 服务的通用内存结论。（`00:20:30–00:22:18`）

因此，uvloop 一类替代事件循环解决的是局部热路径，而不是并行模型。Barillari 估计，在几乎只做原始 TCP 吞吐的特定测试里，收益大致可能在 20% 量级；他同时强调真实应用还会做大量其他工作。Kennedy 也指出，长任务或切换不密集时，这类优化可能几乎无影响。两人的结论不是“不该用更快事件循环”，而是它无法把单线程 asyncio 变成多核运行时。（`00:26:40–00:28:09`）

### TonIO 把 spawn 变成真正的并行入口

TonIO 的起点是从零回答“如果 asyncio 不存在，Python 的异步运行时应是什么样”。它只接受自由线程解释器：Barillari 说明，只要检测到 GIL，运行时就会报错，要求更换解释器。这使“真实线程”成为设计前提，而不是可选加速路径。（`00:30:06–00:31:17`）

对使用者而言，入口既可以是 `tonio.run`，也可以给程序入口加 `tonio.main` 装饰器。TonIO 同时支持常见的 `async`/`await` 写法和基于生成器的 `yield` 写法；后者不要求到处写 `async def`，但调用链仍会因生成器而“着色”，所以它并没有消除同步与异步边界，只是提供另一种记法。（`00:35:59–00:38:40`）

更关键的差异是任务启动语义。调用 `spawn` 后工作会立即开始，可以忘记结果、立刻等待，或保存句柄稍后 join；而不是把“创建可等待对象”“转成任务”和“等待结果”混在一起。Barillari 说明，TonIO 默认启动与 CPU 核数相等的工作线程，并另设按需扩展的 blocking 线程池；两种池的大小都可配置。（`00:39:29–00:41:12`，`00:42:30–00:44:52`）

工作负载决定该把任务放在哪里。按 Barillari 的建议，纯 CPU 或纯 I/O 程序可以使用标准池；只有 CPU 与 I/O 混合时，才需要用 `spawn_blocking` 把 CPU 密集工作隔离到 blocking 池，以免拖慢网络或磁盘工作。这个建议以维持混合负载的响应性为条件，不等于所有 CPU 工作都必须走 blocking 池。（`00:57:35–00:59:43`）

### 真并行也带回锁、竞态与上下文传播

asyncio 的单线程执行隐藏了一个约束：同一时刻通常只有一个协程在运行。TonIO 允许多个线程同时执行后，容器自身线程安全并不意味着一串读写操作具备业务原子性；另一个线程仍可能在两步之间改掉共享状态。Barillari 给出的第二条规则因此是：共享内存上的操作序列若必须保持一致，就需要适当同步。（`00:48:28–00:49:30`，`00:51:28–00:52:25`）

第一条规则更直接：不要持有 `threading` 锁时 `await`。TonIO 的异步锁与线程锁属于不同同步体系；在后者内部等待协程，可能让需要同一把锁或调度资源的工作无法推进，造成死锁。需要跨等待点同步时，应使用 TonIO 的异步锁。项目还提供 semaphore、barrier 等同步原语，但这些工具不会替开发者判断共享状态的正确边界。（`00:50:25–00:53:01`）

上下文变量也不再能无条件沿用单线程直觉。录制时，TonIO 需要在启动运行时时显式开启 context variables 支持，默认值为 false；Barillari 说等 API 稳定后可能改为 true。他把显式选择看作早期试用阶段的提醒：开发者应先确认自己的上下文传播模型在多线程异步执行下成立。（`00:44:52–00:45:24`，`00:48:00–00:48:55`）

### 生态仍在搭桥，当前定位是试验

TonIO 不是 asyncio 的透明替换。录制时，依赖 asyncio task、future 等原语的库不能直接运行；TonIOMonkey 通过 monkey patch 为 Psycopg、HTTPX、HTTPX2、Redis 以及 FastAPI 等部分库提供适配，但覆盖范围仍取决于具体代码路径。Barillari 希望 API 稳定后探索 AnyIO 后端，不过他明确表示可行性尚不确定。（`01:01:08–01:03:36`，`01:06:22–01:06:28`）

项目也在建设较小的原生生态，包括兼容 asyncio 与 TonIO 的底层 HTTP 库、高层客户端，以及一个很早期的 Uvicorn 移植实验。对于 Granian，Barillari 的长期设想是把协议实现与 Python 运行时解耦，未来支持 asyncio、Trio、TonIO 等多种运行时；他没有承诺交付时间，因此不能把它当作现有能力。（`01:03:48–01:05:57`）

成熟度限制同样明确：Barillari 在录制时称版本约为 `0.9.14`、整体仍处 alpha，API 接近稳定但主要只有他一人维护。Windows 是缺失的大功能，当前代码只运行于 POSIX 系统，即 Linux 和 macOS；他希望年底出现某种部分 Windows 支持，但特意拒绝作出承诺。**编辑提示：**实际评估应以当前发布版本和目标依赖为准，而不是按这期节目的路线图预期部署。（`00:54:34–00:55:08`，`01:07:18–01:09:41`，`01:10:36–01:11:12`）

Barillari 的行动建议也限于试用：如果团队确实遭遇 asyncio 的痛点，可以拿真实用例测试 TonIO，并把不能工作的场景或 API 问题反馈给项目。**编辑提示：**结合 alpha 状态、有限适配面和平台限制，更合理的落点是原型、压力测试与迁移可行性验证，而不是未经验证地替换生产运行时。（`01:11:19–01:12:48`）
