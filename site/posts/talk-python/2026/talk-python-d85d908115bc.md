## 速读

一位胃肠病研究者讲述如何从 3 万份样本的追踪难题出发，用 Django 建成承载约 10 TB 数据的研究平台，并在临床治理边界内引入科研 Agent。受访者 Shaun Chuah 的起点并不是软件创业，而是一项跨城市、多医院的炎症性肠病研究：现成企业实验室系统昂贵、部署慢，Excel 又难以承受样本全生命周期与多模态数据，于是他从 Django 教程开始补齐工程能力。

这期适合科研软件、数据平台、AI Agent 和受监管行业的开发者。最值得关注的不是“AI 自动做科学”的口号，而是它依赖的底座：统一组织样本与数据，给文件叠加元数据和关系，把计算放进隔离环境，并让 Django 在 Agent、原始数据与算力之间执行权限控制。节目也没有把系统包装成成熟答案：Foundry120 仍处早期，对外接入需要逐项审查数据类型、规模、伦理审批与驻留要求；Helix 能代写分析代码并从错误中恢复，但关键科研工作仍需懂业务的人验证结果。

## 主题正文

### 先解决样本追踪，再逐步长成平台

2020 年，Chuah 参与的一项研究计划从三个城市的多家医院招募约 200 人，每三个月随访并采集血液、粪便和唾液；他的粗略估算是两年左右会产生约 3 万份样本。同行常见的管理方式是 Excel，而企业实验室系统采购昂贵、可能要约六个月才能部署，并且更偏向医院日常处理数百万样本的场景，不适合一次性的跨地点研究。Chuah 因此决定自己写 Django Web 应用（`00:06:12–00:08:38`）。

这个决定并非建立在深厚开发经验上：他此前主要是在高中用记事本手写过 HTML，后来为统计和绘图写过少量 R 或 Python 脚本。Django 的成熟度与“自带电池”是关键，尤其是经过长期检验的认证、数据库迁移和管理能力；在不能丢数据的研究系统里，这些基础设施比自由拼装更重要。他从官方教程、社区视频和书籍起步，也强调自学者要意识到知识缺口，才能让别人依赖自己写出的系统（`00:08:38–00:13:18`）。

第一版功能很朴素：打印并粘贴 QR 码，扫描后把样本登记到数据库，样本在不同地点移动时再次扫描更新位置。随后问题自然从“样本在哪里”延伸到“样本产生的数据在哪里”：粪便样本会生成微生物组数据，血液样本会生成基因组数据，格式和处理流程各异。Chuah 举自己的游离 DNA 测序为例，每位参与者的一份测序文件约 5–10 GB，但这只发生在研究人群的一个子集，并非 3 万份样本各自都有同样体量（`00:17:00–00:19:58`）。

受访者称平台当前管理约 10 TB 数据，但 3 万份样本仍只有一部分完成处理，有些管线由人工处理少量样本就要约 12 小时。这个规模和耗时都是其团队现状，不应外推为所有生物医学研究。早期数据散落在个人电脑、共享盘和各自维护的 Excel 文件中，后来迁移到 Azure Blob Storage，硬容量配额变成了按月账单；这解决了共享盘空间限制，却没有消除成本问题。对于长期保存，他说课题经费通常只核算约十年，之后保留原始数据还是处理后数据仍是没有简单答案的取舍（`00:20:12–00:24:10`）。

### “文件 + 元数据关系”统一多模态数据

Foundry120 被定义为面向转化科学团队的“研究操作系统”。它围绕三件事展开：在数据库中组织研究、参与者与样本；集中临床数据和科学输出；再让 AI 基于这些上下文协助研究者。Chuah 举例说，过去要回答“有哪些来自接受某种药物治疗参与者的可用样本”，需要把临床数据集与样本数据库连接、筛选，往往要几天；Agent 可以在沙箱中写代码完成连接并返回结果。不过这是平台提出的工作流案例，不是对任意科研查询速度或正确率的保证（`00:24:48–00:27:03`）。

面对内镜视频、MRI、数字病理切片、基因组和表格等异构材料，团队采用的共同模型是“所有数据最终都是文件”，即使表格也倾向保留 CSV；文件之上再建立元数据和关系层，使人和 Agent 能知道它属于哪项研究、参与者或样本。Chuah 把文件称为跨数据类型的共同语言；团队也使用 Parquet，而 SQLite 等文件数据库是主持人提出、Chuah 认为未来可能采用的选项。当前偏好 CSV 的一部分原因，是实验室同事已经熟悉 Excel 和 CSV（`00:35:35–00:38:40`）。

这种选择不是把海量内容直接塞进模型上下文。文件留在 Blob Storage；Helix 需要分析时，系统启动虚拟机，把获准访问的文件送入隔离环境，再把 Agent 生成的 Python 或其他分析代码送去执行，最后将输出交还 Helix 并存回云存储。这样既允许生成新文件和运行分析，也把执行限制在机构自己的 Azure 环境中（`00:38:57–00:40:04`）。

计算侧同样由数据形态决定。团队在 Azure 后端可调度约 350 个 CPU；大型转录组任务可能运行半小时到数小时，因此不适合依赖用户浏览器或笔记本。生物数据中的许多任务可以按参与者并行，云端按需扩容、完成后释放，适合这种间歇性的突发负载。Chuah 将其称为团队针对大文件、高内存和高 CPU 需求做出的特定设计，而不是所有研究软件都应照搬的架构（`00:43:26–00:45:42`）。

### 在临床治理边界内给 Agent 工具

Foundry120 还不是自助注册的成熟 SaaS。受访者说，最近六到十二个月团队才把基础能力从单一课题和疾病中抽离出来；其他团队接入时，需要先建立成员和权限管理，并人工评估数据类型、规模与模态。临床研究对数据存放和处理地点有严格要求，还受各项目伦理审批约束，因此团队会先做合规审查，不能简单按月付费即开通。平台愿意探索外部合作，但能否广泛泛化仍未得到验证（`00:27:09–00:29:28`，`01:00:12–01:00:42`）。

权限边界不是只写在提示词里。Helix 暂存数据和代码时先经过 Django，由后端检查请求、启动虚拟机；Agent 不直接访问原始文件或计算环境。常规角色权限也沿用到 Agent 查询，用户只能让它看到自己本来就能访问的文件。这使 Django 同时承担业务后端和安全中介的角色（`00:39:28–00:40:04`，`00:41:36–00:42:11`）。

外部 MCP 接入也受到同一原则限制。Chuah 表示，团队不能把研究数据随意发给外部编码 Agent；当前推理运行在受控的 Microsoft Azure 区域，以满足其研究所需的数据驻留和 GDPR 合规要求。他给出的现状是多数任务运行在 UK South，面向欧盟合规的任务运行在瑞典。这里的结论是“必须知道推理在哪里发生并能执行机构控制”，不是 MCP 在临床研究中一概不可用（`00:54:33–00:55:41`）。

### Agent 改变的是分工，不是取消验证

Helix 不是针对团队数据重新训练的专用模型，而是类似编码 Agent 的工具调用系统；这样可以替换底层模型，避免监督微调或强化学习的成本与训练数据要求。演示中，它先调用工具取得样本和临床数据，写代码做连接、分组和绘图；遇到执行错误后读取工具输出、修正工作再继续。受访者认为真正困难的一部分是工具设计：开放多少工具、每个工具负责什么、如何让模型正确选择，以及如何在后端工具层执行基于角色的访问控制（`00:47:38–00:51:28`，`00:51:47–00:54:27`）。

效率收益来自把“亲手写分析代码”改成“监督和核验分析”。Chuah 转述，看到系统演示的科学家会把它与过去可能耗时数月或需要许多邮件的工作相比，认为现在几分钟就能完成；过去新成员需要学习 Python 或 R 才能从 Excel 画图，如今可以先让 Helix 生成代码。但他紧接着给出边界：研究者必须验证分析是否正确，工作只是从实现转向审查。这些时间对比是受访者转述的反馈，并非经过独立评测的通用性能数字（`00:48:04–00:50:04`）。

对于未来，Chuah 的措辞仍是“潜力”和“希望”：Agent 可能缩短药物发现中的部分瓶颈，但现实组织、培训和监管需要时间跟上；目前最好的编码模型也不是百分之百可靠。科研人员必须理解任务，检查结果是否符合数量级和领域常识，并对关键流程逐步验证。换言之，Agent 可以更快地产生代码和答案，人仍要决定方向、识别异常并承担关键结论的复核责任（`00:56:09–00:57:50`，`00:58:39–00:59:57`）。
