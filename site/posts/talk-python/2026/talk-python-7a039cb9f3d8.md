## 速读

这期讲清 Python 3.15 内置的采样剖析器 Tachyon：为什么追踪式剖析器会让程序慢两三倍，采样式剖析器如何附加到正在运行的生产程序并保持近零开销，以及从每秒 2 个样本到超百万赫兹的设计取舍与边界。

嘉宾是 CPython 核心开发者、Steering Council 成员 Pablo Galindo Salgado（现就职于 Hudson River Trading，此前在 Bloomberg 参与了这项工作）与 Bloomberg Python 基础设施团队的 László Kiss Kollár。主持人 Kennedy 在开场把卖点概括为：过去剖析 Python 意味着让代码慢两三倍的追踪式剖析器，或随每次运行时更新而损坏的第三方工具；Tachyon 作为标准库组件可附加到运行中的生产程序，首个原型只有每秒 2 个样本，如今据称超过百万赫兹（`00:00:00–00:00:47`）。节目同时保留了两位嘉宾自己声明的条件：默认免停应用的采样只有统计意义，可选的一致读取模式有 1%–2% 的代价，C 扩展内部仍然看不见。

## 主题正文

### 追踪式剖析器为什么让程序慢两三倍

Pablo 先回顾标准库的历史。profile 模块是 Python 里最早的剖析尝试，但架构上吃亏：它用 Python 写成、运行在被剖析的程序内部，测量的其实是“应用加剖析器”的合计，还要用各种技巧估算自身的贡献；他称其代价可以到 20 倍上下，取决于程序在做什么（`00:29:14–00:30:06`）。cProfile 把同一套思路用 C 重写，据他说法比 profile 快约 10 倍，但仍然让程序慢两到三倍——按他的比喻，五分钟的任务会变成十五分钟（`00:31:52–00:32:08`）。

慢的根源是结构性的。这类工具被称为追踪式剖析器：每次函数调用都要被看到并记录，而且它们运行在进程内，等于给每次调用都叠加额外工作（`00:32:30–00:32:49`）。代价换来的是完整数据——函数被调用几次就是几次，绝不遗漏；Memray 出于同样的理由选择追踪，因为你不会想弄丢一次 1 GB 的分配（`00:32:49–00:33:30`）。László 补充了人机工学问题：文档让人分不清该用 cProfile 还是 profile，cProfile 事实上成了默认答案；而想要更高质量的剖析结果，一直得去找外部工具（`00:33:52–00:34:32`）。

更关键的限制是生产不可用。对追踪式剖析器来说，你往往只能构造一个小的测试用例去跑，因为对整个应用运行太慢、太耗时；Kennedy 指出这会带来“本地剖析没问题、生产却另说”的错位（`00:34:33–00:35:07`）。他还给出一个警告：追踪式剖析器的减速并不均匀——大量做 Python 内部函数调用的代码被严重拖慢，而慢在外部系统上的部分几乎不受影响，观察行为本身就扭曲了测量结果（`00:35:20–00:36:13`，`00:37:56–00:38:23`）。

### 3.15 的铺垫：惰性导入与 Faster CPython

进入剖析正题前，节目先聊了 3.15 的显式惰性导入。Pablo 解释，包会拖包，为了用一个小函数可能付出整条导入链的代价；显式 lazy import 让你只为真正用到的导入付费，省时间也省内存（`00:13:57–00:15:41`）。Kennedy 分享了自己把很少用到的顶层导入改成函数内导入后省下约 100 MB 内存的经历，并说在服务器上内存往往比算力更贵；Pablo 补充了二阶效应：无用导入制造的海量 Python 对象会让每一轮垃圾回收都变慢（`00:16:18–00:19:15`）。他提到自己在 3.15 中负责的成果就包括惰性导入和这个剖析器（`00:05:08–00:05:16`）。

Faster CPython 被两人评为明确的成功：从 3.9/3.10 到今天的性能进步清晰可见，只是“显眼的目标”做完了，剩下的大工程 JIT 与去掉 GIL 的自由线程还会互相牵制，而剖析正是确认这些优化真实生效、还是 NumPy 变快的手段（`00:22:07–00:23:32`）。László 记得 3.12 那次跃升最大——“白拿 30% 到 40%”的性能提升让说服用户升级变得容易，这是他的现场回忆（`00:23:33–00:24:14`）。自由线程的收益取决于应用形态（`00:24:53–00:25:31`）；Kennedy 担心生态还没有为竞态条件做好准备，Pablo 则提醒多线程并不线性扩展，为不崩溃付出的额外检查可能吃掉扩展性，而且这类问题需要别的工具、不是本期这个工具能覆盖的（`00:25:31–00:27:25`）。

### 从 PEP 768 到每秒百万采样：Tachyon 的诞生

Tachyon 的直接前身是 PEP 768。Pablo 说，这个 PEP 的“北极星”目标是让 PDB 等调试器能附加到正在运行的生产程序上——程序行为异常时不必停机重跑；为此 CPython 加入了一整套附加并检查运行中进程的机制，随 3.14 发布（`00:42:17–00:43:26`）。这项工作源自他此前与 Bloomberg 同事 Ivana 和 Matt 的项目；Kennedy 补充其标题是“CPython 的安全外部调试器接口”，而“反复问程序在做什么”本身就是剖析（`00:50:31–00:50:38`）。

2025 年 PyCon US 的冲刺周上，Pablo 向 László 提议：把这个附加接口放进循环里调用，就是一个剖析器。两人当场写了个小程序试水。Pablo 给出参照数字：对采样剖析器来说，每秒约 100 次才算进入有用区间（`00:43:26–00:44:18`）；而他们量到的起点只有每秒 2 次（`00:44:21–00:44:35`）。按 Pablo 的说法，整个冲刺周都在提速，结束时已“超过每秒一百万次”（`00:44:36–00:44:53`）；László 记得冲刺期间几乎没有提交代码，实际提交都发生在其后，冲刺结束时大约每秒 10 万到 20 万次，之后 Pablo 又带来四五倍的改进（`00:44:56–00:46:12`）。这些速度数字都是当事人的现场回忆，节目没有附上独立基准；Kennedy 在开场也以“原型每秒 2 个样本、如今超过百万赫兹”复述了同一故事（`00:00:35–00:00:42`）。

### 为什么要进标准库，以及 PEP 799 的收纳

嘉宾并不讳言 Tachyon 不是第一个这类工具：Rust 写的 py-spy 存在已久且质量很好，还有 Austin 等（`00:46:25–00:46:51`）。外部工具的代价是必须理解解释器的私有内部结构——这些部分并不公开，核心开发者的改动一再破坏它们；Pablo 举例说，一度剖析 3.11 比剖析 3.10 更慢，因为 3.11 的内部改动让这件事变难（`00:46:51–00:47:56`）。进标准库因此有三重理由：成为“我们能做到，别人也能照做”的参考实现、保证这一能力永不损坏；作为“电池全带”的一部分保证质量；以及最关键的——他们控制解释器本身，可以为剖析专门改进解释器，这些技巧别人同样可以利用（`00:47:56–00:50:29`）。

组织层面由 PEP 799 收口：新建 profiling 包，最终只有一个追踪式剖析器（基本就是 cProfile，cProfile 兼容别名保留）和一个采样式剖析器，用法变成 profiling.tracing 与 profiling.sampling；纯 Python 的旧 profile 模块进入弃用流程，Kennedy 提醒它将在 3.17 被移除（`00:38:36–00:40:11`，`00:41:47–00:42:13`）。Pablo 说 3.15 定于十月发布（`00:04:30–00:04:34`）。

条件也很明确：Tachyon 依赖 3.15 新增的机制，目前只能用 3.15 剖析 3.15，而 py-spy 可以面向任何版本；未来是否允许跨版本剖析尚未决定（`00:52:21–00:53:28`）。社区已有人在一周内做出面向 3.14 的回移植，Pablo 乐见其成，但提醒 CPython 不回移植功能、出 bug 也别找他们；Kennedy 自己试过把 profiling 包搬去 3.14，发现补丁巨大、每个补丁版本都要持续维护，于是放弃了把它当长期方案的想法（`00:53:31–00:54:51`，`00:55:36–00:56:46`）。

### 附加到生产程序：默认近零开销

这是两位嘉宾花最多时间强调的部分。程序在生产上行为异常时，可以附加上去抓一份剖析数据、拿走离线分析再脱离（`01:01:20–01:02:03`）。默认模式下 Tachyon 从不暂停应用，只做读取（`01:02:03–01:02:09`）；读到正在变化的结构就丢弃这个样本，生成器多的程序更容易出现这种部分读取（`01:02:09–01:02:38`）。应用对此无感知、全速运行，除非把应用和剖析器挤在同一个 CPU 核上（`01:02:38–01:03:02`）。

如果想要每个样本都一致，可以打开 blocking 模式：读取前把应用停住极短一瞬间再恢复。按 Pablo 的说法，默认采样率乃至每秒一万次以内，代价约为 1%–2%，而不是两倍（`01:03:02–01:03:48`）。代价随采样率上升：他的现场估计是每秒 10 万次可能到 20%–80%，冲到每秒一百万次则可能接近两倍级别的减速，且取决于机器能否跑得动（`01:03:52–01:04:17`）。他给出的生产建议是每秒 100 到 1000 次采样，1%–2% 的减速完全可以接受（`01:04:17–01:04:27`）。

Pablo 用“金子”来形容生产内数据：很多时候你只有线上那台行为诡异的机器，没有“在实验室里带着剖析器重启”的选项，附加、看一眼、脱离即可；哪怕 blocking 模式减速五成，跑几秒钟也无妨（`01:04:27–01:05:29`）。他举了 Hudson River Trading 的当天案例：公司超算上首次对所有程序开启这类能力的“放大版”（他说明并非 Tachyon 本身），当天就发现某个应用莫名吃满一整个核，追查后是一个特定路径下“意外平方复杂度”的算法——他说这段代码没人肉眼能看出来，但数据里一目了然，修掉之后每台机器都空出一个核（`01:06:14–01:07:51`）。

László 把可用性条件压到最低：需要的只是应用跑在 3.15 上；最需要工具的时刻，往往正是你手上没有工具的时刻（`01:08:52–01:09:33`）。以较低采样率长期运行即可构成持续剖析（continuous profiling）（`01:09:33–01:09:47`）。他也强调 Tachyon 不只是生产剖析器：可以从程序启动就跟跑整个进程，也适合开发环境里比较两次代码修改前后的剖析快照（`01:09:47–01:11:08`）。

### 功能面与采样模式

功能清单相当长：火焰图、类似 top 的实时函数视图、热力图，以及差分火焰图——改一点代码再跑一次，直接对比哪些函数变快、哪些变慢（`00:56:51–00:58:17`）。Pablo 称它是目前第一个做异步感知的剖析器：事件循环里“慢”的含义会骗人，等你下载 3 GB 文件时，等待本身不会出现在只看运行中协程的火焰图里；Tachyon 因此提供两种模式——只看正在运行的任务，或列出所有等待中的任务（`00:58:17–01:00:24`）。还有 dump 模式：传入 PID，就能像打印异常栈一样打印卡死程序的调用栈，死锁排查可用，且 macOS、Windows、Linux 使用同一机制（`01:00:24–01:01:02`）。

采样模式本质上是样本过滤器（`01:13:29–01:14:06`）。默认的 wall clock 模式如实告诉你程序在睡眠、等网络或读盘上花了多久（`01:14:06–01:15:25`）；CPU 模式滤掉等待样本，只留下你真正能改进的计算（`01:15:25–01:16:06`）；GIL 模式回答“谁攥着 GIL”——他举例说调用 NumPy 的十秒里若有九秒未持 GIL，其他线程本可运行（`01:16:47–01:18:09`）；exception 模式问的是异常处理花了多少时间，迭代器协议的 StopIteration 也算在内，还有查看单条 opcode 的模式（`01:18:52–01:19:43`）。Pablo 特意说明设计目标是覆盖从“只想知道哪五个函数慢”到深度专家的整个使用者区间（`01:18:21–01:18:52`）。另有一个不显眼、只在 Gecko 输出下生效的 all 模式：给样本着色后，可以在时间线上看到 GIL 在线程间的往复与争用（`01:20:07–01:21:14`）。

### 嘉宾声明的边界与后续

第一个边界是 C 代码。Tachyon 是 Python 剖析器，只看得到谁调用了 NumPy、Pandas、Polars 或 CUDA 代码，看不到 C 代码内部；反过来，C 剖析器又拿不到 Python 名字。Pablo 说同时做两者难度按他的说法是“一百万倍”，他们刻意没有把这种复杂度带进标准库（`01:22:00–01:23:45`）。第二个是自由线程场景下线程不线性扩展的问题需要别的工具，他明确说本期讲的工具也不覆盖那种情况（`00:26:43–00:27:25`）。

名字考据：tachyon（速子）是假想的超光速粒子，词根是希腊语的“快”；而官方模块名是朴素的 profiling.sampling，只是“大家都叫它 Tachyon”（`01:11:17–01:12:28`，`01:25:12–01:25:44`）。Pablo 还介绍了他在现雇主的内部项目 Chronon——按他的说法是“Tachyon 的大哥”：支持 3.12–3.15 多版本、深入 C 与内核代码、可流式接入 Grafana，已在公司内使用了九个月，并预告一两个月内开源；这些说法均出自嘉宾本人（`01:23:45–01:25:10`）。两人最后推荐了 László 今年在 PyCon 上关于该主题的演讲（`01:21:28–01:21:57`）。
