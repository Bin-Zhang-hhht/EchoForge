## 速读

DiskCache 用 SQLite 支撑像字典一样的持久化缓存；本期从 LLM、Web 和 notebook 案例讲清收益，也把部署、并发、序列化和性能边界说透。它适合希望避免额外 Redis 服务、又需要跨进程复用结果的 Python 开发者，但不应被当成数据库、队列或所有部署形态下的 Redis 替代品。最值得关注的是：缓存收益来自减少昂贵的重复计算，实际效果仍取决于读写比例、缓存键、磁盘与部署方式。（`00:02:05–00:03:01`，`00:23:32–00:24:30`）

## 主题正文

### 把昂贵的重复工作变成可复用结果

本期嘉宾 Vincent Warmerdam 目前在 Marimo 工作，日常做 Python notebook，也会做 benchmark、LLM 和 Web 相关工作；主持人 Michael Kennedy 则从自己在 Talk Python 网站上的实践切入。两人讨论的共同前提很具体：同一段文本再次送入 LLM、同一个文件再次做机器学习推理，或者同一段 Markdown 每次请求都重新转 HTML，都会重复消耗计算、时间或费用。缓存把输入对应的结果保存下来，下一次命中时直接返回，而不是再次执行昂贵步骤。（`00:02:20–00:03:01`，`00:04:03–00:04:47`，`00:08:34–00:09:06`）

Python 自带的 `functools.lru_cache` 适合小而快的进程内缓存，但进程重启后内容会消失；它保存的是内存对象的引用，不需要序列化，因此在适合的场景下通常更快。DiskCache 的交换条件是把结果落到磁盘，从而具备进程重启后的持久性，也能让同一台机器上的多个进程共享缓存。节目把它概括为“行为像字典、底层使用 SQLite 的文件缓存”，但也提醒它不一定在每个实现细节上都是一个 SQLite 文件。（`00:04:49–00:05:27`，`00:22:30–00:23:08`，`00:24:32–00:25:05`）

这也是它对 LLM 和 notebook 有吸引力的原因：benchmark 的循环中，如果不小心再次触发旧方案，不必重新跑所有模型；数据处理或 embedding 计算中，已经完成的结果也可以留存。收益的前提是同一输入确实能复用结果，并且结果允许被缓存；如果写入比读取还多，节目直言那就失去了缓存的意义，额外的序列化和磁盘操作反而会成为开销。（`00:06:13–00:07:18`，`00:28:05–00:28:19`，`00:24:07–00:24:30`）

### 文件和部署方式决定它能否跨进程工作

DiskCache 的关键不是“磁盘一定比内存快”，而是把共享状态放到了应用进程之外，同时不必运行一个独立缓存服务。Kennedy 的网站在一个大 VM 上运行多个 Docker 容器，并把外部硬盘上的缓存目录作为共享卷；不同用途可以使用不同的 SQLite 文件或目录，例如分别保存 YouTube ID、Markdown 转 HTML 结果和 HTTP 相关结果。一个实际缓存约有 8,970 项、占 9 MB，这只是他的站点案例，不是 DiskCache 的容量或性能保证。（`00:09:44–00:10:16`，`00:11:30–00:12:22`）

持久卷还意味着重建 Docker 镜像后缓存可以保留。相反，在会水平扩展、每个容器都不能共享卷的托管环境中，每个实例可能只能拥有自己的缓存；这仍然有用，但命中率和一致的复用效果会不同。两位嘉宾因此强调，DiskCache 的优点取决于部署形态：它适合多个进程能访问同一台机器上的同一存储，不能简单套用到任意跨主机架构。（`00:10:21–00:10:58`，`00:13:14–00:14:20`）

它的并发边界也必须写进设计。节目将 DiskCache 描述为线程安全、跨进程安全和持久化的组合，并指出底层 SQLite 在多进程写入时仍可能变慢；SQLite 更适合读多写少的场景。缓存文件需要在可访问的本地存储上，嘉宾特别提到网络盘可能带来性能和锁问题，文档也建议不要这样使用。跨进程不等于跨网络，能共享路径不代表网络文件系统就是合适的部署方式。（`00:22:56–00:24:18`，`00:40:58–00:41:47`）

如果应用有多个并发写入者，可以考虑 `FanoutCache`：它通过分片使用多个 SQLite 实例，默认分片数被节目读作 8；读者和写者不会互相阻塞，但写者仍会阻塞其他写者，因此文档建议按并发写入者数量考虑分片。它的代价是按类别清理不如分别建立缓存直观：Kennedy 选择独立缓存文件，正是因为他希望能清除 YouTube ID 而保留昂贵计算的哈希结果。（`00:33:18–00:35:27`）

### API 不止是字典：过期、淘汰、事务和队列

最小用法可以像 Python 字典一样读写、删除和 `get`，并以 pickle 序列化一般 Python 对象；整数等 SQLite 原生类型可能走更直接的存储路径。DiskCache 也提供 memoize 装饰器，按函数和参数记住结果，并能设置过期时间。例如首页或 RSS 这类会更新、但不必每秒重算的结果，可以只缓存五分钟或一分钟。Kennedy 以 RSS endpoint 举例：他的 RSS 响应超过 1 MB，访问量据他估计超过每秒一次，把生成结果按一分钟缓存可以减少反复构建和传输。（`00:20:41–00:22:22`，`00:25:20–00:26:30`，`00:26:32–00:27:41`）

持久化的另一面是缓存不会随进程重启自然清空，数据可能不断堆积。节目提到可以设置过期时间、缓存大小和淘汰策略；讨论中把默认磁盘大小说成 1 GB，并列出按最近存储、最近访问或访问次数等策略进行清理。这里应把 1 GB 看作节目所展示文档的默认值，部署前仍需以所用版本文档和实际配置核对，而不是假定所有版本都相同。（`00:31:50–00:32:34`，`00:42:37–00:44:15`）

对于有顺序要求的工作，DiskCache 还提供更高阶的数据结构。`Deque` 可以用类似队列的方式反复 `popleft`，因此可用于在进程间分发工作；节目还提到，如果进程中断，待处理任务仍可保留。它能成为轻量的自建任务机制，但这不等于完整的任务队列系统：Celery、Redis 或 RabbitMQ 的重试、监控和运维语义不能仅由“把任务放进缓存”自动获得。（`00:38:53–00:40:31`）

`Index` 和事务则适合需要有序映射或一致读取的场景。嘉宾举例说，事务可以确保从缓存中取出的两个值在同一时点存在，不会在两次读取之间被改变。节目还提到 Django cache backend，它以 `FanoutCache` 提供 Django 兼容接口，配置 settings 后可以作为 Redis 等后端的一个替代选项；这降低的是接入门槛，不代表它改变了 SQLite 的本地存储与并发限制。（`00:41:52–00:42:30`，`00:36:48–00:38:50`）

### 性能数字必须连同测试条件一起看

DiskCache 文档中的 benchmark 曾显示它在 get 和 write 速度上超过 Redis，但节目没有把这张图当作普遍结论。两位嘉宾推测差异可能来自网络跳转，并明确说如果 Redis 和应用在同一台机器上，数字会不同；他们还注意到项目始于 2016 年，图表数据可能很旧，而磁盘、内存和 NVMe 设备已经变化。因此，“DiskCache beats Redis”只能作为该 benchmark 的结果，不能脱离硬件、网络、版本、数据大小和读写模式外推。（`00:28:27–00:29:49`）

节目随后用成本而不是绝对速度解释磁盘缓存的价值：高性能 NVMe 容量可能比同等规模内存便宜，缓存放到磁盘也可能让云部署减少内存或计算需求。Kennedy 举出个人价格印象，称约 5 美元可以买到 400 GB 磁盘；这不是经核实的普遍云价格，也不应和 400 GB RAM 做直接的供应商间性能比较。正确的工程问题是：结果是否能复用、内存是否真是瓶颈，以及磁盘延迟是否仍低于重新计算的成本。（`00:29:51–00:31:30`）

Vincent 展示的“code archaeology”notebook 是更有条件的实测案例：它对 Git 历史采样约 100 个时间点，对每个文件和代码行运行 `git blame`，再生成代码变化图；节目中描述一次约 550,000 行规模的图表计算在 M4 Mac 上耗时 2 小时 15 分钟。DiskCache 被用于保存每个文件、每个时间点的结果，notebook 中断后不必全部重算。这里的性能数字属于该算法、项目规模、机器和缓存工作流的组合，不是 DiskCache 单次读写的 benchmark。（`00:45:01–00:45:20`，`00:47:36–00:48:59`）

### 自定义序列化带来空间收益，也带来兼容性责任

DiskCache 默认可以 pickle，但用户也能提供自定义 disk class。节目以 JSON 为例：短小的普通字典不值得额外压缩，文本很多且模式重复时，先用 zlib 压缩再写入缓存才可能有明显收益。嘉宾称高度可压缩的文本“并不罕见”能节省约 80%–90% 磁盘空间，同时也承认压缩和解压会增加开销；这个范围依赖数据内容和实现，不能当作固定比例。（`00:52:18–00:54:40`）

对 NumPy embedding，直接把数组转 bytes 与 pickle 的大小在他们的尝试中基本相同；另一条路线是把浮点数降为 float16 或做量化，以牺牲精度换取空间。一次量化练习中，Vincent 说大约获得 4 倍磁盘空间改善，同时相似度分数损失约 1%；他也说 mileage can vary，并把是否可接受交给具体用途。如果结果要参与精密计算，不能只因为节省空间就降低精度；若只是相似度检索或不报告很多小数位，才值得用真实数据验证这种折中。（`00:56:25–00:58:29`）

序列化还决定缓存能否跨环境复用。pickle 对 Python 版本、NumPy 版本、自定义类的演进都敏感：节目用 Python 3.6/NumPy 1 写入、再由 Python 3.12/NumPy 2 读取作为风险示例。小心设计的 JSON 或其他格式可能更易检查和压缩，但日期时间等类型仍需显式处理。对结构化数据集合，嘉宾认为 Parquet 的列式存储、分区和扫描能力可能更合适，尤其是大表；DiskCache 更像保存可按键取回的计算结果，不应替代适合批量分析的存储格式。（`00:20:54–00:21:43`，`00:52:49–00:55:36`，`00:58:36–01:00:09`）

缓存键是最后一道正确性边界。节目中的网站做法是把 episode、数据类型和 show notes 哈希组合进键，避免源内容变化后错误命中旧结果；LLM 的示例则把“需要返回五个响应”之类的变化也加入键。函数装饰器的键规则要先查清楚，不能假设修改了函数体就一定自动产生新键。键过窄会得到陈旧数据，键过宽又会降低命中率、扩大存储；这部分必须由应用根据输入、版本和失效策略负责。（`01:06:48–01:08:02`，`00:25:20–00:25:51`）
