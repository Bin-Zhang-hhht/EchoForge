# EchoForge — 产品文档

> 版本：v0.6 · 2026-09-11  
> 状态：简化后的实施基线，尚未实现。  
> 本版在 v0.5 内容资产分层基础上正式确定项目名称 **EchoForge**；产品边界、转写策略和三阶段实施路线不变。
> 中文展示名：**EchoForge · 技术播客**；建议仓库名：`echoforge`。

## 1. 产品定义

**项目名：EchoForge**。`Echo` 对应播客、声音和访谈内容，`Forge` 对应提炼、重组与再创作。名称不绑定单一渠道，因此未来即使从 Podcast 扩展到访谈录音、视频或其他长内容，也无需重新命名。

对外中文展示统一使用 **“EchoForge · 技术播客”**；代码仓库和本地项目目录优先使用 `echoforge`。

从配置好的 Podcast RSS 中发现技术访谈，由用户在本地投放 ZCode / GLM 闲时任务，将长播客整理成便于阅读的中文笔记，再发布到 GitHub Pages。

**不是逐字翻译，而是忠实于原意的浓缩、重组和中文改写。** 先把“收集 → 获取逐字稿 → 整理 → 阅读”跑通，不建设大型内容平台。

同时明确三层内容资产：

1. **Source / 本地源资产**：完整逐字稿、时间戳、节目元信息，长期保留，仅本地使用。
2. **Machine Digest / 机器摘要**：ZCode / GLM 自动生成的中文精编，可在检查通过后发布到 GitHub Pages。
3. **Editorial Content / 人工编辑内容**：微信公众号文章、视频脚本等，必须人工核查和重新组织后才能发布。

GitHub 网站承担“信息雷达”；公众号和视频如果后续启用，则承担“人工把关后的内容品牌”。

## 2. 当前确定的方案

| 项目 | 首版决定 |
| --- | --- |
| 项目名称 | **EchoForge**；中文展示名“EchoForge · 技术播客”；建议仓库名 `echoforge` |
| 仓库 | 一个仓库，只维护 `main` 分支；代码、元信息和公开文章按目录分开 |
| 内容来源 | 只支持配置好的公开 Podcast RSS，不自动寻找新订阅源 |
| 来源池 | 维护独立的 [Podcast RSS源清单](Podcast%20RSS源清单.md)；首版只启用少量来源验证，不一次性全开 |
| 日常采集 | GitHub Actions 每天采集元信息、去重和规则过滤 |
| 内容处理 | 用户自行决定频率，在本地投放 ZCode 闲时任务 |
| 转录策略 | Transcript-first；没有现成逐字稿时，由 ZCode 调用 Video Agent Kit 的转写能力 |
| 本地资产 | 完整逐字稿长期保留；音频和一次性中间文件只作为临时缓存 |
| 网站 | VitePress 默认主题，Markdown 驱动，部署到 GitHub Pages |
| GitHub 发布 | 机器摘要可在本地检查通过后直接提交和发布 |
| 公众号 / 视频 | 可以生成草稿或脚本，但必须经过人工核查、改写和确认后再发布；首版不做自动发布 |
| 提醒 | 暂不做；在 Actions 运行摘要或本地查看待处理数量 |

## 3. 核心流程

```text
配置 Podcast RSS
        ↓
GitHub Actions 每日读取 RSS
        ↓
去重、规则过滤，保存元信息到 main/data/items/
        ↓
用户在本地拉取仓库，投放 ZCode 闲时任务
        ↓
Transcript Resolver
   ├─ RSS / Publisher 已有 transcript → 直接获取
   └─ 没有 transcript → 临时下载音频 → Video Agent Kit 转写
        ↓
本地长期保存完整逐字稿与可用的时间戳信息
        ↓
ZCode / GLM 自动整理
        ├─ Machine Digest → site/posts/*.md → GitHub Pages
        ├─ WeChat Draft → 人工核查 / 改写 → 手动发布
        └─ Video Script → 人工核查 / 改写 → 后续视频制作
```

采集和编辑相互独立。几天不处理也不影响元信息继续积累；某一期无法获取正文，不影响其他节目整理。

## 4. 首版只交付这些能力

### 4.1 RSS 收集

维护一份来源配置，保存节目标题、发布时间、原始链接、简短简介，以及 RSS 已提供的音频和转录地址。未知字段留空，不让模型猜。

生产配置只从 [Podcast RSS源清单](Podcast%20RSS源清单.md) 中选择公开 Feed。来源池用于人工维护和后续扩展，不参与运行时自动发现。M2 首次联调只启用 Recsperts、Data Skeptic、Latent Space、Practical AI 和 Software Engineering Daily 五个来源；跑稳后再逐步增加其他核心源。

采集时按稳定 ID 去重，只新增条目，不覆盖本地已经更新的状态。规则仅使用来源、关键词、排除词和可选时长限制，不做复杂评分。

**Actions 不下载音频、不跟进转录正文、不做 ASR、不调用大模型。** RSS 内附的完整正文也不原样存入仓库。

### 4.2 Transcript-first 与本地源资产

本地处理时按以下优先级取得真实内容：

```text
RSS / Podcasting 2.0 transcript
        ↓ 没有
Publisher 官方 transcript
        ↓ 没有
ZCode + Video Agent Kit 转写
```

ZCode 负责任务编排；Video Agent Kit 负责无现成逐字稿时的 ASR。首版不再额外接入 Groq、独立 Whisper 服务或其他收费转写 API。

取得逐字稿后，**完整逐字稿是长期本地资产，不属于缓存**。至少保存一份便于人工阅读的文本；如果来源或转写工具提供时间戳、说话人、VTT/SRT/JSON 等结构化信息，也一并保留原始可用版本，不能伪造缺失的时间戳或 speaker。

音频只作为处理过程中的临时输入。转写成功并完成必要核对后即可删除，不提交 Git，也不要求长期保存。

### 4.3 内容资产分层

逻辑上每期内容分为三层：

```text
Source
  完整逐字稿 / 时间戳 / metadata
  → 本地长期保留，不公开

Machine Digest
  GLM 自动精编 Markdown
  → GitHub / VitePress，可自动发布

Editorial Content
  公众号文章 / 视频脚本
  → 人工选题、核查、重组、改写后才能发布
```

公众号和视频的人工环节不是简单同义改写，而是重新判断哪些观点值得传播、核对上下文与事实、补充必要解释并重新组织叙事。机器产出的公众号稿或视频脚本只能视为草稿。

### 4.4 GitHub 中文精编

每期只生成一篇公开 Markdown，通常包含：

- 开头的速读摘要，说明这期值得关注什么。
- 按主题重组的正文，保留关键观点、案例和分歧。
- 原始来源，以及重要观点的时间段或原文小节定位。

篇幅参考约 1,000～3,000 字，随信息量调整，不凑字数。不单独生产两份重复的“速读稿”和“精读稿”。

允许删除广告、寒暄、重复和口头语，合并分散的同类观点；必须保留原话的条件、不确定性和观点归属。中文转述不冒充直接引语。

没有时间戳时引用原文小节或可识别片段，不编造时间。文末标明“AI 编辑整理，请以原始节目为准”。

公开文章不包含完整逐字稿。逐字稿用于内部核查、后续人工编辑和定位原始内容。

### 4.5 人工发布门

如果后续生成微信公众号或视频内容，必须经过 Human-in-the-loop Publishing Gate：

1. 人工决定是否值得进入公众号 / 视频渠道。
2. 对照本地逐字稿核查关键表述、数字和上下文。
3. 重新组织叙事并补充必要解释，避免把机器摘要直接当成最终稿。
4. 人工确认最终稿后再手动发布或进入视频制作。

**首版不建设微信公众号自动发布、视频自动发布或跨平台发布系统。** 当前只把“机器草稿不得自动对外发布”作为长期产品边界。

### 4.6 网站阅读与更新

使用 VitePress 默认主题，首版只有首页、文章列表、文章详情和内置本地搜索。文章用 Markdown 直接维护，不另存一份文章正文 JSON，不建立后台编辑器。

本地整理完成并推送 `main` 后，由部署工作流构建网站。构建失败时保留已有站点，只修复或重试部署，不重新处理音频或逐字稿。

## 5. 处理记录

每一期元信息文件带一个简单状态：

| 状态 | 含义 |
| --- | --- |
| `pending` | 等待处理 |
| `processed` | 已生成 GitHub 机器摘要并通过本地检查；不等同于网站已经部署成功 |
| `ignored` | 经筛选不处理，保留简短原因 |
| `failed` | 正文不可用、转写失败或其他处理错误，保留简短原因 |

正常任务只选择 `pending`。修复问题后，将指定条目改回 `pending` 即可重试，不建设复杂任务状态机。

公众号和视频的编辑状态不写入首版 GitHub 元信息状态机；它们是本地编辑资产，避免为尚未自动化的渠道扩展状态复杂度。

## 6. 首版不做

暂不做 YouTube、飞书或微信提醒、自动远程触发闲时任务、自动周报、人物专题、主题研究和趋势统计。标签可写在文章里，但不为标签建设独立分析系统。

不做数据库、后端 API、用户账户、向量搜索、知识图谱、多 Agent 编排、自定义网站主题和音视频长期托管。

不做公众号自动发布、视频自动生产/发布。允许本地保留相关人工草稿，但不为这些渠道提前建设发布接口、状态机或平台适配器。

RSS 来源池是人工维护的白名单，不建设“自动发现优质 Podcast”、来源评分、来源推荐或聚合搜索服务。

## 7. 上线标准

使用首批少量真实 RSS，完成一次“采集 → 获取逐字稿 → 本地长期保存 → 机器整理 → Pages 阅读”即可判定首版闭环成立。重点检查：重复采集不新增重复条目；至少 3 篇笔记能读、能回溯来源；本地逐字稿仍可用于人工复核；第二次处理不会重做已完成条目；获取正文失败时不发布虚构内容。

首版不以覆盖所有来源、公众号、视频、多平台分发或完整媒体生产作为上线条件。

## 8. 未来想法

AI 配音、AI 动画、“三分钟带你学习……”视频、微信公众号推文仍是未来方向。未来如果启用这些能力，沿用当前的内容分层：**Source 不公开，Machine Digest 可自动化，Editorial Content 必须人工把关。**
