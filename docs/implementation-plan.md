# EchoForge — 执行计划

> 版本：v0.8 · 2026-09-11
> 依据：[产品文档](product.md)、[架构文档](architecture.md)、[Podcast RSS源清单](podcast-sources.md)
> 当前状态：M1、M2 已完成统一 Docker 环境的本地验证；M3 已完成三篇真实内容的本地闭环，最终验收等待远端 Pages / Actions、私有备份恢复及用户阅读验证。项目名称已确定为 **EchoForge**，建议仓库名 `echoforge`。

## 1. 开发原则

先看到 **EchoForge** 网页，再接上采集，最后用真实播客走通“逐字稿资产 → 机器摘要 → 发布”。不拆大量子里程碑，不为未来视频和公众号设计自动发布接口。

所有公开代码、元信息和文章都放 `main`。本地完整逐字稿、人工笔记和渠道草稿进入 `local-library/`，不提交 Git；临时音频和可重建中间文件进入 `.cache/`。只有逐字稿已保存、可用性检查通过且所需回听疑点已解决后，才可清理临时音频。

首版每批最多 3 篇文章、最多 1 次新 ASR，新增 ASR 音频总时长不超过 120 分钟；优先复用已有可用本地材料。`pending.py --limit 10` 只是候选窗口，不是处理配额。超出预算或无法在预算内确定实际音频时长时保留 `pending` 并报告，不记为失败或忽略；`ignored` 仅用于明确不相关或不值得处理的条目。允许按现有顺序积压，不引入评分。

先看 `rec-sys-daily`、cast2md、Podsidian 等项目中相关小模块再实现，但不整体复制其流水线。脚本保持普通文件，不先包装成 CLI 框架、插件系统或服务。

RSS 来源采用“来源池 + 少量启用”的方式：完整候选名单放在文档里，`config/sources.yaml` 只放当前实际采集的来源。首版不建设来源自动发现或评分系统。

## 2. M1 — 先发布一个可读的网站

**目标：** 一篇手写样例 Markdown 可以通过推送自动出现在 GitHub Pages。

实施内容：

- 若开始新建仓库，优先使用 `echoforge` 作为仓库和项目目录名；建立 `site/`、项目文档目录和忽略规则，使用 VitePress 默认主题。
- 添加首页、文章模板、文章列表生成脚本及内置本地搜索。
- 配置 `site:dev`、`site:build`、`site:preview`，锁定依赖。
- 建立 `deploy.yml`，支持 `main` push 和手动运行；配置 Pages 来源与站点 `base`。
- `.gitignore` 从一开始就排除 `local-library/`、`.cache/`、`.env` 和媒体/转录类本地资产。

样例明确标注为演示，不冒充真实节目。此阶段尚无采集器，后续 M2 再接上条目对应检查。

**完成标准：** 推送后能访问首页、文章列表和详情；列表链接正确；样例标题或独特词能被搜索；修改 Markdown 后站点能更新。此时不需要 AI、音频或第三方密钥。

## 3. M2 — 接通 RSS 采集

**目标：** 每日自动发现新节目，但不在 Actions 中处理正文。

首次联调只启用以下 5 个真实公开 Podcast RSS：

1. Recsperts
2. Data Skeptic
3. Latent Space
4. Practical AI
5. Software Engineering Daily

具体 RSS 地址及后续来源见 [Podcast RSS源清单](podcast-sources.md)。

实施内容：

- 将上述 5 个来源写入 `config/sources.yaml`；Software Engineering Daily 先配置简单关键词过滤，其他 4 个可以先不过滤或仅做非常宽松的过滤。
- 实现 `collect.py`：提取元信息、GUID 优先的稳定 ID、基本规则过滤、只新增文件。
- 尽可能提取 RSS 中公开提供的 `transcript_url`、enclosure/audio URL 和 duration，但缺失字段不猜测。
- 实现 `pending.py`，查看待处理数量和条目；补充 JSON 基本检查。
- 建立 `collect.yml`：每日采集、手动运行、有变化才提交，结果写入 Actions 摘要。
- 为 5 个 Feed 各做一次 smoke test：能访问、能解析、能获得单集标题和稳定标识；某个 Feed 缺少可选字段时不会拖垮整个采集。
- 补充简短 README，说明如何从来源清单增加新源、查看积压和手动重跑。

复用参考：`rec-sys-daily` 的来源配置、RSS 清理和确定性过滤；只迁移必要函数。补上播客特有字段，不直接把博客 Candidate 当播客数据契约。

**完成标准：** 5 个首批 Feed 能完成一次真实采集；同一 Feed 连续采集两次不重复；手动标记过的状态不会被覆盖；没有下载音频或转录正文；一个来源失败时其他来源仍可收集；所有来源失败时有清晰错误。

M2 Gate 通过后，可以按来源清单逐步加入 Software Engineering Radio、Developer Voices、Agentic Conversations 等其他核心源。**扩源不是 M2 完成条件。**

## 4. M3 — 本地逐字稿资产 + 机器摘要闭环

**目标：** 在本地投放一次 ZCode 闲时任务，完成真实节目的“取得逐字稿 → 长期保存 → GLM 精编 → GitHub 发布”。

实施内容：

- 编写 `prompts/process-podcasts.md` 和简短 `AGENTS.md`，落实处理边界、内容原则和发布步骤；已完成。
- 建立 `local-library/<source_id>/<item_id>/` 的长期资产约定，不当作缓存。`metadata.yaml` 最小记录来源获取方式、URL、时间、可用性说明和内容检查结论，不建设 evidence 数据库。
- 实现 transcript-first：优先取得完整可用的官方 / RSS transcript；无法取得完整可用稿时，才在允许且预算足够的情况下由 ZCode 调用 Video Agent Kit ASR。官方稿与 ASR 均核对期次身份、是否逐字稿而非摘要、明显截断和可读性；有时间戳及节目时长时检查覆盖，不用固定字数比例，也不要求广告或音乐逐字转录。工具成功或文件存在不代表材料可用。
- ASR 前确定实际音频时长；无法在预算内确定则延期为 `pending` 并报告。完整可用材料获取失败标 `failed` 并写原因，预算延期保留 `pending`，不能从部分稿、标题或简介生成整期总结。
- 转写音频只暂存在 `.cache/`；完整逐字稿写入 `local-library/` 后长期保留。来源或工具提供时间戳 / speaker / VTT / JSON 时一并保存，不自行伪造。ASR 中不确定的关键术语和数字需要回听。
- 使用用户已有的私有备份机制，为 `local-library/`（含编辑笔记）保留独立副本；首次验证逐字稿和笔记均可恢复，不建设备份服务。
- 使用 GLM 通读完整逐字稿，按“速读 → 主题正文 → 来源与定位”生成中文信息雷达，帮助用户决定是否复听；通常 3–5 个关键主题，不强凑数量。保留证据和限制，1000–3000 字仅作指导，不是发布门槛。正式结果放到 `site/posts/<item_id>.md`。
- 实现两个门：`check.py` 确定性检查元信息、状态、正文和链接格式、双向 item 对应、禁止可执行 Markdown、禁止跟踪 / 暂存的文件；ZCode 显式回查来源中的核心观点、数字、因果、建议、条件、不确定性、归因和真实定位。补充解释必须标明不是来源原话；删去无法核验的外围断言，核心疑点未解决则不发布并标 `failed`、写原因。
- 只有完整材料可用、内容复核和基本检查通过才标为 `processed`，不代表部署成功或独立事实认证。检查并构建，提交本批 GitHub 范围文件，正常同步远端后推送 `main`。
- 只有逐字稿已保存、可用性检查通过且所需回听疑点已解决，才可清理 `.cache/` 中的临时音频。
- 可以试生成一份 `wechat-draft.md` 或 `video-script.md` 来验证本地编辑目录，但**不得作为 M3 完成条件，也不得自动发布**。

**完成标准：** 至少 3 篇互不相同的真实笔记能在 Pages 阅读，分别覆盖官方 transcript、ASR、长篇多主题节目；每篇均有完整可用的本地逐字稿和真实来源定位。用户做一次阅读验收：能决定是否复听、理解一个有来源且边界清晰的观点、定位回原材料；这不是日后每篇发布的人审门。验证重跑跳过已完成内容、获取 / 转写失败记原因而非编造文章、预算延期保留 pending、双重质量门、备份恢复和音频不提前清理；部署重试不要求重新转录或整理。

**达到 M3 即停止扩展首版。** 先实际使用，不追加通知、YouTube、周报、人物研究或自动视频生产任务。

## 5. 人工发布门只定义规则，不做系统

公众号和视频暂不增加新的开发里程碑，只规定以后使用时的边界：

```text
机器生成草稿
    ↓
人工选题
    ↓
对照 local-library/ 逐字稿核查
    ↓
重新组织 / 改写 / 补充解释
    ↓
人工确认
    ↓
手动发布或进入视频制作
```

不能把 GitHub Machine Digest 或机器生成的渠道草稿直接自动同步到公众号 / 视频平台。

## 6. 只做这些必要验证

| 检查 | 方法 |
| --- | --- |
| Feed 可用性 | 首批 5 个来源各做一次真实解析，检查标题、GUID/链接、transcript/enclosure 等可用字段 |
| 去重与状态保留 | 同一小 Feed 重跑两次，比较文件及状态 |
| 采集边界 | 检查网络请求和输出，不访问正文/媒体/模型接口 |
| 来源隔离 | 人为制造一个 Feed 失败，确认其他来源仍继续采集 |
| Transcript-first | 以 1 条完整官方稿和 1 条 ASR 实例验证优先顺序及相同可用性检查；成功返回或文件存在不能直接通过 |
| 部分材料拒绝 | 用截断官方稿、未完成 ASR 各验证一次；不生成整期总结，无法取得完整可用材料则 failed，预算限制则 pending |
| 预算延期 | 候选窗口 10 条不等于处理配额；验证最多 3 篇、1 次新 ASR、120 分钟，超限和无法确定实际时长保留 pending 并报告 |
| 本地资产与恢复 | 发布后逐字稿仍在；用已有私有独立副本恢复逐字稿及编辑笔记 |
| 音频清理门 | 逐字稿未保存、可用性未通过或所需回听疑点未解决，任一情况都不能删除音频 |
| 无正文不发布 | 用一个不可用转录案例验证 failed 与原因，不用标题或简介填补 |
| 双重质量门 | 验证 check.py 格式、状态、双向对应、可执行 Markdown 和禁止跟踪 / 暂存文件检查；ZCode 显式回查核心表述和真实定位，外围不可验证断言删除、核心疑点未解决则 failed 不发布 |
| 一次阅读验收 | 3 篇不同真实笔记分别覆盖官方稿、ASR、长篇多主题；用户能决定复听、理解有来源且有限定的观点、定位原材料，不作为持续人审门 |
| 发布闭环 | 真实本地推送后查看 Pages，再测试一次更新或部署重试 |
| 人工发布门 | 如生成公众号/视频草稿，确认没有任何自动发布步骤 |

使用少量固定样例和必要的真实手工验收即可，不设置覆盖率指标，不做压力测试、复杂测试矩阵或通用验收平台。未执行的外部验证如实记为未执行。

## 7. 首次部署准备

实际部署时补齐仓库地址、Pages `base`、首批 5 个真实 RSS，以及本机 Git、ZCode 和 Video Agent Kit 可用权限即可。这些是部署配置，不是继续编写系统前需要讨论的新产品问题。

本地需要 Docker Desktop / Docker Engine、Compose 和能运行项目工具的 ZCode；项目 Node/Python 依赖只在 Docker 镜像中安装，本地与 GitHub Actions 使用相同镜像阶段和命令。只有处理无现成 transcript 的节目时才会用 Video Agent Kit 的转写能力。不要为了首发把未来视频生产相关能力全部配置一遍。

## 8. 日常闲时任务模板

以下内容已实现为 `AGENTS.md`、`prompts/process-podcasts.md`、Docker Compose 服务和 M3 检查脚本，可作为日常投放任务说明：

```text
阅读 AGENTS.md、prompts/process-podcasts.md 和 templates/post.md。

确认工作区没有不相关改动，拉取 main。
执行 `docker compose run --rm pending --limit 10`，将其作为候选窗口；按本批最多 3 篇文章、最多 1 次新 ASR 且新增音频总时长不超过 120 分钟的预算选取处理项。预算不足或无法在预算内确定实际音频时长的条目保留 `pending` 并报告。

先按元信息筛选。只有明确不相关或不值得处理才标记 ignored 并说明原因，允许按现有顺序积压，不评分。
优先复用本地完整可用材料；否则先获取完整可用的官方 / RSS transcript。
无法取得完整可用稿时，才在允许且预算足够的情况下使用 Video Agent Kit ASR。
ASR 前先检查实际音频时长，并通过 `docker compose run --rm asr-reserve --batch-id <batch-id> --item-id <item-id> --measured-audio-seconds <seconds>` 预约本批唯一名额；无法在预算内确定或预约失败则延期 pending 并报告。
官方稿与 ASR 均核对期次身份、不是摘要、无明显截断且可读；有时长和时间戳时检查覆盖。
不设固定字数比例，不要求转录广告或音乐；工具成功或文件存在不算可用性通过。
无法取得完整可用材料则 failed 并写原因，预算延期则 pending；不从部分材料、标题或简介生成整期总结。

对每一期：
1. 检查通过后，将完整逐字稿保存到 local-library/<source_id>/<item_id>/transcript.md。
2. 实际有时间戳、speaker、VTT/JSON 等结构化输出则一并保存，不伪造；metadata.yaml 最小记录获取方式、URL、时间、可用性说明和内容检查结论。
3. 音频和一次性中间文件只放 .cache/；ASR 中不确定的关键术语、数字需要回听，疑点未解决不得清理音频。
4. 通读完整逐字稿，按速读、主题正文、来源定位写中文信息雷达，帮助决定是否复听；通常 3–5 个关键主题但不强凑，1000–3000 字是指导而非门槛，保留证据和限制。
5. 正式结果写入 site/posts/<id>.md。ZCode 显式回查核心观点、数字、因果、建议、条件、不确定性、归因及真实定位；补充解释标为补充而非原话。删除无法验证的外围断言，核心问题未解决则 failed、写原因且不发布。
6. 可生成 wechat-draft.md / video-script.md 作为人工编辑草稿，但不要发布。

完整逐字稿、人工笔记、公众号草稿和视频脚本不要提交 Git。
使用已有私有备份机制保留 local-library/（含编辑笔记）的独立副本，首次验证逐字稿和笔记均可恢复，不建设备份服务。

执行 `docker compose run --rm content-check`，检查元信息、状态、正文、链接格式、文章双向对应、禁止可执行 Markdown 和禁止跟踪 / 暂存文件。
只有完整材料可用、ZCode 内容复核和基本检查通过才标 processed；这不表示已部署或经过独立事实认证。
执行 `docker compose run --rm site-build`。
只提交本批有关 GitHub 文件；正常同步远端，冲突时停止，不 force push。
检查通过后推送 main，不另行 dispatch，不修改工作流或依赖。

只有逐字稿已完整保存、可用性检查通过且所需回听疑点已解决，才可以删除 .cache/ 中相应临时音频。

最后说明成功、忽略、失败和预算延期的数量及原因，延期条目保持 pending。
区分“已推送”和“已部署”，没有部署结果时不要说网站已更新成功。
如果生成公众号或视频草稿，明确标记“待人工审核”，不得声称已发布。
```
