# EchoForge — 执行计划

> 版本：v0.6 · 2026-09-11  
> 依据：[产品文档](产品文档.md)、[架构文档](架构文档.md)、[Podcast RSS源清单](Podcast%20RSS源清单.md)  
> 当前状态：M1～M3 均未开始。本轮只更新文档，未修改远端仓库或执行部署。项目名称已确定为 **EchoForge**，建议仓库名 `echoforge`。

## 1. 开发原则

先看到 **EchoForge** 网页，再接上采集，最后用真实播客走通“逐字稿资产 → 机器摘要 → 发布”。不拆大量子里程碑，不为未来视频和公众号设计自动发布接口。

所有公开代码、元信息和文章都放 `main`。本地完整逐字稿、人工笔记和渠道草稿进入 `local-library/`，不提交 Git；临时音频和可重建中间文件进入 `.cache/`，转写完成后可清理。

先看 `rec-sys-daily`、cast2md、Podsidian 等项目中相关小模块再实现，但不整体复制其流水线。脚本保持普通文件，不先包装成 CLI 框架、插件系统或服务。

RSS 来源采用“来源池 + 少量启用”的方式：完整候选名单放在文档里，`config/sources.yaml` 只放当前实际采集的来源。首版不建设来源自动发现或评分系统。

## 2. M1 — 先发布一个可读的网站

**目标：** 一篇手写样例 Markdown 可以通过推送自动出现在 GitHub Pages。

实施内容：

- 若开始新建仓库，优先使用 `echoforge` 作为仓库和项目目录名；建立 `site/`、项目文档目录和忽略规则，使用 VitePress 默认主题。
- 添加首页、文章模板、文章列表生成脚本及内置本地搜索。
- 配置 `site:dev`、`site:build`、`site:preview`，锁定依赖。
- 建立 `deploy.yml`，支持 `main` push 和手动运行；配置 Pages 来源与站点 `base`。
- `.gitignore` 从一开始就排除 `local-library/`、`.cache/`、`.env` 和媒体/转录类本地资产。

样例明确标注为演示，不冒充真实节目。此阶段尚无采集器，后续 M2 再接上条目对应检查。

**完成标准：** 推送后能访问首页、文章列表和详情；列表链接正确；样例标题或独特词能被搜索；修改 Markdown 后站点能更新。此时不需要 AI、音频或第三方密钥。

## 3. M2 — 接通 RSS 采集

**目标：** 每日自动发现新节目，但不在 Actions 中处理正文。

首次联调只启用以下 5 个真实公开 Podcast RSS：

1. Recsperts
2. Data Skeptic
3. Latent Space
4. Practical AI
5. Software Engineering Daily

具体 RSS 地址及后续来源见 [Podcast RSS源清单](Podcast%20RSS源清单.md)。

实施内容：

- 将上述 5 个来源写入 `config/sources.yaml`；Software Engineering Daily 先配置简单关键词过滤，其他 4 个可以先不过滤或仅做非常宽松的过滤。
- 实现 `collect.py`：提取元信息、GUID 优先的稳定 ID、基本规则过滤、只新增文件。
- 尽可能提取 RSS 中公开提供的 `transcript_url`、enclosure/audio URL 和 duration，但缺失字段不猜测。
- 实现 `pending.py`，查看待处理数量和条目；补充 JSON 基本检查。
- 建立 `collect.yml`：每日采集、手动运行、有变化才提交，结果写入 Actions 摘要。
- 为 5 个 Feed 各做一次 smoke test：能访问、能解析、能获得单集标题和稳定标识；某个 Feed 缺少可选字段时不会拖垮整个采集。
- 补充简短 README，说明如何从来源清单增加新源、查看积压和手动重跑。

复用参考：`rec-sys-daily` 的来源配置、RSS 清理和确定性过滤；只迁移必要函数。补上播客特有字段，不直接把博客 Candidate 当播客数据契约。

**完成标准：** 5 个首批 Feed 能完成一次真实采集；同一 Feed 连续采集两次不重复；手动标记过的状态不会被覆盖；没有下载音频或转录正文；一个来源失败时其他来源仍可收集；所有来源失败时有清晰错误。

M2 Gate 通过后，可以按来源清单逐步加入 Software Engineering Radio、Developer Voices、Agentic Conversations 等其他核心源。**扩源不是 M2 完成条件。**

## 4. M3 — 本地逐字稿资产 + 机器摘要闭环

**目标：** 在本地投放一次 ZCode 闲时任务，完成真实节目的“取得逐字稿 → 长期保存 → GLM 精编 → GitHub 发布”。

实施内容：

- 编写 `prompts/process-podcasts.md` 和简短 `AGENTS.md`，限定读写范围、内容原则和发布步骤。
- 建立 `local-library/<source_id>/<item_id>/` 的本地长期资产约定；明确它不是缓存。
- 实现 transcript-first：优先 RSS / Publisher transcript；没有现成转录时，由 ZCode 调用 Video Agent Kit 完成 ASR。
- 转写音频只暂存在 `.cache/`；逐字稿写入 `local-library/` 后长期保留。来源或工具提供时间戳 / speaker / VTT / JSON 时一并保存，不自行伪造。
- 使用 GLM 基于完整逐字稿生成 GitHub Machine Digest；正式结果放到 `site/posts/<id>.md`。
- 完成文章、条目状态和基本对应检查；本地检查还要确认正式文章存在可回溯的完整逐字稿资产。
- 检查并构建，提交本批 GitHub 范围文件，正常同步远端后推送 `main`。
- 确认逐字稿已保存后，可以清理 `.cache/` 中的临时音频。
- 可以试生成一份 `wechat-draft.md` 或 `video-script.md` 来验证本地编辑目录，但**不得作为 M3 完成条件，也不得自动发布**。

**完成标准：** 至少 3 篇真实笔记能在 Pages 阅读；每篇都存在本地完整逐字稿供人工复核；重要观点有来源定位；再次运行会跳过已完成内容；一条正文获取 / 转写失败会记录原因而不是编造文章；部署重试不要求重新转录或整理。

**达到 M3 即停止扩展首版。** 先实际使用，不追加通知、YouTube、周报、人物研究或自动视频生产任务。

## 5. 人工发布门只定义规则，不做系统

公众号和视频暂不增加新的开发里程碑，只规定以后使用时的边界：

```text
机器生成草稿
    ↓
人工选题
    ↓
对照 local-library/ 逐字稿核查
    ↓
重新组织 / 改写 / 补充解释
    ↓
人工确认
    ↓
手动发布或进入视频制作
```

不能把 GitHub Machine Digest 或机器生成的渠道草稿直接自动同步到公众号 / 视频平台。

## 6. 只做这些必要验证

| 检查 | 方法 |
| --- | --- |
| Feed 可用性 | 首批 5 个来源各做一次真实解析，检查标题、GUID/链接、transcript/enclosure 等可用字段 |
| 去重与状态保留 | 同一小 Feed 重跑两次，比较文件及状态 |
| 采集边界 | 检查网络请求和输出，不访问正文/媒体/模型接口 |
| 来源隔离 | 人为制造一个 Feed 失败，确认其他来源仍继续采集 |
| Transcript-first | 至少测试 1 条有官方 transcript、1 条需要 Video Agent Kit ASR 的节目 |
| 本地资产持久化 | GitHub 文章发布后，确认 `local-library/` 逐字稿仍存在，`.cache/` 音频可删除 |
| 无正文不发布 | 用一个不可用转录案例验证 `failed` 与原因 |
| 文章基本正确 | 检查 item 对应、来源链接、非空正文，并抽查关键表述与本地逐字稿一致 |
| 发布闭环 | 真实本地推送后查看 Pages，再测试一次更新或部署重试 |
| 人工发布门 | 如生成公众号/视频草稿，确认没有任何自动发布步骤 |

使用少量固定样例和必要的真实手工验收即可，不设置覆盖率指标，不做压力测试、复杂测试矩阵或通用验收平台。未执行的外部验证如实记为未执行。

## 7. 首次部署准备

实际部署时补齐仓库地址、Pages `base`、首批 5 个真实 RSS，以及本机 Git、ZCode 和 Video Agent Kit 可用权限即可。这些是部署配置，不是继续编写系统前需要讨论的新产品问题。

本地需要 Python、Node 和能运行项目工具的 ZCode。只有处理无现成 transcript 的节目时才会用 Video Agent Kit 的转写能力。不要为了首发把未来视频生产相关能力全部配置一遍。

## 8. 日常闲时任务模板

以下内容在 M3 完成后，可作为投放任务时的说明；其中脚本和命令当前仍待实现。

```text
阅读 AGENTS.md、prompts/process-podcasts.md 和 templates/post.md。

确认工作区没有不相关改动，拉取 main。
执行 python scripts/pending.py --limit 10，处理返回的这一批 pending 条目。

先按元信息筛选。不相关的标记 ignored 并说明原因。
优先获取 RSS / Publisher 提供的官方逐字稿。
没有逐字稿时，临时下载允许处理的音频，并调用 ZCode Video Agent Kit 完成转写。
没有真实正文就标记 failed，不根据简介生成文章。

对每一期：
1. 将完整逐字稿保存到 local-library/<source_id>/<item_id>/transcript.md。
2. 如果实际有时间戳、speaker、VTT/JSON 等结构化输出，一并原样保存；不要伪造缺失信息。
3. 音频和一次性中间文件只放 .cache/。
4. 基于完整逐字稿按主题写成中文 Machine Digest，突出重要观点、案例和分歧。
5. 正式结果写入 site/posts/<id>.md，逐期更新 GitHub 条目状态。
6. 可生成 wechat-draft.md / video-script.md 作为人工编辑草稿，但不要发布。

保留条件、说话人归属和来源定位，不逐字翻译，不捏造时间戳。
完整逐字稿、人工笔记、公众号草稿和视频脚本不要提交 Git。

执行 python scripts/check.py 和 npm run site:build。
只提交本批有关 GitHub 文件；正常同步远端，冲突时停止，不 force push。
检查通过后推送 main，不另行 dispatch，不修改工作流或依赖。

确认 local-library/ 中逐字稿已完整保存后，可以删除 .cache/ 中已完成节目的临时音频。

最后说明成功、忽略和失败的数量及原因。
区分“已推送”和“已部署”，没有部署结果时不要说网站已更新成功。
如果生成公众号或视频草稿，明确标记“待人工审核”，不得声称已发布。
```
