# EchoForge — 产品文档

> 版本：v0.7 · 2026-09-11
> 状态：M1 网站已完成本地验证；M2/M3 尚未实现，远端 Pages 部署待验证。
> 本版明确个人信息雷达的阅读目标、逐字稿可用性、发布检查、批次预算与本地资产保护；保持现有架构和 M1–M3 路线，不增加系统。
> 中文展示名：**EchoForge · 技术播客**；建议仓库名：`echoforge`。

## 1. 产品定义

**项目名：EchoForge**。`Echo` 对应播客、声音和访谈内容，`Forge` 对应提炼、重组与再创作。名称不绑定单一渠道，因此未来即使从 Podcast 扩展到访谈录音、视频或其他长内容，也无需重新命名。

对外中文展示统一使用 **“EchoForge · 技术播客”**；代码仓库和本地项目目录优先使用 `echoforge`。

从配置好的 Podcast RSS 中发现技术访谈，由用户在本地投放 ZCode / GLM 闲时任务，将长播客整理成便于阅读的中文笔记，再发布到 GitHub Pages。

**核心目标是个人信息雷达：帮助用户决定是否值得收听或回听，并理解关键技术观点及其依据与限制。** 不替代完整收听，也不要求覆盖节目全部话题。不是逐字翻译，而是忠实于原意的筛选、重组和中文改写。先把“收集 → 获取逐字稿 → 整理 → 阅读”跑通，不建设大型内容平台。

同时明确三层内容资产：

1. **Source / 本地源资产**：完整逐字稿、时间戳、节目元信息，长期保留，仅本地使用。
2. **Machine Digest / 机器摘要**：ZCode / GLM 自动生成的中文精编，可在检查通过后发布到 GitHub Pages。
3. **Editorial Content / 人工编辑内容**：微信公众号文章、视频脚本等，必须人工核查和重新组织后才能发布。

GitHub 网站承担“信息雷达”；公众号和视频如果后续启用，则承担“人工把关后的内容品牌”。

## 2. 当前确定的方案

| 项目 | 首版决定 |
| --- | --- |
| 项目名称 | **EchoForge**；中文展示名“EchoForge · 技术播客”；建议仓库名 `echoforge` |
| 仓库 | 一个仓库，只维护 `main` 分支；代码、元信息和公开文章按目录分开 |
| 内容来源 | 只支持配置好的公开 Podcast RSS，不自动寻找新订阅源 |
| 来源池 | 维护独立的 [Podcast RSS源清单](podcast-sources.md)；首版只启用少量来源验证，不一次性全开 |
| 日常采集 | GitHub Actions 每天采集元信息、去重和规则过滤 |
| 内容处理 | 用户自行决定频率，在本地投放 ZCode 闲时任务 |
| 转录策略 | Transcript-first：优先可用完整稿，依次检查 RSS、Publisher；无法取得时，仅在许可和批次预算内调用 Video Agent Kit ASR |
| 本地资产 | 完整逐字稿长期保留并私有备份；音频满足删除条件后清理，中间文件为临时缓存 |
| 网站 | VitePress 默认主题，Markdown 驱动，部署到 GitHub Pages |
| GitHub 发布 | 可用材料上的机器摘要通过脚本基本检查与模型内容复核后才可提交和发布 |
| 公众号 / 视频 | 可以生成草稿或脚本，但必须经过人工核查、改写和确认后再发布；首版不做自动发布 |
| 提醒 | 暂不做；在 Actions 运行摘要或本地查看待处理数量 |

## 3. 核心流程

```text
配置 Podcast RSS
        ↓
GitHub Actions 每日读取 RSS
        ↓
去重、规则过滤，保存元信息到 main/data/items/
        ↓
用户在本地拉取仓库，投放 ZCode 闲时任务
        ↓
Transcript Resolver：RSS → Publisher → 许可且预算内的 Video Agent Kit ASR
        ↓ 每级检查身份、完整性与可读性；不完整先尝试取得完整稿
        ├─ 预算不足 / 时长无法确认 → pending + 批次报告
        ├─ 材料不可用 / ASR 失败 → failed，不生成整期摘要
        ↓ 可用完整稿
本地长期保存完整逐字稿与可用的时间戳信息
        ↓
ZCode / GLM 自动整理
        ├─ Machine Digest → 脚本检查 + 模型内容复核 → site/posts/*.md → GitHub Pages
        ├─ WeChat Draft → 人工核查 / 改写 → 手动发布
        └─ Video Script → 人工核查 / 改写 → 后续视频制作
```

采集和编辑相互独立。几天不处理也不影响元信息继续积累；某一期无法获取正文，不影响其他节目整理。

## 4. 首版只交付这些能力

### 4.1 RSS 收集

维护一份来源配置，保存节目标题、发布时间、原始链接、简短简介，以及 RSS 已提供的音频和转录地址。未知字段留空，不让模型猜。

生产配置只从 [Podcast RSS源清单](podcast-sources.md) 中选择公开 Feed。来源池用于人工维护和后续扩展，不参与运行时自动发现。M2 首次联调只启用 Recsperts、Data Skeptic、Latent Space、Practical AI 和 Software Engineering Daily 五个来源；跑稳后再逐步增加其他核心源。

采集时按稳定 ID 去重，只新增条目，不覆盖本地已经更新的状态。规则仅使用来源、关键词、排除词和可选时长限制，不做复杂评分。

**Actions 不下载音频、不跟进转录正文、不做 ASR、不调用大模型。** RSS 内附的完整正文也不原样存入仓库。

### 4.2 Transcript-first 与本地源资产

本地处理时按以下优先级取得真实内容：

```text
RSS / Podcasting 2.0 transcript → 身份、完整性、可读性检查
        ↓ 无可用完整稿（不完整先尝试补全）
Publisher 官方 transcript → 同样检查
        ↓ 仍无可用完整稿，且获准、时长已知、预算足够
ZCode + Video Agent Kit 转写 → 同样检查；失败不生成整期摘要
```

ZCode 负责任务编排；Video Agent Kit 只负责无法取得可用完整逐字稿时、许可和预算内的 ASR。首版不再额外接入 Groq、独立 Whisper 服务或其他收费转写 API。

**完整逐字稿是长期本地资产，不属于缓存。** 在 `local-library/` 至少保存便于阅读的文本及节目元信息；来源或工具实际提供的时间戳、说话人、VTT/SRT/JSON 一并保留，缺失信息不补造。

取得逐字稿后，先验证节目身份、文本不是简介、没有明显截断，并完成基本可读性检查。优先保证可用的完整逐字稿；有时长信息时可用时间戳对照，但不设固定字数比例，也不要求广告或音乐必须被转写。官方稿不完整时先尝试补全，再在预算允许且得到许可时使用 ASR；不可用的 ASR 记为转写失败。预算暂时无法满足则保持 pending，不能用部分文本生成整期摘要。

### 4.3 内容资产分层

逻辑上每期内容分为三层：

```text
Source
  完整逐字稿 / 时间戳 / metadata
  → 本地长期保留，不公开

Machine Digest
  GLM 自动精编 Markdown
  → GitHub / VitePress，可自动发布

Editorial Content
  公众号文章 / 视频脚本
  → 人工选题、核查、重组、改写后才能发布
```

公众号和视频的人工环节不是简单同义改写，而是重新判断哪些观点值得传播、核对上下文与事实、补充必要解释并重新组织叙事。机器产出的公众号稿或视频脚本只能视为草稿。

### 4.4 GitHub 中文精编

每期只生成一篇公开 Markdown，通常包含：

- 开头的速读摘要，说明这期值得关注什么。
- 按主题重组的正文，保留关键观点、案例和分歧。
- 原始来源，以及重要观点的时间段或原文小节定位。

文章开头速读回答“讲了什么、适合谁、有什么价值”。正文通常组织为 3–5 个关键点，但不是硬性配额；按内容需要保留证据、案例、适用条件、分歧和未决问题。所有来源必须落到真实位置：原始链接、时间戳（有则使用）或可识别的原文小节/片段。篇幅参考约 1,000～3,000 字，仅作指导，不是发布门槛。

允许删除广告、寒暄、重复和口头语，合并分散的同类观点；必须保留原话的条件、不确定性和观点归属。中文转述不冒充直接引语。

没有时间戳时引用原文小节或可识别片段，不编造时间。文末标明“AI 编辑整理，请以原始节目为准”。

公开文章不包含完整逐字稿。逐字稿用于内部核查、后续人工编辑和定位原始内容。

### 4.5 两道发布检查

脚本检查元数据、状态、正文和链接格式，并拒绝可执行 Markdown（脚本、组件等）与不应 staged/tracked 的文件（逐字稿、音频、人工草稿、编辑备注、凭据等私有资产）；模型对照可用完整稿复核数字、因果、建议、归属、限定条件、不确定性和来源定位，删除无法验证的外围主张，并将模型新增解释明确标注。核心主张无法解决时不发布，记录失败原因。自检不是独立事实认证。

`processed` 只表示材料可用且内容与基本检查通过，不表示部署成功或完成事实认证。

**公众号 / 视频人工发布门**：后续生成这类内容时，仍需 Human-in-the-loop Publishing Gate：

1. 人工决定是否值得进入公众号 / 视频渠道。
2. 对照本地逐字稿核查关键表述、数字和上下文。
3. 重新组织叙事并补充必要解释，避免把机器摘要直接当成最终稿。
4. 人工确认最终稿后再手动发布或进入视频制作。

**首版不建设微信公众号自动发布、视频自动发布或跨平台发布系统。** 当前只把“机器草稿不得自动对外发布”作为长期产品边界。

### 4.6 网站阅读与更新

使用 VitePress 默认主题，首版只有首页、文章列表、文章详情和内置本地搜索。文章用 Markdown 直接维护，不另存一份文章正文 JSON，不建立后台编辑器。

本地整理完成并推送 `main` 后，由部署工作流构建网站。构建失败时保留已有站点，只修复或重试部署，不重新处理音频或逐字稿。

## 5. 批次预算与处理记录

首版每批最多处理 3 篇文章和 1 期新 ASR 节目，新 ASR 音频总时长不超过 120 分钟；已有可用逐字稿可复用。无法确认时长时先取得实际时长；无法建立预算依据则在批次报告中保持 `pending`，不新增状态。`ignored` 仅用于明确无关或不值得处理的条目，不用来掩盖预算不足。允许积压，沿用当前待处理列表排序，不增加评分或调度系统。

音频仅在逐字稿已保存、可用性检查通过且所有必需的回听疑点已解决后删除。ASR 逐字稿本身不等于已核验的原始内容。`local-library/` 通过现有私有机制做独立副本备份，包含编辑备注；首次验收恢复一集节目及其备注，不建设备份服务。

每一期元信息文件带一个简单状态：

| 状态 | 含义 |
| --- | --- |
| `pending` | 等待处理 |
| `processed` | 已生成可用 GitHub 机器摘要并通过脚本检查与模型内容复核；不等同于网站已经部署成功或完成独立事实认证 |
| `ignored` | 仅因明确无关或不值得处理而不处理，保留简短原因 |
| `failed` | 正文不可用、转写失败、核心主张无法解决或其他处理错误，保留简短原因 |

正常任务只选择 `pending`。修复问题后，将指定条目改回 `pending` 即可重试，不建设复杂任务状态机。

公众号和视频的编辑状态不写入首版 GitHub 元信息状态机；它们是本地编辑资产，避免为尚未自动化的渠道扩展状态复杂度。

## 6. 首版不做

暂不做 YouTube、飞书或微信提醒、自动远程触发闲时任务、自动周报、人物专题、主题研究和趋势统计。标签可写在文章里，但不为标签建设独立分析系统。

不做数据库、后端 API、用户账户、向量搜索、知识图谱、多 Agent 编排、自定义网站主题和音视频长期托管。

不做公众号自动发布、视频自动生产/发布。允许本地保留相关人工草稿，但不为这些渠道提前建设发布接口、状态机或平台适配器。

RSS 来源池是人工维护的白名单，不建设“自动发现优质 Podcast”、来源评分、来源推荐或聚合搜索服务。

## 7. 上线标准

实施路线保持 M1 网站、M2 采集、M3 本地逐字稿与机器摘要。M3 使用首批少量真实 RSS 完成“采集 → 获取可用完整逐字稿 → 本地长期保存 → 两道检查 → Pages 阅读”，交付至少 3 篇真实笔记，覆盖官方逐字稿、ASR 和长篇多主题访谈三种场景。

用户做一次性阅读验收：能判断是否值得收听或回听、理解关键观点的证据与限制、定位到真实来源。这是 M3 验收，不是每篇文章的长期人工发布门。还需检查重复采集不新增重复条目、第二次处理不重做已完成条目、材料不可用不发布、本地逐字稿可回溯，并从私有独立副本实际恢复一期节目材料及编辑备注。上述均为待实施的验收要求，不是本轮已完成的验证。

首版不以覆盖所有来源、公众号、视频、多平台分发或完整媒体生产作为上线条件。

## 8. 未来想法

AI 配音、AI 动画、“三分钟带你学习……”视频、微信公众号推文仍是未来方向。未来如果启用这些能力，沿用当前的内容分层：**Source 不公开，Machine Digest 可自动化，Editorial Content 必须人工把关。**
